### IFC-004 — audio engine  *(RESERVED — NOT YET CONTRACTED)*

**Status**: proposed
**As-built**: Number reserved so it is not taken; the contract is not written. Do not
implement against this file — there is nothing here to implement against yet.

**Parties**: player-mode apps (`webRadioApp`, `localPlayerApp`) ↔ the audio engine ↔ `wrAudio` pump task
**Transport**: mutex-guarded singleton + post-request/poll-result (IFC-002 M3, M4)

**Why it must exist.** ADR-059 D2 extracted a system-owned engine and specified its shape in a design
doc (`M-AUDIO-ENGINE-extraction.md` §3) — but a design doc records how a decision was reached, not the
standing obligation. Two apps now drive one `Audio` object across a task boundary (X050, high risk),
and the rules live in source comments.

**What it must cover** (from the design doc and X048/X050/X052/X063):
- `Source{URL|FILE}` — and the borrowed-pointer lifetime rule: `str` is valid **for the call only**;
  `connect()` copies it into the pump task's own buffer before returning.
- `acquire()` / `teardown()` ordering: pump task → `Audio` → arena, in that order.
- The single-instance constraint: one DAC (GPIO26), one 23 216 B Helix arena, one 6 400 B InBuff.
- ABORT/TEARDOWN request precedence, and the ≤100 ms loopTask-block bound (TASK-398).
- Which callbacks fire on the pump task and are therefore flag-only (IFC-002 I4).
- The arena/libc-fallback duality, which is **unsettled** — see TASK-452.

**Blocked on**: TASK-452 (retire the arena from the FILE path). Contracting the allocator behaviour
before that decision lands would document something about to change.

**Version**: none — stub
