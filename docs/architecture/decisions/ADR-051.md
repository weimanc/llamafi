### ADR-051 — 2026-07-18 — Taskbar icons: 36×36 budget, native-resolution authoring for hand-made art

**Status**: accepted (2026-07-18, human sign-off via decision gate)

**Context**:

M-TASKBAR-ICONS's bake pipeline (`gen_taskbar_icons.py`) LANCZOS-resizes any
source PNG down to `TASKBAR_ICON_W`×`_H` (24×24) regardless of source
resolution. Redesigning the PlaneRadar icon (TASK-302 follow-up) surfaced a
class of authoring bugs this creates for hand-drawn/programmatic icons:
scaling a shape and its canvas together is a post-bake no-op, and
double-LANCZOS (supersample → intermediate canvas → 24×24) does not preserve
fill fractions, so the only way to know the shipped fill ratio was bake-and-
measure. Full analysis and option space:
`docs/architecture/designs/M-ICON-PIXELART-native-icon-authoring.md`.

Independently, 24×24 is a self-imposed budget using only 53%/60% of the
45×40 slot. Render constraints measured in `taskbar.h`: 3px active-indicator
bar at the slot's left edge, 1px separator hline at the slot bottom. A 36×36
glyph centres at x-offset 4 / y-offset 2, clearing both. Verified this
session: `app/gen/golden.sha256` covers `taskbar_icons.cpp/h` **and**
`shell_layout.h`, so both the size bump and any re-bake require a golden
regen (closes the design doc's "unverified" note).

**Decision** (three coupled calls, decided together 2026-07-18):

1. **Budget grows to 36×36.** `TASKBAR_ICON_W`/`_H` = 36 in
   `gen/shell_layout.h`. 80%/90% slot fill, 4px/2px margins clearing the
   indicator bar and separator. Centering math in `taskbar.h` already
   derives from the constants — no layout code changes.

2. **Option B — native resolution for hand-authored icons.**
   Programmatic/hand-drawn icons are authored as pixel art directly at
   `TASKBAR_ICON_W`×`_H`, read from `shell_layout.h` (never hardcoded) by
   `gen_icon_drafts.py` and successor tooling. `gen_taskbar_icons.py` skips
   resampling entirely when source dimensions already equal the target —
   the source PNG *is* the shipped icon (WYSIWYG). Imported/licensed art
   (Winamp bolt, Material Symbols) keeps its high-res master and the
   existing LANCZOS resize path.

3. **Warn-only fill-ratio check at bake.** `gen_taskbar_icons.py` prints
   per-icon fill (bbox of alpha>128 ÷ target size, per axis) and warns when
   the **major axis** falls outside [85%, 97%] — below reads undersized,
   100% is edge-to-edge (the PlaneRadar overshoot failure mode). Minor axis
   unchecked (deliberate wide-flat glyphs like aquarium's 100%×29% stay
   legal). Never fails the build; no exemption machinery.

**Consequences**:

- Every existing baked icon grows to 36×36 at next bake: sources smaller
  than 36 (the 32×32 set: clock, weather, stock, teletext) upscale and
  render softer until re-touched. Accepted as interim state — Option B
  forces no flag day; re-touching is opportunistic per icon.
- PlaneRadar's icon pair is re-authored natively at 36×36 as the first
  test case (it surfaced the whole question).
- Flash cost: 36×36 RGB565 = 2592 B/icon vs 1152 B — ~+31.7 KB across the
  current 11 icon pairs. Negligible against the 0x290000 app partition.
- Size bump + re-bake touches golden-covered files (`shell_layout.h`,
  `taskbar_icons.cpp/h`) → golden.sha256 regen + `run/check` gate, and a
  DUT eyeball pass per BP-048 (init must paint; eyeball gate).
- A future contributor can still hand `gen_taskbar_icons.py` an oversized
  programmatic source and silently re-enter the resize path — accepted
  Option B residual; the fill-ratio warning is the tripwire.

**Supersedes**: none. Refines M-TASKBAR-ICONS's bake pipeline; crystallised
from `M-ICON-PIXELART-native-icon-authoring.md`.
