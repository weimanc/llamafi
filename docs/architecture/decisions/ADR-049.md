### ADR-049 — 2026-07-10 — M-PLANERADAR airport/runway DB: V-europe bounding-box bake

**Status**: proposed (2026-07-10) — pending human accept

**Context**:

M-PLANERADAR's optional runway overlay needs an embedded airport/runway
database, generated (like the reference project's
`scripts/build_large_airports.py`) from OurAirports CSVs. The reference embeds
**global** coverage (`large_airport` class + non-helipad runways) as a ~140 KB
C source file — compiled flash cost is what matters, not source size. Our
device is at ~62% flash used; the design doc's original D3 lean was "(a)
trimmed — bake with a generous continental bounding box," but that lean was
an estimate, not a measurement, and the actual airport class filter (large
only vs. large+medium) and bbox size were still open (OQ2).

Phase 0 (`docs/architecture/designs/M-PLANERADAR/phase0-airport-db.md`) built
a host-only trial (`app/tools/host/pr_airport_bake_trial.py`) replicating the
reference's exact selection logic against a pinned OurAirports commit, and
measured **compiled** `.rodata` bytes (not source KB) for three variants, plus
an in-range content check around the home default location.

**Decision**:

Adopt **V-europe**: bounding box lat 35°..62°, lon −11°..30° ("generous
continental"), `large_airport` class only, non-helipad runways with both
endpoints resolved. Measured: **240 airports / 355 runways / 12.1 KB**
compiled flash.

Measured comparison table (for the record):

| Variant | Filter | Airports/Runways | Flash |
|---|---|---|---|
| V-global | none (reference as-is) | 1114 / 1707 | 57.4 KB |
| **V-europe** | bbox lat 35..62, lon −11..30 | **240 / 355** | **12.1 KB** |
| V-nl500 | 500 km radius around home default | 39 / 70 | 2.2 KB |

In-range check: within the 36.8 km worst-case fetch radius (25 km preset),
**EHAM is the only airport ever in range, identical across all three
variants** — trimming from V-global to V-europe costs zero visible runways at
any shipped preset. Within a 100 km band (the tolerance for "user changes
lat/lon in Settings without a rebake"), EHAM + EHRD, also identical across
variants. `medium_airport` inclusion was evaluated and **rejected**: +25.5 KB
buys mostly military fields (EHDL/EHGR/EHKD/EHVK) plus Lelystad (EHLE) — not
worth it at this cost, and the parameterised bake script makes it a one-line
change to revisit if ever needed.

Adoption: the reference's `build_large_airports.py` becomes `run/bake-airports`
in our bake-script conventions (`app/gen/`, `golden.sha256` determinism gate,
ADR-008 pattern), taking `--bbox` / `--center-radius-km` arguments with
V-europe as the committed default — a parameter, not a fork.

**Consequences**:

- R3 (flash growth) is a non-issue at 12.1 KB against ~62% current usage —
  removes flash pressure as a reason to prefer a smaller variant.
- Runway overlay coverage is correct for the home default today and tolerant
  of any plausible relocation within the 100 km band without a rebake.
  Outside the baked region, the overlay must render *gracefully absent*
  (empty), never garbage — this is a firmware correctness requirement, not
  optional polish.
- V-global (57.4 KB) remains available as a fallback if bbox maintenance
  ever becomes annoying — cheap enough to not foreclose that option.
- Determinism (two-run byte-identity) is **not** settled by this ADR — the
  trial bake emits no C file, so that check transfers to the actual firmware
  bake implementation (`run/bake-airports`), same gate pattern as the skin
  bake (ADR-008).
- The preview tool (`preview_planeradar.py`) now renders real EHAM (6
  runways) + EHRD (1 runway) geometry sourced from the same data
  (`fixtures/planeradar/airports_preview.json`), closing design question Q4
  (runway label density = all in-range airports labeled) — see
  `phase0-preview-ui.md`.

**Supersedes**: none — this is the first measured resolution of D3/OQ2 in
`docs/architecture/designs/M-PLANERADAR-plane-radar-app.md`; that doc is
updated in place with a "Phase-0 revision" note.
