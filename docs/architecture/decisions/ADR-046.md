### ADR-046 — 2026-06-25 — Per-app error-state endpoint + red taskbar active-bar signal

**Status**: accepted (2026-06-25)

**Context**:

The taskbar active-slot indicator (`taskbar.h:renderActiveIndicator`) is a 3 px vertical bar
drawn on the currently-active app's slot, today with two states:

- `TASKBAR_ACTIVE_COLOR = 0x07E0` (green) — active, idle
- `TASKBAR_BUSY_COLOR   = 0xFD20` (amber) — `g_shellBusy` (a synchronous HTTP poll/fetch in flight)

There is no signal for a *sustained failure* condition. The motivating case (2026-06-25):
a "Stock can't pull data" report that turned out to be the Spotify Web API returning **403**
(owner-account Premium lapsed — TASK-243) and starving the shared TLS yield (TASK-244). The
device already knows the failing condition — the 403 status is captured at
`spotifyTaskStorage.cpp:193-195` (`heartbeat::recordPoll`, surfaced as `last=403`) — but
nothing surfaces it on the UI. We want a third indicator state (red) to flag a genuine,
non-transient error.

The signal should not be Spotify-specific. The `App` base class already exposes a clean
shell-polled health endpoint precedent — `App::hasPendingAsync()` (`appShell.h:18`), a
non-pure virtual with a safe `false` default that apps override. A per-app **error** endpoint
is the natural sibling, letting any app (Stock's `fetchFailed`, Weather/Crypto fetch errors,
Teletext/WebRadio, and Spotify's 403) report a hard error through one contract that the shell
renders uniformly.

Forces: keep the change inside the existing base-class contract (don't special-case Spotify in
the shell); preserve the `check_build.sh` golden-hash gate (which is why `TASKBAR_BUSY_COLOR`
is a firmware-only `#define` in `taskbar.h`, not in generated `shell_layout.h`); define
precedence and latching unambiguously so every app behaves predictably.

**Decision**:

1. **New base-class endpoint.** Add to `struct App` (`appShell.h`):
   ```cpp
   // Return true while the app is in a sustained error state (e.g. auth/HTTP
   // failure that will not self-heal by retrying). Sticky — set when the error
   // is detected, cleared by the app on the next successful operation. Shell
   // polls this to colour the taskbar active-slot indicator red. Safe default
   // = false (offline apps need not override).
   virtual bool hasError() const { return false; }
   ```

2. **Render contract — tri-state precedence: error (red) > busy (amber) > idle (green).**
   `renderActiveIndicator` colours the active slot's bar red when the **active** app's
   `hasError()` is true, regardless of busy. New firmware-only constant in `taskbar.h`
   (NOT in `shell_layout.h`, to preserve the golden hash):
   `#define TASKBAR_ERR_COLOR 0xF800`. The shell re-renders the indicator on the same
   triggers it already uses for busy (`setShellBusy`, app switch, tick poll).

3. **Latching semantics.** `hasError()` is **sticky**: an app sets its error condition when
   detected and clears it on the next successful operation (mirrors Stock's existing
   `fetchFailed` / `fetchOkCount` discipline). The shell does no latching of its own — it
   only reads the endpoint. This keeps "what is an error" and "when does it clear" owned by
   each app, where the domain knowledge lives.

4. **Accepted limitation (recorded deliberately).** The signal recolours *the active app's*
   bar only, so an app's error is visible **only while that app is active** — there is no
   persistent per-slot health dot. Consequence: a Spotify 403 shows red only when Spotify is
   the active app, not while the user is in another app. This was the explicit product choice
   (cheapest option; "recolor the active bar"). Emergent upside: because the endpoint is
   generic, an app shows its **own** red when its **own** operation hard-fails. Caveat: the
   403 *starvation* case (TASK-244) makes other apps *slow*, not *failed* (e.g. Stock's
   heatmap eventually returns 200), so those apps go red only on a genuine fetch error, not on
   starvation-induced lag. Do not expect red during the slow-but-eventually-succeeds case.

**Scope split:** the mechanism (endpoint + render + precedence + matrices + tests, with
Spotify wired as the first consumer) lands as TASK-245. A breadth-first audit + per-app error
wiring (Stock/Weather/Crypto/Teletext/WebRadio, confirm offline apps stay default-false) lands
separately as TASK-246, gated on TASK-245.

**Rejected:**
- *Persistent per-slot health dot* (always-visible green/amber/red on the Spotify slot from any
  app) — more code (a per-slot overlay independent of the active bar) and a new render region;
  deferred in favour of the cheaper active-bar recolor. Revisit if the active-only limitation
  proves inadequate in use.
- *Spotify-specific red in the shell* (hard-code a 403 check in the renderer) — rejected as it
  breaks the base-class abstraction and doesn't generalise to the other apps' error states.
- *Parsing the 403 body for a precise "no Premium" reason* — the reason string lives in the
  response body, which the vendored `SpotifyArduino` discards on non-200; capturing it needs a
  lib patch. Out of scope here — the bare 403 *status* is sufficient to set `hasError()`.
  (See TASK-244 option 3.)
