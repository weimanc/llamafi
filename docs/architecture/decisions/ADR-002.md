### ADR-002 — 2026-04-27 — VU meter sourced from Spotify `audio-analysis`, beat-synchronised

**Status**: superseded by ADR-009 (2026-05-07 — Spotify deprecated `audio-analysis` for new Developer apps; this ADR's data source is no longer accessible from this device's client)

**Context**:
The Winamp 2 classic skin includes a stereo VU meter that, in the original application, is driven from the live audio output stream. This system is a Spotify Connect *controller* (per ADR-006): audio never traverses the device, so no PCM samples or spectrum data are available locally.

The Spotify Web API exposes no real-time audio buffer. It does expose two derived data sources:

- `GET /v1/audio-features/{id}` — one small object per track (energy, danceability, valence, loudness, tempo). Cheap to fetch and cache.
- `GET /v1/audio-analysis/{id}` — a larger object (~30–80 KB JSON) containing per-segment loudness, beats, bars, sections, and timbre vectors, all timestamped relative to track start.

Three options were considered:
- **(a)** Synth from `audio-features` only — a slow envelope shaped by track-level energy and tempo. Cheapest in memory and bandwidth; visibly disconnected from what the listener hears.
- **(b)** Synth from `audio-analysis` — drive a stereo envelope from per-segment loudness and align kicks to the `beats[]` timestamps. Fits the Winamp visual idiom (responsive bouncing) without requiring real audio.
- **(c)** Add an on-device I2S microphone, FFT locally, render real spectrum. Honest data, but adds hardware, ADC noise concerns, and decouples the VU from what Spotify is actually playing (any room sound contaminates it).

What needs a decision: which data source the VU synthesis logic consumes.

**Decision**:
Use option **(b)**. The VU synthesis module consumes cached `audio-analysis` for the currently playing track and emits a stereo envelope that the renderer reads each frame.

Sketch of the synthesis rule (refinement deferred to implementation):

- On track change, fetch `audio-analysis` for the new track once and cache it (keyed by track id).
- On each render frame (or a ~20 Hz tick inside the super-loop), look up the active `segment` for the current playback position and use its loudness fields to set a target envelope level.
- Apply attack/release smoothing so the meter behaves like an analog VU rather than tracking segment boundaries as steps.
- On `beats[]` timestamps, inject a short transient onto the envelope so kicks read visibly.
- Stereo width is faked: split the mono envelope across L/R using a slow LFO, optionally modulated by track `valence` or section index. (The API does not expose per-channel data.)

Behaviour when data is unavailable:

- If the track is unplayable or analysis 404s (some tracks lack analysis), the VU module reports `source = features` and a coarser envelope from `audio-features` is used.
- If neither is available, `source = off` and the VU rect renders idle.
- If playback is paused, the envelope decays to zero and holds.

**Consequences**:
- *Easier*: No new hardware. VU "feels" tied to the music because it is locked to the track timeline.
- *Harder*: Per-track cache adds flash/RAM pressure (see Open Questions in `architecture.md`). Eviction policy needed (proposed: LRU keyed by track id, sized to N most-recent tracks). `audio-analysis` is not currently exposed by `SpotifyArduino`; either the library is extended, forked, or a small helper using the existing TLS client is added (Open Question in `architecture.md`).
- *Constrained*: The VU is not a true audio meter. If the user is listening on a different device with EQ or limiting, the on-screen VU will not reflect that. This is accepted as cosmetic.
- *Constrained*: Tracks without analysis fall back to a coarser look; a small fraction of catalogue may behave noticeably differently.
- *Not chosen*: Option (c) is left available for a future revision if the system later grows an audio path.
