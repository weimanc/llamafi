### ADR-025 — 2026-05-22 — Shell geometry single source of truth (M-SHELL-LAYOUT)

**Status**: proposed

**Context**:

The project maintains two existing categories of shared constants between host
Python tooling and firmware:

| Category | Source | Bridge | Gap |
|----------|--------|--------|-----|
| Skin-derived (WINDOW_W, sprite UVs, hit-zones) | `bake_skin.py` measures WSZ | `gen/skin_layout.h` | `render_hitzones()` ignores the dicts, hardcodes literals instead |
| Hardware-fixed (SCREEN_W=320, SCREEN_H=240) | `cheapYellowLCD.h` | none — duplicated | `preview_vis.py:56-57` hardcodes; low risk (hardware fixed) |

M-MULTIAPP introduces a third category: **shell geometry constants** — taskbar
position, width, slot height, slot count, indicator style, indicator colour,
separator colour. These are design decisions (not skin-measured, not hardware-fixed)
that must be consumed by both firmware (`appShell.h`) and Python preview/test tools.

Without a shared mechanism, constants will be defined independently and drift on
the first edit. Investigation also surfaced two pre-existing drift risks that are
fixed in the same pass:

- `render_hitzones()` in `bake_skin.py` hardcodes zone coordinates instead of
  reading from `POSBAR_LAYOUT`, `VOLUME_LAYOUT`, `CBUTTON_POSITIONS`.
- `run_serialdbg_tests.py` and `run_sync_tests.py` hardcode screen coordinates with
  `originX=22` baked in. `originX` shifts to 0 in M-MULTIAPP (ADR-024); every
  `tap`/`drag` in both test scripts will miss by 22 px.

Three options for the shell geometry mechanism:

**Option A** — Manually maintained `gen/shell_layout.h`. Developer edits it
whenever constants change. Firmware `#include`s it; Python tools parse it.
Risk: requires two edits per change; same drift risk it aims to prevent.

**Option B** — Interactive preview tool (`preview_layout.py`) emits
`gen/shell_layout.h` on export. Developer runs tool, approves configuration,
presses `e`, commits result. Firmware `#include`s it; Python tools parse it via
`parse_shell_layout()`.

**Option C** — Constants live in firmware only (`appShell.h`); Python tools parse
that file via regex. No generated file needed. Risk: Python must parse arbitrary C
header syntax alongside structs and function declarations; breaks the `gen/`
boundary.

---

**Decision**

**Option B.**

The interactive preview tool is the decision-making artefact for shell geometry.
Coupling the `e`-key export to `gen/shell_layout.h` means the design tool and the
build artefact are the same action. This mirrors how `bake_skin.py` is both the
design tool and the generator of `gen/skin_layout.h`.

Staleness risk (header out of sync with direct firmware edits) is addressed by:
- `_Static_assert(TASKBAR_X + TASKBAR_W == 320, ...)` in `appShell.h` — compile-time
- T127 semantic grep — CI-time
- T129 PlatformIO build with deliberately wrong value — VE gate

**`gen/shell_layout.h` schema** (geometry constants only; aesthetic constants
filled in after the preview session):

```c
#define TASKBAR_X          275
#define TASKBAR_W           45
#define TASKBAR_SLOT_COUNT   6
#define TASKBAR_SLOT_H      40
#define TASKBAR_ICON_W      24
#define TASKBAR_ICON_H      24
#define TASKBAR_BG_RGB565   ...   // set by preview export
#define TASKBAR_ACTIVE_STYLE 'A'  // set by preview export
#define TASKBAR_ACTIVE_COLOR ...  // set by preview export
#define TASKBAR_SEP_ENABLED  1    // set by preview export
#define TASKBAR_SEP_COLOR   ...   // set by preview export
```

**`parse_shell_layout()` helper** added to `bake_skin.py` (imported by all tools).
Must strip inline comments before returning values.

**`coords.py`** new module in `Spotify-Diy-Thing/tools/`. Parses
`gen/skin_layout.h` and exposes `originX`-aware named helpers for all hit-zone
coordinates. Both test scripts replace all `tap`/`drag` literals with calls to
`coords.py`. After M-MULTIAPP shifts `originX` to 0, test scripts require no
change — `coords.py` derives `originX` from `(SCREEN_W - WINDOW_W) // 2`.

**Pre-existing gaps fixed in this pass** (all in `bake_skin.py`):
- `render_hitzones()` zone list rebuilt from `POSBAR_LAYOUT`, `VOLUME_LAYOUT`,
  `CBUTTON_POSITIONS` dicts.
- `preview_vis.py:58` WINDOW_W read from `gen/skin_layout.h` via helper.

---

**Alternatives considered:**

**Option A (manual header)**: Acceptable fallback but creates a two-edit
requirement per change. Rejected in favour of the tighter tool-generates-header
coupling.

**Option C (parse appShell.h)**: Fragile — Python must navigate C struct/function
syntax. Breaks the `gen/` boundary. Rejected.

---

**Consequences:**

What becomes easier:
- Single `e` keypress in the preview tool locks in approved aesthetic values and
  produces the firmware-ready header simultaneously.
- `coords.py` insulates all test scripts from `originX` changes — M-MULTIAPP
  layout shift requires no test script edits.
- `render_hitzones()` correctness is guaranteed by construction; no drift possible.

What becomes harder:
- `gen/shell_layout.h` must be committed after every preview session; it is a
  build input (included in `golden.sha256`).
- `parse_shell_layout()` must handle mixed value types (int, hex, char literal)
  and strip inline comments — T128 verifies this before use.
- `coords.py` must be audited against `gen/skin_layout.h` to confirm all required
  `#define`s exist (several may be missing from current emit block).
