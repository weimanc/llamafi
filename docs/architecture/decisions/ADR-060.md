### ADR-060 — [2026-08-15] — M-SRCLAYOUT: source layout and state ownership

**Status**: proposed — 2026-08-15

**Design doc**: [M-SRCLAYOUT-main-decomposition.md](../designs/M-SRCLAYOUT-main-decomposition.md)

**Context**

`app/src` is 30 022 lines. `main.cpp` alone is **5 880 lines** — just under 20 % of the firmware
source in one file — and holds four unrelated things: seven `App` subclasses defined inline
(1 678 lines, of which `StockApp` is 711), the shell dispatch (321), `setup()` (631), and the
`SERIAL_DEBUG` console (~2 780, which never ships in the production binary).

The pattern that would fix this **already exists in this repo and works**. Six apps live in their own
files today (`webRadioApp.h` 1 929, `aquarium/aquariumApp.h` 1 598, `planeRadarApp.h` 1 428,
`localPlayerApp.h` 1 003, `teletextApp.h` 724, `clockApp.h` 669), and `SettingsApp`'s sections are
already split across `settings/*.h`. This is not a new architecture; it is finishing an existing one,
applied backwards to the apps that predate it.

**What is *not* the problem — recorded because it was asserted during analysis and is false.** The
claim that these headers cannot be included from a second `.cpp` (duplicate-symbol link errors) does
not hold. `dataTask.h` has 32 declarations and zero definitions — bodies are in
`dataTaskStorage.cpp`, the textbook-correct split. There are **zero** namespace-scope non-`static`,
non-`extern` variable definitions across all 58 headers. App classes are classes, so their members
are implicitly `inline`. Only three true external-linkage function bodies sit in a header
(`audio/audioEngine.h:83,94,209`), and `:82` already documents that constraint. Proof by existence:
`dataTask.h`, `spotifyTask.h` and `planeRadarApp.h` are already included from two `.cpp` files each
and link. **A future reader must not design against a linkage barrier that does not exist.**

The real barrier is **where the mutable state lives**, and it is a gravity well rather than a wall.
`main.cpp` holds 21 `g_`-prefixed globals — 13 app instances, ~9 loose shell variables, 5 shared
widgets — and 72 `extern` declarations across the headers point back at them. Because those
definitions sit at `main.cpp:164`–`1971`, any code touching them must be textually downstream of that
point, and `main.cpp` is the only translation unit that is. The include list is correspondingly
load-bearing: `settings/*.h` is pulled in mid-file at `938`–`944`, apps are instantiated immediately
before the `dbg` shims referencing them. Every new feature landed here because it was the only
location with the whole world already in scope.

**Decision**

**D1 — `main.cpp` is reduced to trimmed includes, a delegating `setup()` and `loop()` — target under
300 lines.** `setup()`'s 631-line body moves **verbatim** into `shell/boot.h` as `bootSequence()`,
leaving `void setup() { bootSequence(); }` behind: a pure move, one call site added, nothing
reordered. This is deliberately **not** M-SRCLAYOUT OQ3, which proposes decomposing `setup()` into
staged init functions and stays deferred — the boot ordering is load-bearing (TASK-288, 404, 426).
App classes move to
`apps/`, shell dispatch to `shell/appShell.cpp`, the debug console to `debug/serialConsole/`.

**D2 — App instances are owned by their own file and reached through the registry.** `appRegistry.h`'s
X-macro is extended to generate an `App*` table; `App& appById(AppId)` is declared in
`shell/appTable.h` and defined once in `appShell.cpp`. `switchApp` / `appTick` / `appHandleInput`
stop naming individual apps and index instead. One accessor replaces thirteen, built on machinery
that already exists and is already staleness-gated by `run/check`.

**D3 — Shell state is consolidated into one owned struct.** The loose flags (`g_shellBusy`,
`g_shellBusySetMs`, `g_previousAppId`, `g_appLaunched[]`, `s_inGesture`, `s_lastTouchX/Y`,
`s_cooldownMs`, `s_tbPressedSlot`, `s_tbPressedApp`) become `struct ShellState`, exposed as
`ShellState& shell()`, owned by `appShell.cpp`. `appShell.h`'s `currentAppId` and `main.cpp:164`'s
`g_previousAppId` — the same concept under two naming conventions in two files — unify here.

**D4 — Accessors use file-scope `static`, NOT the Meyers (function-local static) singleton.**

```cpp
static ShellState s_shell;                        // ACCEPTED
ShellState& shell() { return s_shell; }

static ShellState& shell() { static ShellState s; return s; }   // REJECTED
```

Three target-specific reasons: **(a)** lazy construction breaks deterministic boot — `setup()` is 631
lines of deliberately staged init (WiFi → SPIFFS → NTP → display → apps), and with `dram0_0_seg`
headroom historically measured between 0 B and 40 B, "when does this allocate" is not a question to
delegate to the compiler; **(b)** C++11 thread-safe statics emit a guard variable plus
`__cxa_guard_acquire/release` per singleton, and the concurrency here is real (`dataTask`,
`spotifyTask`, the audio pump task), so ×13 apps this is measurable flash and DRAM —
`-fno-threadsafe-statics` removes the cost and reintroduces a genuine first-use race; **(c)** the
static-initialization-order fiasco that Meyers singletons exist to defeat is not present, because
init order here is explicit and readable in `setup()`, which is strictly better than lazy magic.

**D5 — The cross-TU initialization-order property must be preserved deliberately.** D2 moves the 13
app instances into separate translation units, where construction order between TUs is unspecified.
This is safe **today** only because **none of the 13 app classes has a user-defined constructor** —
verified across `main.cpp` and all six already-extracted headers — so no constructor has side effects
or reads another global. Adding a side-effecting constructor to any `App` subclass after D2 lands
reintroduces the fiasco that D4(c) relies on being absent. App construction stays trivial; anything
with ordering requirements goes in `init()`, which the shell calls in a defined order.

**D6 — Copy construction is deleted on `App` subclasses.** They are singletons by intent; `= delete`
on the copy constructor and assignment operator makes that intent enforced rather than assumed. One
line each, no runtime cost.

**D7 — Staging separates text moves from translation-unit changes, and they land separately.**

| Stage | What | TU change | Risk |
|---|---|---|---|
| A | 7 inline app classes → `apps/` (+ the 6 existing app headers, same commit) | none | ~none |
| B | `SERIAL_DEBUG` console → `debug/serialConsole/` | none | ~none (not in prod binary) |
| C | D2 + D3 + D4 + D5 + D6 — state ownership | **yes** | real, measured |
| D | selected modules promoted to their own `.cpp`, one at a time | yes | real, measured |

**Stages A and B are *proposed* as a standalone deliverable** — this ADR is `proposed`, so nothing
here is approved yet, and that wording is deliberate. They are text moves within the existing
translation unit, deliver the majority of the benefit, need no new convention, and take `main.cpp`
from 5 880 to roughly 1 400 lines. **Stages C and D should be a separate approval decision** taken
once A/B's benefit has been felt in practice rather than argued on paper — the cost, the memory risk
and the new state-ownership vocabulary all concentrate in C.

**D8 — Behaviour-neutrality is verified, not argued.** Reusing ADR-059 D2's discipline verbatim: the
extraction commits carry no behavioural hunks; `git diff -M --stat` shows ≥95 % rename similarity;
`./run/check` green at every stage; `.map` extents captured before and after. `dram0_0_seg` headroom
is **re-derived fresh at each stage, never remembered** — it is a documented moving target in this
project (0 B on 2026-07-29/30, 40 B on 2026-08-02 after the M-CEEFAX cut). Stage D declines any
module whose promotion costs more than **256 B** of `dram0_0_seg` without an explicit recorded trade.

**D9 — The ≥3-run baseline is captured before Stage A lands**, not after, with the flaky set
pre-declared from it (the ADR-059 D13 rule, same trap, same answer). No stage requires Spotify
playback or a DUT audio path; `run/check` plus a DUT navigation pass is the whole gate. (An earlier
draft added "so TASK-442 does not block this work" — TASK-442 was root-caused and fixed on
2026-08-15, so that clause is retired. The independence never rested on it.)

**Consequences**

*Easier.* Adding an app becomes one file plus one registry row instead of a five-site edit to
`main.cpp` (which is why `NEW-APP-CHECKLIST.md` had to exist). The repo's single worst merge-conflict
hotspot disappears — every parallel session currently touches `main.cpp`. Diffs become
self-evidently scoped. Agent context cost drops on every future task: changing 711 lines of
`StockApp` no longer means loading a 5 880-line file, which is both a token cost and an error
surface. `ShellState` becomes inspectable as a unit, which is part of why `cmdGet` needed 616 lines.

*Harder.* `git blame` on moved code needs `-M`/`--follow`; this project's comments carry task
references (TASK-278, 287, 289, 291, 295, 299…) whose rationale is recovered by blaming the line, so
the ergonomics genuinely degrade. **308 `main.cpp:NNN` line-number citations across 49 documentation
files, plus 44 `main.cpp` references in `feature_inventory.yaml`, are invalidated** — a real cost,
paid once as **TASK-464**, at the end of Stage B, rather than being smuggled into a stage commit as
hygiene or repeated per-stage across the same 49 files. Feature work on the
touched files must pause during a stage, because the pure-move contract makes concurrent edits
conflict badly.

*Constrained.* No `App` subclass may take a side-effecting constructor (D5). Stages A/B **do not**
speed up compilation — still one TU — and anyone expecting that from the readability stages will be
disappointed; only Stage D delivers it, and Stage D is the risky one. `shell()` makes global state
easier to reach than today's arrangement, which is a live risk of entrenching the coupling it was
meant to reduce (D4/M-SRCLAYOUT §D5): new code reaching for `shell()` is a review question, not a
default.
