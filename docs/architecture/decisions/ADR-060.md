### ADR-060 — [2026-08-15] — M-SRCLAYOUT: source layout and state ownership

**Status**: **accepted for Stages A+B only — 2026-08-16, human sign-off (E-01).** C, D, E and F are
**not** authorised by this ADR and need a separate, narrower one; see D7. Preconditions recorded there
for that later ADR: D2's `WINAMP_DISPLAY` gap closed (TASK-496) and D8's flash gate in place.

Prior status: proposed — 2026-08-15. **Stages A and B of D7 have already landed** (`78caa95`,
`b36f184`) ahead of sign-off — unreviewed, not DUT-verified, and they discharge none of D0. That is
a sequencing failure recorded rather than tidied away; see D7.

**Design doc**: [M-SRCLAYOUT-main-decomposition.md](../designs/M-SRCLAYOUT-main-decomposition.md)

**Context**

`app/src` is 30 022 lines. `main.cpp` alone is **5 880 lines** — just under 20 % of the firmware
source in one file — and holds four unrelated things: seven `App` subclasses defined inline
(1 678 lines, of which `StockApp` is 711), the shell dispatch (321), `setup()` (631), and the
`SERIAL_DEBUG` console (~2 780, which never ships in the production binary).

The pattern that would fix this **already exists in this repo and works**. Six apps live in their own
files today (`webRadioApp.h` 1 929, `aquarium/aquariumApp.h` 1 598, `planeRadarApp.h` 1 428,
`localPlayerApp.h` 1 003, `teletextApp.h` 724, `clockApp.h` 669), and `SettingsApp`'s sections are
already split across `settings/*.h`. This is not a new architecture; it is finishing an existing one,
applied backwards to the apps that predate it.

**What is *not* the problem — recorded because it was asserted during analysis and is false.** The
claim that these headers cannot be included from a second `.cpp` (duplicate-symbol link errors) does
not hold. `dataTask.h` has 32 declarations and zero definitions — bodies are in
`dataTaskStorage.cpp`, the textbook-correct split. There are **zero** namespace-scope non-`static`,
non-`extern` variable definitions across all 58 headers. App classes are classes, so their members
are implicitly `inline`. Only three true external-linkage function bodies sit in a header
(`audio/audioEngine.h:83,94,209`), and `:82` already documents that constraint. Proof by existence:
`dataTask.h`, `spotifyTask.h` and `planeRadarApp.h` are already included from two `.cpp` files each
and link. **A future reader must not design against a linkage barrier that does not exist.**

The real barrier is **where the mutable state lives**, and it is a gravity well rather than a wall.
`main.cpp` holds 21 `g_`-prefixed globals — 13 app instances, ~9 loose shell variables, 5 shared
widgets — and 72 `extern` declarations across the headers point back at them. Because those
definitions sit in the globals block near the top of `app/src/main.cpp` (`currentAppId` through the
app-instance table), any code touching them must be textually downstream of that
point, and `main.cpp` is the only translation unit that is. The include list is correspondingly
load-bearing: `settings/*.h` is pulled in mid-file at `938`–`944`, apps are instantiated immediately
before the `dbg` shims referencing them. Every new feature landed here because it was the only
location with the whole world already in scope.

**Decision**

**D0 — The unit of physical design is a component: one class, one `.h`, one `.cpp`.**

This is the governing decision; D1–D3 are consequences of it. It is not a style preference — it is
what the standard references require, and this codebase violates all of them:

| Reference | Requirement | Status at adoption |
|---|---|---|
| C++ Core Guidelines **SF.1** | `.cpp` for code files, `.h` for interface files | violated — 58 headers, 8 `.cpp` |
| C++ Core Guidelines **SF.5** | a `.cpp` includes the `.h` defining its interface | n/a — most classes have no `.cpp` |
| C++ Core Guidelines **SF.11** | headers are **self-contained** | violated — app headers depend on `main.cpp`'s include order |
| Lakos, *Large-Scale C++ Software Design* | a **component** (`.h`+`.cpp`) is the atomic unit of physical design, testing and dependency management | violated — no component boundaries exist |
| Google C++ Style Guide | self-contained headers, `.h`/`.cc` pairs | violated |

Lakos is the governing reference because this is exactly his distinction. The **logical** design here
is sound — a clean `App` interface, an X-macro registry, per-app `dbgGet`/`dbgSet`. The **physical**
design is absent: one translation unit held 20 % of the source.

Three header-only exceptions, so the rule is not applied mechanically: **pure interfaces / abstract
base classes** (`app.h` is correctly a header with no `.cpp`), **templates**, and
**`constexpr`/`inline` helper sets** (`util/mathUtil.h`, `touch/hitbox.h`). Everything else — all
thirteen apps, the shell, the taskbar, the boot sequence, the debug console — is a component.
Target: **~28 components**, an ordinary count for 30 000 lines of C++.

**D0a — the embedded objection is bounded and does not defeat D0.** Lost cross-TU inlining is the
counter-argument on a 320 KB-RAM device. It is much smaller than it appears: **every `App` method is
`virtual`**, so the shell↔app boundary — which carries the most calls — is *already* dispatched
through a vtable and inlined nowhere. Splitting app bodies into `.cpp` files costs nothing there. An
app's internal helpers stay in its own `.cpp` and keep being inlined; shared `inline` utility headers
keep being inlined. What is genuinely lost is cross-app inlining of small non-virtual helpers **and whole-program `-Os`
across the ~30 000 lines that currently share one compiland by accident of `#include`** — the
narrow virtual-dispatch claim survives review (@Developer finding 5), the broader "cost is bounded"
conclusion drawn from it does not, which is why the gate in D8 is the load-bearing part. Therefore: cost is **measured per component**, and a component whose promotion exceeds
**256 B** of `dram0_0_seg` may stay header-only **with the measurement recorded**. An evidence-based
exception, never a default.

**Corrected — @Developer review, 2026-08-16 (finding 3): the gate was measuring the wrong axis.**
Lost cross-TU inlining is primarily a **flash** cost, not a static-DRAM one. Two verified facts:
this toolchain passes **`-fno-lto` unconditionally**
(`framework-arduinoespressif32/tools/platformio-build-esp32.py:84`), so today's inlining exists
*only* because everything is `#include`d into one TU and Stage E removes it outright; and ADR-059
`:425` measured a comparable change at **88 B DRAM against 3 984 B flash** — a ~45:1 ratio in the
direction this ADR was not gating. `check_build.sh` has **no flash check at all**.

**Stage E's per-component budget therefore records and gates BOTH**: `dram0_0_seg` ≤ 256 B *and* a
`.text`/`.rodata` delta from the same `.map`. Same grep, different section names. A component could
otherwise pass the DRAM test while quietly eating kilobytes of flash until a partition overflow much
later.

**D1 — `main.cpp` is an entry point containing no logic. Target: under 40 lines.**

```cpp
void setup() { boot::run(); }
void loop()  { shell::tick(); }
```

`setup()`'s 631-line body moves **verbatim** into `boot/boot.cpp` as `boot::run()` — a pure move, one
call site added, nothing reordered. This is deliberately **not** M-SRCLAYOUT OQ3, which proposes
*decomposing* `setup()` into staged init functions and stays deferred: the boot ordering is
load-bearing and hard-won (TASK-288, 404, 426). App classes become components under `apps/`, shell
dispatch under `shell/`, the debug console under `debug/serialConsole/`.

**D2 — A composition root owns every app instance.** Not `main.cpp`, and **not** each app defining its
own global. `shell/appTable.cpp` is the single place all thirteen are constructed, driven by the
existing X-macro registry, exposing `App& appById(AppId)`. `switchApp` / `appTick` /
`appHandleInput` stop naming individual apps and index instead.

**D2 is NOT yet implementable as sketched — @Developer review, 2026-08-16 (finding 1).** The X-macro
sketch above assumes all thirteen apps are unconditional. They are not: `app/src/main.cpp` (`g_appLaunched`) and
`:296-303` gate `SpotifyApp`, `WebRadioApp` and `LocalPlayerApp` behind `#ifdef WINAMP_DISPLAY`, and
`app/src/main.cpp` (`aquariumDbgGet`) already forks the table itself — populated under `WINAMP_DISPLAY`, `{}` otherwise.
`[env:cyd2usb]` is a real declared env that does not define it. Applied as written, `appTable.cpp`
either fails to compile that env or needs a registry format this ADR claims is already sufficient.

**Stage D's definition-of-done therefore includes resolving this, before it lands:** either
(a) declare non-Winamp builds out of scope and retire `cyd2usb` (ADR-061 D8 already proposes demoting
it), or (b) add a conditional column to `appRegistry.h` and thread it through the table. **(a) is the
lean**, and it makes D2 and ADR-061 D8 interdependent — neither should land without the other.

*Why nobody hit this:* `check_build.sh` builds only `WINAMP_DISPLAY` envs, so the gap is un-gated —
which is ADR-061 D6's argument arriving from a second direction.

An earlier draft of this ADR had each app define its own instance alongside its class. That is
**wrong on two counts**: it moves scattered ownership one directory down rather than removing it, and
it makes an app impossible to link without constructing it — which defeats the isolation a component
exists to provide. `run/check` step 6 already gates the registry against drift, so the table cannot
fall out of sync with `AppId`.

**D2a — Dependencies are levelized and acyclic** (Lakos's second requirement after components):

```
level 3  apps/*                    level 1  audio/ player/ winamp/ settings/ taskbar/
level 2  shell/ boot/ debug/       level 0  util/ gen/ touch/ app.h
```

An app never includes another app; nothing at level 0–1 includes `apps/` or `shell/`. Known violation
to clear on the way: `apps/spotifyApp` and `apps/webRadioApp` both reach into `winamp/winampDisplay.h`,
which reaches back into player-mode concepts — ADR-059's capability mask is the accepted fix.

**D2b — `app/lib/` is level −1, and project-authored code inside it is a *declared* exception.**

The levels above cover `app/src/` only. `app/lib/` holds vendored third-party libraries and sits
**below** level 0: `app/src` may depend on it; it must never depend upward on `app/src`.

That boundary is currently crossed by one thing, and the design must name it rather than pretend it
is absent. **`mb_arena.{h,cpp}`** (`app/lib/ESP32-audioI2S/src/`, 336 lines) is **project-authored**
— created by this project in `f36152b` (TASK-261 Phase 2), not by upstream — yet lives inside the
vendored fork. It has fan-in from both trees: five call sites in `app/src`
(`audio/audioEngine`, `webRadioApp`, `localPlayerApp`, `main.cpp`, the debug console) and two patched
sites inside the library itself (`mp3_decoder.cpp`, PATCH-MEMBUDGET-1/2).

Its *level* is right — a level −1 allocator that both trees depend on. What is wrong is that it is
there **by accident of the build system** rather than by decision: a vendored `lib/` directory cannot
include from `src/`, so the arena had to live where the patched decoder could reach it.

Rules:

1. **Project-authored code in `app/lib/` requires a `LOCAL_PATCHES.md` entry.** Without one, a
   platform or library bump silently deletes it. That file was created on 2026-08-15 (TASK-449)
   precisely because this fork had carried patches for months with no record; `mb_arena` is the
   largest of them.
2. **It must be a component in the D0 sense.** `mb_arena` already is — a self-contained `.h`/`.cpp`
   pair with one job. It is, ironically, the cleanest component in the tree and the only one outside
   the tree the component model covers.
3. **Relocating it to `app/src/mem/arena.{h,cpp}` is the architecturally correct end state**, blocked
   on a build-system question nobody has answered: can a PlatformIO `lib/` directory include from
   `src/`? Until that is checked, the arena stays where it is **as a recorded exception, not an
   oversight.** Filed as TASK-476.

Anything else project-authored that appears under `app/lib/` follows the same three rules, or it is a
defect.

> **Correction owed in code — filed as TASK-477.** `mb_arena.h`'s own header comment states *"All
> public symbols are no-ops … when `MEMBUDGET_PHASE1` is not defined — production (`cyd2usb_winamp`)
> is byte-clean."* **Production defines it.** `platformio.ini:93` sets `-DMEMBUDGET_PHASE1` inside
> `[env:cyd2usb_winamp]`, and has since TASK-262 promoted the A-lite arena on 2026-06-29. The comment
> was true when written and was never updated — a BP-DOC-2 failure occurring in code rather than in a
> document, and a live argument that the practice applies to source comments too. The arena ships.

**D3 — Shell state is consolidated into one owned struct.** The loose flags (`g_shellBusy`,
`g_shellBusySetMs`, `g_previousAppId`, `g_appLaunched[]`, `s_inGesture`, `s_lastTouchX/Y`,
`s_cooldownMs`, `s_tbPressedSlot`, `s_tbPressedApp`) become `struct ShellState`, exposed as
`ShellState& shell()`, owned by `appShell.cpp`. `appShell.h`'s `currentAppId` and `app/src/main.cpp` (`g_previousAppId`)'s
`g_previousAppId` — the same concept under two naming conventions in two files — unify here.

**D4 — Accessors use file-scope `static`, NOT the Meyers (function-local static) singleton.**

```cpp
static ShellState s_shell;                        // ACCEPTED
ShellState& shell() { return s_shell; }

static ShellState& shell() { static ShellState s; return s; }   // REJECTED
```

Three target-specific reasons: **(a)** lazy construction breaks deterministic boot — `setup()` is 631
lines of deliberately staged init (WiFi → SPIFFS → NTP → display → apps), and with `dram0_0_seg`
headroom historically measured between 0 B and 40 B, "when does this allocate" is not a question to
delegate to the compiler; **(b)** C++11 thread-safe statics emit a guard variable plus
`__cxa_guard_acquire/release` per singleton, and the concurrency here is real (`dataTask`,
`spotifyTask`, the audio pump task), so ×13 apps this is measurable flash and DRAM —
`-fno-threadsafe-statics` removes the cost and reintroduces a genuine first-use race; **(c)** the
static-initialization-order fiasco that Meyers singletons exist to defeat is not present, because
init order here is explicit and readable in `setup()`, which is strictly better than lazy magic.

**D5 — The cross-TU initialization-order property must be preserved deliberately.** D0 splits the
tree into ~28 translation units, where construction order *between* TUs is unspecified. D2 contains
most of the exposure by putting all thirteen app instances in **one** TU (`shell/appTable.cpp`),
where order is well-defined top-to-bottom. The residual risk is safe **today** only because **none of the 13 app classes has a user-defined constructor** —
verified across `main.cpp` and all six already-extracted headers — so no constructor has side effects
or reads another global. Adding a side-effecting constructor to any `App` subclass after D2 lands
reintroduces the fiasco that D4(c) relies on being absent. App construction stays trivial; anything
with ordering requirements goes in `init()`, which the shell calls in a defined order.

**D6 — Copy construction is deleted on `App` subclasses.** They are singletons by intent; `= delete`
on the copy constructor and assignment operator makes that intent enforced rather than assumed. One
line each, no runtime cost.

**Stages A and B created zero components.** They moved text into headers that are still not
self-contained and still included from `main.cpp`; the translation-unit count is unchanged at 8.
`main.cpp` got shorter — 5 880 → 1 726 — while the tree continued to violate SF.1, SF.11 and Lakos
exactly as before. This is recorded plainly because an earlier draft of this ADR framed A+B as
delivering "the majority of the benefit", which measured against D0 is false: they delivered
readability, not physical design.

### What this ADR authorises — narrowed on review, 2026-08-16

**This ADR signs off Stages A and B only. C, D, E and F require a separate, narrower ADR.**

@Developer's framing challenge, which I accept: this ADR argues Stage E from first principles —
Core Guidelines, Lakos, Google style — *as if physical-design purity were an end in itself*. On this
target the honest cost/benefit is thinner than the argument implies. There is one binary, `-fno-lto`,
no off-target unit tests instantiating `App` subclasses, and no second consumer of any component.
The benefits this ADR's own Consequences section lists — fewer `main.cpp` merge conflicts, scoped
diffs, lower agent-context cost — were **mostly captured by A+B already**, at near-zero risk
(5 880 → 1 726 lines). Stage E's distinct win is incremental build time, mentioned once in passing,
and **no one in this project's history has complained about build time.**

Meanwhile Stage E's costs were underweighted twice: the budget measured the wrong axis (D8, above),
and the composition root it depends on has a real compilation gap (D2, above) that four documents and
one Architect missed until review.

So: **land A+B, live with them for a milestone, then decide C/D on felt benefit** — which is what
M-SRCLAYOUT §5b already recommended and what this ADR should have said instead of pre-approving the
whole chain. Preconditions for that later ADR: D2's `WINAMP_DISPLAY` gap fixed, and D8's flash gate
in place.

**Stage E is the one that discharges D0**, and **D must precede it** — an app cannot become an
independently linkable component while its instance lives in `main.cpp` and the shell state it reads
has no declared accessor.

**D8 — Behaviour-neutrality is verified, not argued.** Reusing ADR-059 D2's discipline verbatim: the
extraction commits carry no behavioural hunks; `git diff -M --stat` shows ≥95 % rename similarity;
`./run/check` green at every stage; `.map` extents captured before and after. `dram0_0_seg` headroom
is **re-derived fresh at each stage, never remembered** — it is a documented moving target in this
project (0 B on 2026-07-29/30, 40 B on 2026-08-02 after the M-CEEFAX cut). Stage E declines any
component whose promotion costs more than **256 B** of `dram0_0_seg`, with the measurement recorded
in the task (D0a).

**D9 — The ≥3-run baseline is captured before the next stage lands**, not after, with the flaky set
pre-declared from it (the ADR-059 D13 rule, same trap, same answer). **This was not done for Stages
A and B** — they landed on `run/check` alone, with no DUT baseline before or after. That debt is
owed before Stage C. No stage requires Spotify
playback or a DUT audio path; `run/check` plus a DUT navigation pass is the whole gate. (An earlier
draft added "so TASK-442 does not block this work" — TASK-442 was root-caused and fixed on
2026-08-15, so that clause is retired. The independence never rested on it.)

**Consequences**

*Easier.* Adding an app becomes one file plus one registry row instead of a five-site edit to
`main.cpp` (which is why `NEW-APP-CHECKLIST.md` had to exist). The repo's single worst merge-conflict
hotspot disappears — every parallel session currently touches `main.cpp`. Diffs become
self-evidently scoped. Agent context cost drops on every future task: changing 711 lines of
`StockApp` no longer means loading a 5 880-line file, which is both a token cost and an error
surface. `ShellState` becomes inspectable as a unit, which is part of why `cmdGet` needed 616 lines.

*Harder.* `git blame` on moved code needs `-M`/`--follow`; this project's comments carry task
references (TASK-278, 287, 289, 291, 295, 299…) whose rationale is recovered by blaming the line, so
the ergonomics genuinely degrade. **308 `main.cpp:NNN` line-number citations across 49 documentation
files, plus 44 `main.cpp` references in `feature_inventory.yaml`, are invalidated** — a real cost,
paid once as **TASK-464**, at the end of Stage B, rather than being smuggled into a stage commit as
hygiene or repeated per-stage across the same 49 files. Feature work on the
touched files must pause during a stage, because the pure-move contract makes concurrent edits
conflict badly.

*Constrained.* No `App` subclass may take a side-effecting constructor (D5). No app may include
another app, and nothing at level 0–1 may include `apps/` or `shell/` (D2a). Stages A/B **do not**
speed up compilation — still one translation unit — and anyone expecting that from them will be
disappointed; incremental build time improves only with Stage E, which is also where the memory
measurement lives. `shell()` makes global state
easier to reach than today's arrangement, which is a live risk of entrenching the coupling it was
meant to reduce (D4/M-SRCLAYOUT §D5): new code reaching for `shell()` is a review question, not a
default.
