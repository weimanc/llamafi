### ADR-014 — 2026-05-09 — M-CHROME tier 2 — composite-static + dynamic-volume

**Status**: accepted (2026-05-21 — both halves implemented: composite-static (TASK-040, fbbe421) + dynamic-VOLUME (TASK-041, b8f37d3..8075176); T070a + T070b PASS)

**Context**:

M-CHROME tier 1 (TASK-023/024/025) shipped MONOSTER + a runtime-rendered kbps/kHz strip. Tier 2 was originally framed as "bake the rest of the main-window sprites" — TITLEBAR, VOLUME, BALANCE — at full resolution (~178 KB extra atlas) which doesn't fit (98.6 % flash, 18 KB free).

User-proposed reframing during scoping: instead of growing the atlas surface and renderer, composite the *static* decoration directly onto `MAIN_BG` at bake time. The runtime never has to know those sprites exist. The dynamic ones (just VOLUME, given the user's stated scope) get a regular sprite atlas + render path.

Affirmed scope this round:
- TITLEBAR active variant: static, composite onto MAIN_BG.
- BALANCE centered frame: static, composite onto MAIN_BG.
- kbps "192" + kHz "44" text: static, composite onto MAIN_BG (was runtime via SKIN_GLYPH in tier 1).
- MONO/STEREO indicator: **accepted as static** ("STEREO lit / mono dim") — composite onto MAIN_BG. Drop MONOSTER atlas + dynamic switching.
- VOLUME slider: **dynamic** — extend SpotifyArduino's `getCurrentlyPlaying` parser to surface `device.volume_percent`; bake a small VOLUME atlas with N keyframes; render at runtime indexed by the new snapshot field.

**Decision**:

1. **Bake-time composite onto MAIN_BG.**
   - `tools/bake_skin.py` gains a "composite static decoration" pass after loading MAIN.BMP and before emitting RGB565. Steps run in this order, each Pillow-side:
     - Crop TITLEBAR.BMP (27, 0, 302, 14) → paste onto MAIN_BG at (0, 0).
     - Pick a centered frame from BALANCE.BMP (frame 14 of 28) → paste at (177, 57). Cyan pixels (Winamp's transparency convention) substituted to MAIN_BG's underlying color via Pillow alpha mask.
     - Render kbps `"192"` and kHz `"44"` glyph-by-glyph from TEXT.BMP onto MAIN_BG at (110, 43) and (156, 43).
     - Composite the static MS_STEREO_ON + MS_MONO_OFF pair onto MAIN_BG at (212, 41) using MONOSTER.BMP.
   - The result is one 275×116 RGB565 array — same flash footprint as today, richer pixels.
2. **Drop the redundant runtime renderers and atlases.**
   - `winampDisplay::drawBitrateSampleRate()` deleted.
   - `winampDisplay::drawMonoStereo()` deleted; `redrawMetadataStrip()` and the snapshot-seq watcher in `checkForInput` deleted (the strip is now baked-in).
   - MONOSTER.BMP removed from `TIER3_SHEETS` in the bake tool. SKIN_MONOSTER atlas + sprite-UV defines disappear from `gen/`.
3. **Add VOLUME as a real dynamic feature.**
   - Lib patch: extend `SpotifyArduino`'s currently-playing JSON filter to include `device.volume_percent`. Add `int volumePercent` field to `CurrentlyPlaying` struct (default `-1` for "unknown / no device"). Same pattern as the existing `currentlyPlayingType` field.
   - Snapshot: add `int8_t volumePercent` (`-1` for unknown). `spotifyTask::onCurrentlyPlaying` populates it.
   - Bake: VOLUME.BMP loaded with 5 keyframes selected from the 28-frame source (every ~6th frame: green low / yellow / orange / red / red max). `gen/skin_layout.h` exposes a `VOLUME_FRAME(n)` macro returning a SkinUV.
   - Render: new `winampDisplay::drawVolume(int percent)` selects the appropriate keyframe + blits at (107, 57). Called from `repaintChrome()` and from the snapshot-seq watcher in `checkForInput` so it tracks live volume changes.

**Why this shape, briefly:**

- Composite-static vs more atlases: zero flash growth on the static elements, one less runtime render path each, and the bake-tool change is a one-time cost that lives on the host. The trade-off is "kbps/kHz/balance/titlebar are fixed at bake time" — re-baking is required to change them — which matches the user's intent (these aren't expected to vary).
- Dynamic volume vs static: the user explicitly wants this driven by API. The ~2 KB lib patch + ~2 KB atlas + ~30 LOC render is small and self-contained.

### Amendment 1 — 2026-05-10 — §3 dynamic-VOLUME corrections + sentinel decision + asset inspection

**Trigger**: Architect review of TASK-041 against current code (post-fbbe421). §3 referenced integration points that no longer exist after TASK-040 deletions, and deferred the sentinel-rendering decision in a way that VE could not write a clean acceptance test against. LL-016 also calls for asset inspection before locking keyframe coordinates. This amendment closes those gaps before TASK-041 starts.

#### A1.1 — Render trigger: snapshot reader, not touch path

§3 originally said *"Wired into `repaintChrome()` and the snapshot-seq watcher inside `checkForInput`."* That watcher was deleted in TASK-040 (the previous metadata-strip use case is now baked-in). The volume render must instead be driven from `spotifyLogic.h::updateCurrentlyPlaying()`, which is the single existing snapshot-seq reader.

**Revised wiring**:
- `updateCurrentlyPlaying` already gates on `seq == lastRenderedSeq` and bails when the snapshot is unchanged. Volume rendering reuses that gate but adds a separate value-cache so it isn't suppressed by the existing `isSameTrack` early-return path (volume can change while track stays the same).
- Add `static int8_t lastVolumeRendered = -2;` inside the function (`-2` is "never rendered" — distinct from the `-1` "no device" sentinel below).
- After the seq-bump check, **before** the `isSameTrack` branch, call `sp_Display->drawVolume(snap.volumePercent)` whenever `snap.volumePercent != lastVolumeRendered`. Update the cache.
- `repaintChrome()` also calls `drawVolume(lastVolumeRendered)` (or the sentinel keyframe if cache is `-2`) so a SCREEN_LOG → chrome-repaint cycle restores the slider.

#### A1.2 — Sentinel rendering: dedicated 6th keyframe

§3 originally deferred the choice between "lowest keyframe", "skip the slider", and an unspecified neutral. Each is wrong in its own way ("lowest" lies as zero-volume; "skip" leaves a hole; neutral is ambiguous).

**Decision: bake a 6th keyframe = "no device / unknown".** Visually distinct (greyed/empty track, no fill bar). Selected when `volumePercent < 0`. The `drawVolume` API then has six valid render paths:

| volumePercent | Keyframe |
|---|---|
| < 0 (sentinel) | KEYFRAME_NONE — greyed empty track |
| 0..19 | KEYFRAME_0 (≈ frame 0 of source) |
| 20..39 | KEYFRAME_1 (≈ frame 7) |
| 40..59 | KEYFRAME_2 (≈ frame 14) |
| 60..79 | KEYFRAME_3 (≈ frame 20) |
| 80..100 | KEYFRAME_4 (≈ frame 27, max) |

Atlas surface: 6 × 68×13 = 5,304 px = 10,608 bytes. Fits in the 18 KB headroom.

Source for KEYFRAME_NONE: bake-tool synthesises it from KEYFRAME_0 by replacing the green "fill" pixels with the background-grey palette colour, leaving the track outline intact. (Alternative considered and rejected: re-purpose VOLUME.BMP's frame 0 directly — but frame 0 in canonical Winamp is "minimum non-zero volume" with a single green pixel lit, not an empty track.)

#### A1.3 — VOLUME.BMP layout: empirically confirmed canonical for this skin

Per LL-016, asset inspected via `_decode_bmp_rle8` (which transparently dispatched to PIL since VOLUME.BMP is `compression=0` uncompressed; manual decoder returned None and fell through). Findings on `skins/base-2.91.wsz/VOLUME.BMP` (68×433, 8 bpp, uncompressed):

- **28 frames** stacked vertically, 15-px stride, frames 68×13 with a 2-px inter-frame gap baked into the stride.
- Frame `n` interior: `(0, n*15, 68, 13)` for n in 0..27.
- Volume **knob** sprite at `(0, 420, 68, 13)` — out of scope for §3 unless touch-control lands later.
- High-delta row scan recovered the boundaries cleanly (every 15 rows from y=15 through y=405); no non-canonical y-stride drift, unlike BALANCE.BMP.

Keyframe selection commits to frames `0, 7, 14, 20, 27`:

| Keyframe | Source y range | Notes |
|---|---|---|
| KEYFRAME_0 | (0, 0, 68, 13) | minimum non-zero |
| KEYFRAME_1 | (0, 105, 68, 13) | low quarter |
| KEYFRAME_2 | (0, 210, 68, 13) | mid |
| KEYFRAME_3 | (0, 300, 68, 13) | three-quarter |
| KEYFRAME_4 | (0, 405, 68, 13) | max |
| KEYFRAME_NONE | synthesised | grey-track variant of KEYFRAME_0 |

Pre-impl gate: Developer must visually confirm the chosen frames look distinct after bake (`gen/composite/volume_keyframe_*.png`, emitted via the same per-element review tooling as TASK-040). LL-016: visually inspect before committing.

#### A1.4 — Snapshot writer location

§3 originally said *"`spotifyTask::onCurrentlyPlaying` populates it."* No such callback exists; snapshot writes happen inline in the task body's poll-success branch (around the existing `g_snapshot.isPlaying = ...` block, under `portENTER_CRITICAL`). Update wording to: *"Set in the snapshot-write block of the poll-success branch in `spotifyTask` task body, alongside `isPlaying` / `progressMs` / `playingType`."*

#### A1.5 — `drawVolume` interface

```cpp
// In WinampDisplay (public). Negative percent = sentinel ("no device").
// Idempotent: caller is responsible for caching the last-rendered value
// to avoid redundant blits (see updateCurrentlyPlaying integration).
void drawVolume(int percent);
```

Implementation:
- Compute `keyframeIndex = percent < 0 ? KEYFRAME_NONE : pickKeyframe(percent)` where `pickKeyframe` is the 5-bucket mapper above.
- Single `blitSprite(originX + VOLUME_X, originY + VOLUME_Y, SKIN_VOLUME, SKIN_VOLUME_W, keyframeUv)` per call.
- `VOLUME_X=107, VOLUME_Y=57` (canonical Winamp main-window position; verified non-colliding with BALANCE composite at x=177 and kbps text at y=43-49).

#### A1.6 — Verification gate refinement

T070 split into:
- **T070a** — [chrome-001] Volume snapshot field reaches DUT chrome within one poll. Spike-harness `setVolume` row (or manual `curl` against `/v1/me/player/volume`); observe `[D][chrome] drawVolume pct=NN keyframe=K` log line + visual eyeball within ≤ 5 s.
- **T070b** — [chrome-001] Sentinel keyframe shows when no active device. Boot DUT with no Spotify Connect device active; observe KEYFRAME_NONE rendered. Then transfer playback to a device; observe transition to a real keyframe within one poll.

VE owner; planned. Both must pass before TASK-041 closes.

#### A1.7 — Sub-task split unchanged; impl ordering

TASK-041 still ships as one PR per §A1 above. Internal commit ordering recommended:
1. Bake-tool: select 5 keyframes + synthesise KEYFRAME_NONE; emit `SKIN_VOLUME` atlas + `VOLUME_KEYFRAME_*` SkinUV defines + `VOLUME_X`/`VOLUME_Y` macros.
2. Snapshot: add `int8_t volumePercent` field; populate in task body's poll-success snapshot-write block; expose via `copySnapshot`.
3. Renderer: `drawVolume(percent)` + `pickKeyframe(percent)` helper.
4. Wire-in: `updateCurrentlyPlaying` value-cache + `repaintChrome()` call.

Each step compiles + flashes cleanly on its own (steps 1–3 are dead code until step 4 wires them; intentional, eases review).
