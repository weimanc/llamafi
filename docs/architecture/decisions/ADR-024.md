### ADR-024 — 2026-05-22 — Multi-app shell switching model (M-MULTIAPP)

**Status**: proposed

**Context**:

The device currently runs a single app: the Winamp-skinned Spotify player. The
5in1 reference project (`resource/5in1`) demonstrates five lightweight apps (Clock,
Weather, Crypto, Matrix rain, Game of Life) that share the same display. Porting
those apps requires a switching model and a persistent chrome strategy.

Three axes require decisions before implementation tasks can be filed:

1. **Layout** — does Winamp chrome stay on screen across all apps, or does each
   app take the full display?
2. **Concurrency** — do apps run concurrently (FreeRTOS tasks) or sequentially
   (one active at a time)?
3. **State** — is app state discarded on switch, or preserved in RAM?

---

**Decision**

**1. Layout: co-existence — Winamp chrome always visible**

The 320×240 landscape canvas is split:
- Left column: 275×240 px — Winamp main window (y: 0–115) + app canvas (y: 116–239)
- Right strip: 45×240 px — icon-only taskbar, always visible

`originX` shifts from 22 (centred) to 0 (left-aligned). All downstream
`originX`-relative coordinates are unaffected; only the baseline moves.

The full-screen takeover alternative (each app owns 320×240) was rejected: it
removes the Winamp chrome on every non-Spotify view, breaks the visual identity
of the device, and requires Spotify state to be destroyed and rebuilt on every
switch.

**2. Concurrency: single active app; taskbar is not a FreeRTOS task**

Only one app runs at a time. The taskbar is a persistent input layer and rendering
strip — it is not a FreeRTOS task. Its hit-zone is checked first in
`checkForInput()` before the active app receives the event.

Network I/O uses dedicated FreeRTOS tasks (same pattern as `spotifyTask`):
- `spotifyTask` — unchanged, always running in background
- `dataTask` — new, shared by Weather and Crypto; posts results via spinlock

Clock, Matrix rain, and Game of Life are compute-only and need no network task.

Full concurrent app execution was rejected: increases RAM pressure, complicates
rendering ordering, and provides no user-visible benefit for this use case.

**3. State: preserved across switches in named per-app structs**

Each app has a dedicated POD state struct in RAM. On switch:
`saveAppState()` → clear app canvas → `currentAppId = next` → `restoreAppState()`
(or `initAppState()` on first launch) → `renderTaskbar()` → `repaintApp()`.

State is never heap-allocated. Total RAM budget: ~3.8 KB for all six apps
(dominated by `LifeAppState` at ~2.9 KB for the 55×48 GoL grid).

Union-per-slot layout (each slot sized to largest member ≈ 17.4 KB total) is
rejected in favour of named structs (3.8 KB total).

**4. Canvas constraint**

All apps render into x: 0–274. The taskbar strip (x: 275–319) is never written
by any app. `switchApp()` clears only `tft.fillRect(0, 0, 275, 240, TFT_BLACK)`.

---

**Alternatives considered:**

**Full-screen takeover per app**: Simpler rendering, no taskbar, each app gets
320×240. Rejected: loses Winamp chrome on non-Spotify views; Spotify state must
be torn down and rebuilt on each switch.

**Concurrent app execution (all apps running FreeRTOS tasks)**: Maximum
responsiveness. Rejected: RAM pressure, render ordering complexity, display bus
contention. No user-visible benefit for sequentially-used lightweight apps.

**Floating taskbar overlay (not always visible)**: Triggered by edge-swipe.
Rejected: complicates hit-testing, adds gesture state machine, no benefit for
six fixed apps.

---

**Consequences:**

What becomes easier:
- `switchApp()` is a single well-defined entry point for all app transitions.
- Network tasks (`spotifyTask`, `dataTask`) are decoupled from the render loop.
- `appShell.h` is a small, self-contained module.

What becomes harder:
- `originX = 0` change invalidates all existing test harness `tap`/`drag`
  coordinates (see shell-layout.md Gap 1; mitigated by `coords.py`).
- 5in1 source apps target portrait 240×320; all render logic must be rewritten
  for landscape 275×240 (or 275×124 below Winamp chrome). No mechanical transpose.
- `LifeAppState` at ~2.9 KB is the largest single struct; monitor heap if more
  apps are added.
