### ADR-031 — 2026-05-25 — Aquarium app: 275 px sprite viewport + 8-bit depth + Preferences dropped

**Status**: proposed

**Context**:

`resource/ASCII_Aquarium/ASCII_Aquarium_CYD.ino` (v1.67) is a standalone Arduino sketch
targeting a 320×240 CYD display with its own WiFi, NTP, SD capture, and a four-tab settings
UI backed by `Preferences`. The port target is the multi-app shell (M-MULTIAPP), where the
app canvas is constrained to `x: 0..274` (TASKBAR_X = 275), and WiFi, NTP, touch, and
Preferences are already managed by the host firmware.

The ESP32-2432S028R has no PSRAM; sprite memory comes entirely from the internal heap (~300 KB
usable under Arduino). Minimising sprite footprint is a hard requirement.

Three structural decisions are required before implementation begins:

**Decision 1 — Sprite width: 275, not 320**

The upstream creates `canvas.createSprite(SCREEN_W, SCREEN_H)` = 320×240. The multi-app shell
reserves `x: 275..319` for the taskbar. An app that writes to that region would corrupt the
taskbar strip.

Three options:

- **(A) 320×240 sprite + clip**: allocate 320×240 and mask all draw calls to x < 275. Complex;
  every draw call in ~50 functions requires a clip guard or a scissor rect. TFT_eSPI sprites do
  not have a built-in clip region. Ruling out: fragile, high maintenance burden.

- **(B) 275×240 sprite**: allocate 275×240; `canvas.pushSprite(0, 0)` pushes only the left 275
  px. All `SCREEN_W` references become `AQ_CANVAS_W = 275`. The taskbar strip is physically
  unaddressed by `pushSprite`. Ruling in: clean, consistent with every other app in the shell
  (all use `tft.fillRect(0, 0, 275, 240, ...)` or direct `tft.drawXxx` bounded to x < 275).

- **(C) 320×240 sprite + offset push**: push at `(0, 0)` but allocate 320 wide and clip
  `pushSprite` at 275. TFT_eSPI does not support a width-clipped `pushSprite` in the 2.0.x
  Arduino-ESP32 era — the call takes `(x, y)` only. Ruling out: not directly supported.

**Decision**: Option **B** — 275×240 sprite. Every `SCREEN_W` reference in ported code is
replaced with `AQ_CANVAS_W = 275`. The `pushSprite(0, 0)` call pushes exactly the app viewport.

**Decision 2 — Sprite colour depth: 8-bit**

Options considered:

- **(A) 16-bit RGB565**: 275×240×2 = 132 000 bytes. Full colour fidelity but consumes ~44% of
  the usable internal heap on its own.
- **(B) 8-bit indexed**: 275×240×1 = 66 000 bytes. TFT_eSPI maps `setTextColor`/`fillRect`
  RGB565 values to the nearest palette entry at draw time. Sufficient for fish glyphs, bubbles,
  seaweed, and the blue gradient. 4-bit (16 colours, 33 KB) was considered and rejected: 16
  colours cannot represent 12 fish species + gradient + seaweed without visible quantisation.
- **(C) No sprite, direct TFT**: 0 bytes overhead but requires per-entity erase logic;
  overlapping fish erase each other's pixels, producing visible artefacts. Rejected.

**Decision**: Option **B** — `setColorDepth(8)`, 66 000 bytes from internal heap. No fallback
to 16-bit; if 66 KB cannot be allocated the app sets `_spriteReady = false` and skips rendering.

**Decision 3 — Preferences: dropped, replaced by compile-time constants**

The upstream stores fish count, bubble count, octopus/seahorse frequency, seaweed sway speed,
seaweed length, clock style, timezone, WiFi credentials, and background mode in ESP32 NVS
via the `Preferences` library. On load, `loadPersistentState()` reads all of these and on
change `saveSettings()` writes them.

In the multi-app shell context:

- WiFi credentials are managed by WiFiManager and stored in NVS by that library — a second
  `Preferences` namespace for aquarium WiFi would be redundant and could collide.
- NTP timezone is set once at boot by `configTime()` in `main.cpp` — per-app timezone
  management conflicts with host ownership.
- The settings UI (four tabs: Tank, Seaweed, Clock, Background) is the only mechanism in the
  upstream to change these values. Dropping the settings UI (no useful screen real-estate in a
  275 px viewport already occupied by fish) renders persistence moot.
- NVS `Preferences` namespaces have a 15-character key limit and a fixed bucket count. Adding
  another namespace increases NVS wear and namespace pressure on a partition shared with
  WiFiManager and the DoubleResetDetector.

The chosen constants match the upstream defaults exactly (the "out-of-box" experience):

```
AQ_FISH_COUNT   = 16    (DEFAULT_FISH)
AQ_BUBBLE_COUNT = 10    (DEFAULT_BUBBLES)
AQ_OCTOPUS_FREQ = 1     (DEFAULT_OCTOPUS_FREQUENCY)
AQ_SEAHORSE_FREQ= 1     (DEFAULT_SEAHORSE_FREQUENCY)
AQ_SWAY         = 1.10f (DEFAULT_SWAY)
AQ_SEAWEED_LEN  = 1.35f (DEFAULT_SEAWEED_LENGTH)
AQ_SEAWEED_RAND = 0.35f (DEFAULT_SEAWEED_LENGTH_RANDOMNESS)
Background      = BACKGROUND_BLUE_GRADIENT (DEFAULT_BACKGROUND_MODE)
Clock           = small-text, top, white, always visible
```

**Decision**: `Preferences` is dropped entirely. Settings are `static constexpr` constants in
`aquariumApp.h`. `loadPersistentState()` and `saveSettings()` / `serviceSettingsPersistence()`
are not ported. No NVS access from `AquariumApp`.

**Consequences**:

What becomes easier:
- No NVS read at `init()` — fast startup, no flash I/O on app switch.
- No collision risk with WiFiManager or DRD NVS namespaces.
- All simulation parameters are auditable at compile time.
- Port scope is significantly reduced (~700 lines of settings UI + persistence code not ported).

What becomes harder / constrained:
- Aquarium parameters are not user-adjustable without a firmware reflash. This is acceptable
  for a device where the target user experience is a decorative screensaver, not a tunable
  simulation.
- If per-user tuning is required in future, the recommended path is to add an in-app touch
  gesture (e.g. long-press for fish count cycle) rather than re-introducing `Preferences`.

**Supersedes**: nothing. Scoped to M-AQUARIUM.

**Closes**: "sprite viewport and Preferences strategy for Aquarium port" (M-AQUARIUM design
review, 2026-05-25).
