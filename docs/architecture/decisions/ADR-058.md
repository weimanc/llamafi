### ADR-058 — [2026-07-31] — M-CEEFAX viability: resolve the 3-way TLS contention or cut the feature

**Status**: accepted — 2026-07-31 — **Option D (cut Ceefax)**. Human decision after
EXP-020 falsified Option A. Ceefax backend removed (commit 41448f5); NOS Teletekst
remains as the sole teletext source, DUT-verified post-cut. The `TeletextSource`
seam is kept dormant for a possible future backend. (Original proposed analysis
and the A/B/D options retained below as the decision trail.)

**Update 2026-07-31 (EXP-020 DONE — Option A FALSIFIED):** the external throttle
cleared and the integrated build **connects** for the first time
(`WStype_CONNECTED` fires — servicing fix validated), crash-free, no `errno=11`.
But it then **drops ~90 ms after connecting** — the instant the relay's first
data burst arrives — cleanly (no `WStype_ERROR`), with memory recovering, at
**freeDma ≈ 24 K**. Crucially this reproduces **fully isolated** (Spotify
compiled out AND the WebRadio station-fetch stubbed), so it is **not** cross-app
contention: Ceefax's *own* ~47 KB TLS allocation leaves only ~23 K of the ~70 K
pool, too little to buffer the incoming carousel. **This falsifies Option A** —
there is no other TLS consumer left to pause, and pausing them can't raise the
~70 K baseline. The endpoint/channel-ID/handshake are byte-identical to the
6 h-stable spike; the spike survived only because its narrow build had more
free-DMA headroom after the same TLS cost. **The real fork is now B vs D**
(A is off the table); see the revised Decision below. Full data: EXP-020.

**Supersedes**: the coexistence-acceptance portion of ADR-057 (the "accept
best-effort connectivity / accept transient Spotify degradation" stance),
whose acceptance was **withdrawn 2026-07-31** after a functional DUT test found
the feature had never actually connected. See tasks.md TASK-374 (REOPENED) and
TASK-376.

---

**Context**

M-CEEFAX (ADR-057) shipped on 2026-07-30 and was briefly accepted the same day
**without a functional DUT test**. When one was finally run (2026-07-31,
TASK-376) it revealed the feature never connected and could crash the device.
Two sessions of root-causing have now separated the *fixable bugs* from the
*architectural question*:

*Fixed / solvable (transport + protocol are sound):*
- The connect-path crash (Guru Meditation LoadProhibited) is root-caused and
  fixed — it was an **uninitialized `_client_cert`/`_client_key` in the pulled
  `WebSocketsClient`** (`begin()` never initializes them; `loop()` then installs
  a garbage client cert on the fresh `WiFiClientSecure`, and the next connect
  `strlen`s it). Fixed by calling `beginSslWithClientKey(...,nullptr,nullptr)`.
  Verified crash-free. (commit 44b5fb0)
- The handshake-servicing and reconnect-throttle bugs (TASK-376 #1/#2) are
  landed, plus a fast-fail socket-storm they introduced is fenced by the
  invariant `kServicingWindowMs(3s) < setReconnectInterval(4s) < kRetry
  IntervalMs(15s)`.
- Protocol decode + rendering are proven (EXP-005/006; the render layer is
  shared, unmodified, with the shipped NOS Teletekst source).

*The unresolved question — and it is architectural, not a bug:*

This ESP32 has a **single ~77 KB DMA-capable heap**. One mbedTLS handshake
needs a contiguous ~16 KB × 2 (`CONFIG_MBEDTLS_SSL_MAX_CONTENT_LEN = 16384`)
plus overhead — call it ~40–55 KB peak per TLS session. The firmware already
runs **two** TLS consumers against that pool:
- `spotifyTask` — background Now-Playing poll (~every 5 s)
- `dataTask` / WebRadio — periodic fetches and, when playing, a persistent
  audio stream

Ceefax adds a **persistent third** TLS/WebSocket session. Three concurrent
handshakes do not fit in 77 KB. This is the same DMA-capacity ceiling ADR-057's
own spike (EXP-006) measured — it reproduces *with Spotify entirely disabled*,
so it is a capacity limit, not a scheduling race. Its symptoms, seen again this
session:
- Spotify's poll takes `SSL - Memory allocation failed` (-32512) while Ceefax
  is active — the exact degradation TASK-374's coexistence gate has **never**
  passed.
- Under the deepest DMA dips, `socket()` returns `errno=11` ("No more
  processes") — lwIP's 16-slot socket table starves and *all* TLS on the device
  (including Spotify) fails until it drains.

ADR-057 already identified the "deeper fix" (shrink the mbedTLS buffer via
`CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH`) and locked a human decision on
2026-07-29 to **not** rebuild the precompiled `framework = arduino` binary for
it. That constraint still holds unless explicitly revisited.

**Not yet verified at all:** a successful connect + page render on the
*integrated* build. Both DUT sessions were ultimately blocked from observing it
— the first by the crash, the second by an external device-side TLS throttle
(the relay edge and/or the home router rate-limiting the device's IP after
heavy test volume; the host still gets `HTTP/1.1 101`). So "it displays a page"
is proven for the design-stage spike, **not** for the shipped feature. Viability
therefore rests on *two* gates, not one:
- **Gate 1 (functional):** does the integrated build connect + acquire + render
  a page at all? (Expected yes — transport/protocol/crash are handled — but
  unconfirmed.)
- **Gate 2 (coexistence):** can it do so without degrading Spotify/WebRadio
  below an acceptable bar? (This is the hard one; has never passed.)

---

**The core question**

Is a live-teletext *second source* worth the engineering needed to make three
concurrent TLS consumers coexist on a 77 KB DMA pool — or is the honest call to
cut it? ADR-057 answered "yes, accept degradation"; that answer was withdrawn
because the degradation is real and the feature was never functionally proven.

---

**Options**

**A. Foreground TLS exclusion — pause the *other* TLS consumers while the user
is actively on the Ceefax source (Architect-recommended path to evaluate).**

Ceefax is a *foreground* activity: the user is looking at teletext, not
background-polling music metadata. So collapse the 3-way contention to ~1-way
by giving Ceefax the DMA pool for the duration of its foreground session.

- Mechanism: the project already has `tlsYield()`/`tlsResume()`
  (architecture.md "TLS coexistence") which pauses **`spotifyTask`**. Extend the
  same protocol to cover **`dataTask`**, and hold the yield for Ceefax's whole
  foreground session (`onResume`→`onSuspend`), not just per reconnect attempt.
- Honest subtleties this must resolve (do **not** present A as a clean win):
  1. **WebRadio audio.** If a station is *playing* when the user opens Ceefax,
     its stream is a persistent TLS session; yielding it = the music stops.
     Policy needed: either (i) don't pause a live audio stream (accept the
     contention only in that specific combination, which may reintroduce the
     failure), or (ii) treat "open Ceefax" as mutually exclusive with WebRadio
     playback (pause/mute), which is a UX decision for @PM.
  2. **Boot-time transient.** The worst contention observed is the *startup*
     storm (Spotify token refresh + WebRadio initial fetch + Ceefax connect all
     at once), independent of foreground exclusion. Ceefax should additionally
     hold off connecting until the initial TLS bring-up settles (e.g. gate its
     first attempt behind a post-boot delay / a "system TLS idle" signal), so it
     never *starts* into the storm.
  3. **Steady-state cost.** With the foreground app = Teletext/Ceefax, `dataTask`
     is largely idle for the other fetch-apps anyway; the real steady-state
     competitor is just the Spotify poll (already yieldable). So in the common
     case A may be nearly free — the cost is concentrated in the two edge cases
     above.
- Pros: no framework rebuild; uses an existing, proven mechanism; matches the
  foreground/background reality of the UX.
- Cons: needs new cross-task coordination (dataTask yield) and a WebRadio-audio
  policy call; still unproven until a real coexistence soak passes Gate 2.

**B. Shrink the mbedTLS per-connection footprint (`CONFIG_MBEDTLS_SSL_VARIABLE_
BUFFER_LENGTH`).** The direct capacity fix — variable-length TLS buffers grow
only as far as each session needs instead of pre-reserving 16 KB × 2, which
could make three sessions genuinely fit.
- Pros: attacks the root cause (capacity), benefits *all* TLS on the device.
- Cons: requires rebuilding the precompiled Arduino framework binary from
  source — explicitly declined by human decision on 2026-07-29 as
  disproportionate to one feature. Reopening that is a real scope decision, not
  an Architect default.

**C. Accept transient degradation (the withdrawn ADR-057 Option A).** Ship it,
let Spotify's poll take self-recovering `SSL -32512` while the user is on
Ceefax. Rejected 2026-07-31: proven real, and the `errno=11` socket-table
starvation is a *harder* failure than "one poll retries" — it can take Spotify
down entirely, not transiently. Not recommended without at least A's boot-time
and socket-exhaustion fences in place.

**D. Cut the feature.** Remove `CeefaxTeletextSource`; keep NOS Teletekst as the
sole teletext source (it works, no second TLS session). The `TeletextSource`
seam stays (cheap, already shipped) so Ceefax could return if the platform gains
headroom.
- Pros: eliminates the entire contention class; zero ongoing risk to the two
  shipped TLS apps; smallest code.
- Cons: loses the live-carousel UK teletext source that EXP-005/006 built.

---

**Decision (proposed)**

1. **Gate the whole question behind Gate 1 first.** Before any coexistence work,
   confirm the integrated build actually connects + acquires + renders a page on
   the DUT (one clean `ceefax_connect_check.py` run once the external throttle
   clears — no server-hammering). If it can't even do that, the coexistence
   question is moot and the answer is **D (cut)**.

2. **If Gate 1 passes, prototype Option A** (extend `tlsYield`/`tlsResume` to
   `dataTask` + hold for the foreground session + a post-boot connect delay),
   then run TASK-374's coexistence soak as **Gate 2**. Decide the WebRadio-audio
   policy (A-subtlety 1) with @PM before building. **First cheaply test whether
   A's premise even holds** — `EXP-020` uses the existing `-DDISABLE_SPOTIFY`
   build as a static stand-in for the exclusion; if Ceefax can't connect+render
   even with the pool near-to-itself, skip A entirely and go to B/D.

3. **If Option A's prototype does not pass Gate 2**, do **not** fall back to
   C. Escalate the binary choice to human: **B** (reopen the framework-rebuild
   decision) or **D** (cut). Architect lean if forced: **D** — a second teletext
   source is not worth a framework rebuild's ongoing maintenance burden on this
   hardware.

---

**Revised decision (post-EXP-020, 2026-07-31) — Option A is eliminated; choose B or D.**

EXP-020 ran the premise-check step 2 called for and **Option A failed it**:
fully isolated (Spotify out, WebRadio stubbed), Ceefax connects then drops
~90 ms later at freeDma ≈ 24 K, because its *own* ~47 KB TLS allocation alone
leaves too little of the ~70 K pool to buffer the relay's opening burst. Pausing
other TLS consumers — all that Option A does — cannot raise that baseline, so A
**cannot** make Ceefax viable on this hardware. Steps 2 (prototype A) and its
Gate-2 soak are therefore **moot**.

The decision collapses to a straight **B vs D**, a human/@PM call:
- **B — reopen the framework rebuild** (`CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH`
  to shrink the per-connection TLS footprint). This is the *only* option with a
  path to viability, since the wall is Ceefax's own TLS size, not coexistence.
  It benefits all TLS on the device but carries the maintenance burden ADR-057
  weighed and the human declined on 2026-07-29.
- **D — cut Ceefax**, keep NOS Teletekst (works, no second TLS session). Remove
  `CeefaxTeletextSource`; the `TeletextSource` seam + `teletextCountry` can stay
  dormant so it can return if the platform ever gains DMA headroom (e.g. a
  future PSRAM board, or if B is done for other reasons).

**Architect recommendation: D.** A live UK-teletext *second* source is a nice-to-
have; it is not worth reopening a precompiled-framework rebuild and its ongoing
maintenance cost for a device whose primary job (Spotify + WebRadio) already
uses the DMA pool to its limit. Keep the crash/servicing fixes (they make the
NOS-only path no worse) and the seam; retire the Ceefax backend. If @PM/human
instead value the teletext source enough to fund **B**, that is a legitimate
call — but it is a platform investment, not a feature tweak.

*(Retained caveat: the exact drop mechanism — receive-burst alloc failure — is a
strong hypothesis, not instrumented. It could be confirmed by probing the
WebSockets receive/alloc path, but that does not change B-vs-D: the isolated
failure at ~24 K free is the deciding fact.)*

This ADR does **not** authorize shipping Ceefax as-is. It stays non-functional /
unproven until Gate 1 and Gate 2 are both green.

---

**Consequences**

- M-CEEFAX stays **open** (TASK-376 / TASK-374 REOPENED). The crash fix and
  servicing fix (commit 44b5fb0) are retained regardless of this decision —
  they are correct and make the *NOS-only* path no worse.
- If **A** is chosen: new coupling between `CeefaxTeletextSource` and both
  `spotifyTask` and `dataTask`; a documented WebRadio-audio-vs-Ceefax UX rule;
  the coexistence soak (TASK-374) becomes the acceptance gate.
- If **D** is chosen: `CeefaxTeletextSource` and its pump/DMA-gate/servicing
  machinery are removed; NOS remains; the `TeletextSource` interface and
  `teletextCountry` setting can stay dormant or be reverted per @PM.
- Either way, the process lesson stands: **no teletext-source close-out without
  a green `ceefax_connect_check.py`** (functional-test-before-accept).
