### ADR-008 — 2026-05-07 — Skin bake tool implementation choices

**Status**: accepted (2026-05-07, back-filled — implementation already shipped at Spotify-Diy-Thing@a9682be without a prior ADR; this records the decisions for future reference); **amended 2026-05-09** (decision #8 — see Amendment 1 below)

**Context**:

ADR-003 settled the *direction* (host-side bake → committed `gen/` artefacts) but explicitly deferred several implementation choices: tool language, build wiring, pixel format, atlas packing, output file layout, file location relative to the sketch directory. The M2 tier-1 implementation (TASK-012, m2-001) made all of those choices in one session without a separate ADR. This document captures them so the rationale survives future iteration.

**Decisions and rationale**:

1. **Tool language: Python with Pillow.**
   PlatformIO already runs Python for `extra_scripts`, so the host build environment is Python-ready. Pillow handles 24-bit BMPs natively. Rejected: Node + sharp (extra runtime), Go (heavyweight for this scope), C++ (no upside).

2. **Build wiring: standalone manual invocation.**
   Per user preference. Bake is run on demand (`python3 tools/bake_skin.py -i ... -o ...`), not as a PIO pre-build hook. Trade-off: a stale `gen/` is possible if the source skin changes and the user forgets to re-bake. Mitigation: `gen/` files are committed, so a stale generated tree is at worst an out-of-date build, not a breakage. If this becomes a foot-gun, promote to a PIO `extra_scripts` step in a successor ADR.

3. **Pixel format: RGB565 little-endian (uint16_t).**
   Matches TFT_eSPI's native fast path on ESP32. ADR-003 named RGB565 as the natural choice; this ADR locks little-endian byte order (native ESP32) for `pushImage`. Renderer must call `tft.setSwapBytes(true)` before pushing — that detail belongs in the renderer (M3) but is a constraint on this ADR.

4. **Atlas packing: per-source array, no merged atlas.**
   `SKIN_MAIN_BG`, `SKIN_CBUTTONS`, `SKIN_FONT` are emitted as separate C arrays, not packed into a single sheet. Reason: each source BMP already serves as its own atlas in Winamp's design; collapsing them into one buys ~zero pixel reduction (no dead space to remove) and complicates UV bookkeeping. ADR-003 allowed "one or more C arrays"; we land on three.

5. **Output file layout: `SpotifyDiyThing/gen/skin_assets.c` + `SpotifyDiyThing/gen/skin_layout.h`.**
   Inside the sketch directory so PlatformIO's `src_dir = SpotifyDiyThing` recursive scan picks them up automatically. No `platformio.ini` change required. Constants and `extern` declarations in the header; data definitions in the `.c`.

6. **Layout schema: `SkinUV { int16_t u, v, w, h }`, sprite UVs as `#define`'d compound literals, screen positions as `#define` x/y pairs.**
   Pre-processor constants compose into `(SkinUV){ x, y, w, h }` literals at the call site. Compile-time visibility, no runtime initialiser cost. Macro names are `CB_<NAME>_N` (normal) and `CB_<NAME>_P` (pressed).

7. **Tiered scope by milestone.**
   Tier 1 (M2 close-out): main background, 5 transport buttons (prev/play/pause/stop/next), raw font atlas. Tier 2 (M3 wiring needs): font glyph UV table, time digits (NUMBERS.BMP), play/pause indicator (PLAYPAUS.BMP), seek bar (POSBAR.BMP), title bar (TITLEBAR.BMP). Splitting is purely scope-control — the tool itself doesn't change shape across tiers.

8. **External dependency: ImageMagick CLI.**
   Pillow's `BI_RLE8` BMP decoder fails on Winamp's `TEXT.BMP` (raises `ValueError: not enough image data`). Tool falls back to `magick` for any BMP that Pillow can't decode. ImageMagick is a hard requirement for the bake step — document in deploy notes. Alternative considered: hand-rolled RLE8 decoder (~30 lines). Rejected as not worth the maintenance cost when a battle-tested decoder is one shell-out away.

9. **Source skin: committed verbatim into the repo.**
   `Spotify-Diy-Thing/skins/base-2.91.wsz` (Base-2.91 from `archive.org/details/winampskins_base-2.91`). Provenance recorded in commit message. Skin is fixed at compile time per ADR-003; treating the `.wsz` as a checked-in input rather than a build-time download removes a network dependency from the bake step.

10. **Generated files committed.**
    Per ADR-003. The bake tool is *idempotent given the same `.wsz`*; a re-bake should produce a byte-identical diff. Golden hash committed at `SpotifyDiyThing/gen/golden.sha256` (added 2026-05-07, tier-2 batch). Determinism check: `cd SpotifyDiyThing/gen && sha256sum -c golden.sha256` (T025).

11. **Glyph UV table — lookup, not computed offset.**
    `SKIN_GLYPH[128]` is a 128-entry `SkinUV` array indexed by ASCII. Lower-case folds to upper at bake time (smaller renderer, no runtime branch). Unmapped codes resolve to a known-blank cell at `(29*5, 0)`. Char map lives in `CHAR_MAP` in `tools/bake_skin.py` — a single source of truth that's easy to override per skin if a non-standard `text.bmp` ever shows up.

**Consequences**:
- *Easier*: zero build-system cognitive load (no pre-build hook), zero runtime parsing on device, IDE/intellisense works on the generated header without a build step.
- *Harder*: re-bake is a manual step the user has to remember if the skin source changes. Mitigated by the source skin being committed — accidental drift is unlikely.
- *Constrained*: changing pixel format (e.g. to a palette-8 packed atlas) becomes a breaking change to both the bake tool and the renderer. Future ADR-003 successor would have to handle both.
- *External dep*: ImageMagick must be on PATH. Document in M2 deploy notes; CI implication when CI is set up.

**Open**:
- Whether `gen/` should be in `.gitignore` once the bake step is proven (per ADR-003 it stays committed; revisit only if generated diffs become noisy).

### Amendment 1 — 2026-05-09 — Decision #8 superseded: manual BI_RLE8 decoder is primary

**Trigger**: User reported BALANCE.BMP composite rendering as a 2-pixel thin strip on a sea of cyan. Investigation (TASK-042) found:

1. Pillow 11.3.0's `BmpRleDecoder` (Python `PyDecoder`) **silently mis-decodes** RLE8 streams that use the delta opcode (`00 02 dx dy`). On base-2.91.wsz's `BALANCE.BMP` (419 delta opcodes across 433 rows, all `delta(9, 0)` to encode the transparent left border), Pillow ignores the dx and writes pixel data to the wrong x coordinates. ~56 % of pixels mismatch a spec-compliant decode (16,588 of 29,444).
2. ImageMagick **fails outright** on the same file: `unable to runlength decode image @ error/bmp.c/ReadBMPImage/1147`. The fallback path in decision #8 does not catch the silent PIL failure either, because PIL never raises — it returns garbage and execution continues.
3. ffmpeg decodes correctly. A 30-LOC hand-written `_decode_bmp_rle8` in `tools/bake_skin.py` is byte-identical to ffmpeg.

**Revised decision**: Manual BI_RLE8 decoder is now the **primary** path for any BMP with `compression=1` (8 bpp RLE). The PIL → ImageMagick fallback chain is retained for non-RLE BMPs and as a safety net for unrelated edge cases, but is no longer load-bearing for the Winamp-skin-RLE8 path.

**Consequences**:
- *Silent-corruption guard*: a library that produces output is more dangerous than one that errors. Manual decoder eliminates the trust-PIL-output failure mode for the file class we actually use. (Cross-ref: LL-017.)
- *Slightly more code in the bake tool*: ~30 LOC of opcode-walking. Worth the maintenance cost — the alternative was an undiagnosable corruption bug shipping in flash.
- *ImageMagick dependency*: still required by the file format set on disk today (TEXT.BMP path), but its weight has shifted from "essential" to "edge-case fallback". A future cleanup pass could remove the magick dep entirely if all currently-handled files round-trip through the manual decoder. Out of scope for this amendment.
- *Deterministic output*: still byte-identical bake-to-bake. `gen/golden.sha256` regenerated as part of TASK-042 close-out.

**Decision #8 status**: superseded by this amendment. Original wording retained above for traceability.
