### ADR-039 — [2026-06-04] — No shared base class between StockApp list and SettingsApp tab content

**Status**: accepted (2026-07-18 sweep — the restraint held: no shared base class was introduced; the list-row convention stands, and M-SETTINGS-STYLE's widget kit (2026-07-16) later formalised the settings side without contradicting this)

**Context**

`StockApp::repaintList()` uses a header + fixed-height-rows pattern:
a title line, a rule, then a loop of rows rendered at fixed column X positions,
with y-range math in `handleInput()` to convert tap Y to row index.

`SettingsApp` tab content (e.g. the `app` tab) will use a structurally
identical layout. The question: extract a `ListMenuApp` base class shared
by both, or treat the pattern as a documented convention only?

The two concrete row types differ substantially:

| | StockApp | SettingsApp |
|---|---|---|
| Columns | 3 (symbol / price / pct) | 2 (label / value) |
| Data source | Fetched float data | In-memory config state |
| Tap action | Drill to sub-view | Cycle value in-place |
| Mutability | Read-only rows | Interactive rows |

**Decision**

No shared base class. The list-row pattern is documented as a convention in
`settings.md §List-row content pattern`. The shared row height (26 px) is
named identically in both apps (`ST_LIST_ROW_H` / `SETTINGS_ROW_H`) as a
documented convention, not enforced via inheritance.

Rationale:

1. **Column mismatch.** A shared `drawRow(i)` would need to be pure virtual
   or templated on column layout — adding polymorphic machinery that saves
   nothing in either implementation.

2. **Interaction mismatch.** StockApp rows navigate; SettingsApp rows mutate
   state in-place. A shared base for both `onRowTap()` semantics requires
   enough abstraction that neither class is simpler as a result.

3. **Two instances don't justify extraction.** Rule of three: extract a
   base class when a third distinct consumer appears. At two instances,
   the documentation approach costs nothing and preserves flexibility.

4. **No vtable cost.** Both classes are singletons (`static g_stockApp`,
   `static g_settingsApp`). No heap allocation. Vtable pointer is 4 bytes
   per instance — not the concern here. The concern is unnecessary coupling
   between two otherwise independent app implementations.

**Trigger for revisiting**: a third `App` subclass that renders a header +
row list. At that point extract `ListMenuApp` with `virtual drawRow(int i)`
and `virtual void onRowTap(int i)`.

**Consequences**

- `SettingsApp` implements `drawSettingsRows()` as a private static helper
  (defined in `settings.md §List-row content pattern`). Not shared with
  `StockApp`.
- Row height 26 px is a soft convention. Future deviation requires no
  coordination — either app can change its row height independently.
- `settings.md` is the canonical reference for the row-pattern geometry
  and colour constants.

**Supersedes**: nothing.
