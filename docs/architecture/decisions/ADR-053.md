### ADR-053 — 2026-07-19 — WebRadio station-list fetch shall run before Spotify's TLS session ever forms, backed by a persistent SPIFFS cache

**Status**: parked (2026-07-19, human decision — none of the evaluated
options appealed enough to adopt now; not rejected outright, revisit if the
underlying fragmentation issue reoccurs or worsens). Root cause and
design-space survey stand as reference. A separate, complementary angle —
gating `spotifyTask::begin()` on `g_settings.playerMode` — is being explored
independently; see `M-SPOTIFY-BOOT-GATE.md` once filed.

**Context**:

DUT investigation (2026-07-19, `get heap` exact-byte measurement) root-caused
WebRadio's "no stations" symptom: the background station-list fetch fails
with `-101` — `WR_FETCH_MIN_TLS_BLOCK = 40*1024` guard
(`app/src/dataTaskStorage.cpp:769`, TASK-289) refusing the fetch because the
largest contiguous free heap block (`heap_caps_get_largest_free_block`) is
too small.

The moment Spotify's persistent TLS session first connects, it carves
~30-40 KB out of the middle of what was a pristine ~73 KB contiguous free
block, permanently splitting it into ~43 KB + ~30 KB pieces. Tearing the TLS
session back down (`spotifyTask::tlsYield()`, already called by WebRadio's
own fetch) frees the *bytes* — total free heap fully recovers (e.g.
78616 → 118740) — but the **split never re-coalesces**: the largest
contiguous block stays pinned at ~43 KB for the rest of the boot, regardless
of Spotify's connect/disconnect cycling. That leaves only ~2 KB of margin
above the guard, so any small concurrent allocation trips the skip. This is
a **permanent per-boot ceiling**, not a transient dip — confirmed by
measurement, not inferred. Full exploration, ruled-out causes, and the
design-space survey (including why the project's established
`tlsYield`/`tlsResume` pattern — already used here — doesn't fix this
specific failure mode) are in
`docs/architecture/designs/M-HEAP-FRAGMENTATION.md`.

Four other structural directions were evaluated and are not being taken:
lowering the 40 KB guard (undermines its crash-avoidance purpose, doesn't
touch the fragmentation); a heavier `spotifyTask` teardown around the fetch
(M-RECLAIM's Q3-b — unproven benefit against this specific failure mode,
real null-safety/latency cost, parked pending a cheap DUT spike); a
dedicated TLS-scratch arena hooking mbedTLS's global allocator (mechanically
the "real" version of a reservation, but the same global-blast-radius
objection ADR-047 Amendment 1 already raised against a smaller mbedTLS
change applies more severely here — parked as longer-horizon R&D); and
reserving unrelated address space to "push out" Spotify's later allocation
(unsound — a general-purpose allocator can't be steered that way).

**Decision**:

WebRadio's station list gets a persistent SPIFFS cache and a deterministic,
pristine-heap boot-time refresh, instead of relying solely on an on-demand
fetch that (per the measurement above) is racing a ceiling that's already
permanent by the time it runs in the common case:

1. **Cache-first UX.** Every successful station-list fetch is persisted to
   SPIFFS (same mechanism already used for `wifi_creds.json` /
   `spotify_diy_config.json` / `settings.json`). WebRadio app entry loads
   the cached list immediately, independent of heap state or network — the
   user always sees *a* list, not "no stations."
2. **Deterministic pristine-heap boot fetch.** Boot sequencing
   (`main.cpp`) is reordered so `dataTask::begin()` runs, and a bounded
   one-shot WebRadio station-list fetch executes and either completes or
   times out (~8 s), **before** `spotifyTask::begin()` is called. Before
   that call the heap has never been touched by Spotify's carve-and-split
   pattern, so this fetch — the one that matters most — gets the largest
   possible contiguous block deterministically rather than probabilistically.
3. **Rare mid-session re-fetch (country change / manual refresh) is
   unchanged.** It keeps today's `tlsYield`-protected path and the
   `WR_FETCH_MIN_TLS_BLOCK` guard as a best-effort fallback; an occasional
   skip there is a materially smaller problem than "no stations, ever,"
   since it's now a rare, explicit action rather than every WebRadio entry.

This is the direct extension of ADR-047 Amendment 1's own established
reasoning for `mb_arena`'s JIT-reservation ("the two big needs are
sequential and disjoint ... sequence so they never compete for the same
contiguous block") to this problem: sidestep the ceiling by never letting
Spotify's TLS connect happen before the one fetch that needs a clean heap,
rather than trying to win space back from a heap that's already permanently
split.

**Consequences**:

- *Easier*: WebRadio has a station list on essentially every boot, without
  new allocator machinery, without touching mbedTLS, without any
  `spotifyTask` lifecycle changes. Built entirely from infrastructure
  already trusted in this codebase (`dataTask`, `enqueueWebRadioStations`,
  SPIFFS persistence, `tlsYield`).
- *Harder*: boot sequencing gains one more moving part — `spotifyTask::begin()`
  is now conditionally delayed by up to the prefetch's timeout. Cold-boot
  time-to-first-`currently-playing` grows by a bounded amount on every boot,
  not just WebRadio-visiting ones.
- *Constrained*: an offline first-ever boot (no cache, no network) still
  shows no stations — unchanged from today, not a regression. The
  mid-session re-fetch guard's ~2 KB margin problem is unsolved, just made
  rare instead of routine; if DUT data later shows that residual path fails
  often enough to matter, the next levers are the parked options above (Q3-b
  spike first — cheap; the mbedTLS arena only if that's insufficient).
- *Risk*: the boot-order dependency must not regress the four other
  `dataTask` fetchers (Weather/Crypto/Stock/Teletext/PlaneRadar/Geocode),
  none of which depend on `spotifyTask` — expected inert, but Developer
  must verify against M-RECLAIM's Q2 `dataTask` sequencing notes before
  implementing (open question OQ2 in the design doc).

**Verification gate** (handed to VE, formalizing the design doc's Exit
criteria): DUT, ≥5 cold boots — station list `count > 0`, no `-101` skip,
sampled after Spotify's TLS has provably connected at least once. DUT,
≥3 cold boots — `lfbInt` captured immediately before `spotifyTask::begin()`
clears `WR_FETCH_MIN_TLS_BLOCK` with margin comparable to the guard's
original "clean fetch" calibration (`maxBlk ≥ 47 KB`,
`dataTaskStorage.cpp:764-768`). Full serialdbg suite green on
`cyd2usb_winamp`; boot latency delta measured and recorded. `./run/check`
5-gate green; `mem_manifest.yaml`'s build-time budget assertion unchanged.

**Supersedes**: none. Amends the operational understanding behind ADR-045 /
ADR-047 (both remain accepted; this ADR doesn't change WebRadio's playback
memory story, only its station-list-fetch reliability). Companion design:
`docs/architecture/designs/M-HEAP-FRAGMENTATION.md`.
