### ADR-017 — 2026-05-15 — M-LIST — Playlist panel data source + layout

**Status**: accepted (2026-05-15 — whiteboard session; human sign-off on orientation C, queue-first, row-0 = currently-playing).

---

## Context

M-LIST adds a playlist/queue strip to the unused screen real-estate below the Winamp chrome. Three Spotify Web API candidates were evaluated. An orientation decision (landscape C vs portrait B) was also required. See `docs/architecture/decisions/ADR-017-api-candidates.md` for the full candidate analysis.

Current panel geometry:

```
320 × 240 landscape (CYD2USB)
Winamp chrome: 275 × 116 px (WINDOW_W × WINDOW_H)
Centred today:  originX = (320-275)/2 = 22, originY = (240-116)/2 = 62
```

---

## Orientation Decision

**Decision: Option C — landscape, top-align chrome.**

| Option | Panel rotation | UI rotation | Playlist area | Change surface |
|---|---|---|---|---|
| **C (chosen)** | landscape — no change | none | **320 × 124 px** below chrome | `originY = 0` (one-line) |
| **B (rejected)** | portrait `setRotation(0/2)` (240×320) | 90° bake-time | 240 × 45 px | rotated atlas + layout-constant swap + touch coord swap + screenLog flip |

Option B yields 3× less playlist area in exchange for phone-like ergonomics. The complexity cost is disproportionate. C wins.

After change: `originX = 22` (horizontal centering preserved), `originY = 0`.
Playlist strip: `y ∈ [116, 240]`, `x ∈ [0, 320]`.

---

## API Data Source Decision

**Decision: `GET /me/player/queue` — Tier 1.**

Rationale: the queue reflects the **actual playback order** including manually-queued overrides that diverge from the source playlist. A playlist-items fetch would show source-playlist order and be stale whenever the user queues tracks out of sequence. Queue is what Winamp's own playlist window displayed.

Tiers:

| Tier | Endpoint | Status |
|---|---|---|
| 1 (current) | `GET /me/player/queue` | **chosen — implement now** |
| 2 (future) | `GET /me/player/currently-playing` context → `GET /playlists/{id}/items` | deferred — richer source, higher complexity |
| 3 (future) | `GET /me/playlists` browser | out of scope — no design yet |

See `ADR-017-api-candidates.md` for full analysis of all three.

## Design Decisions

### 1. Row layout

Row 0 = **currently-playing track** (matches chrome title strip, provides scroll context for the queue below).
Rows 1-6 = next-up queue items.

```
y=116 ┌────────────────────────────────┐
      │ [►] Currently Playing Track   │  row 0 — highlighted
y=132 ├────────────────────────────────┤
      │  Next Up Track 1              │  row 1
y=148 ├────────────────────────────────┤
      │  Next Up Track 2              │  row 2
      │  ...                          │
y=236 │  Next Up Track 6              │  row 6
y=240 └────────────────────────────────┘
```

### 2. Font

TFT_eSPI built-in **Font 2 (12 × 16 px)**. `124 px / 16 px = 7 rows` fills the strip exactly.  
Character width 12 px → `320 / 12 ≈ 26 chars` per line — sufficient for `"Artist - Title"` truncated with `…`.

Rejected: Font 1 (6×8) — legible but not in keeping with Winamp's larger text aesthetic.

### 3. Colours

- Row 0 (current track): white text `0xFFFF`, yellow-gold highlight bar `0x8400` (Winamp palette).
- Rows 1-6 (queue): `0xAD55` (Winamp dark grey-green, matches skin body colour).
- Strip background: black `0x0000`, painted once per queue update (no per-row fill).

### 4. Queue snapshot struct

New `QueueSnapshot`, separate from the hot-path `Snapshot` struct. Under the same spinlock.

```cpp
#define QUEUE_MAX 7

struct QueueEntry {
  char name[48];
  char artist[32];
  char uri[64];       // needed for tier-2 tap-to-play (TASK-021)
};

struct QueueSnapshot {
  QueueEntry items[QUEUE_MAX];   // [0] = currently_playing, [1..6] = queue[]
  uint8_t    count;              // valid items (may be < QUEUE_MAX if queue short)
  uint32_t   seqno;             // bumped on each write; display detects changes
};
```

Total size: 7 × (48+32+64) + 5 = **1 013 bytes** in RAM. Acceptable.

### 5. Queue poll cadence

- **On track change**: when `Snapshot::trackUri` changes between polls, schedule an immediate queue fetch after the currently-playing call completes.
- **60 s keepalive**: user may reorder queue without advancing the track; re-fetch every 60 s regardless.
- No additional FreeRTOS task — queue fetch runs inside `spotifyTask` (already owns the TLS client).

### 6. SpotifyArduino extension

New `getQueue(processQueueCallback cb)` method using the existing `makeGetRequest` path. Same pattern as LOCAL_PATCHES helpers. Endpoint: `GET /v1/me/player/queue`. Parse only `name`, `artists[0].name`, `uri` for the first 7 items using an ArduinoJson filter doc to bound heap.

### 7. OAuth scope

Current token scope: `user-read-playback-state user-modify-playback-state`.

`GET /me/player/queue` requires **`user-read-currently-playing`** in addition to `user-read-playback-state`. Need to verify at DUT time whether the current token implicitly satisfies this (Spotify sometimes accepts `user-read-playback-state` as a superset). If not: regenerate token via `get_refresh_token.py` with the additional scope added to its scope string, then `uploadfs`.

### 8. Redraw gating

Display reads `QueueSnapshot::seqno` each loop iteration. Redraws the strip only when seqno advances. Rate cap: 1 Hz max (queue data changes slowly). Dirty flag separate from chrome dirty flag.

### 9. Tier-2: tap-to-play (TASK-021, deferred)

Hit-test: `y > 116` → `row = (y - 116) / 16`. Bounds-check against `count`. On tap: `enqueue(ACT_PLAY_URI, row_index)` → task reads `QueueSnapshot::items[row_index].uri` → `playAdvanced`. Index-in-snapshot approach avoids a URI string in the `Request` struct and is race-free (task is the sole writer of the snapshot).

### 10. ScreenLog overlay

screenLog paints full-screen then chrome repaints on top. With `originY=0`, the chrome now occupies `y=0..116`. screenLog's top strip (older lines) will be partly obscured by chrome — acceptable, as it's a diagnostic overlay. Bottom strip `y≈116..240` overlaps the playlist strip; screenLog takes precedence when enabled (diagnostic mode vs production mode). No layout-constant changes required for screenLog.

## Sub-task mapping

| Task | Scope | Tier |
|---|---|---|
| **TASK-020a** | `originY = 0` layout shift (1 line) | 1 |
| **TASK-020b** | `QueueSnapshot` struct + spinlock accessors + `getQueue` helper + poll logic in `spotifyTask` | 1 |
| **TASK-020c** | `drawPlaylist()` renderer in `winampDisplay.h` + seqno-diff hook in main loop | 1 |
| **TASK-021** | Tap-on-row → `ACT_PLAY_URI` dispatch | 2 |
| **TASK-022** | Portrait rotation (option B) | cancelled — option C chosen |

## Verification gates (TASK-020 close)

- DUT visual: chrome flush with top edge; no black margin above chrome.
- DUT visual: playlist strip shows currently-playing in row 0 (yellow-gold highlight), queue rows below.
- Queue updates within ≤ 5 s of track advance.
- 60 s keepalive re-fetches queue (confirm via heartbeat/log).
- `screenLog` overlay still functional when `SCREEN_LOG` defined.
- Flash budget delta ≤ +3 % on `cyd2usb_winamp`.
- OAuth scope: queue endpoint returns 200 (not 403). If 403: add `user-read-currently-playing` to `get_refresh_token.py` scope, regenerate token, `uploadfs`.

---

## Out of scope (deferred)

- Option B portrait rotation (TASK-022 cancelled).
- Context-based playlist fetch (Tier 2 data source — see `ADR-017-api-candidates.md`).
- Playlist browser (`GET /me/playlists` — Tier 3).
- Tap-to-play (TASK-021, Tier 2).
- Album art thumbnails per row — no room at Font 2 row height.
- Scrolling within the strip (7 rows is the hard limit at this font size).

---

## Consequences

- *Easier*: users see up-next queue at a glance; the ~50 % black margin below the chrome is eliminated.
- *Harder*: `spotifyTask` gains a second API call type; `QueueSnapshot` is a new shared data structure under spinlock.
- *Constrained*: queue endpoint may require a token re-mint if `user-read-currently-playing` is not implicitly covered. Verify before declaring TASK-020 done.
- *Process*: `TASK-022` cancelled — no option-B work needed.
