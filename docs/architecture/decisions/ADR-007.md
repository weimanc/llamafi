### ADR-007 — 2026-05-04 — Force fresh TLS socket per Spotify request

**Status**: accepted (2026-05-04, human sign-off)

**Context**:

TASK-007's M1 capability spike (DUT run 2026-04-29, post time-001 fix and credential rotation) showed an asymmetric failure pattern in the vendored `SpotifyArduino` library:

- `GET /v1/me/player/currently-playing` succeeds repeatedly in the 5 s background poll loop.
- The very next non-GET on the same boot (`POST` for `nextTrack`, `PUT` for `pause` / `play` / `seek` / `setVolume` / `toggleShuffle` / `setRepeatMode`) fails on `client->println()` send with mbedTLS error `0x0050` (`MBEDTLS_ERR_NET_CONN_RESET`). The request never reaches Spotify.

Library inspection (`Spotify-Diy-Thing/lib/SpotifyArduino/src/SpotifyArduino.cpp`) identifies the cause:

- A single `WiFiClientSecure* client` is shared across every request type.
- Both `makeRequestWithBody` (POST/PUT) and `makeGetRequest` send `HTTP/1.0`. Per RFC 1945, the server closes the connection after the response unless `Connection: keep-alive` is negotiated, which the library never does.
- Between requests the library calls only `client->flush()` and then `client->connect(host, portNumber)`. It never calls `client->stop()`. When `connect()` is invoked on a `WiFiClientSecure` whose underlying socket has already been closed by the peer, the Arduino-ESP32 2.0.17 implementation can return success without re-establishing TLS, after which the next write triggers `0x0050` from the half-dead session.
- This is a known-bad pattern of `WiFiClientSecure` reuse in Arduino-ESP32 2.0.x. It is amplified here because GETs hit `api.spotify.com` and POSTs for token refresh hit `accounts.spotify.com` — the host can change between calls, but the same client object is reused.

TASK-009 enumerated three fixes:

1. Allocate a fresh `WiFiClientSecure` per request, free after.
2. Explicitly `stop()` the existing client before each `connect()`.
3. Migrate the affected endpoints to Arduino-ESP32's `HTTPClient`, which manages connection lifecycle internally.

The original recommendation was option 3. With the half-closed-socket pattern now confirmed, options 1 and 2 are equivalent in TLS lifecycle terms — both guarantee a fresh handshake — and option 2 is the smaller change.

What needs a decision: which fix to take, scoped to ADR-006's "preserve the baseline" stance.

**Decision**:

Take option 2: insert `client->stop()` before `client->connect(...)` in **both** `makeRequestWithBody` and `makeGetRequest` inside the vendored library. Drop `client->flush()` in the same spots — `stop()` supersedes it.

Rationale:

- Directly addresses the diagnosed root cause (stale half-closed socket reused across requests).
- Two-line change inside `lib/SpotifyArduino/src/SpotifyArduino.cpp`. No new abstractions, no allocator churn, no rewrite of streaming/parsing/JPEG-fetch paths. Aligns with ADR-006 ("change the UI; leave everything else").
- Reject option 1: identical TLS effect to option 2 but adds heap allocation per request. ESP32 heap is already tight (free heap ≈ 218 KB at idle per `i` row of the spike); per-request `WiFiClientSecure` allocations risk fragmentation under sustained polling. No upside over option 2.
- Reject option 3: `HTTPClient` migration rewrites how every request is built, sent, and parsed. The library's `currentlyPlaying`, `audio-features`, `audio-analysis`, and album-art-streaming code paths all share the bespoke parser. Refactoring all of them to use `HTTPClient` is weeks of work to fix a two-line bug. Keep on file as the fallback if option 2 fails verification.

The change lives in the **vendored** copy under `lib/SpotifyArduino/`, not the upstream PlatformIO dep cache. The fork is already vendored (TASK-007 added `getBearerToken()` there); this extends that fork. Mark the diff with a comment referencing this ADR so the reason survives a future re-vendor.

`SPOTIFY_DEBUG` stays disabled (LL-003), so the fix must not depend on debug-only logging to be observable. Verification is via the spike harness's per-key results, not log messages.

**Consequences**:

- *Easier*: every non-GET endpoint becomes available — unblocks TASK-002 (touch seek), TASK-003 (touch play/pause + volume), and the M5 milestone in general. `pause`/`play`/`next`/`previous`/`seek`/`setVolume`/`shuffle`/`repeat` go from `FAIL` to `OK` on the spike harness with no upstream API changes.
- *Harder*: every request now pays a full TLS handshake (~hundreds of ms on ESP32). The 5 s poll loop already absorbs this for GETs, and user-driven controls are sparse and tolerate latency, so the cost is acceptable. If poll cadence is later tightened or batched controls are introduced, revisit.
- *Constrained*: keep-alive across requests is renounced for this library. If a future endpoint demands it (e.g. server-sent events, large multi-request flows), that is a new ADR — likely option 3 at that point.
- *Open*: option 3 (`HTTPClient` migration) remains the documented fallback. If verification (TASK-009 follow-up DUT run) shows option 2 does not close all the failing rows, escalate to option 3 without further architecture review — this ADR pre-authorises the fallback.
- *Risk*: a pure-`stop()` fix assumes the failure mode is socket-state, not e.g. a TLS-context bug that survives `stop()`. Mitigation: VE re-runs the full key matrix from TASK-007 (rows `>` `<` ` ` `p` `P` `s` `S` `+` `-` `v` `h` `H` `r` `R` `o`); all must return `[OK]`. Partial pass triggers option-3 escalation.

**Verification gate** (handed to VE):

After the change is in place and the device is reflashed, the existing spike harness (env `cyd2usb_spike`) must produce `[OK]` on every PUT/POST row from the TASK-007 matrix. The `f` and `a` rows remain `HTTP 403` (TASK-010 territory, not addressed here). The `i` row remains `OK`. GET via the background poll loop must continue to succeed — the `stop()` insertion in `makeGetRequest` must not regress it.
