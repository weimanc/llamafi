### ADR-001 — 2026-04-27 — Layered architecture with swappable platform leaves

**Status**: accepted

**Context**:
The system is a Spotify Connect *controller* (no audio path) running on an embedded board with an LCD and touchscreen, presenting a Winamp 2 classic skin UI. Two execution targets are required from day one:

1. **DUT**: target hardware — MCU + LCD + touch + WiFi (specifics TBD, see Open Questions).
2. **PC mirror**: a host-side build of the same UI, used to develop and iterate the interface without a device in the loop.

Forces:
- UI iteration on the DUT is slow (flash cycles, no debugger ergonomics, physical handling).
- Spotify API responses, OAuth, and TLS are awkward to develop against on bare MCU.
- The Winamp skin is fixed (classic, single skin), so asset processing can be moved to build time.
- VU metering cannot be sourced from the Spotify Web API (no audio stream is available to a controller-only device); see ADR-002 (forthcoming).
- Touch input timing, render pacing, and player-position interpolation must feel identical across DUT and PC to make the mirror a faithful development surface.

What needs a decision: how to structure the codebase so that core behavior (state, polling, intent handling, VU synthesis, render logic) is written once and runs on both targets, while hardware- and host-specific code is isolated and replaceable.

**Decision**:
Adopt a layered architecture in which a single, portable **core** owns all behavior, and **platform leaves** provide target-specific implementations of a small, fixed set of capabilities.

Layers:

1. **Core (portable)**
   - `PlayerState` — single in-memory model: track metadata, `position_ms`, `is_playing`, shuffle/repeat, volume, VU ring buffer, connection status.
   - `Poller` — periodic Spotify API reads → `PlayerState` updates.
   - `Interpolator` — advances `position_ms` between polls against a monotonic clock; resyncs on poll.
   - `VuSynth` — drives the VU ring buffer from cached track analysis (mechanism per ADR-002).
   - `IntentHandler` — translates UI intents (PlayPause, Next, Prev, SeekTo, VolumeSet, ToggleShuffle, ToggleRepeat) into Spotify commands; applies optimistic local updates, reconciles on next poll.
   - `Renderer` — pure function over `PlayerState` and the baked skin layout, emitting draw commands against an abstract surface.

2. **Platform leaves (per target)**
   - `Surface` — pixel blit / rect fill / sprite blit primitives. DUT: LCD driver. PC: SDL2 (or equivalent) window at native skin resolution.
   - `Input` — emits `Intent` values. DUT: touch controller poll/ISR. PC: mouse mapped to touch coordinates.
   - `SpotifyTransport` — HTTPS request/response. DUT: on-device TLS + OAuth refresh. PC: same, or a mock transport that replays canned JSON fixtures.
   - `Clock` — monotonic milliseconds. DUT: MCU tick. PC: host wall clock.
   - `Storage` — persistent key/value for OAuth refresh token and `audio-analysis` cache. DUT: flash partition. PC: local file.

3. **Build targets**: `make pc` and `make dut` (or PlatformIO/IDF equivalents) compile the same `core/` against different `platform/` implementations.

Dependency direction is strict: `core/` must not include any `platform/` header except the abstract interfaces it depends on. Platform leaves may not call into other leaves.

**Consequences**:
- *Easier*: UI development without a DUT; deterministic replay of Spotify scenarios via mock transport; identical behavior validation across PC and DUT; later substitution of a different board, LCD, or touch IC affects only the relevant leaf.
- *Harder*: Every new capability that touches hardware must first be expressed as a portable interface, then implemented twice (DUT + PC). For trivial features this is overhead.
- *Constrained*: `core/` cannot use platform-specific types (e.g. RTOS handles, vendor SDK structs) directly. Time, randomness, and I/O all flow through abstract interfaces.
- *Open*: The core/leaf boundary is enforceable by build configuration but not by language alone (in C/C++); discipline and review carry the rest.
