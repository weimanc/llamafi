### ADR-026 — 2026-05-25 — App lifecycle interface (M-MULTIAPP)

**Status**: proposed

**Context**:

M-MULTIAPP step 2 shipped a taskbar strip and app-switching stub but did not implement the `App` lifecycle interface that `app-lifecycle.md` specified. Ad-hoc dispatch (`switch (id) { case Spotify: ... case Clock: ... }` in `main.cpp`) and taskbar hit-testing inside `WinampDisplay::checkForInput()` produced four active defects — taskbar slots wiped on every playlist draw (B1), Winamp transport sprites painting over the Clock canvas (B2), PLEDIT blank after returning to Spotify (B3), and intermittent PLEDIT text overflow (B4). All share the same root: no interface boundary between an app and the shell.

The layering violation is specific: `WinampDisplay` (a display backend) includes `appShell.h`, references `currentAppId`, and calls `switchApp()`. A display backend should have no knowledge of which app is active or how to switch apps.

Three structural options:

**Option A — Patch ad-hoc**: Fix each bug in place. `drawPlaylist()` gutter changed to `TASKBAR_X`. `pendingReleaseAt` moved inside the Spotify guard. `invalidatePlaylist()` called from `switchApp(Spotify)`. No interface introduced.
Risk: every new app requires another case in each dispatch switch; the same class of bug recurs on the next app addition. `WinampDisplay` retains its `appShell.h` dependency.

**Option B — App ABC + shell refactor**: Introduce a pure-virtual `App` interface (`init / resume / suspend / tick / handleInput`). Each app is a concrete class. `appHandleInput()` owns the taskbar check. `WinampDisplay` loses its shell dependency entirely. Bugs B1–B4 are fixed as consequences of correct lifecycle, not as targeted patches.

**Option C — FreeRTOS task per app**: Each app runs as a suspended task; `switchApp()` resumes one and suspends the rest. Full concurrent state isolation.
Overkill for apps that have no concurrent I/O (Clock, Matrix, Life). Significant RAM overhead (each task needs a stack). Rejected.

---

**Decision**

**Option B.**

The `App` interface is the design that `app-lifecycle.md` already specified. The step 2 implementation shortcut that interface and introduced structural debt that is now costing real defects. Adding a third or fourth app on top of ad-hoc dispatch (Option A) will repeat this.

Option B fixes all four bugs as natural consequences and makes every future app a self-contained unit. The cost is a one-time refactor of `WinampDisplay` and `main.cpp`; the scope is bounded (no protocol changes, no new FreeRTOS tasks, no RAM increase).

**`App` interface** (declared in `appShell.h`):

```cpp
struct App {
    virtual void init()                    = 0;   // first launch
    virtual void resume()                  = 0;   // canvas cleared; repaint
    virtual void suspend()                 = 0;   // save transient state
    virtual void tick()                    = 0;   // called every loop()
    virtual bool handleInput(int x, int y) = 0;   // app-canvas coords only
    virtual ~App() = default;
};
```

**Layering rules** (binding after this ADR):
- `WinampDisplay` has no `appShell.h` dependency.
- Taskbar hit-testing (`p.x >= TASKBAR_X`) lives exclusively in `appHandleInput()` in `main.cpp`. No app implements taskbar logic.
- `renderTaskbar()` is called by the shell only (`switchApp()`, `setup()`). Not by any `App` implementation.
- `App::resume()` is responsible for painting the full app canvas. The shell clears first, but no app assumes any particular pixel state on entry.

**SpotifyApp specifics**: `resume()` calls `repaintChrome()` then `invalidatePlaylist()` (new method on `WinampDisplay`). This is the correct fix for B3 and B4 by ensuring PLEDIT is repainted from a clean seqno. `suspend()` is a no-op for now; TASK-088 adds explicit field copies when other apps require them.

**`handleInput` signature** (resolved):

```cpp
enum class TouchPhase : uint8_t { Press, Move, Release };
virtual bool handleInput(TouchPhase phase, int x, int y) = 0;
```

Shell owns `ts.touched()` reads and drives the gesture state machine (`Press` / `Move` / `Release`). Apps do not poll the touch hardware. `checkForInput()` override on `SpotifyDisplay` is retired; serial debug callers call `winampDisplay.handleWinampInput()` directly.

---

**Alternatives considered:**

**Option A (targeted patches)**: Fixes the symptoms without the structural fix. Acceptable as an emergency if the device is needed urgently; not acceptable as a long-term position. The refactor becomes harder after each new app added under the old pattern.

**Option C (per-task apps)**: Correct isolation model but excessive overhead for predominantly-stateless display apps. No app other than `spotifyTask` has blocking I/O that would benefit from task concurrency.

---

**Consequences:**

What becomes easier:
- Each new app (Matrix, GoL, Weather, Crypto) is a self-contained class; no case added to shell dispatch switches.
- `WinampDisplay` can be developed and tested without knowing about the app shell.
- B1–B4 are structurally impossible under the new layering rules.
- TASK-088 (`saveAppState`/`restoreAppState`) slots into `SpotifyApp::suspend()` / `resume()` naturally.

What becomes harder:
- Serial debug injection (`cmdTap`/`cmdDrag` in `main.cpp`) must be updated to call `winampDisplay.handleWinampInput()` directly instead of going through `spotifyDisplay->checkForInput()`. Low effort; one-time change.
- Touch read ownership (single read in shell vs. per-app polling) requires a small API decision before implementation.
