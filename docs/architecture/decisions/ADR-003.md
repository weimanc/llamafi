### ADR-003 — 2026-04-27 — Skin assets baked at build time; no runtime parser

**Status**: accepted (2026-04-28, under ADR-006)

**Context**:
The system targets a single skin (Winamp 2 classic). Original Winamp skins ship as `.wsz` archives (renamed `.zip`) containing BMP sprite sheets and plain-text layout files (`region.txt`, `pledit.txt`, `viscolor.txt`, etc.) defining hit regions, colors, and slicing.

Two ways to consume skin data on the device were considered:

- **(a) Runtime parser** — ship the raw `.wsz` (or its unpacked contents) onto the device, parse layout files at boot, decode BMPs into framebuffer-friendly format on the MCU.
- **(b) Build-time bake** — run a host-side tool that parses the skin once, slices sprites, converts to the LCD's pixel format, and emits C arrays plus a static layout/hit-region table compiled into the firmware.

Forces:
- Single skin is in scope (per project pitch); runtime swap is explicitly out of scope.
- MCU flash and RAM are constrained; BMP decoders, ZIP readers, and text parsers add code size and bug surface.
- The skin is fixed at compile time, so any work that can shift to the host saves device resources without any loss of capability.
- The LCD is the CYD's 320×240 ILI9341 (per baseline). RGB565 is the natural pixel format to match TFT_eSPI's native fast path; palette8 is possible but not currently motivated. Final choice is an Open Question in `architecture.md` but does not block this ADR.

What needs a decision: where skin parsing and pixel conversion happen.

**Decision**:
Adopt option **(b)**. Skin assets are processed by a host-side build-time tool. The tool produces:

- `gen/skin_assets.c` — sprite atlas as one or more C arrays in the chosen pixel format, plus per-sprite UV offsets.
- `gen/skin_layout.h` — static tables for button rectangles, the VU rect, text rects, marquee region, slider tracks, and any 9-slice metadata required by the renderer.

Rules:

- The bake tool runs on the host as a PlatformIO pre-build step (extra_scripts) or as a standalone `make` target invoked before `pio run`. Implementation choice deferred.
- Generated files (`gen/skin_assets.c`, `gen/skin_layout.h`) are committed alongside source for IDE/intellisense convenience; the bake tool re-emits them on skin change.
- No `.wsz`, `.zip`, `.bmp`, or skin layout text is shipped to the device. The MCU has no parser for any of these formats.
- The pixel format is a single project-wide setting (`SKIN_PIXEL_FORMAT`), consumed by the bake tool and the renderer.

**Consequences**:
- *Easier*: Smaller firmware (no decoders); faster boot (no parse step); layout changes are caught at build time, not at boot on a device.
- *Harder*: Host build dependency on a new tool. Anyone modifying the skin must rebuild rather than hot-swap on device. (Accepted: out of scope.)
- *Constrained*: Runtime skin swap and user-supplied skins are precluded by this design. A future ADR would have to supersede this one to enable them.
- *Open*: Final pixel format and atlas packing strategy depend on LCD selection and flash budget (tracked in `architecture.md` Open Questions).
