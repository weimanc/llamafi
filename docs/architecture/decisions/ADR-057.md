### ADR-057 — [2026-07-30] — M-CEEFAX: NMS Ceefax as a second TeletextApp source

**Status**: accepted — 2026-07-30

**Context**

A protocol reverse-engineering spike (EXP-005) and a DUT resource-contention
spike (EXP-006) validated adding NMS Ceefax (`nmsceefax.co.uk`) as a second
live teletext source alongside the shipped NOS Teletekst app (M-TELETEXT /
ADR-044). Unlike NOS's page-addressed HTTP GET, Ceefax is a persistent
WebSocket relay of a real off-air-style UK teletext broadcast carousel:

- Endpoint: `wss://internal.nathanmediaservices.co.uk/websockets/ceefax`
- Outbound frames are comma-joined values (`Array.prototype.toString()`, not
  JSON — sending real JSON gets the connection closed); inbound frames are
  JSON arrays (`header`/`row`/`pageExists`/etc.)
- Row/header content bytes (after `& 0x7F` parity masking) are byte-identical
  to NOS's decoded control-code scheme — the entire render pipeline
  (`teletextApp.h::_drawGrid()`, mosaic tables, colour palette) applies
  **unmodified**; only fetch/transport/navigation differ
- Live carousel model: no single "page ready" instant. A requested page's
  content arrives once the broadcast carousel cycles to it (observed 5–20 s+),
  then continues updating live for as long as the slot stays acquired
- Page addressing maps cleanly onto the existing 100–899 convention:
  `magazine = NNN // 100`, `page_byte = int(f"{NNN % 100:02d}", 16)` (BCD-style)
- Fastext link targets are broadcast separately as packet 27 (X/27/0, FLOF) —
  six Hamming-8/4-coded link fields, decoded and DUT-data-verified on host
  (`ceefax_client.py::decode_flof_packet()`)

A DUT resource-contention spike (`app/src/ceefaxWsSpike.h`, branch
`rnd/ceefax`, since merged/removed) found **real, DUT-confirmed contention**:
a persistent second TLS/WebSocket client held open concurrently with
`dataTask`'s periodic fetches degraded Spotify's TLS reliability by
~4× (hard failures) / ~11× (TLS-error lines) vs. an unmodified `run/stress`
baseline over an identical fetch plan — root-caused to a DMA-capable-heap
capacity ceiling (not a scheduling race; reproduces even with Spotify
entirely disabled), and once, under low memory, a reconnect attempt crashed
the device outright (Guru Meditation Error). A DMA-gated reconnect mitigation
(don't pump the WebSocket client's reconnect logic below a measured free-DMA
threshold) was implemented and DUT-verified to eliminate both the crash and
the failed-attempt churn.

The deeper fix (shrink mbedTLS's per-connection buffer footprint —
`CONFIG_MBEDTLS_SSL_VARIABLE_BUFFER_LENGTH`, the direct analog of
`PATCH-MEMBUDGET-4`'s I2S DMA-ring reduction) was investigated and found to
require rebuilding this project's precompiled `framework = arduino` binary
from source — real, bounded work, but disproportionate to this feature.
**Human decision, locked 2026-07-29: accept best-effort connectivity, do not
pursue the framework rebuild.**

Full design-space enumeration and leans: `M-CEEFAX.md` (DS-1 through DS-7).

**Decision**

1. **Not a new app — a second `TeletextSource` behind the existing
   `TeletextApp`.** `teletextCountry` (reserved in `AppSettings` since
   ADR-044/M-TELETEXT) gains a Ceefax value. Rationale (DS-6): taskbar slots
   are the scarce resource (already flagged in M-TELETEXT's own context —
   the shell was scrolling at 9–10 apps before Teletext became the 10th);
   the render/UI layer is proven 100% shareable (host prototype, zero
   changes needed to `build_cell_grid`/strip/keypad/row-tap-link scanning);
   and `teletextCountry` was reserved in the original design specifically
   for this. `TeletextApp` gains a small `TeletextSource` interface
   (`ready()`, `grid()`, `navigate(page)`, `onResume()`, `onSuspend()`) with
   two implementations: the existing NOS poll backend (`onResume()`/
   `onSuspend()` no-ops) and a new Ceefax backend (`onResume()` starts the
   pump task, `onSuspend()` tears it down) — an ordinary strategy-pattern
   seam, not a forced abstraction.

2. **Transport: dedicated pump task, not `dataTask`.** Mirrors
   `WebRadioApp`'s `wrEnsurePumpTask()`/`wrTeardownPumpTask()` pattern
   (`xTaskCreatePinnedToCore`, ack-based teardown) — `dataTask`'s
   stack-allocate-per-request model doesn't fit a connection that must stay
   open across a 5–20 s+ carousel wait and then keep receiving live updates.
   Started in the Ceefax `TeletextSource`'s `onResume()`, torn down in
   `onSuspend()` — the connection is live only while Ceefax is the active
   teletext source, not for the whole session (EXP-006's spike tested the
   deliberately-worse always-on case; production scope is narrower).

3. **DMA-gated reconnect is a hard requirement, not an optimization.**
   Port `ceefaxWsSpike.h`'s free-DMA-threshold gate (don't pump
   `WebSocketsClient::loop()`'s reconnect path below the measured safe
   threshold) into the production pump task verbatim — this is what makes
   the feature safe to ship at all (DUT-verified: eliminates the crash and
   the cross-app TLS degradation). **Accepted limitation, not a bug to
   chase further**: the connection may not always establish in a given
   session on this no-PSRAM board. `isConnecting()` (below) is the
   user-visible signal for "still trying."

4. **Fastext bar: real labels/colours, targets only when packet-27 supplies
   them.** Row 24's colour-coded segments parse with the same logic as
   NOS's `ftl=`-driven labels (host-verified, byte-identical control-code
   scheme). Packet 27 (FLOF) decode — Hamming 8/4, not the 24/18 triplet
   scheme X/26 and X/28 enhancement packets use — is host-validated
   (`decode_flof_packet()`) and should be ported to firmware as part of this
   milestone, not deferred; a button's target is `None`/inert only when a
   given page genuinely carries no FLOF data for that colour, matching real
   teletext decoder behaviour, not an implementation gap.

5. **Navigation without `pn=`/`ftl=` metadata**: prev/next = page number ± 1
   (no "skip missing pages" smartness NOS's metadata provides); subpage
   ▲/▼ stay permanently dimmed (no subcode navigation surfaced by this
   client); row-tap inline hyperlinks port unmodified (DS-3, proven on host).

6. **TLS root CA: alias, no new certificate.** `CEEFAX_ROOT_CA` defined as
   `OPEN_METEO_ROOT_CA` in `dataTaskCerts.h` — the served chain
   (`leaf ← Let's Encrypt YE2 ← ISRG Root YE ← (cross-signed by) ISRG Root
   X1`) verifies against the already-pinned X1 root (confirmed via
   `openssl verify`, same shape as the existing `NOMINATIM_ROOT_CA` alias).
   Same cross-sign-dependency caveat as that alias: if the relay ever drops
   the cross-signed intermediate, this needs a two-root bundle
   (`COINGECKO_ROOT_CA` pattern), not a replacement cert.

7. **Taskbar status flags — deliberately diverge from the NOS mapping.**
   `isConnecting()` fires on **every** navigation (not just the first-ever
   load like NOS): the 3–20 s+ acquisition wait is long and visible on every
   page change, and the taskbar amber indicator is what stays useful while
   the app isn't foregrounded. `hasError()` requires a sustained-failure
   latch, not a raw reconnect pass-through — ordinary 3 s-backoff reconnects
   are not errors (matches ADR-046 Amendment 2's sticky-latch precedent, and
   the still-open Spotify `isHealthy()` gap noted in `tasks.md` is the same
   class of bug to avoid repeating). Threshold: **N ≥ 2 consecutive failed
   reconnect attempts** — set from a full 6-hour host-side observation
   (EXP-006 DS-7 follow-up: 1 outage total, the initial 7.5 s acquisition,
   zero drops for the remaining ~5h59m52s). Caveat carried forward: this
   says drops are rare, not how the relay recovers from a real one, since
   none occurred to observe — revisit the threshold if production telemetry
   ever shows it flapping or missing genuine outages.

8. **Settings**: `teletextCountry` (already reserved, `uint8_t`, values
   0=NOS/NL, 1=Ceefax/UK) becomes interactive in the Teletext settings
   sub-section — was greyed out pending exactly this milestone.

**Consequences**

- `teletextApp.h` gains the `TeletextSource` interface + Ceefax
  implementation; existing NOS behaviour must be provably unchanged
  (`run/check` + existing teletext DUT tests as the regression gate).
- New pump task, mirroring `webRadioApp.h`'s pattern — stack size, ack
  semaphore, teardown timeout all need sizing/tuning on DUT, not assumed
  from the WebRadio precedent's numbers.
- `dataTaskCerts.h` gains `CEEFAX_ROOT_CA` (`= OPEN_METEO_ROOT_CA` alias).
- New WebSocket library dependency (`links2004/WebSockets`, `2.7.3` proven
  in the spike) — flash footprint impact to be measured at DUT-gate time.
- `AppSettings`'s `teletextCountry` field's Settings UI row goes from
  greyed-out label to a live selector — `run/check`'s settings-wiring gate
  (ADR-050) applies.
- **DMA-gate threshold and the accept-best-effort decision are shipped
  product behaviour, not implementation debt** — release notes / user-facing
  copy (if any) should not promise reliable Ceefax connectivity on first
  attempt; "still connecting" (amber) is expected, ordinary behaviour, not
  a bug report trigger.
- `docs/architecture/architecture.md` update triggers (post-acceptance):
  (1) add `internal.nathanmediaservices.co.uk` / `CEEFAX_ROOT_CA` to the TLS
  endpoint inventory; (2) note the pump-task pattern as the precedent for any
  future persistent-connection app (alongside WebRadio); (3) close the
  "multi-country teletext" open question from ADR-044 with a reference here.

### Amendment 2026-07-30 — item 3's "eliminates the TLS degradation" claim is wrong; only the crash half holds

TASK-374's DUT coexistence gate (M-CEEFAX close-out) falsifies half of item
3's parenthetical claim ("DUT-verified: eliminates the crash **and** the
cross-app TLS degradation") and of the Context paragraph's matching wording
("eliminate both the crash and the failed-attempt churn"). Corrected reading:

- **Crash half — holds.** The DMA gate (fragmentation-aware: free-bytes AND
  `largest_free_block`) plus `kMaxConsecutiveAttempts = 5` produced a
  crash-free 10-min coexistence soak. This part of item 3 stands.
- **Degradation half — does NOT hold.** With Ceefax parked in the foreground
  (pump task attempting reconnects), Spotify's independent poller went
  **0/8 → 0/10 → 0/11 successful across three soaks**, each with 7–10 genuine
  `SSL -32512` "memory allocation failed" TLS-layer failures — vs. a 0-TLS-
  line baseline with Ceefax off. The cross-app degradation is real, repeated,
  and DUT-confirmed on the shipped build (`ad94f60`), not eliminated.

Root-cause characterization (PROP-008 follow-ups): each reconnect attempt
leaks **~47 KB of DMA-capable heap that never returns for the rest of the
session** — instrumented as +4 heap blocks that never free and a
`largest_free_block` frozen at exactly 10228 B for 4.5 min. `heap_caps_dump`
matched the leaked blocks to an mbedTLS `in_buf`/`out_buf` pair (two identical
16732 B blocks ≈ `CONFIG_MBEDTLS_SSL_MAX_CONTENT_LEN=16384` + record
overhead), with `WebSocketsClient::clientDisconnect()`'s conditional-`stop()`
asymmetry as the leading (unconfirmed) suspect. This is a genuine leak, not
transient contention.

**Open decision.** PROP-008 hands PM/Architect three options (A: accept as
documented limitation; B: further mitigate — attempt-cap/interval/threshold
or an explicit `stop()`; C: R&D isolation of the vendored WebSocket teardown).
A review of PROP-008 (2026-07-30) flagged that **Option A's central premise —
that the degradation is "bounded strictly to the window a user is actively on
Ceefax" — was asserted but never measured, and the orphaned-buffer leak theory
predicts the opposite. A DMA-recovery test (measure global free-DMA after
`switchApp` away from Teletext, across repeated visits — 2026-07-30, DUT)
**settled it: the premise is false.** Free-DMA never returns to its 76684
baseline after the first Ceefax visit; it drops permanently to 34052 (a
**~42.6 KB session-lifetime loss**, with `lfbDma` losing exactly 16384 B = one
`CONFIG_MBEDTLS_SSL_MAX_CONTENT_LEN` mbedTLS content buffer) and stays there
across teardown and repeated visits. It does **not** compound unboundedly per
visit (the DMA gate self-limits further attempts once heap is depressed), but
it is a one-time device-wide regression lasting until reboot — not
window-bounded. Option A must therefore be re-described against the true cost,
and Option B/C's explicit-`stop()`/cleanup fix now recovers a concrete ~42.6 KB
rather than a marginal amount. See PROP-008's "DMA-recovery test" section.

**Not a novel bug — a known, still-open upstream gap.** Checked whether this
is a documented issue rather than something to root-cause from scratch: it
is. `WiFiClientSecure`'s own historical CA/cert-leak-on-failed-handshake bug
(espressif/arduino-esp32 #5781/#3808/#5480) was fixed by PR #5945
(merged 2021-12-14) and is already present in our pinned Arduino-ESP32
2.0.17 — confirmed by reading the vendored source, that specific leak is
not what we're hitting. The actual match is one layer up:
`Links2004/arduinoWebSockets` (our pinned WebSockets, v2.7.3) has a
long-standing, still-open class of issues where `WStype_DISCONNECTED` never
fires when the remote side goes unresponsive mid-session (#297, #373, #84,
#864 open, #706 open, #290, #271) — #864 describes almost exactly this
project's scenario. Since that disconnect-detection gap is what's supposed
to trigger the cleanup that frees the mbedTLS buffers, a connection the
library never recognizes as disconnected plausibly never gets that cleanup
either. This causal link (detection gap → buffer leak) is this project's
own synthesis, not something an upstream maintainer has confirmed — no
existing issue connects the two explicitly. See PROP-008's fifth follow-up
for sources and the reframed Option C (check for a newer upstream fix /
file a new issue, rather than an from-scratch isolation spike).

**Correction (EXP-019, 2026-07-30) — walk back "the premise is false /
permanent ~42.6 KB session leak."** An Option-C on-device isolation
(instrumenting the *vendored* `app/lib/WiFiClientSecure/ssl_client.cpp`)
found the deterministic-permanent-leak model does **not** hold: `stop_ssl_socket()`
(the buffer free) **is** called constantly (cleanup not skipped), TLS
handshakes succeed then churn, and `freeDma` **oscillates and recovers**
(variable end state) rather than sticking. The earlier "stuck at 34052
forever" was one **metastable** regime (gate latched closed), not a hard
unfreed allocation. Confounded by observer effect + network variance, so the
result is **inconclusive**, not a clean reversal — but enough that: (1) the
`#864` "cleanup-skipped" causal link above is a **candidate hypothesis, not
confirmed** (cleanup was observed running); (2) the ~42.6 KB figure is *one
metastable session outcome*, not a fixed cost; (3) a `stop()`-adding fix is
**not** indicated (stop already runs). Robust residue: transient `freeDma`
dips (6152 observed) are the real crash risk, which the DMA gate bounds.
Direction escalated to human. Detail: `docs/rnd/reports/EXP-019-ceefax-tls-leak-isolation.md`.

**Resolution (EXP-019 lead b, 2026-07-31) — there is no leak; item 3's
degradation is transient and window-bounded after all.** Out-of-band
measurement (inline `ssl_setup`/`stop_ssl_socket` counters, no hot-path prints)
showed `setup − stop` **persistently ≤ 0** (every SSL context freed) and
`freeDma` at rest **recovering to ≥ baseline** across visits. The "permanent
~42.6 KB / not window-bounded" claim above was a **metastable artifact** and is
**retired**. Net corrected picture for item 3: the DMA gate eliminates neither
the transient cross-app degradation nor an intermittent low-DMA crash, but the
degradation is **real, transient, and bounded to the active-Ceefax window**
(Ceefax connect churn starves DMA → Spotify's un-gated TLS poll takes a
self-recovering `SSL -32512`) — i.e. Option A's original "bounded to the window"
framing is essentially correct, and the earlier "premise is false" amendment is
itself withdrawn. The only non-cosmetic residual is the intermittent
crash-under-low-DMA class the gate bounds but doesn't fully close. Full detail:
EXP-019 lead(b).

### Acceptance decision 2026-07-31 — Option A accepted; M-CEEFAX closed

Human-approved. After PROP-008's full A/B/C exploration (lead a: no upstream
WebSockets fix exists; lead b: no leak; lead c/isolation: mechanism understood),
**Option A is accepted** and M-CEEFAX is closed. The accepted, documented
limitation is:

> While a user is actively on the Ceefax teletext source, its DMA-gated
> reconnect attempts transiently contend for DMA-capable heap. During that
> window Spotify's independent poll may intermittently fail with a
> self-recovering `SSL -32512` ("memory allocation failed"). This is bounded to
> the active-Ceefax window (memory recovers on leaving Ceefax — **not** a leak),
> never affects NOS or other apps, and Spotify resumes normally on its next
> successful poll. This extends the milestone's already-accepted "best-effort
> connectivity" posture to Spotify coexistence.

**One residual carried openly, not hidden by this acceptance:** at the deepest
transient DMA dips the contention can *occasionally* crash/reboot the device
rather than degrade gracefully (EXP-019 saw one reboot at `lfbDma=8180`, not
reproduced on a repeat; PROP-008 soak 1 had 1 crash, soak 2 had 0). The DMA
gate bounds but does not fully eliminate this class. **Sanctioned future
mitigation if it proves user-visible in practice: gate-tuning only** — raise
`kMinLargestFreeBlockForConnect` to keep `lfbDma` above Spotify's ~16 KB TLS
need during churn, and/or lower `kMaxConsecutiveAttempts`. This is a bounded
threshold change, not a structural fix, and needs a multi-minute re-soak per
[[persistent-conn-dma-gate-pattern]]. Filed as the disposition of TASK-374;
TASK-375 (leak fix) is closed moot.

This supersedes the earlier "eliminates the degradation" language (item 3 /
Context) and the intervening "permanent leak / premise is false" amendments —
read those as the investigation trail, this block as the settled position.
