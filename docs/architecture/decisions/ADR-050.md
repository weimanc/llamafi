### ADR-050 — 2026-07-16 — Every persisted setting has a runtime owner outside settings/

**Status**: accepted (2026-07-16, human sign-off)

**Context**:

The 2026-07-16 settings audit (design:
`docs/architecture/designs/M-SETTINGS-WIRE2-global-settings-wiring.md`) walked
all 45 `AppSettings` fields through persisted / editable / **consumed** checks.
Persistence and UI coverage were complete; five settings were edited, saved,
and then partially or entirely ignored at runtime (G1–G5: `posixTz` not applied
at boot, `fmt24h` and `dateFmt` with zero consumers, city `lat/lon` written but
never read, auto-brightness ticking only while the Settings → Display screen is
open).

All five defects share one shape: **the Settings section that edits the value
was also the only actor applying it.** A section's `tick()` runs only while
that section is the active settings view, and nothing re-applies section-owned
state at boot — so behaviour silently degrades to "works only inside the
Settings screen" or "works until reboot".

Every correctly-wired setting in the same store already follows one of three
ownership patterns, none of which live in `settings/`:

| Pattern | Owner | Examples |
|---|---|---|
| Global flow object, ticked from the main loop, `applyMode()` at boot | `g_ledFlow` (`main.cpp:2044`, `:2136`) | LED mode/colour |
| Pull-on-resume consumer in the owning app (M-SETTINGS-APP-WIRE D1) | each app's `init()`/`resume()` | stock tickers/mode, crypto, aquarium, matrix, life, clock style, teletext, webRadio, planeRadar |
| Snapshot-at-enqueue for dataTask-coupled values (cross-core safety) | `enqueueWebRadioStations()`, `enqueuePlaneRadar()` | webRadio country/cap, prLat/prLon |

The audit also surfaced two save-policy ambiguities in the same territory:
`webRadioLastStation` is mutated in RAM on every station change
(`webRadioApp.h:1182`) but never saved by the app — it persists only when some
unrelated `saveSettings()` happens to fire; and `SettingsApp::_cancel()` writes
the entry-time snapshot to flash, which persists whatever RAM drift existed at
Settings entry.

**Decision**:

1. **Ownership rule.** Every `AppSettings` field must have a *named runtime
   owner outside* `app/src/settings/` that (a) applies the value at boot,
   after `SettingsStorage::load()`, and (b) reacts to changes — via one of the
   three established patterns above (global flow / pull-on-resume /
   snapshot-at-enqueue). Which pattern applies is declared when the field is
   added (design doc `Registers:` line or task text), not discovered later.

2. **Sections are editors.** Code under `app/src/settings/` renders, edits,
   validates, and persists. It never owns hardware or runtime behaviour. Live
   preview during an edit is allowed only through the owner's
   `pause()`/`resume()` handshake (the `g_ledFlow` idiom,
   `ledSection.h:117/122`) — the section borrows the resource and must hand it
   back; it never writes the hardware directly.

3. **No RAM-drift fields.** A writer that mutates `g_settings` outside the
   Settings UI either saves (immediately with unchanged-value skip, for
   deliberate low-frequency actions — the M-PLAYER-STATE §4 policy) or the
   field's RAM-only window is explicitly bounded and documented. For
   `webRadioLastStation` specifically: per-change saves are wrong (auto-skip
   can churn stations, flash wear), so the owner coalesces — persist on app
   `suspend()`/eject if the value changed since load. With rule 3 in force,
   `_cancel()`-writes-the-snapshot becomes harmless (there is no unsaved drift
   to clobber) and its revert-then-save semantics are kept as-is.

4. **Enforcement.** (a) `NEW-APP-CHECKLIST.md` gains an "owner declared?" item
   for any new setting; (b) the static gate
   `app/tools/check_settings_wiring.py` (M-SETTINGS-WIRE2 §6c) asserts every
   field appears in `load()`, `save()`, and ≥1 file outside `settings/` +
   `settingsStorage.*`, with an allowlist for documented-reserved fields —
   wired into `run/check` warn-only first (cert-preflight precedent), promoted
   to failing once green; (c) VE's T-SETW suite validates the behavioural side
   (T-SETW-01/02 round-trip + defaults; per-owner wiring tests).

**Consequences**:

- Adding a setting acquires a small up-front cost: name the owner and the
  pattern before the field lands. In exchange, "edited but ignored" and
  "works until reboot" become structurally impossible rather than
  audit-discovered — the five G-gaps would each have been caught at review.
- The G1–G5 remediation work (M-SETTINGS-WIRE2 §4) becomes rule-compliance,
  not judgement calls: `BacklightFlow` exists because rule 2 forbids
  `DisplaySection` calling `ledcWrite()`; boot `configTzTime` exists because
  rule 1(a) demands a boot applier.
- Sections get simpler over time (TASK-327's migration direction composes:
  kit widgets for rendering, owners for behaviour).
- The static gate adds a `run/check` step; warn-only initially, so no
  gate-flake risk until promotion.
- Constraint accepted: some settings genuinely have no continuous runtime
  behaviour (e.g. `teletextPage` is read once at app entry) — pull-on-resume
  *is* their owner; the rule requires an owner, not a ticker.
