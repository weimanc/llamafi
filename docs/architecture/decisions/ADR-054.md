### ADR-054 — 2026-07-19 — Spotify's TLS connect is gated on the persisted player mode, not spun up unconditionally at boot

**Status**: accepted (2026-07-19, human sign-off)

**Context**:

`spotifyTask::begin(&spotify)` (`app/src/main.cpp:2372`) — which spawns
Spotify's async HTTP polling task and shortly after connects its persistent
TLS session — is gated only by the `DISABLE_SPOTIFY` compile-time macro (a
separate no-PSRAM WebRadio-only build variant, TASK-255, not the standard
production build). It is not gated on `g_settings.playerMode`
(`settingsStorage.h:21`) at all, so a boot where the user's own persisted
preference is `WebRadio` still spins up and connects Spotify's polling
session — a service the user's own settings say they don't currently want
active.

Full investigation in `docs/architecture/designs/M-SPOTIFY-BOOT-GATE.md`.
Five findings from that investigation shape this decision:

1. **TASK-264/Q3-a (`spotifyTask::setWebRadioActive()`) already exists and
   is already wired into every `switchApp()` transition, including the
   boot-time switch into WebRadio mode** — but a race in `taskBody()`'s loop
   shape (the idle flag is only checked at the top of the `for(;;)` loop,
   before `xQueueReceive`, and not re-checked before the self-issued
   `ACT_POLL` dispatches after the queue-wait times out) means the very
   first TLS connect still fires ~5 s after `begin()`, regardless of
   `playerMode`, before the flag set by the boot-time `switchApp(WebRadio)`
   call gets a chance to take effect.
2. **A second, independent TLS connect happens earlier still and is
   unaffected by any gate on `begin()`.** `main.cpp:2363`'s eager
   `spotifyRefreshToken()` → `spotify.refreshAccessToken()` call opens a
   real TLS connection on the *same shared* `WiFiClientSecure client` object
   `spotifyTask` uses, in `setup()`, 9 lines before `begin()` is even
   reached — regardless of `playerMode`. Gating `begin()` alone does not
   prevent this connect.
3. **That eager refresh call is functionally redundant.** `SpotifyArduino`
   already auto-refreshes lazily (`autoTokenRefresh = true` default,
   `checkAndRefreshAccessToken()` called before every real API call) — the
   first genuine Spotify API call after boot would trigger the same refresh
   automatically if the eager call were skipped.
4. **Toggling back to Spotify mid-session already works today**, via the
   same shipped `setWebRadioActive(false)` path every eject-to-Spotify site
   already calls — no new toggle-back mechanism is needed, and repeated
   toggling doesn't compound latency (the task/stack/queue are never torn
   down, only the TLS session cycles).
5. **The DUT test harness's readiness wait
   (`run_serialdbg_tests.py::Dut._wait_for_ready()`) hard-blocks every test
   connection on a successful Spotify poll**, with the only existing bypass
   being the `DISABLE_SPOTIFY` build-time case. Left unaddressed, this
   design would make every test-harness connection against a device
   persisted in `WebRadio` mode eat a ~120 s hang before running a single
   test.

**Decision**:

1. **Seed `spotifyTask`'s TLS-idle flag before the task's first loop
   iteration**, closing Finding 1's boot race. `spotifyTask::begin()` gains
   a `bool startIdle` parameter, set from `bool bootIntoWebRadio =
   wifiConnected && (g_settings.playerMode == (uint8_t)PlayerMode::
   WebRadio)` — the **same** condition `main.cpp:2407`'s existing boot
   switch already uses (not raw `playerMode` alone: if WiFi isn't up at
   boot, `currentAppId` stays `Spotify` regardless of the persisted
   preference, and that visibly-active Spotify app must still be allowed to
   connect once WiFi comes up via the background supervisor — seeding from
   raw `playerMode` would silently strand it idle). `s_webRadioActive` is
   set **before** `xTaskCreatePinnedToCore()` runs, so the task's very first
   top-of-loop check already sees it, before ever reaching
   `xQueueReceive`/`doPoll()`. The boot-time `switchApp(WebRadio)` call and
   its existing `setWebRadioActive(true)` become purely confirmatory.
2. **`reqQueue`/`g_taskHandle`/`s_tlsYieldedSem` are always created** —
   `spotifyTask::begin()` still runs unconditionally at its current
   `setup()` location; only its *initial idle state* changes. This is a
   deliberate choice over deferring `begin()` itself to first
   toggle-to-Spotify: it inherits M-RECLAIM's already-accepted Q3-a
   reasoning ("the task object survives, so the null-safety story holds")
   and requires **zero** new null-safety audit across the unconditional
   `spotifyTask::` accessors — unlike a fully-lazy-start design, which would
   leave those handles null for the entire (open-ended-duration, runtime,
   reversible) WebRadio session and reopen the exact audit cost M-RECLAIM's
   Q3-b already priced as real and non-trivial.
3. **The eager `refreshAccessToken()` network call is skipped under the
   same `bootIntoWebRadio` condition** (`spotify.setRefreshToken()` still
   runs — pure string store, no network — priming the library for whenever
   the first real call does happen). The library's existing
   `checkAndRefreshAccessToken()` performs the refresh lazily at that point
   instead. This is the change that actually closes Finding 2's gap; without
   it, the side-effect heap-fragmentation benefit motivating part of this
   work does not materialize, even with (1)/(2) shipped.
4. **`run_serialdbg_tests.py`'s `_wait_for_ready()` gains a
   `playerMode`-aware readiness branch**, mechanically identical in shape to
   the existing `spotify=off`/`DISABLE_SPOTIFY` branch: WiFi-up +
   shell-responsive counts as ready when the persisted mode is `WebRadio`,
   skipping the poll-wait. Required regardless of whether (3) ships, since
   (1) alone already changes whether `[spotify.poll] ok 200` appears on a
   `WebRadio`-mode boot.
5. **Toggle-back to Spotify is unchanged** — reuses the existing, shipped,
   already-DUT-exercised `setWebRadioActive(false)` path from every
   eject-to-Spotify site.

**Consequences**:

- *Easier*: a `WebRadio`-mode boot no longer opens any Spotify network
  connection until the user explicitly asks for it (eject/Settings toggle
  to Spotify) — the primary goal. As a validated (DUT-measured, not
  assumed — see the design doc's Exit criteria) consequence, such a boot
  also avoids the TLS-connect-driven heap fragmentation
  `M-HEAP-FRAGMENTATION`/`ADR-053` (both parked) measured, without touching
  any of that parked design's rejected/deferred options.
- *Harder*: a revoked/expired refresh token on a `WebRadio`-mode boot now
  surfaces at first toggle-to-Spotify instead of immediately at boot —
  acceptable given the change's own premise (don't touch Spotify until
  asked), but a real shift in when that failure becomes visible.
- *Constrained*: the seed condition must track `main.cpp:2407`'s existing
  boot-switch guard exactly (`wifiConnected && playerMode == WebRadio`), not
  simplify to raw `playerMode` — doing so would strand a visibly-active
  Spotify app (the no-WiFi-at-boot edge case) in permanent idle.
- *Risk*: the DUT harness change (4) is a required, not optional, part of
  this change — shipping (1)-(3) without it degrades every future
  test-harness run against a device left in `WebRadio` mode.

**Verification gate** (handed to VE, formalizing the design doc's Exit
criteria): ≥5 cold boots in `WebRadio` mode show no `[spotify.poll]` log
line before an explicit toggle; ≥3 cold boots confirm (via `get heap`) no
permanent heap-block split comparable to `M-HEAP-FRAGMENTATION`'s measured
~43 KB ceiling; ≥5 toggle-to-Spotify actions connect within a bounded,
recorded latency inside `ADR-046`'s existing "connecting" amber tolerance;
≥3 repeated toggle cycles confirm no compounding latency; a no-WiFi-at-boot
scenario confirms the visibly-active Spotify app still connects once WiFi
comes up; the DUT harness connects promptly (no ~120 s hang) against a
device left in `WebRadio` mode. Full serialdbg suite green on
`cyd2usb_winamp`; `./run/check` 5-gate green.

**Supersedes**: none. Independent of, and does not amend,
`ADR-053`/`M-HEAP-FRAGMENTATION` (both parked) — this decision's heap-side
benefit is a validated consequence of gating Spotify's connect on user
intent, not a resurrection of ADR-053's declined Option E. Extends the
Q3-a mechanism `M-RECLAIM-dynamic-resident.md` designed and TASK-264
shipped; does not touch Q3-b (still parked, unshipped, unneeded by this
decision).
