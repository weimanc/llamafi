### ADR-052 — 2026-07-19 — Display repair: extract the viewport-scoped-repair primitive, not a unified delta-engine framework

**Status**: proposed (2026-07-19, awaiting human sign-off)

**Context**:

TASK-354 (M-CLOCK-FACE-COMMON.md §Part 1, shipped 1401e9f) fixed a whole-face
flicker in the Clock app's Flip and Nixie faces: both redrew their entire
static layer every second just because a colon blinked. On this board's
unbuffered SPI display, any erase-then-redraw of pixels that didn't need to
change is visible as flicker/tear. The fix was a discrete-slot delta engine
(`FaceFrame{digs[4], colon}`, diffed per tick, `drawDigit(i)`/`drawColon()`
hooks called only for changed slots).

TASK-357 (dr-damped motion smoothing, shipped 1f66252) introduced the same
anti-pattern in a new shape: PlaneRadar's `_render()` now runs at ~10 Hz
whenever any single aircraft's dead-reckoned position is dirty
(`_motionDirty()`), and unconditionally repaints the *entire* scene —
`_erasePrev()` erases every tracked aircraft, `_redrawGridStatics()` redraws
all 4 range rings + crosshair + every in-range runway, then every aircraft is
redrawn with full tag-occlusion recompute. Human-reported as visible
"twitchy" tearing, explicitly linked to the Clock precedent. TASK-357's own
notes flag the fix as deferred: a per-aircraft dirty-rect erase/redraw +
scoped static-layer repair, not yet implemented.

Research this session (see `M-DISPLAY-DELTA-COMMON.md`) confirmed TFT_eSPI's
`setViewport(x,y,w,h,vpDatum=false)` clips every subsequent draw call at the
individual-pixel level (verified by reading `TFT_eSPI.cpp`'s implementation:
internal auto-clip to screen bounds, `_vpOoB` inhibits all drawing when the
box is fully off-screen, no crash on bad input). This means an app's
*existing* whole-static-layer redraw function can be reused **verbatim**,
wrapped in `setViewport(dirtyBox); redrawStatic(); resetViewport();`, to
cheaply and correctly repair only a dirty rectangle — no new per-app
clipping/geometry code. Zero current uses in the codebase (`grep -rn
setViewport app/src/` → empty).

The open question this ADR settles: given two data points (Clock's discrete-
slot diff, PlaneRadar's continuous-2D dirty-rect), and a wider inventory
survey turning up **five more independently-invented instances** of "compute
a delta, redraw only what changed" (VU meter's per-column width diff +
pixel-exact background restore; WebRadio's region-scoped posbar/scroll
repaint; Weather's per-field change-gated erase; Digital clock face's string-
cache erase; Game of Life's diff-render toroidal grid) — should this become
one shared framework, or should only the genuinely-common mechanism be
extracted?

**Decision**:

Extract a single small stateless helper — `withViewportRepair()`, living in
`app/src/util/tftViewportRepair.h` alongside `mathUtil.h`/`timeFmt.h` — that
wraps `setViewport`/`resetViewport` around a caller-supplied redraw callback.
**Do not** build a unified "dirty-rect sprite" base class or delta-engine
framework spanning apps.

Rationale: the seven instances found (Clock ×2 shapes, VU meter, WebRadio,
Weather, Digital, Game of Life, plus PlaneRadar's still-open one) solve the
same *problem class* with **structurally different data shapes** — discrete
slot arrays, 1-D bar widths, scroll-offset regions, string-valued fields,
toroidal grid cells, and 2-D dead-reckoned sprites with rotation and tag
occlusion. None of the six already-working solutions share code today, each
is small, each is already correct and (where applicable) DUT-proven. Forcing
them into one abstraction to serve an eighth, not-yet-written consumer is
premature generalization from what is really still a two-data-point sample
for the *2-D sprite* sub-case (Clock's discrete-slot engine and PlaneRadar's
sprite motion do not share a natural base class — see
`M-DISPLAY-DELTA-COMMON.md` design space). The one piece that generalizes
cleanly *by construction* — because it's a direct wrapper over an existing
TFT_eSPI primitive with no app-specific state — is the viewport clip/reset
pairing itself, which is also the one piece with a real footgun if
reimplemented ad hoc per call site (TFT_eSPI's viewport is a single global,
non-stacking rectangle; a forgotten `resetViewport()` on any exit path
silently clips every subsequent draw call app-wide).

**Consequences**:

- PlaneRadar's deferred TASK-357 follow-up (per-aircraft dirty erase/redraw +
  grid-static repair) has a ready-made, already-verified-safe primitive to
  build on, instead of hand-rolling viewport calls inline.
- Clock's TASK-354 delta engine is untouched — no code change, no forced
  migration to a new abstraction for framework purity.
- VU meter, WebRadio posbar/scroll, Weather/Digital/Game-of-Life diff-render:
  untouched. Each already handles its own case correctly; no shared surface
  area is added or subtracted for them by this decision.
- `withViewportRepair()` reduces SPI *write* volume (the actual driver of
  visible tearing on this board) proportional to the dirty box, but does
  **not** reduce the CPU cost of iterating a redraw function's shape list —
  a static-layer function with an expensive *generation* step (not just an
  expensive *pixel count*) would need its own bbox-aware early-out, which
  this helper deliberately does not provide. Flagged as a non-goal, not
  silently assumed away.
- If a *third* continuous-2-D-sprite app appears later (beyond Clock's
  discrete slots and PlaneRadar's dead-reckoned aircraft) doing the same
  dirty-rect-motion shape PlaneRadar does, that is the point to revisit
  whether a shared sprite base class is now justified by evidence rather
  than by pattern-matching on two examples.

**Supersedes**: none. Companion to `M-CLOCK-FACE-COMMON.md` (TASK-354,
implemented) and `M-DISPLAY-DELTA-COMMON.md` (this design, draft).
