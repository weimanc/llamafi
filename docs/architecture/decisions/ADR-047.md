## Context

EXP-009 settled the *technical* question: the no-PSRAM CYD **can** play MP3 radio (bare and with the full
TFT). The wall is **resident footprint + heap contiguity**, not silicon and not the display. That converts the
milestone's open question from "is it even possible" into a **product-scope decision**: how much do we invest
to make WebRadio reliable on this board, given it costs engineering and ongoing maintenance?

This ADR does **not** make the call — it frames it so the human operator can. The call gates whether the
M-MEMBUDGET / M-RECLAIM / spike work gets scheduled.

## Options

### Option B — accept best-effort, close the milestone (the current lean)
Keep ADR-045 as-is: WebRadio stays best-effort on no-PSRAM (plays on fast HTTP streams when the heap is
unfragmented; auto-skips dead ones). No further investment. The station-fetch / UI / eject / settings / the
player-mode work (TASK-259/260) all stand regardless.
- **Cost:** zero new engineering. One firmware. Honest, documented (EXP-009).
- **Give up:** WebRadio never becomes a first-class reliable feature on the multi-app board.

### Option A-lite — reserved overlay arena + 2-site library fork (designed this session)
Reserve a shared foreground-scratch internal arena at boot; redirect the audio library's two big allocation
sites into it (deterministic placement); reclaim the mutually-exclusive resident blocks (M-RECLAIM) to finance
it. Yields **reliable WebRadio on the multi-app build, no second firmware.**
- **Cost:** vendored audio lib (low ongoing cost — BP-042 freezes us on v2.3.0 anyway), a **fixed-slot
  free-list arena allocator** (panel-corrected: a bump allocator does NOT survive auto-skip churn — the
  decoder frees/re-allocs on every `connecttohost`), a **3-site fork** (decoder alloc + matching free + InBuff,
  to avoid heap corruption), the M-RECLAIM teardown work, ~15 K net RAM (after overlay financing), and the
  spike to de-risk.
- **Risk:** the spike's Phase-1 kill-gate could show the reservation infeasible or the app set won't fit →
  falls back to B. Bare PASS ≠ multi-app PASS (LL-086). The allocator must survive the auto-skip free/realloc
  cycle (Phase 2a tests it explicitly).

### Option A-full — dedicated radio appliance / second firmware (largely superseded)
Strip to a boot-direct-to-WebRadio variant. Heavier; introduces a second firmware to maintain (BP-041). Mostly
dominated by A-lite, which keeps one firmware. Retained only as a fallback if A-lite's coexistence fails but a
radio appliance is still wanted.

## Decision criteria

1. **Do you want internet radio as a first-class, reliable feature on this board** — enough to own an arena
   allocator + a vendored-lib fork?
2. **Risk appetite:** A-lite is de-riskable *cheaply* — PROP-membudget-spike Phase 0/1 is ~one boot alloc + a
   soak and gives a hard yes/no before any fork effort.

## Recommendation

**Gate on the cheap spike, don't pre-commit the build.** Specifically:
- If WebRadio reliability is something you want → **schedule spike Phase 0/1 only** (cheap, DUT) as the kill
  test. Phase-1 PASS → commit to A-lite (Phase 2 fork). Phase-1 FAIL → **Option B**, milestone closes,
  ADR-045 stands.
- If WebRadio was always a "nice if it works" extra → **choose B now**, skip the spike, close the milestone.
- Either way, **TASK-259/260 (player mode + persistence) proceed** — they're independent UX value.

## Consequences (by outcome)

- **B chosen:** ADR-045 stands; TASK-255 stays parked; M-MEMBUDGET/M-RECLAIM/PROP-spike become shelved design
  (kept for the record); milestone closes on a quantified, honest note.
- **A-lite via spike:** file TASK-261/262 (spike + cleanup); M-RECLAIM Q3-a/Q4 become real tasks; this ADR is
  re-issued as **Accepted** with the spike numbers.

## Amendment 1 (2026-06-28) — fetch-vs-arena sequencing (TASK-267)

**Problem (TASK-265 finding):** the arena is reserved at **boot and held for the whole session**. WebRadio's
station fetch (`init()`) needs a ~40 K mbedtls SSL context, but with the 24 K arena held the heap has only
~35 K contiguous → fetch fails `-32512`. The arena (decoder) and the fetch TLS (list) are the two big heap
consumers, and the always-held reservation starves the fetch.

**Decision: Option (a) — JIT-reserve the arena at `_play()`, not boot; financed by the overlay; with a
contiguity measurement and graceful fallback.**

Rationale — the two big needs are **sequential and disjoint**: the fetch (at `init()`) needs ~40 K TLS
*transiently* and frees it before any `_play()`; the decoder needs the 24 K arena *only during playback*. They
never coexist. So:
- **`init()`/fetch:** no arena held → full heap (~55 K contiguous) → SSL succeeds.
- **On WebRadio mode entry, TASK-264's overlay tears Spotify down** (frees ~50 K + defragments) — so the heap
  at `_play()` is *fresh*, not the deep-fragmented EXP-008 state that motivated boot-reservation.
- **`_play()`:** `mb_arena_reserve()` (moved here from `setup()`), then construct `Audio` (halved-DMA
  `i2s_driver_install`, PATCH-MEMBUDGET-4) → decoder allocs land in the arena. **`mb_arena_free()` on stop**,
  so it is held only during playback (and released for the next fetch).

**Why not the others:**
- **(b) reserve-at-boot, release-for-fetch, re-acquire** — same re-acquire-contiguity question as (a) plus
  extra churn. Dominated by (a).
- **(c) shrink mbedtls buffers** (`MBEDTLS_SSL_IN/OUT_CONTENT_LEN` 16 K→4 K) — saves ~24 K so fetch + arena
  coexist, but mbedtls config is **global**: risks Spotify's API TLS + any endpoint sending large TLS records.
  Too broad a blast radius for a fetch-only problem. **Kept only as the fallback if (a)'s measurement fails.**
- **(d) fetch-before-reserve with a cached list** — doesn't handle on-entry re-fetch (country change / refresh);
  delays boot. Rejected.

**The risk (a) carries, and the measurement that retires it:** boot-reservation existed to dodge `_play()`-time
fragmentation (EXP-008: ~21–24 K usable deep in a session). (a) must prove **24 K contiguous reliably survives
to `_play()`** *given the overlay has just run*. **Validation = a Phase-1-style probe at the new reservation
point:** capture `lfbInt` immediately before `mb_arena_reserve()` in `_play()`, ≥ 3 cold-boot trials ×
(enter WebRadio → fetch OK → play), on `cyd2usb_webradio`. PASS = fetch succeeds (count > 0) AND the JIT
reserve succeeds (`lfbInt ≥ 24 K` / `mb_arena` non-null) AND playback holds. **Graceful fallback already
wired:** `mb_arena_alloc` routes to libc `malloc` when the arena is absent/full (`mb_arena.h`), so a failed
JIT reserve degrades to today's best-effort playback — never a crash. **If the measurement shows the JIT
reserve unreliable** → fall back to (c) or a smaller arena; re-open here.

This amendment is the content of **TASK-267**; on its validation PASS, the promotion gate (TASK-262) clears
except for TASK-243 (Premium / Spotify-active).
