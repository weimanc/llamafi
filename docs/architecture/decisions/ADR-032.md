### ADR-032 — 2026-05-26 — Heap arbitration between sprite apps and SSL data tasks

**Status**: proposed

**Context**:

When the aquarium app holds its sprite (32–40 KB contiguous internal heap), the mbedTLS
SSL handshake required by `dataTask` (weather, crypto) fails with
`SSL - Memory allocation failed`. The ESP32-2432S028R has no PSRAM; a single internal
heap block of ~40.9 KB is the only contiguous allocation available to both the sprite
and SSL. They cannot coexist in memory simultaneously.

The degradation is graceful — data tasks retry; stale data is shown; updates resume
after the user navigates away — but weather and crypto data will not update for the
entire duration of an aquarium session, which may be many minutes.

This is a general problem: any future app that holds a large contiguous allocation
(album-art buffer, visualization sprite) will exhibit the same SSL conflict with
`dataTask`.

A protocol is required that allows a memory-holding app to temporarily release its
allocation, permit a single SSL round-trip, and then re-acquire — without violating the
TFT_eSPI thread-safety constraint (all sprite operations must occur on the loop()
thread).

Full design space explored in:
[`docs/architecture/designs/M-AQUARIUM/sprite-heap-arbitration.md`](../designs/M-AQUARIUM/sprite-heap-arbitration.md)

**Decision**:

Introduce a **heap arbitration protocol** with three parts:

1. **Two new optional methods on `App`** (`appShell.h`):

   ```cpp
   virtual bool yieldHeap()   { return false; }
   virtual void reclaimHeap() {}
   ```

   `AquariumApp` (and any future memory-heavy app) overrides both. Default
   implementations are no-ops, so all existing apps are unaffected.

2. **`heapArbitrator` module** (`app/src/heapArbitrator.h`, companion `.cpp`):

   Three volatile flags govern the handshake:
   - `g_yieldRequested`    — `dataTask` → `loop()`: please release heap
   - `g_yieldAcknowledged` — `loop()` → `dataTask`: released, SSL may proceed
   - `g_reclaimRequested`  — `dataTask` → `loop()`: SSL done, re-acquire heap

   `heapArbitrator::service(App* activeApp)` is called once per `loop()` iteration
   (before `appTick`). It checks and dispatches the flags, calling `yieldHeap()` or
   `reclaimHeap()` on the active app — always on the `loop()` thread.

   `heapArbitrator::request(timeoutMs)` is called from `dataTask` before any SSL
   operation. It sets `g_yieldRequested`, then spins until `g_yieldAcknowledged` or
   the timeout (default 150 ms) expires. Returns `true` if the yield succeeded.

   `heapArbitrator::release()` is called from `dataTask` after the SSL operation
   (regardless of success/failure). It sets `g_reclaimRequested` and clears the
   acknowledgement flags.

3. **`loop()` integration**: one `heapArbitrator::service()` call added at the top of
   the main loop, before `appTick`.

   **`dataTask` integration**: `request()` / `release()` bracket each HTTPS fetch.

All TFT_eSprite operations remain on the `loop()` thread. The `dataTask` thread only
writes/reads the volatile flags and spins for ≤ 150 ms. This is within the observed
data-task timeout budget and does not affect SSL handshake timing.

**Consequences**:

What becomes easier:
- Weather and crypto fetch on every poll cycle regardless of active app.
- Any future large-allocation app automatically participates by overriding two methods.
- The `App` interface remains the single seam; `dataTask` has no knowledge of which
  app is active.

What becomes harder / constrained:
- The 150 ms spin in `dataTask` is a new soft real-time constraint on `loop()`. If the
  main loop stalls beyond 150 ms (e.g. during a large playlist or skin render), the
  yield will time out and SSL will likely fail — same outcome as today, no regression.
  The timeout is configurable.
- `AquariumApp::reclaimHeap()` may fail to allocate the sprite if the heap has not
  fully defragmented after SSL completes. Handled by the existing `!_spriteReady` retry
  path — no new failure mode.
- A new translation unit (`heapArbitrator.cpp`) is added to the firmware.

**Supersedes**: nothing. Extends M-AQUARIUM (ADR-031) and M-MULTIAPP app-interface
design.

**Prerequisites before implementation**:
- VE review of the flag-handshake protocol (testability, race analysis).
- IFC-001 definition for the `dataTask ↔ heapArbitrator` boundary.
- PM scheduling (unscheduled as of 2026-05-26).
