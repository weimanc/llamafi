### ADR-067 — [2026-09-04] — DUT entry points verify and refuse; they never flash and never restore

**Status**: accepted
**As-built**: yes, as of 2026-09-07 — TASK-633 landed 2026-09-06 with two of its three mechanisms
dead; TASK-661 repaired them and verified both arms on hardware. See the **as-built assessment** at
the end of this file, which is the honest record of what shipped. `DUT_NO_RESTORE=1` no longer
appears anywhere under `run/`; retiring its ledger row is @PM's (TASK-633).
**Ruled**: human, 2026-09-03 (TASK-618) and 2026-09-04 (Architect's decision E, with the refusal code
fixed at **3**).
**Design doc**: [M-HARNESS2 architect review](../designs/M-HARNESS2-architect-review.md) §6
**Requirement**: [R51](../../verification/M-HARNESS2-requirements.md), plus `F-19`
**Supersedes** the practice recorded at `run/lib.sh:16` ("ENV_PROD is deliberately NOT overridable:
every test script's trap restores production, and that must stay production") for test entry points.

---

**Context**

Fifteen scripts under `run/` carry an EXIT trap and a reference to `ENV_PROD` — `run/test`,
`run/test-targeted`, `run/test-sync`, `run/player-gate`, `run/wr-gate`, `run/stress`, `run/wr-soak`,
`run/pr-soak`, `run/pr-fetch-soak`, `run/ae04`, `run/task488`, `run/browser-player`,
`run/playorder-player`, `run/task424-repro`, and the shared `run/lib.sh` they all source. The trap's
whole job is to reflash production firmware no matter how the script exits. That safety control is
correct in the world it was written for and **hardened into an obstruction when the context
changed**: TASK-557 pins this board to the `-DBOD_WATCH` debug build, so a script that unconditionally
restores production cannot be run at all. The consequence is measured — an ~80-minute DUT session
that would settle **32 of 58** open items is unrunnable
([WP-Z §5](../../verification/reviews/M-TESTQUAL-Z-findings-review.md)).

The proposed fix was a `DUT_NO_RESTORE=1` opt-out. My review's objection stands and is the reason
this is an ADR rather than a flag: (1) it is a suppression flag on an unconditional side effect, so
the trap fires *sometimes* and every future reader must know which mode they are in to know what
state the board is in; (2) its justification has an expiry nobody owns — this repo's own
`wifi_creds.h` shim sat dead in the build for months (TASK-404); (3) it entrenches the real defect,
which is that a **test** entry point owns **firmware lifecycle**.

**Decision**

**D1 — a DUT entry point verifies and refuses. It never flashes and it never restores.** It reads the
board's build identity, compares it against what the run declares it needs, and refuses if they
differ. Flashing becomes an explicit caller action through the existing `run/flash*` scripts — which
is already how `run/flash-player`, `run/flash-webradio` and `run/screendump` behave; none of them
restores production. The trap is **deleted**, not guarded.

**D2 — the refusal code is 3, `[SETUP-FAIL]`, with a build-identity reason.** Not 4. The board is
present, addressable and responsive; what is wrong is that the host is pointed at a subject the run
did not ask for, and [M-TESTARCH precedence](../designs/M-TESTARCH-precedence-hierarchy.md) §4 rule 2
already places exactly this in the RIG vocabulary: `elf-mismatch` and `prod-firmware-flashed` are
named there, at exit 3. Exit 4 means "the board is not a valid subject" in the sense of *unfit* — a
HEALTH condition about the hardware's state, carrying `NOT-RUN` for every id.

*Recorded correction, because the corpus should not carry the older reading unchallenged:* my review
§6 recommended **exit 4**, and [PM review §5(c)](../../project/M-HARNESS2-PM-review.md) paraphrases
the ruling as "the 'not a valid subject' code", which in M-TESTARCH's vocabulary is 4. **Exit 3 is
correct and the 2026-09-04 ruling is right**: a wrong-build refusal is `elf-mismatch`, that reason is
already RIG, and routing it to 4 would have split one condition across two codes depending on which
script noticed it.

**D3 — `DUT_NO_RESTORE=1` is a dated interim exception, owned by TASK-618, and nothing else.** Its
retirement condition is TASK-633's conversion. Its ledger row is itself a blocking failure when stale
— the same discipline this programme imposes on every other exception. It is not the answer; it is
the thing that lets Phase 2 run before the answer lands.

**D4 — the cost is 1.5 days plus a `CLAUDE.md` update, and the review that called it small was
wrong.** @Developer's correction, recorded here because my review implied a two-script edit: the trap
is shared across the scripts enumerated in the Context, so the conversion is a change to the shared
lifecycle in `run/lib.sh` and to each entry point that inherits it, **plus** the `CLAUDE.md` run-script
table, which today promises a restore that will no longer happen. The documentation half is not
optional garnish — after this lands, *the board stays on whatever build the last flash put there*,
and a table that says otherwise is a trap of a different kind.

**D5 — the standing hazard is restated as part of this decision.** **Never kill a `run/flash*`, soak
or test script mid-flight.** It races the trap-guarded restore and can boot-loop the board. This is
recorded on this rig and it is the reason the answer to a pinned board was ever a flag rather than
Ctrl-C.

**D6 — verify-and-refuse is what makes ADR-066 D3 checkable.** The entry point must read build
identity to refuse, and the same value is the artifact's build-identity field. One mechanism, two
consumers; neither is speculative.

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| `DUT_NO_RESTORE=1` as the permanent answer | A suppression flag on an unconditional side effect, with an expiry nobody owns, entrenching the wrong ownership. Sanctioned only as D3's dated interim. |
| Make `ENV_PROD` overridable | Turns a safety control into a footgun: a mistyped env silently becomes "production" for the restore. The problem is the restore, not the constant. |
| Keep the restore and have the entry point re-flash the *debug* build it needs | Still puts firmware lifecycle in a test entry point, and inside a pinned-board window it is a flash inside a measurement window, which TASK-557 forbids. |
| Kill the script mid-flight when the board is pinned | D5. It races the restore and can boot-loop the board. |
| Entry points refuse with exit 4 (my review's recommendation) | D2 — splits `elf-mismatch` across two exit codes and re-labels a rig condition as a health one. |

**Consequences**

- *Easier*: any run can state which build it requires and get a loud, correctly-classified refusal
  instead of a silent reflash. `run/wr-gate`, which checks no build identity today (`F-19`), gains
  the check the player gate already has.
- *Harder*: the caller now owns getting the right firmware onto the board. That is a real ergonomic
  cost — two commands where there was one — and it is the price of the entry point no longer being
  able to destroy the state a test was investigating.
- *Constrained*: `CLAUDE.md`'s run-script table and `docs/process/dut_workflow.md` must change in the
  same commit, and the "always restores prod firmware on exit" promise must be **removed**, not
  softened.
- *Cost*: 1.5 days plus the documentation update (D4), not the afternoon my review implied.
- *Risk accepted*: a board left on a debug build after a run is a state a future session must notice.
  Verify-and-refuse is exactly the mechanism that notices it, which is why the risk is bounded by the
  same change that creates it.

**Obliges**

| Who | What |
|---|---|
| @Developer | **TASK-633** — the conversion, the trap deletion across the shared lifecycle, the `CLAUDE.md` and `dut_workflow.md` updates |
| @VE | the required-build declaration at each entry point; `run/wr-gate` gains the identity check (`F-19`) |
| @PM | retire `DUT_NO_RESTORE=1`'s ledger row when TASK-633 lands; a stale row is a blocking failure |

**Unblocks**: [tasks-harness2.md](../../project/tasks-harness2.md) **TASK-633** — already OPEN and
already noted "TASK-618 ruled", so this ADR confirms rather than releases it, and fixes its refusal
code at 3. Phase 2's entry criterion is satisfied by TASK-633's landing; until then the sanctioned
interim exception is the permitted path, unchanged.

## As-built assessment — 2026-09-07 (Architect, TASK-661)

**Status of this ADR changes from "not yet as-built" to as-built, with the record below.** The
decision is not revisited: it was right. What follows is what actually shipped against it.

### What shipped, and what of it was alive

TASK-633 landed on 2026-09-06: the trap deleted across `run/lib.sh`, `require_build` added to all
fourteen entry points, `lib/verify_build.py` written, a 27-arm negative suite, a blocking gate
(`gate/check_entrypoint_lifecycle.py`) at zero, and the `CLAUDE.md` / `dut_workflow.md` updates D4
required. Every artefact reported green. The first hardware session
([phase-2 review](../../verification/reviews/M-TESTQUAL-phase2-session-review.md) §D-1/§D-2), four
minutes in, found that **two of the three mechanisms had never executed**:

| Mechanism | State as shipped | Fixed |
|---|---|---|
| the refusal (`require_build` → `lib.verify_build`) | **dead** — run from cwd `app/`, so every entry point died `No module named lib.verify_build`, **exit 1**, which is neither of the codes D2 defines | `d3a3600` (cwd `app/tools`), verified on hardware 2026-09-07 |
| the port open the refusal needs | **false-positive** — opened while the monitor still held the port, so the rig's *normal* state produced a false `elf-mismatch`-class exit 3 on a healthy, correctly-built board | TASK-661/D-1b below, verified on hardware |
| the ELF comparison the refusal is *for* | **dead since 2026-08-17** — `lib/dut.py`'s comparand path resolved to `app/tools/.pio/build`, which does not exist, so BP-017's guard silently did nothing for three weeks and every run printed `elf=? expected=?` | TASK-661/D-2 below, verified on hardware |

Only D3 (the interim `DUT_NO_RESTORE=1` exception) and the deletion of the trap itself were ever
really exercised. **D6 — "verify-and-refuse is what makes ADR-066 D3 checkable" — was false on the
ground for the whole period**: the premise field it feeds (`premise.elf`) was written `null`.

### D-1b, ruled: the verify owns the port for its duration

`require_build` now **stops the monitor before its port open and restarts it on the refusal path**;
on the success path the monitor stays down, the caller's own kill step becomes a no-op and its EXIT
trap restores it exactly as before. This keeps both properties TASK-633 traded against each other: a
refused run still leaves the rig precisely as it found it, and a run on the right build is not
refused for a reason that has nothing to do with its subject.

The two alternatives were rejected against this ADR's own reasoning. *Tolerate a held port* — there
is nothing to tolerate: two openers on one CH340 do not degrade to a partial read, they produce
`SerialException: … multiple access on port?`, so "tolerating" it can only mean skipping the check,
which is the state D1 exists to end. *Verify from something other than a port open* — the board's
elf is readable only over the port; anything else means trusting a host-side record of the last
flash, i.e. assuming the thing the ADR requires be verified. The reset budget is unchanged: this is
still one open, replacing the flash that used to reset the board here anyway.

### What now guarantees the decision is executed rather than merely present

1. **One definition of the comparand.** `lib.dut.BUILD_ROOT` is the single source, imported by
   `lib/verify_build.py` rather than recomputed. D-2 existed because two modules each derived the
   path from their own `__file__` and one of them moved house.
2. **A guard that cannot compare refuses.** A missing host artifact, and a board that states no elf,
   both raise `SetupFailure("elf-unverifiable")` → RIG → exit 3. The old shape wrapped the whole
   comparison in `if _fw.exists():`, which is how three weeks of runs passed a check that never ran.
3. **The gate executes the mechanism.** `check_entrypoint_lifecycle` gains C5/C6, which source the
   real `run/lib.sh`, actually call `require_build` (host half, then board half against a port that
   cannot be a board), and read `BUILD_ROOT` by running the modules. Both arms are mutation-tested
   in the negative suite (`A12`/`A13` rebuild D-1a and D-2 in a throwaway copy and require the gate
   to name each), per BP-068.
4. **Hardware, once, deliberately.** Both arms of the contract were driven against board
   `d48afcc8eed0` on 2026-09-07: a `DUT_ENV=cyd2usb_player` run **refused at exit 3** naming the
   board's real elf `732c8567` against the wanted `ac924a1c`, restarted the monitor it had stopped,
   and flashed nothing; the default run **verified at exit 0** (`elf=732c8567 expected=732c8567`)
   and passed its test. This is the first execution of the refusal in the conversion's life.

### Why nothing caught it, and the residual risk

`check_entrypoint_lifecycle` asserted that the string `require_build` *appeared* in a script that
opens a DUT. Three text checks, all satisfied by a call that could not run — the same defect class
this programme exists to remove (an oracle that cannot observe its subject), sitting inside the gate
written to enforce this ADR. The move that killed the ELF guard was reviewed as "moved VERBATIM,
verified byte-identical", and byte-identity is exactly the check that cannot see a `__file__`-
relative path change homes.

**The honest limit: a host-only gate cannot fully validate a hardware path.** C5/C6 prove the
mechanism *runs* — the module imports, the shell function returns 3, the two modules agree on where
the artifact lives. They cannot prove the board answers `info` with an `elf`, that the monitor
actually released the port, or that a refusal reaches a human before a 40-minute suite does. Those
are DUT-owed and were discharged by hand on 2026-09-07 (above); they are **not** re-checked by any
gate, and inventing one that appeared to would be the same defect again. The residual risk is
therefore: *a change to the firmware's `info` reply, to the monitor's port handling, or to a driver
that opens its own port, can re-break the refusal, and no host gate will say so.* It is carried by
**@VE**, discharged by the first entry-point run of any DUT session — which now fails loudly rather
than silently, because every one of the three "cannot compare" paths is a refusal with a code. The
first session after any change to `run/lib.sh`'s verify block, `lib/dut.py`'s guard, or the `info`
reply must state in its report which of the two arms (refusal / verification) it observed.

assessment triggered (which gates execute their mechanism and which only pattern-match) is reported
separately to @PM and is not part of this decision.
