### ADR-067 — [2026-09-04] — DUT entry points verify and refuse; they never flash and never restore

**Status**: accepted
**As-built**: not yet — this ADR authorises TASK-633; it has not landed. `DUT_NO_RESTORE=1` is the
sanctioned interim path until it does.
**Ruled**: human, 2026-09-03 (TASK-618) and 2026-09-04 (Architect's decision E, with the refusal code
fixed at **3**).
**Design doc**: [M-HARNESS2 architect review](../designs/M-HARNESS2-architect-review.md) §6
**Requirement**: [R51](../../verification/M-HARNESS2-requirements.md), plus `F-19`
**Supersedes** the practice recorded at `run/lib.sh:16` ("ENV_PROD is deliberately NOT overridable:
every test script's trap restores production, and that must stay production") for test entry points.

---

**Context**

Fifteen scripts under `run/` carry an EXIT trap and a reference to `ENV_PROD` — `run/test`,
`run/test-targeted`, `run/test-sync`, `run/player-gate`, `run/wr-gate`, `run/stress`, `run/wr-soak`,
`run/pr-soak`, `run/pr-fetch-soak`, `run/ae04`, `run/task488`, `run/browser-player`,
`run/playorder-player`, `run/task424-repro`, and the shared `run/lib.sh` they all source. The trap's
whole job is to reflash production firmware no matter how the script exits. That safety control is
correct in the world it was written for and **hardened into an obstruction when the context
changed**: TASK-557 pins this board to the `-DBOD_WATCH` debug build, so a script that unconditionally
restores production cannot be run at all. The consequence is measured — an ~80-minute DUT session
that would settle **32 of 58** open items is unrunnable
([WP-Z §5](../../verification/reviews/M-TESTQUAL-Z-findings-review.md)).

The proposed fix was a `DUT_NO_RESTORE=1` opt-out. My review's objection stands and is the reason
this is an ADR rather than a flag: (1) it is a suppression flag on an unconditional side effect, so
the trap fires *sometimes* and every future reader must know which mode they are in to know what
state the board is in; (2) its justification has an expiry nobody owns — this repo's own
`wifi_creds.h` shim sat dead in the build for months (TASK-404); (3) it entrenches the real defect,
which is that a **test** entry point owns **firmware lifecycle**.

**Decision**

**D1 — a DUT entry point verifies and refuses. It never flashes and it never restores.** It reads the
board's build identity, compares it against what the run declares it needs, and refuses if they
differ. Flashing becomes an explicit caller action through the existing `run/flash*` scripts — which
is already how `run/flash-player`, `run/flash-webradio` and `run/screendump` behave; none of them
restores production. The trap is **deleted**, not guarded.

**D2 — the refusal code is 3, `[SETUP-FAIL]`, with a build-identity reason.** Not 4. The board is
present, addressable and responsive; what is wrong is that the host is pointed at a subject the run
did not ask for, and [M-TESTARCH precedence](../designs/M-TESTARCH-precedence-hierarchy.md) §4 rule 2
already places exactly this in the RIG vocabulary: `elf-mismatch` and `prod-firmware-flashed` are
named there, at exit 3. Exit 4 means "the board is not a valid subject" in the sense of *unfit* — a
HEALTH condition about the hardware's state, carrying `NOT-RUN` for every id.

*Recorded correction, because the corpus should not carry the older reading unchallenged:* my review
§6 recommended **exit 4**, and [PM review §5(c)](../../project/M-HARNESS2-PM-review.md) paraphrases
the ruling as "the 'not a valid subject' code", which in M-TESTARCH's vocabulary is 4. **Exit 3 is
correct and the 2026-09-04 ruling is right**: a wrong-build refusal is `elf-mismatch`, that reason is
already RIG, and routing it to 4 would have split one condition across two codes depending on which
script noticed it.

**D3 — `DUT_NO_RESTORE=1` is a dated interim exception, owned by TASK-618, and nothing else.** Its
retirement condition is TASK-633's conversion. Its ledger row is itself a blocking failure when stale
— the same discipline this programme imposes on every other exception. It is not the answer; it is
the thing that lets Phase 2 run before the answer lands.

**D4 — the cost is 1.5 days plus a `CLAUDE.md` update, and the review that called it small was
wrong.** @Developer's correction, recorded here because my review implied a two-script edit: the trap
is shared across the scripts enumerated in the Context, so the conversion is a change to the shared
lifecycle in `run/lib.sh` and to each entry point that inherits it, **plus** the `CLAUDE.md` run-script
table, which today promises a restore that will no longer happen. The documentation half is not
optional garnish — after this lands, *the board stays on whatever build the last flash put there*,
and a table that says otherwise is a trap of a different kind.

**D5 — the standing hazard is restated as part of this decision.** **Never kill a `run/flash*`, soak
or test script mid-flight.** It races the trap-guarded restore and can boot-loop the board. This is
recorded on this rig and it is the reason the answer to a pinned board was ever a flag rather than
Ctrl-C.

**D6 — verify-and-refuse is what makes ADR-066 D3 checkable.** The entry point must read build
identity to refuse, and the same value is the artifact's build-identity field. One mechanism, two
consumers; neither is speculative.

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| `DUT_NO_RESTORE=1` as the permanent answer | A suppression flag on an unconditional side effect, with an expiry nobody owns, entrenching the wrong ownership. Sanctioned only as D3's dated interim. |
| Make `ENV_PROD` overridable | Turns a safety control into a footgun: a mistyped env silently becomes "production" for the restore. The problem is the restore, not the constant. |
| Keep the restore and have the entry point re-flash the *debug* build it needs | Still puts firmware lifecycle in a test entry point, and inside a pinned-board window it is a flash inside a measurement window, which TASK-557 forbids. |
| Kill the script mid-flight when the board is pinned | D5. It races the restore and can boot-loop the board. |
| Entry points refuse with exit 4 (my review's recommendation) | D2 — splits `elf-mismatch` across two exit codes and re-labels a rig condition as a health one. |

**Consequences**

- *Easier*: any run can state which build it requires and get a loud, correctly-classified refusal
  instead of a silent reflash. `run/wr-gate`, which checks no build identity today (`F-19`), gains
  the check the player gate already has.
- *Harder*: the caller now owns getting the right firmware onto the board. That is a real ergonomic
  cost — two commands where there was one — and it is the price of the entry point no longer being
  able to destroy the state a test was investigating.
- *Constrained*: `CLAUDE.md`'s run-script table and `docs/process/dut_workflow.md` must change in the
  same commit, and the "always restores prod firmware on exit" promise must be **removed**, not
  softened.
- *Cost*: 1.5 days plus the documentation update (D4), not the afternoon my review implied.
- *Risk accepted*: a board left on a debug build after a run is a state a future session must notice.
  Verify-and-refuse is exactly the mechanism that notices it, which is why the risk is bounded by the
  same change that creates it.
