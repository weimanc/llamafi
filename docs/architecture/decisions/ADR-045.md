### ADR-045 — 2026-06-24 — WebRadio playback memory viability on no-PSRAM hardware

**Status**: accepted (2026-06-24)

**Context**:

The 2026-06-24 DUT session (TASK-232 → TASK-233) supplied the empirical heap data that
M-WEBRADIO.md §Memory budget explicitly deferred ("Audio decode + I2S buffers ~40–60 KB …
Empirical validation needed — run heap watermark logging on DUT"). The result invalidates the
budget's optimism on the production board (ESP32-2432S028R, **no PSRAM**):

- **Wall 1 (TASK-232, resolved):** HTTPS audio streams fail `connecttohost()` immediately with
  `ssl_client (-32512) SSL - Memory allocation failed` — the audio-stream mbedTLS handshake
  can't get its ~40 KB even after `spotifyTask::tlsYield()`. radio-browser's votes list is
  ~73% HTTPS, so the list was mostly unplayable. Fixed by filtering to `http://` streams and
  paging the list (see ADR-029 amendment for the cleartext-media decision).
- **Wall 2 (TASK-233, this ADR):** with HTTPS removed, HTTP streams connect and enter PLAYING
  but most die within ~5 s: `MP3Decoder_AllocateBuffers(): not enough memory`. The Helix MP3
  decoder needs ~29 KB across 9 separate buffers, allocated lazily when the first frame
  arrives. Measured at play entry: `free≈67 KB`, `maxAlloc≈39 KB` *pre-connect*, fragmented
  further by the input buffer + socket by decode time. Failure is **intermittent and
  fragmentation-dependent** — ~3 of 16 stations held ≥14 s in one scan, and the *same* station
  held one run and died the next. The TASK-218 watchdog is behaving correctly (it reports a
  genuine dead decode, not a false trip).

Both walls are the same root cause: a no-PSRAM board running the Winamp UI + WiFi + (primary)
Spotify + an audio decoder has no reliable internal-RAM headroom left for stream decode.

Forces: WebRadio is a secondary multiapp, not the product's core (Spotify is). We have not yet
attempted to *free* resident RAM for playback, nor measured the exact decode-moment gap or the
per-buffer Helix sizes — so we cannot yet say the gap is unbridgeable. But we also cannot ship a
feature that parks the UI on `ERROR_STALL` whenever a station fails to decode. A decision is
needed on (1) whether WebRadio stays in MVP scope on this hardware, and (2) what the user-visible
contract is while the memory question is resolved.

**Decision**:

WebRadio **remains in scope on no-PSRAM hardware as an explicitly best-effort feature — not
declared unsupported, not promised reliable.** The direction is three ordered moves; the
expensive one is gated on measurement.

1. **UX contract now — graduate auto-skip-on-stall from deferred (TASK-219 Tier 3) into MVP.**
   The user-visible behaviour must be "tunes past a dead station to a playable one," never
   "parks on a stall." The bounded retry→skip subset of the already-designed §Auto-retry/auto-
   skip policy becomes mandatory: on `ERROR_STALL`, retry once, then advance to the next
   station, bounded so it stops after scanning the list once and lands on the best result.
   `webRadioAutoSkip` **defaults ON** (was config-only/false) given the evidence — a tight-heap
   board is exactly where the user needs the skip. This converts TASK-233's intermittent decode
   failure from a hard stop into tolerable, self-healing degradation, and is cheap (designed,
   no new mechanism).

2. **Measurement spike — gates all memory-budget work.** Before any RAM surgery, instrument the
   exact failure point: free heap **and** `maxAlloc` captured around `MP3Decoder_AllocateBuffers`
   (not just pre-connect), plus the size of each of the 9 Helix buffers, to determine whether the
   wall is *total-headroom* (addressable by freeing RAM) or *single-block/contiguity* (not). The
   `maxAlloc` pre-connect log already added is step one. This honours the design's own "empirical
   validation needed" note and the project's measure-before-committing culture (BP-030).

3. **Conditional memory reduction (direction "free more RAM") — gated on the spike.** IF the
   spike shows a small total gap with no single-block wall, pursue freeing resident internal RAM
   during WebRadio playback: free `s_webRadioDoc` (5 KB) after the station fill (make it
   heap-alloc/free, not a permanent static); release Spotify-side display/response buffers while
   WebRadio owns the screen; audit other static buffers. IF the spike shows a contiguity wall or
   an unbridgeable total gap, escalate to declaring WebRadio **PSRAM-only** — gate the app behind
   a runtime PSRAM check (hide/disable the slot on no-PSRAM boards) rather than shipping a
   feature that can't decode.

**Rejected:** pre-allocating / reordering the Helix decoder buffers (the library lazy-allocates
on first frame) — it requires patching ESP32-audioI2S/Helix internals, a fork and maintenance
burden. Revisit only if (3) fails and PSRAM-gating is unacceptable.

**MVP exit criterion (supersedes the Tier-1-only criterion in M-WEBRADIO.md §Error states for
no-PSRAM hardware):** from cold entry on the no-PSRAM DUT, WebRadio reaches a stable PLAYING
state (holds ≥ 60 s) within ≤ 6 auto-skips on ≥ 90 % of attempts. If memory reduction lands and
raises first-station decode success, that is upside, not a separate gate.

**Consequences**:

- WebRadio ships *honest*: best-effort, self-healing via auto-skip; the user gets audio whenever
  any station decodes, and never a frozen UI. Spotify (the core feature) is unaffected — its TLS
  is yielded and resumed around playback (verified TASK-218/222).
- Auto-skip becomes load-bearing, not convenience — its bound and "stop after one pass" logic
  must be solid (a runaway skip loop would be worse than a stall). VE owns a test for the bound.
- The heavier memory work is deferred behind a cheap spike, so we neither abandon WebRadio
  prematurely nor sink effort into RAM surgery that the data might show is futile.
- A clean fallback exists (PSRAM-gating) if the gap proves unbridgeable — no open-ended risk.
- Sets precedent: secondary multiapps that need a large transient allocation must validate the
  no-PSRAM heap envelope empirically before MVP close, not from a paper budget.

**Amends**: ADR-029 (see its 2026-06-24 cleartext-media amendment for Wall 1 / TASK-232).
**Related**: TASK-232 (done), TASK-233 (this), TASK-218 (watchdog, verified), TASK-219 (Tier 3
auto-skip — graduated to MVP by this ADR).

### Amendment 2026-06-24 — RAM-recovery re-investigation sanctioned (TASK-239/240/241)

A post-decision RAM audit (PM-driven) found this ADR's "ceiling-bound, don't invest in memory
surgery" ruling rested on EXP-007's **as-is** heap measurement, which did not account for ~14 KB
of *reclaimable resident RAM* (`s_webRadioDoc` 5 KB + `s_heatmapDoc` 2.5 KB lazy-alloc; dataTask
stack 20 KB→~14 KB). The decoder needs free ≈ 65 KB to allocate; the failed 16 KB-buffer run had
59.5 KB. Reclaiming ~14 KB → ~73 KB could let the larger input buffer (the underrun fix) and the
decoder coexist — the scenario this ADR ruled out without testing.

**Architect position:**

1. **Re-investigation sanctioned; this ADR may be superseded.** ADR-045 stays `accepted` and in
   force *operationally* (auto-skip ships, no memory surgery beyond the planned reclaim). But
   TASK-241 (re-run the 16 KB-buffer experiment *with* the reclaim) is a **decision gate** whose
   DUT result feeds an amendment: PASS → supersede the "ceiling-bound / no memory surgery" stance
   with "stable via targeted reclaim"; FAIL → the 38.9 KB caps-restricted block is the wall, this
   ADR stands unchanged. Do **not** pre-commit the verdict or ship buffer-size changes before the
   gate.

2. **dataTask stack trim (TASK-240) — cross-feature ruling.** `dataTask` is shared by all fetchers,
   so the high-water mark MUST be taken against the **deepest** stack consumer, not a WebRadio
   fetch. Measure `uxTaskGetStackHighWaterMark` after a single session that exercises **every**
   fetcher at least once — weather, crypto, stock quote, stock chart, teletext (worst-case page),
   WebRadio (full multi-page paging) — and trim only to `(stack − min headroom seen) + ≥ 2 KB
   margin`, rounded up to 1 KB. Likely-deepest paths to be sure to hit: teletext grid parse and the
   WebRadio multi-page fetch. VE owns confirming the coverage. `spotifyTask` (10 KB) is tighter —
   mbedTLS handshake needs 6–8 KB stack — so leave ≥ 3 KB margin there or skip it.

3. **Fetch→playback fragmentation sequencing (TASK-239) — ruling.** Because contiguous-block
   availability is the core constraint, the lazy docs must not churn near the audio allocations:
   - `s_webRadioDoc`: alloc at fetch start, **free immediately after `appendHttpStations()` copies
     stations into the result struct** — before `tlsResume()` and long before any `_play()`. Never
     hold it across playback; never realloc during playback.
   - `s_heatmapDoc`: alloc/free within the heatmap fetch only (Stock app); never resident in
     WebRadio.
   - The frees must complete **before** the audio path's first allocation so the bytes coalesce
     back into the usable pool before the decoder needs its block. The existing `HEAP pre-connect
     free=… maxAlloc=…` log at `_play()` entry is the verification point — TASK-241 must confirm the
     reclaim actually raised free/maxAlloc at decode time, not just nominally freed memory elsewhere.
