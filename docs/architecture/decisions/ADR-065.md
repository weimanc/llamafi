### ADR-065 — [2026-09-04] — The serial console is a versioned interface (IFC-007), and it may push

**Status**: accepted
**As-built**: not yet — IFC-007 exists as of this ADR's commit; no protocol change has landed.
**Ruled**: human, 2026-09-04, on the Architect's decision C
([M-HARNESS2-architect-review.md](../designs/M-HARNESS2-architect-review.md) §9).
**Design doc**: [M-HARNESS2 architect review](../designs/M-HARNESS2-architect-review.md) §4.3, §7
**Requirements**: [R7, R25, R26, R27](../../verification/M-HARNESS2-requirements.md); findings
`C-18`, `C-2`, `H-8`
**Interface**: [IFC-007](../interfaces/IFC-007.md)

**Context**

`architecture.md:106-107` calls the `get`/`set`/`tap`/`drag`/`switchApp` protocol "the DUT test
surface for the whole VE suite". [M-TESTARCH](../designs/M-TESTARCH-test-architecture.md) §4 I1 calls
it "a contract, not a debug aid" and asserts "every `get` reply is a versioned, additive-only JSON
object". **It has no IFC number.** It is the seam the entire T3 tier is a client of, and it is the
only major seam in this system with no contract document, while IFC-004, IFC-005 and IFC-006 are
reserved stubs for smaller things.

The cost of that gap is already on the record. I1 "has been treated as already true" and is not:
`get wifiCfg` prints a bare bracket line and *then* a JSON ack carrying no fields
(`app/src/debug/serialConsole/cmdGet.cpp:202-214`), and `Dut.read_json()` discards every line not
starting with `{` (`app/tools/lib/dut.py:1086`) — so the one command that distinguishes TASK-426's
dead-SSID wedge from a genuinely absent AP is, from the harness's point of view, mute
([M-TESTARCH precedence](../designs/M-TESTARCH-precedence-hierarchy.md) §3(a)).

Two requirements then push on the protocol itself. **R25** wants correlated request/reply, because a
one-reply desync is currently undetectable (`C-18`, `C-2`) and `T-UART-01`'s `except` branch is
unreachable — but it is written as the document's only flag-day, touching every consumer at once.
**R26** wants `watch`/subscribe, which breaks the one-line request/response invariant that every
existing consumer assumes. Both are irreversible in practice once shipped.

**Decision**

**D1 — the console becomes IFC-007, a versioned interface.** Parties, transport, the reply object's
shape, the key namespace, the error vocabulary and the invariants are recorded there. The interface
document is authoritative over the requirement documents for protocol questions.

**D2 — correlated replies are optional and additive. There is no flag-day.** A caller **may** supply
a sequence id (`get#7 wifi`); when it does, and only then, the reply echoes it (`"seq":7`). A caller
that supplies none gets exactly today's reply, byte for byte. Consequences, all deliberate:

* every unpatched consumer keeps working with no change on the day this lands;
* `lib/dut.py` opts in immediately and gets desync detection for the whole suite in one file;
* **the ratchet is the count of non-correlated call sites**, which starts high and shrinks, rather
  than a migration that must complete before anything works.

R25 stays a MUST; what this decision refuses is its *shape*, not its substance.

**D3 — unsolicited event lines are permitted, and constrained.** The console may emit lines the host
did not request. Three constraints, all binding:

1. **Every unsolicited line is a JSON object carrying an explicit event marker** — it is
   distinguishable from a reply by its own content, never by timing or by position.
2. **No push key ships until every consumer discards unknown unsolicited lines safely.** The
   one-line request/response assumption is held by ~19 files and four separate `SerialDut` harnesses
   ([Dev review](../designs/M-HARNESS2-DEV-review.md) row 31); the first push line into an
   unprepared reader desyncs all of them, which is the exact defect R25 exists to detect. **R47's
   single-session-layer consolidation (TASK-599) is therefore a precondition of shipping any push
   key, not a parallel nicety.** Permitting push is not scheduling it.
3. **The pushable key set is derived mechanically from the polling loops it replaces** (R26's ~10
   keys), never authored. A subscribe surface that grows by hand becomes a second, un-gated key
   namespace.

*Recorded dissent, once, per the review record:* my review DEFERRED R26 on the grounds that async
push breaks a load-bearing invariant on the memory-constrained build for a win P4's evidence
suggested was correctness rather than speed. The ruling permits it and I record the constraints
rather than re-litigating it; D3(2) is where my objection lands as an obligation instead of a veto.

**D4 — additive-only, no renames, with the generated key list as the enforcement.** BP-024's rule
("field set VE-gated; extend, don't rename") stops being a comment on one command and becomes a
property of the surface, gated by `app/tools/gen/gen_get_keys.py`, whose full-tree scan landed with
TASK-600 (`gen_get_keys.py:48` globs `.h/.hpp/.cpp/.cc`; the key count went 43 → 111 the moment it
stopped globbing headers only). A key or field that disappears between two runs of the generator is a
`run/check` failure, not a test mystery discovered months later on hardware.

**D5 — the generator's completeness is itself gated.** R7's *generator-completeness* clause is
promoted to MUST: the key count is compared full-tree in `run/check`. A contract enforced by a
generator that cannot see half the firmware is not enforced — which is precisely the state TASK-600
found and fixed.

**D6 — what IFC-007 does not yet decide.** The document ships with its open items stated rather than
guessed: the reply object's version field and how it increments; the closed error vocabulary for a
refused key (ADR-063 D3's active-app refusal needs a named error, and it is the first client); and
the framing rule for a reply that must exceed one line. These are recorded as open in IFC-007, not
silently assumed.

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| R25 as a mandatory sequence id on every command (the flag-day) | Touches every consumer at once, on a surface with four independent harnesses; the additive form gets the same detection with a shrinking ratchet instead of a migration. |
| Leave the console undocumented and keep I1 in a design doc | I1 has been quoted as already true for months while `get wifiCfg` violates it in shipped code. A contract nobody can point at is not a contract. |
| Refuse push outright (my review's DEFER) | Overruled. D3's constraints carry the objection instead. |
| Version the console by a global protocol number consumers must negotiate | Nothing in this system can force a lockstep upgrade of firmware and host, and a negotiated version would add a failure mode where a mismatch is silent. Additive-only makes the version advisory, which is what an unbreakable protocol needs. |

**Consequences**

- *Easier*: a desynchronised console becomes detectable rather than a class of unattributable flake;
  a renamed field becomes a host-side, one-second `run/check` failure instead of a DUT mystery.
- *Harder*: the console acquires change control. Adding a key is free; removing or renaming one now
  costs a gate exception with an owner and a date.
- *Constrained*: **every** new console surface on this programme — ADR-063's delegated
  `dbgGet`/`dbgSet`, ADR-064's `get sig` and `set now`, R14's armed-injector enumeration — lands
  under IFC-007's additive-only rule and appears in the generated key list. There is no side door.
- *Cost*: D2 is small — an optional token in the parser and an echoed field. D4/D5 are largely
  already paid (TASK-600, DONE 2026-09-04). D3's precondition is the expensive one: TASK-599 is ~4.5
  days ([Dev review](../designs/M-HARNESS2-DEV-review.md) row 31), and it is the price of push, which
  is why push is permitted rather than scheduled.

ADR alone — R25/R26 were cut from the board by [PM review §4.1](../../project/M-HARNESS2-PM-review.md)
and are deliberately not rows. What this ADR does is **bind** the rows that touch the console:
TASK-600 (done), TASK-637, TASK-638, TASK-635 and TASK-599 all now land under IFC-007.
