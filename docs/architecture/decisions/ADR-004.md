### ADR-004 — 2026-04-27 — Optimistic UI updates on intent

**Status**: superseded by ADR-006 (2026-04-28)

**Superseded because**: this ADR was framed around the `IntentHandler` / `PlayerState` components introduced by ADR-001, which has itself been superseded. Under ADR-006 (UI-only swap on the Spotify-Diy-Thing baseline), there is no `IntentHandler` component for this rule to attach to. The *behavioural* intent — flip local UI state immediately on touch, fire the API call, let the next poll reconcile, debounce seek-drag to release — survives as an implementation pattern in `touchScreen.h` / `spotifyLogic.h`, not as an architectural decision. Recorded in `architecture.md` Target section instead.

**Context**:
Spotify Web API calls have round-trip latency typically in the 200–500 ms range over WiFi, sometimes worse. The poll cadence in the proposed tasking model is ~1 Hz. If the UI waited for the next successful poll to confirm the effect of a user action before updating visibly, every button press would feel laggy: a play/pause tap might take half a second to redraw the play button, and a seek-bar drag would not move until the following poll.

Three approaches were considered:

- **(a) Pessimistic** — issue API call, hold UI until poll confirms.
- **(b) Optimistic** — mutate `PlayerState` immediately on intent, issue API call in parallel, reconcile (and roll back if needed) on the next successful poll.
- **(c) Optimistic + speculative poll** — same as (b) but trigger an extra `/me/player` poll shortly after the API call resolves, to cut reconciliation latency from ~1 s to ~250 ms.

Forces:
- The system is a controller; users expect near-instant feedback similar to a phone app.
- API calls can fail (network, token expiry, device unavailable). The UI must not lie indefinitely.
- The Winamp aesthetic includes a moving seek bar and an animated play/pause button — both benefit visibly from immediate response.

What needs a decision: how `IntentHandler` (per ADR-001) interacts with `PlayerState` and the Spotify transport.

**Decision**:
Adopt option **(b)** with provision for (c) as an optional refinement (see Consequences).

Rules:

- On every intent emitted by the `Input` leaf, `IntentHandler` first applies the expected effect to `PlayerState` immediately, then issues the corresponding Spotify API call.
- For `PlayPause`, `Next`, `Prev`, `ToggleShuffle`, `ToggleRepeat`, `VolumeSet`: the local mutation is the obvious one (flip `is_playing`, advance/reset track placeholder, set the flag, set volume).
- For `SeekTo(ms)`: `position_ms` snaps to the requested position immediately; the interpolator continues from there.
- On API success: nothing further until the next poll updates state authoritatively.
- On API failure: an error is recorded in `PlayerState.last_error`; the optimistic mutation is *not* rolled back synchronously. The next successful poll reconciles state to ground truth, which will undo the local mutation if the action did not take effect.
- During a seek-bar drag: position updates locally on every drag event for visual feedback; the API `seek` call is fired only on drag release (debounce). This avoids hammering the API and the rate limit.
- Track-change intents (`Next`, `Prev`) do not attempt to predict the next track id; they clear track-derived fields (title, artist, duration, VU analysis) and mark the track as transitioning until the next poll fills it in.

**Consequences**:
- *Easier*: UI feels responsive; the seek bar tracks the finger; play/pause flips instantly. The `Renderer` does not need any special "pending" state.
- *Harder*: Brief visual glitches are possible when an action fails or another client (phone app) overrides state between an intent and the next poll. Accepted as the cost of responsiveness.
- *Constrained*: `PlayerState` mutations on intent must be safely reconcilable — no field may be derived from optimistic state in a way that cannot be corrected on the next poll.
- *Optional refinement* (c): once the system is stable, `IntentHandler` may schedule a one-shot poll ~250 ms after a successful API call to shorten the reconciliation window. This is a tuning knob, not a separate decision.
- *Out of scope*: a UI-level "undo" or toast on rollback. If the next poll contradicts the optimistic mutation, the UI silently snaps to the truthful value.
