### ADR-006 — 2026-04-28 — Stay on Spotify-Diy-Thing baseline; UI-only swap

**Status**: accepted

**Supersedes**: ADR-001 (layered core + platform leaves), ADR-004 (optimistic UI as architectural decision), ADR-005 (single `PlayerState` with locally interpolated position as architectural decision).

**Context**:
ADR-001 proposed a portable `core/` + per-target `platform/` leaves layout, with a PC-mirror build target as a first-class peer of the DUT firmware. ADR-004 and ADR-005 specified component-level discipline (`IntentHandler`, `PlayerState`) that only made sense inside that layered shape.

On review, the project's actual constraint is narrower: the `Spotify-Diy-Thing/` firmware works, its toolchain works, its persistence model works, and its OAuth bootstrap works. The thing the user wants to change is the **UI** — replace the simple track + album-art screen with a Winamp 2 classic skin, and extend touch input to drive more controls. Nothing else.

The layered proposal pays a large abstraction tax (every hardware dependency expressed as an interface, every capability implemented twice, a host build target with its own toolchain) for benefits the project does not need. The PC mirror is convenient for UI iteration but is not a requirement.

What needs a decision: the architectural shape of the target system, given the new constraint that the baseline is preserved wherever possible.

**Decision**:
Keep the Spotify-Diy-Thing baseline architecture. Change the UI; leave everything else.

Specifically:

- **Toolchain**: Arduino + PlatformIO + `espressif32@6.9.0`, env `cyd2usb`. Unchanged.
- **Super-loop in `loop()`**: kept. No FreeRTOS task split, no portable `core/`.
- **`SpotifyArduino` library**: used directly, no wrapper, no `SpotifyTransport` interface. Extended (or its usage extended) to cover seek, shuffle, repeat, volume, and the `audio-analysis` endpoint per ADR-002. Whether to extend the library, fork it, or add small helpers alongside it is a downstream decision (Open Question), not an architectural one.
- **Persistence**: SPIFFS for Spotify creds + refresh token; NVS for WiFi creds (managed by WiFiManager). Unchanged.
- **OAuth bootstrap**: `get_refresh_token.py` host-side, bake into SPIFFS. Unchanged.
- **Display abstraction**: `spotifyDisplay.h` survives as the seam. The current `cheapYellowLCD.h` implementation is replaced by a Winamp-skin renderer (new file). The `matrixDisplay.h` / HUB75 backend is dropped from scope.
- **Touch input**: `touchScreen.h` extended from three hard-coded zones (prev / dead / next) to skin-region hit-testing driven by the baked layout table from ADR-003. Same XPT2046 polling discipline.
- **Polling**: `spotifyLogic.h` keeps its current poll cadence and structure. Extended to also fetch `audio-analysis` once per track change (per ADR-002) and to interpolate `progress_ms` between polls so the seek bar advances smoothly. Interpolation is a few lines in the existing loop, not a separate component.
- **Skin assets**: baked at build time per ADR-003, emitted as C arrays compiled into the firmware. No runtime skin parser.
- **VU meter**: synthesised from cached `audio-analysis` per ADR-002, contained in one new module. Not elevated to a `VuSynth` component in a layered architecture.

**No PC mirror.** UI iteration is on the DUT. If a host-side preview becomes necessary later, it can be added without disturbing the firmware structure (e.g. a thin SDL harness around the renderer module), and that is a future ADR if it ever happens.

**No `IntentHandler`, no `PlayerState` as a canonical shared model.** State lives where the baseline puts it: in the `SpotifyArduino` instance and in module-local globals. UI feedback on user actions (the concern that motivated ADR-004) is handled inline in the touch handler and renderer — flip the local play/pause flag immediately, issue the API call, let the next poll reconcile. This is a coding pattern, not an architecture.

**Consequences**:
- *Easier*: minimal new abstractions, minimal new build complexity, minimal divergence from a working baseline. Most of the existing firmware code keeps working unchanged.
- *Harder*: UI iteration requires a flash cycle; no host-side preview. Accepted given project scope.
- *Constrained*: position interpolation, optimistic UI feedback, and VU synthesis live as small additions to existing files (or one new module each), not as a layered component graph. Discipline carries the rest.
- *Open*: whether to extend `SpotifyArduino`, fork it, or add helpers — tracked as an Open Question in `architecture.md`.
