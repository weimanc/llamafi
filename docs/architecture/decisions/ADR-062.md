### ADR-062 — [2026-08-27] — Resolve the DUT port by stable identity, not enumeration order

**Status**: accepted
**As-built**: 2026-08-27, same commit as the fix (TASK-547).

**Revised from the initial decision below** (kept for the record, not rewritten): the first fix
re-scanned `/dev/ttyUSB*` fresh at restore time. The actual root fix is R1 — prefer
`/dev/serial/by-id/`, udev's own persistent symlink, over `/dev/ttyUSBn` entirely, everywhere a
port is resolved. `/dev/ttyUSBn` is assigned by enumeration order, which is exactly what goes stale;
`/dev/serial/by-id/usb-1a86_*` is assigned by device identity and updates itself under the same path
across a re-enumeration, so nothing downstream needs to re-resolve anything — the path handed out at
script start (and the one `lib/dut.py`'s `resolve_port()` gets too, since it shells out to
`run/port`, which shares this fix) stays valid for the device's entire session. The restore-time
rescan (R2, below) is kept as a second layer for the fallback path (no `/dev/serial/by-id/` — no
udev, or a stripped environment) and for an explicit `PORT=/dev/ttyUSBn` override, both of which stay
exposed to enumeration-order drift by construction.

**One limit worth recording, confirmed against `dmesg` after this fix landed**: this project's CH340
boards report `SerialNumber=0` — no per-unit serial in the USB descriptor — so `/dev/serial/by-id/`
names the *port role* ("the CH340 currently attached"), not a specific physical unit. Verified live:
swapping the physical DUT mid-session, the symlink transparently followed the new unit and an
in-flight `run/test-targeted` run completed cleanly through the flash/test/restore cycle without
interruption. This is exactly the rig's actual usage pattern (one DUT at a time) and needs nothing
further. It would NOT disambiguate two CH340s attached simultaneously — `/dev/serial/by-path/` is
the fallback for that (topology-based, tied to the physical port instead of device identity), not
attempted here since nothing in this project runs multiple DUTs concurrently today.

**Context**

Every `run/*` DUT script (`run/test`, `run/test-targeted`, `run/player-gate`) follows the same
shape: `PORT=$(resolve_port)` once near the top, then a `trap _cleanup EXIT INT TERM` whose whole
job is to reflash production firmware and restart the monitor no matter how the script exits — the
safety net the rest of this project's DUT tooling is built on top of (BP-020/BP-021, CLAUDE.md's
"Minimum safety gate", every `run/test*` docstring). `_cleanup()` reuses the same `$PORT` value
cached at script start for that restore flash, unchanged, in all three scripts.

`resolve_port()` (`run/lib.sh`) already carries a comment recording that this class of bug shipped
once before: an off-by-one path bug meant a *different* copy of the resolver (`lib/dut.py`) silently
kept asking for `/dev/ttyUSB0` after the CH340 re-enumerated to `ttyUSB1`. That copy was fixed. The
underlying hazard — a CH340 device path is not guaranteed stable for the multi-minute duration of a
DUT session — was not: nothing re-checks it before the one operation that must not get it wrong.

**Live incident, 2026-08-26.** A `run/test-targeted T087,T091` run: debug firmware flashed
successfully to `/dev/ttyUSB1` (step 2/6). The device re-enumerated (confirmed via `lsusb` showing a
new bus device number — a real USB-level event, cause undetermined; kernel `dmesg` is
permission-restricted on this host for this user, so the specific trigger — ESP32 reset pulse
coupling into the CH340, a marginal connection, or something else — could not be confirmed either
way) to `/dev/ttyUSB0` before the trap fired. The exit-trap restore, still holding `/dev/ttyUSB1`,
failed outright:

```
A fatal error occurred: Could not open /dev/ttyUSB1, the port doesn't exist
ERROR [test-targeted]: prod restore failed
[SETUP-FAIL] rig condition — NO TESTS RAN
```

The DUT was left on debug firmware, requiring a manual `./run/flash` to recover. The one guarantee
every `run/*` script's docstring makes — "always restores prod firmware... on exit" — did not hold,
for a class of failure the codebase had already seen and only partially fixed.

**What doesn't work: calling `resolve_port()` again at cleanup time.** `resolve_port()` checks
`${PORT:-}` first and returns it unchanged if set — this is intentional, it's what makes the
documented `PORT=/dev/ttyUSB1 ./run/test` override work. But every script sets the shell variable
`PORT` from `resolve_port()`'s own first call, so by the time `_cleanup()` runs, `$PORT` is a set
variable in the same shell process and a second call to `resolve_port()` short-circuits straight
back to the stale cached value. A naive fix is a no-op.

**R1 — implementation.** `_scan_ch340_port()` (`run/lib.sh`) now checks `/dev/serial/by-id/usb-1a86_*`
first and returns the symlink path directly if found; only falls through to the `/dev/ttyUSB*`
VID:PID loop below if no `by-id` entry exists. `resolve_port()` and `run/port` are unchanged apart
from delegating to this — so `lib/dut.py`'s Python-side `resolve_port()` (which shells out to
`run/port`) inherits R1 with no code change of its own, same as the design's original intent ("the
shell layer owns that fact").

**Decision (R2 — the restore-time rescan, now the fallback layer)**

Split the live VID:PID scan out of `resolve_port()` into its own function, `_scan_ch340_port()`, and
add `restore_port(at_start, was_explicit)`:

- If the script's original `PORT` was an **explicit user override** (the `$PORT` environment
  variable was already set before the script's own `resolve_port()` call), `restore_port()` returns
  it unchanged. An explicit override is a statement of intent — "use exactly this port" — for
  multi-rig setups or manual pinning, and the restore step must not second-guess it.
- Otherwise, `restore_port()` re-runs the live VID:PID scan and returns whatever it finds *now*,
  logging the change if the port moved. If the rescan itself fails (device genuinely gone, `udevadm`
  unavailable), it falls back to the value cached at script start and warns — no worse than today's
  behavior, never silently swallowed.

Each of the three scripts captures `_PORT_EXPLICIT="${PORT:-}"` immediately before its own
`PORT=$(resolve_port)` call, and their `_cleanup()` calls `restore_port "$PORT" "$_PORT_EXPLICIT"`
to get the port for the restore flash and the monitor restart, instead of using `$PORT` directly.

**Scope, deliberately narrow.** Only the exit-trap restore step changes. The scripts' *other* uses of
`$PORT` (the initial debug/leg flash, the DUT session used to run the actual tests) are left as a
single resolution each — those are one-shot operations close to their own `resolve_port()` call in
wall-clock time, and if the device moves between resolution and that first use, the failure is loud
and immediate (`SETUP-FAIL port-busy` / esptool's own "port doesn't exist"), correctly categorized as
a rig condition rather than silently wrong. The restore step is different in kind: it can run
minutes after `PORT` was cached, it is the thing every other script's safety promise depends on, and
today it had zero resilience to exactly the failure this ADR's own incident produced.

**Consequences**

- *Easier*: a mid-run CH340 re-enumeration no longer defeats the trap-guarded restore. The DUT comes
  back on production firmware even if its device path moved since the script started.
- *Harder*: nothing meaningfully new — `restore_port()` is a pure function, unit-testable without a
  DUT (feed it canned `at_start`/`was_explicit` values and a stubbed scan).
- *Constrained*: the fix depends on `_scan_ch340_port()` staying a pure live scan with no `$PORT`
  short-circuit of its own — any future edit to `resolve_port()` must keep that split intact, or the
  restore step silently regresses back to today's behavior.
- *Out of scope*: root-causing *why* the CH340 re-enumerated (no `dmesg` access on this host for this
  user; would need `sudo` or a udev rule capturing the event). This ADR makes the failure survivable,
  not diagnosed away.
