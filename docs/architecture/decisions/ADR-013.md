### ADR-013 — 2026-05-08 — DMA SPI for display blits — **deferred**

**Status**: rejected (for now) — measurement-driven; documented rationale below for future revisit.

**Context**:

TASK-032 was queued as the second M-PERF tier-2 ADR after TASK-031 (async Spotify HTTP). The original framing: TFT_eSPI's `initDMA` / `pushImageDMA` overlap blit transfers with CPU work; candidates were `repaintChrome` (~32 KB), `screenLog::tick`'s `fillScreen` (153 KB) + chrome repaint, `blitMainBackground` (64 KB).

After 031 shipped, the heartbeat data is:

```
loop_max=16ms slow=spotify.poll:8ms
```

The 8 ms `slow=spotify.poll` is now dominated by the snapshot read + the display calls that follow it (`printCurrentlyPlayingToScreen` + `displayTrackProgress`). Display IS the loop's worst path now. So in principle DMA-ifying it should help.

**Why we're not doing it:**

The hoped-for DMA win is "blit happens in the background while the CPU does other work." Walking through our actual hot paths:

1. **`repaintChrome` (only fires from `showDefaultScreen` and `screenLog::tick`):** the sequence is `blitMainBackground` → `drawTransportButtons` → `drawStatusIndicator` → `blitSprite(POSBAR_BG)` → `drawTimeDigits` → `drawTitleText`. **Every one of those is itself a SPI write.** While DMA is moving 64 KB of MAIN_BG to the panel, the CPU has nothing useful to do — the next blit also needs the same SPI bus. CPU + DMA are racing for the same single shared resource.

2. **`screenLog::tick`'s `fillScreen`:** same problem. After fillScreen, every drawString call drives SPI. The CPU's "free time" during DMA is pinned by the next blit's wait.

3. **`blitMainBackground` standalone (e.g. on track change):** could in theory free the CPU for ~12.8 ms (64 KB at 40 MHz SPI). But this is called rarely — the chrome doesn't repaint on track changes; `printCurrentlyPlayingToScreen` only repaints the title slot region. The benefit is mostly latent.

In short: **all our display work funnels through one SPI bus. CPU-vs-DMA parallelism doesn't pay when both want the same bus.** DMA shines on systems where the CPU has truly independent work (PSRAM-backed framebuffer, async network sockets needing servicing during a blit) — that's not us. Our loop is already short (~16 ms) precisely because we just moved network IO off it.

**Higher-ROI alternatives (cheap, recorded for follow-up):**

- **Bracket multi-blit chrome paths with `tft.startWrite()` / `tft.endWrite()`.** Keeps CS asserted across the sequence, eliminates per-pushImage chip-select toggle + addr-window setup overhead. ~3–10 % gain on `repaintChrome` based on TFT_eSPI usage notes. ~10 LOC. **Yes, ship this** — captured below as a follow-up task.
- **Touch press-feedback state machine (TASK-034).** Replaces the 80 ms `delay()` in `checkForInput` with a millis-deadline. Direct 80 ms reduction on touch-press latency in the worst case. Already on the backlog; keep it priority-up.
- **screenLog incremental redraw** — only the newly-arrived line. Saves ~85 % of screenLog SPI traffic. Bigger work; only worth it if the overlay becomes primary, which today it isn't.

**When to revisit DMA:**

- If we add a non-display source of CPU work that runs in parallel with blits (e.g. JPEG decode for album art moves to a non-blocking task — TASK-014). That genuinely creates CPU/DMA parallelism.
- If we ever switch to a wider data path (parallel 8/16-bit interface to the TFT, not SPI). Different math entirely.
- If the chrome repaint surface grows substantially (M-CHROME tier 2: TITLEBAR + VOLUME) and the cost rises measurably.

**Tracked as**: this ADR closes TASK-032 with verdict deferred. New TASK-038 picks up the cheap startWrite/endWrite bracketing.
