### ADR-042 — [2026-06-08] — Harness–DUT synchronisation: bgPoll isolation + HTTPClient log suppression

**Status**: accepted

**Context**

The DUT regression harness (run_serialdbg_tests.py) has accumulated 8 timeout-related
fix commits in 30 commits, all targeting network-dependent tests (T-BUSY-*, T-CDWN-*,
T169, T_WX_*, T_CX_*). Audit identified three root causes:

1. **UART garbling**: The ESP32's HTTPClient debug log runs on Core 0 and interleaves
   with serial command responses from Core 1, splitting JSON lines. The harness recovers
   with blind 3 s sleeps and retries.

2. **Background poll races**: The Spotify background poll task advances `fetchOkCount`
   and `shellBusy` concurrently with test operations. The harness cannot distinguish
   "the fetch triggered by my tap" from "a background Spotify fetch", forcing defensive
   stacking of multiple completion-verification mechanisms.

3. **No synchronisation contract**: No authoritative rule specifying which mechanism
   owns which scenario. Tests evolved by trial-and-error, stacking
   `_wait_shell_not_busy()` + `_wait_chart_complete()` + `time.sleep()` in combination
   until locally stable.

Full design exploration and VE review in `docs/architecture/designs/harness-sync-rethink.md`.

**Decision**

Adopt Option E from the design doc: two surgical firmware additions plus a harness
synchronisation contract.

**E1 — Suppress HTTPClient verbose log in the debug build.**
Add `-DCORE_DEBUG_LEVEL=1` to the `cyd2usb_winamp_debug` env build flags and call
`esp_log_level_set("HTTPClient", ESP_LOG_NONE)` + `esp_log_level_set("HTTP_CLIENT",
ESP_LOG_NONE)` in `setup()` under `#ifdef SERIAL_DEBUG`. This eliminates Core 0 serial
noise without restructuring RTOS tasks or adding a mutex. E1 is gated by T-UART-01
(empirical garbling test — see design doc).

**E2 — Add `set bgPoll 0/1` debug command to `spotifyTask`.**
A `volatile uint8_t s_bgPollEnabled` flag (default: 1) gates self-initiated background
polls. `dbg_set("bgPoll", "0")` suspends them; `dbg_set("bgPoll", "1")` resumes.
Explicit `ACT_FORCE_POLL` queue entries bypass the flag. `resetTls()` unconditionally
resets the flag to 1 — `reconnect` is a recovery operation and must restore the task
to its fully operational default state regardless of any prior suspension.

**E3 — Establish a harness synchronisation contract.**
`_bgpoll_suspended(dut)` is a context manager (not a monolithic `_isolated_op`) that
wraps only the bgPoll suspend/resume. Pre-conditions are explicit at each call site.
Blind `time.sleep(N > 0.5)` is prohibited in test bodies except at documented
firmware-side delays (inline comment required). Combined sleep budget across T-BUSY-01,
T-BUSY-01b, T-CDWN-02, T169 must total ≤ 4 s post-refactor. Contract committed to
`docs/process/harness_sync_contract.md`.

**Deferred: Option D (seq-tagged async completion events).** The correct long-term fix
is for the DUT to emit per-operation completion events (eliminating the `shellBusy`
polling model entirely). Deferred pending burn-in evidence after E1+E2.

**Consequences**

- T-BUSY-*, T-CDWN-*, T169 are expected to stabilise without per-test defensive sleeps.
- The debug build loses HTTPClient verbose log on the primary UART. If HTTP-level
  diagnosis is needed, a `get log` ring-buffer (future work) or secondary UART can
  provide it. This is an accepted trade-off.
- `bgPoll` suspend/resume introduces new test infrastructure state. Tests must always
  resume bgPoll — the `_bgpoll_suspended` context manager `finally` block is the
  enforcement mechanism. A leaked suspend (harness crash mid-test) will cause the DUT
  to appear frozen on subsequent tests; the harness entry guard (`get bgPoll` →
  `set bgPoll 1` if `enabled:0`) mitigates this.
- `resetTls()` resets `s_bgPollEnabled = 1` unconditionally (SERIAL_DEBUG guard). This
  is an invariant: reconnect always restores full operational state.
- Firmware identity is verified at harness startup by elf-hash comparison
  (`_verify_debug_firmware()` extended to issue `info` and compare `elf` field against
  `.pio/build/cyd2usb_winamp_debug/firmware.bin+0x20+144`). A build compiled without
  E1 flags produces a different elf hash and fails fast with reflash instructions.
- Three new test cases cover the bgPoll command surface: T-BGPOLL-01 (suspend/verify),
  T-BGPOLL-02 (reconnect resets flag), T-BGPOLL-03 (force-poll bypasses suspension).
- The `shellBusy` polling mechanism remains in place. It is NOT deprecated by this ADR
  — it is given a defined role (pre-condition check only) within the synchronisation
  contract. Full deprecation requires Option D, which is deferred. If Option D
  (seq-tagged events) is adopted in a future ADR, `get shellBusy` must be removed from
  the debug command surface in that same ADR — not deprecated separately. Splitting the
  removal would recreate the mechanism-ownership ambiguity this ADR is resolving.
- VE must update affected test specs to replace stacked `_wait_shell_not_busy` calls
  with `_bgpoll_suspended` + explicit pre-conditions per the updated sync contract table
  in the design doc.

**Supersedes**: nothing. Related: ADR-021 (serial debug framework), M-SERIALDBG design.
