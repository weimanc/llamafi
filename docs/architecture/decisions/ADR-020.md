### ADR-020 — 2026-05-16 — Speculative post-intent poll for track-change actions

**Status**: accepted (2026-05-16, Architect close of M7 open question)

**Context**:

The async poll task (`spotifyTask`, TASK-031b) runs `getCurrentlyPlaying` at a base cadence of `kPollPeriodMs = 5000 ms`, with exponential backoff on failures. Optimistic UI (ADR-004) flips local state immediately on touch — play/pause, volume, shuffle, repeat all look correct the instant the user taps, with reconciliation at the next poll.

Two actions resist optimistic display:

- **`ACT_NEXT` / `ACT_PREV`** — The new track is unknown until Spotify responds. With shuffle enabled the new track is entirely unpredictable; even without shuffle the firmware does not maintain a local track queue for "next" prediction beyond the rendered playlist strip. The display stays on the previous track name, album art, and metadata for up to 5 seconds (or longer if backoff is active).
- **`ACT_SEEK`** — Position interpolation (ADR-005) tracks visual progress locally, but if Spotify snaps the seek to a different position (e.g., it rejects a seek past `durationMs`) the interpolated bar will diverge until the next poll.

Architecture.md proposed "a speculative one-shot poll ~250 ms after a successful intent to shorten the reconciliation window." The question is whether to implement this and for which actions.

**Rate-limit analysis**:

Spotify's unofficial Web API rate ceiling is ~180 req/min per application. Current steady-state: 12 req/min at 5 s cadence. A speculative poll adds 1 req per relevant action. Even at a sustained 10 track-changes per minute (extremely high for a Spotify controller), total request rate = 12 + 10 = 22 req/min — well within the ceiling. No rate-limit risk for any realistic usage pattern.

**Decision**:

Implement speculative post-intent poll for **`ACT_NEXT` and `ACT_PREV` only**. After a successful API call for either action, the task waits `750 ms` then executes an immediate poll (equivalent to `ACT_FORCE_POLL`) before returning to the normal `xQueueReceive` wait.

- **750 ms delay** rather than the 250 ms originally sketched — gives Spotify's API time to update the playing context before the poll fires. Empirical: Spotify's Next endpoint typically propagates in 200–600 ms; 750 ms catches >95 % of cases. If the speculative poll still sees the old track (Spotify hasn't propagated yet), it is treated as a normal poll result and the regular cadence takes over — no retry loop.
- **Not for `ACT_SEEK`** — position interpolation already handles the visual gap acceptably. Seek reconciliation at the next regular poll is sufficient; the user is not waiting for new metadata.
- **Not for `ACT_PLAY / ACT_PAUSE / ACT_VOLUME / ACT_SHUFFLE / ACT_REPEAT`** — all are fully handled by optimistic UI. A speculative poll would only waste a request slot.

**Implementation**:

In `spotifyTaskStorage.cpp`, after the `ACT_NEXT` / `ACT_PREV` branch executes its API call successfully, insert:

```cpp
vTaskDelay(pdMS_TO_TICKS(750));
doPoll();   // same helper called on ACT_POLL / ACT_FORCE_POLL
```

No new queue messages, no state flags. The task self-sequences synchronously within the task body. Backoff counter is not incremented if the speculative poll succeeds; if it fails, normal backoff rules apply (same as any other poll failure).

The existing `ACT_FORCE_POLL` path (used by the `reconnect` serial command and the logo-tap TLS reset in M-CONN) is unchanged — it remains an externally-enqueued action. The speculative poll here is internal to the task body.

**Why not a shorter delay (250 ms)**:

250 ms is at the low end of Spotify's typical propagation window observed informally. Polling too early reliably returns the stale track, making the speculative poll useless and consuming a request slot for no benefit. 750 ms costs one extra second of latency (vs. no speculative poll) in the failure case, which is imperceptible. The floor is not 250 ms.

**Why not poll for all control actions**:

Adding a 750 ms post-poll to play/pause inflates the effective touch-response time for those actions from ~50 ms (optimistic flip) to ~800 ms before the task is ready to process another action. For high-frequency or rapid-fire controls, this degrades responsiveness. Actions where optimistic UI is sufficient must not pay the speculative poll cost.

**Consequences**:

- *Better*: Track name, artist, album art, and duration update within ~1–1.5 s of a next/previous action instead of waiting up to the full 5 s poll period.
- *Constrained*: The 750 ms window is empirical; if Spotify's propagation is consistently faster on a given network (e.g., local Wi-Fi with low RTT), the delay can be reduced. If consistently slower (high-latency mobile hotspot), increasing to 1000 ms is safe under rate-limit analysis. Treat as a tunable constant `kPostTrackChangeDelayMs`.
- *No change* to the queue protocol or task priority. The task remains single-threaded; no concurrent polls are possible.

**Closes**: "Spotify rate-limiting headroom — the optimistic-UI pattern allows a speculative one-shot poll ~250 ms after a successful intent to shorten reconciliation" from `architecture.md` Open Questions.

**Tracked-as**: new sub-task under M7 (or inline in M-PERF tier-1 if instrumentation lands first).
