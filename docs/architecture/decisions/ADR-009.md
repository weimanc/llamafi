### ADR-009 — 2026-05-07 — VU meter data source after Spotify deprecated audio-analysis

**Status**: accepted (supersedes ADR-002)

**Context**:

ADR-002 chose Spotify's `audio-analysis` endpoint as the data source for the Winamp VU meter. During the M1 spike (2026-04-29, TASK-007 DUT run) both `/v1/audio-features/{id}` and `/v1/audio-analysis/{id}` returned **HTTP 403** for this device's client app. Spotify deprecated those endpoints for new Developer apps in late 2024 (Web API change-log). The dev app `db2ff394…` was created post-deprecation, so it has no access — and an account in default ("Development") quota mode cannot regain access without a manual approval cycle.

ADR-002's premise no longer holds. We need a new data source decision before any VU code lands. The renderer (M6) is otherwise blocked, but no other milestone depends on this — TASK-010 has been parked until now.

The four candidates from the original ADR are reconsidered against the post-deprecation reality:

- **(a)** Synthesise from `audio-features` only. **Now also dead** — the same 403 applies. Equivalent to (e) below.
- **(b)** Synthesise from `audio-analysis`. **Dead** — primary blocker.
- **(c)** Apply for Spotify "Extended Quota Mode". Manual review; weeks to months; no guarantee it's granted for a hobbyist project; doesn't unblock the milestone.
- **(d)** On-device I²S microphone. Honest spectrum but contaminated by room noise; needs a hardware addition (mic + bias network); decouples VU from "what Spotify is sending" since the device just listens to whatever's audible.
- **(e)** Synthesise from `currentlyPlaying` only. The endpoint we *do* have access to gives us track id, position, duration, is_playing, and (sometimes) `track.tempo` indirectly via the embedded simplified-track object. We can drive a coarse envelope from elapsed position + a hand-tuned shape, and key transients off a synthetic beat clock derived from a fixed BPM (no per-track tempo without `audio-features`).

**What needs a decision**: which data source the VU synthesis module consumes — given that the original choice (b) is no longer reachable.

**Decision**:

Use option **(e)** — synthesise from `currentlyPlaying` data only — for the first cut. Keep option **(c)** (Extended Quota request) as a parallel non-blocking track: if it's granted later, the synthesis module gets a richer input, but neither M6 nor any user-visible milestone is gated on it.

Synthesis sketch (implementation refinement intentionally deferred):

- A 20 Hz tick inside the super-loop reads `progressMs` and `is_playing` from the cached `currentlyPlaying` snapshot.
- The envelope is a synthetic shape: a slow swell modulated by track index (so consecutive tracks differ visibly) plus a per-tick noise floor for "alive" jitter. No claim that this tracks real audio.
- Beat clock: assume a flat 120 BPM unless we later acquire tempo. Inject a short transient on every beat boundary derived from the beat clock + a per-track phase offset (cheap pseudo-random from track id).
- Stereo split: mirror the mono envelope across L/R with a slow ±15 % LFO so the two channels visibly differ.
- On pause / stop / no-track, the envelope decays to zero with the same release time the renderer uses.

Explicitly **not** done in (e):

- No claim to be music-locked. Read the source comment as "this is decoration, not visualisation."
- No tempo per track. If/when (c) lands, swap the beat-clock module for a real-tempo-driven one without touching the renderer.
- No spectrum bins beyond two channels (mono envelope split). The Winamp VU needle pair only needs two values.

**Why not (d) [microphone]**:

- Hardware addition (analog mic + bias + I²S wiring) on a board that's already at 96.8 % flash.
- Room noise contamination is qualitatively wrong for a *Spotify* visualiser — the VU would react to people talking next to the device.
- ESP32 ADC noise floor on the CYD has known issues; calibration burden out of proportion to a decorative feature.

**Why (e) over (c)-only**:

- (c) is unbounded in time and may never land. Shipping a decorative envelope today is strictly better than blocking M6 on Spotify's review queue.
- The synthesis interface ((c) result feeds an envelope generator) is the same regardless of input source, so promoting (c) to drive (e)'s envelope module later is a code-local change.

**Consequences**:

- *Easier*: M6 is unblocked. Implementation is bounded — no new endpoints, no new hardware. Failure modes are all visual (envelope looks wrong) rather than runtime (network errors). Synthesis can ship at any tier of fidelity.
- *Harder*: Setting honest expectations in commits and the user-facing config — the VU is decorative; calling it a "level meter" would mislead.
- *Constrained*: Adding a real audio source later (microphone or, in some hypothetical world, on-device decode) means revisiting this ADR.

**Tracked as**: TASK-010 transitions from `open` to `in_progress` when implementation starts; renames `vu-001` from "audio-analysis-driven" to "synthesised-from-currentlyPlaying" in the feature inventory.

**Open**:

- Whether to expose a kill-switch (`VU_DECORATIVE = false` to render the rect as static skin art) — defer to implementation.
- Beat-clock seeding: hash of track id vs. position-at-start vs. always 0. Defer.
- Whether (c) Extended Quota application is worth the form-fill if the VU module abstraction is good enough that swapping inputs is trivial — bias toward "yes, file it once and forget" but not on the critical path.
