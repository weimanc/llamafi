### ADR-040 — [2026-06-05] — WifiSection extends SettingsSection (not standalone WifiFlow)

**Status**: accepted

**Context**

`wifi-settings.md` (draft 2026-06-04) described a `WifiFlow` class with its
own lifecycle interface (`start()`, `active()`, `tick()`, `handleInput()`).
This predated the `SettingsSection` base class, which was finalised in
commit 8005297 alongside `SliderWidget`.

`SettingsSection` provides:
- `enter()` / `leave()` lifecycle
- `tick()` for async/periodic polling
- `handleInput(phase, x, y) → SectionResult`
- `repaint()` / `title()`
- Protected chrome helpers (`drawHeader`, `drawRow`, `tapToRow`, `isBackTap`)

The question: retrofit `WifiFlow` to extend `SettingsSection`, or keep it as
a standalone class owned/delegated-to by `SettingsApp`?

**Decision**

`WifiSection : public SettingsSection`.

Rename `WifiFlow` → `WifiSection` and implement the `SettingsSection` contract
directly. `SettingsApp` pushes a `WifiSection` instance via its section-push
mechanism rather than holding a separate `g_wifiFlow` object.

**Rationale**

1. **Lifecycle parity.** `enter()`/`leave()`/`tick()`/`repaint()` map
   one-for-one onto `WifiFlow::start()` / `active()` / `tick()` / `repaint*()`.
   No adapter shim needed.

2. **Chrome reuse.** `drawHeader()`, `drawRow()`, `isBackTap()`, `tapToRow()`
   are already in the base. Reimplementing them in `WifiFlow` would be
   duplication.

3. **Consistent nav signal.** `SectionResult::GoBack` tells `SettingsApp`
   to pop the section — exact same mechanism used by every other section.
   A standalone `WifiFlow` would need a separate boolean return convention.

4. **`title()` elegance.** The base `drawHeader()` calls `title()` — a
   simple `switch(_step)` in `title()` gives dynamic header text without
   any extra repaint machinery.

**Consequences**

- `wifi-settings.md` updated: `WifiFlow` → `WifiSection`, class sketch
  shows `public SettingsSection` inheritance.
- Phase 1 (`WifiStep::Status / Scanning / List`) implemented first;
  Phase 2 (`Keyboard / Connecting / Result`) extends the same class.
- `SettingsApp` does not hold a separate `g_wifiFlow`; it pushes/pops a
  `WifiSection` object using the same section mechanism as other sections.

**Supersedes**: the `WifiFlow` class sketch in `wifi-settings.md` draft 2026-06-04.
