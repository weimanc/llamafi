### ADR-059 — [2026-08-07] — M-WINAMP-PLAYER: system-owned audio engine, one PLEDIT renderer, and a three-valued player mode

**Status**: **accepted — 2026-08-07**, human sign-off on all thirteen decisions (D1–D13).

Revised the same day, before sign-off, after [VE](../designs/M-WINAMP-PLAYER-VE-review.md) and
[Developer](../designs/M-WINAMP-PLAYER-DEV-review.md) reviews: **D7 was factually wrong and is
corrected** (original retained as the decision trail); D6 amended (DEV-1); D12 and D13 added from the
VE findings.

**What acceptance authorises.** Implementation of TASK-408..423 may begin. It does **not** pre-approve
the outcome of D1 — TASK-408 is a genuine gate, and a failing probe closes the milestone with a
hardware note rather than triggering a redesign. Three constraints ride with acceptance and are not
renegotiable at implementation time without a new ADR:

1. **TASK-423 runs first** (D11) — the reclaim, before anything spends the headroom.
2. **D13's ≥3-run baselines must be captured *before* TASK-409, 412 and 417 land**, not after. That is
   DUT time ahead of the refactors, not concurrent with them.
3. **D2's move stays a move** — the extraction commit carries no behavioural hunks, and lands only
   behind `run/check` 6/6 plus a ≥30 min `wr-soak`.

Statuses elsewhere move with this: the five design documents go `draft → accepted`; the seven reserved
`feature_inventory.yaml` entries stay `reserved` until Developer implements them; `test_coverage: []`
stays empty until VE lands the suite.

**Context**

The player slot is one `AppId` with two remote-source modes (`M-PLAYER-STATE`, ADR-scope
TASK-259/260). Adding local MP3 playback from SD card — with file browsing, M3U playlists and a
genuinely editable PLEDIT — runs into three structural facts that no amount of feature code works
around:

1. **The audio engine belongs to WebRadio.** The `Audio` singleton, its mutex, the `wrAudio` pump
   task, `mb_arena` acquire/release, the `audio_process_extern` visualisation tap and the volume
   sink are file statics inside `webRadioApp.h`. Hardware permits exactly one instance: one internal
   DAC, one 23 216 B Helix arena, one 6 400 B InBuff, against a 290 KB INTERNAL ceiling with 60 KB
   reserved headroom (`app/mem_manifest.yaml`).
2. **PLEDIT is implemented twice.** `winampDisplay.h` renders the Spotify queue;
   `webRadioApp.h` renders the station list with an independently-evolved copy of the same geometry,
   gesture machine and thumb maths. A third source implies a third copy.
3. **No playlist has ever existed as data.** `QueueSnapshot` is a poll result — read-only, replaced
   wholesale, keyed by `seqno`. Nothing models an owned, mutable, persisted ordered list, so
   reorder/add/delete/save has nowhere to live.

Separately, the SD slot on this ESP32-2432S028R has never been mounted by this firmware
(`M-AQUARIUM/overview.md` dropped the donor's `SD.h` path as out of board config), and the operator
has directed that player-mode cycling move off the eject button onto the taskbar Winamp icon, with
eject repurposed per mode.

Full working-out, including the rejected options and their reasoning, is split across an umbrella
and four workstream documents: `designs/M-WINAMP-PLAYER.md` (umbrella — reuse audit, memory and
flash budgets, build variants, registry), `M-SDFS-sd-card-exploration.md`,
`M-AUDIO-ENGINE-extraction.md`, `M-PLEDIT-ABSTRACTION-playlist-source.md`, and
`M-WINAMP-PLAYER-local-playback.md`. Three of the four workstreams have standalone value and do not
depend on the SD card existing.

**Decision**

**D1 — Phase 0 is a hard gate.** No implementation work past the probe begins until an `sdprobe`
command on the physical DUT demonstrates: successful VSPI mount (5/18/19/23, own `SPIClass`),
sustained sequential read ≥ 200 KB/s, worst-case single-read latency ≤ 50 ms, mount heap delta
≤ 8 KB, and a long-filename round-trip. On failure the milestone closes with a hardware note.
SPIFFS is explicitly **not** an accepted fallback: 1.4 MB shared with skin/settings/config is about
one track.

**Amended 2026-08-08 — the mount-heap bar was wrong; throughput and latency passed with room.**
TASK-408 measured 637 KB/s worst-of-5 under a named Aquarium load (bar 200) and 3.71 ms worst-case
read latency (bar 50) — both pass by 3× and 13×. Mount heap measured **15 300 B against a ≤8 KB
bar**, and the bar is what gives.

*Why the bar was wrong.* I set ≤8 KB with the derivation "fits the parent's runtime budget without a
reclaim" — a figure that was never computed against anything. The measured cost is structural and
comes from the precompiled IDF's FATFS configuration, not from the implementation:

- `FF_MAX_SS = MAX(FF_SS_SDCARD=512, FF_SS_WL=CONFIG_WL_SECTOR_SIZE=4096)` → **4096**. The 4 KB
  sector size comes from the *wear-levelling* layer used for SPI-flash FATFS, which this project does
  not use for SD. SD cards are 512-byte sectors; we pay 8× per buffer for a feature we never invoke.
- `CONFIG_FATFS_PER_FILE_CACHE=y` → `FF_FS_TINY=0` → **every open `FIL` carries its own 4096 B
  cache**, on top of the volume window.

At one open file that is already ~8 KB, so the original bar was unreachable by construction for any
usable configuration — the Player needs at minimum an audio file and a playlist file open at once.

*Ruling — accept, with one recovery and two new conditions.*

**Accepted at ~15 KB.** The decisive comparison is against the mode that already ships: WebRadio's
concurrent peak is decoder 23 216 + InBuff 6 400 + ~40 KB TLS ≈ **70 KB**. Player is FATFS 15 300 +
decoder 23 216 + InBuff 6 400 + playlist ~5 200 + browser ~2 500 ≈ **52.6 KB** — still ~17 KB
*cheaper* than a mode running on this hardware today, because local playback opens no TLS.

**Rejected: rebuilding the IDF** to change `CONFIG_WL_SECTOR_SIZE`. The platform is pinned at
`espressif32@6.9.0` for a documented reason, and rebuilding the framework to change a sector size the
SD path does not need is disproportionate to a 12 KB saving — precisely the class of change the
audio-library version pin (BP-042) exists to discourage.

**Rejected as a memory fix: `esp_vfs_fat_sdspi_mount`.** `FF_MAX_SS` and `FF_FS_TINY` are compiled
into the precompiled FATFS; the API choice does not change either. It remains a legitimate option for
other reasons, but it recovers nothing here and should not be adopted on this argument.

**Recovery not in the original three options: `max_files`.** ~~Mount with `max_files=4` and
re-measure; expect ~4 KB back.~~ **Retracted 2026-08-09 — this was wrong in both direction and
substance, see the amendment below.**

*Two conditions attached to the acceptance:*

1. **Measure the concurrent peak, not the mount delta.** 15 300 B is the mount cost in isolation; the
   number that matters is free heap and largest-free-block with SD mounted *and* the decoder arena
   held *and* a playlist loaded.
2. **Confirm `mb_arena_acquire()` still succeeds with SD mounted.** The arena needs 23 216 B
   **contiguous** `MALLOC_CAP_INTERNAL`, and the lazy-mount order now carves 15 KB out of the heap
   before the arena looks for its block. This is the DEV-2-3 fragmentation lesson — the 8 KB pump-task
   stack was already shown to be capable of fragmenting the block the arena needs — and it is a
   failure mode that will not show up in a mount-delta measurement. If acquire fails or gets flaky,
   the fix is ordering (acquire the arena before mounting), not more memory.

### D1 amendment #2 — 2026-08-09, after the `max_files` sweep

**T_SD_06 closes as an accepted exception, at `max_files=3`, with a lifecycle change.**

*My `max_files=4` recommendation was wrong twice over, and the measurement caught both.* It assumed
the mount was using the Arduino default of 5; it was already at 2, so "expect ~4 KB back" pointed the
wrong way — 4 slots *adds* 8 KB. And "do not go below 4" named the first value that breaks playback
outright. The sweep (exactly +4 136 B per slot, one `sizeof(FIL)`, mount and unmount agreeing
byte-for-byte):

| `max_files` | mount | largest free block | arena (23 216 contiguous) fits? |
|---|---|---|---|
| 1 | 11 164 | 32 876 | yes (+9 660) — but 1 slot cannot walk a directory |
| 2 | 15 300 | 28 740 | yes (+5 524) |
| **3** | **19 436** | **24 604** | **yes (+1 388)** |
| 4 | 23 572 | **20 468** (measured) | **NO (−2 748)** |
| 5 | 27 708 | 16 332 | no (−6 884) |

Only the `max_files=4` row is measured; the others are derived linearly from it and the per-slot
constant, and should be confirmed rather than trusted. **At `max_files=4` the decoder arena cannot be
acquired and nothing would ever play** — a failure the mount-cost table alone does not show, and the
reason condition 2 above existed.

**There is no configuration that meets the ≤8 KB bar.** The floor is 11 164 B at one slot —
`sizeof(FATFS)` = 4 156 (a 4 096 B window) plus ~7 KB of non-context overhead before the first file
slot exists. The bar is unreachable, not missed. `T_SD_06` is therefore recorded as an **accepted
exception**, not a pass: the gate is not retuned to fit the result, and TASK-408 closes as
*"passed with one recorded exception"* with the numbers on the record.

*`max_files` = 3* — **but only with the closure rule below. Corrected 2026-08-09 (operator).**

My first count was audio + browser directory handle + the entry `openNextFile()` returns, and it
**omitted the playlist file itself**. §3 reads row text *on demand*, so the `.m3u` handle is held for
the session. The full enumeration:

| Consumer | Held while | |
|---|---|---|
| audio file | a track is playing | 1 |
| playlist `.m3u` | the session, if row text is read on demand | 1 |
| browser directory handle | the browser is open | 1 |
| browser entry (`openNextFile()`) | transient, but concurrent with the directory handle | 1 |
| save `.tmp` | a save is running | 1 |

| Scenario | Peak |
|---|---|
| PLEDIT scrolling while playing | audio + playlist = **2** |
| Save while playing | audio + source + `.tmp` = **3** |
| **Browsing while playing** | audio + playlist + dir + entry = **4** |

So 4 *is* reachable, and the earlier "3 is the true concurrent maximum" was wrong.

**Resolution — a closure rule, not a bigger table.** The file browser is a **modal full-canvas list
over the player** (§4): while it is open, PLEDIT is not rendering and no row text is being read.
`LocalPlaylistSource` therefore **closes its `.m3u` handle when the browser opens and reopens it when
the browser closes**. The index lives in RAM as byte offsets, so closing costs nothing and reopening
is a path lookup plus a seek. Peak returns to 3 and the memory table above stands.

*Ordering matters within that rule:* on browser exit, close the directory and entry handles **before**
reopening the playlist, or the transition itself momentarily needs 4.

**Fallback if the closure rule proves awkward:** `max_files=4`. Note that the "arena does not fit at
4" row in the table above was measured **mount-first**, which is the ordering this amendment
replaces. Under arena-first the arena is taken from a clean heap and FATFS's small allocations fit
around it, so 4 may well be viable — but that is a hypothesis, not a result. **Re-measure the whole
table under arena-first before relying on any row of it.**

*Lifecycle change — acquire the arena **before** mounting SD.* 3 slots leaves only 1 388 B of
largest-free-block margin over the arena, which is not enough to survive any fragmentation. The
asymmetry that resolves it: **the arena needs one contiguous 23 216 B block, while FATFS needs
~19 KB in many smaller pieces.** Small allocations tolerate a fragmented heap; the arena cannot. So
`LocalPlayerApp::resume()` acquires the arena *first*, then mounts — reversing the order in
local-playback §10, and making the arena **mode-scoped in Player mode rather than play-scoped**. It
is held for the whole Player session and released in `suspend()`.

This is a deliberate departure from WebRadio's JIT-per-play discipline, justified because in Player
mode the arena is needed for essentially the entire session anyway, and pre-committing it makes
acquisition deterministic instead of dependent on whatever the filesystem left behind. If the arena
cannot be acquired at `resume()`, Player mode enters degraded (`hasError()`) and never mounts — a
clean, early, diagnosable failure rather than a mount that succeeds and a play that mysteriously
does not.

**D2 — Extract the audio engine to `audio/audioEngine.h`, as a pure move.** The engine owns the
singleton, mutex, pump task, arena lifecycle, vis tap and volume sink; WebRadio and LocalPlayer are
peer clients. The only new surface is `connect(const Source&)` with `Source = {URL | FILE}` —
`connecttoFS(SD, path)` reuses the existing post-to-pump-task-and-poll-result path unchanged. A
second `Audio` instance is rejected as physically impossible; leaving the engine inside
`webRadioApp.h` with a second caller is rejected as an uncontracted dependency. Because this code
carries the fixes from TASK-278/287/289/291/295/299/392/398, the move lands only behind
`./run/check` 6/6 **and** a full-length `run/wr-soak` — a short soak does not clear it.

**D3 — Playlists are a RAM index over an SD-backed file, not an in-RAM entry array — one immutable
array with two permutations over it.** Load builds an immutable `entries[]` of
`{uint32 offset, uint16 durSec, uint16 flags}` (8 B; 2 KB at 256 tracks) whose subscripts are stable
entry ids, plus two `uint16` permutations: `viewOrder[]` (what PLEDIT renders and SAVE writes) and
`playOrder[]` (what playback advances through) — 512 B each, 3 KB total. Also a ≤8-row text cache and
a bounded staging arena for not-yet-written additions. Reorder and delete are permutation edits with
zero file I/O; save is one sequential copy pass through `viewOrder` into a temp file plus rename. A
full in-RAM array (~46 KB at 256 tracks) is rejected on budget; re-scanning the file per repaint is
rejected on latency.

The two-permutation split is not incidental structure — it is what makes shuffle safe (D8). A
shuffle order expressed as positions into a mutable array is invalidated by any reorder; a shuffle
implemented by permuting the index in place destroys the user's playlist order the next time they
save. With the split, **shuffle provably cannot affect what PLEDIT shows or what SAVE writes**,
because it only ever touches `playOrder`.

**D4 — One PLEDIT renderer behind a `PlaylistSource` interface.** `pleditView.h` owns all chrome,
rows, thumb and gestures; `SpotifyQueueSource` and `StationListSource` advertise `CAP_PLAY` only,
`LocalPlaylistSource` advertises the full capability set. The renderer hides controls the source
does not advertise rather than relying on default-false mutators. Extraction proceeds in three
separately-verified commits (Spotify caller → WebRadio caller → local caller); if either extraction
step cannot be made pixel-identical, the fallback is a third renderer for local playlists only —
shipped scroll behaviour is not traded for deduplication.

**D5 — Editing is modal, not gestural.** PLEDIT title-bar tap toggles edit mode; the bottom bar
becomes `[+] [–] [↑] [↓] [SAVE]`. Drag-to-reorder is rejected: 16 px rows on a resistive panel, in
direct collision with the velocity-scroll gesture tuned in TASK-277. The modal form is also
skin-authentic (real Winamp's ADD/REM/SEL/MISC/LIST strip) and reuses existing button/hitzone
patterns.

**D6 — Player mode becomes three-valued; cycling moves to the taskbar icon; eject becomes
"load media".** `PlayerMode { Spotify=0, WebRadio=1, Player=2 }` — the persisted `uint8_t` schema is
unchanged. Tapping the player slot while the player is already active cycles the mode and persists;
tapping it from another app restores the persisted mode. Eject means "load media from this source"
in all three modes: Spotify → TLS reset + force poll, WebRadio → station refresh/browse, Player →
open the file browser. The Winamp logo tap retains its TLS-reset behaviour; the duplicated
affordance is harmless, silently removing a recovery path is not.

**Amended 2026-08-07 (DEV-1).** The cycle cannot be expressed inside `resolvePlayerSlot()`, as the
first draft of this decision assumed. `switchApp()` early-returns on same-app (`main.cpp:2014`), so a
tap on the already-active player slot resolves to the current app and silently no-ops. Worse, the two
dispatch sites guard *differently* — production (`main.cpp:2001`) carries its own
`if (target != currentAppId)` at `:2002`, while the serial-injection drain (`main.cpp:2793`) calls
`switchApp()` unconditionally and relies on its internal return. A cycle branch added to one site
only would make the feature behave differently under the harness than in production: the TASK-406
defect class, invisible to every build gate.

The decision is therefore: **a single shared helper owns both the restore and the cycle decision** —
`resolvePlayerTap(AppId tapped, bool playerAlreadyActive)` — called from *both* dispatch sites, the
same discipline TASK-279 already imposes on `shellTbPress()`/`shellTbCommit()` for exactly this
reason. `resolvePlayerSlot()` survives unchanged as the pure restore case so its existing callers are
undisturbed.

**D7 — The taskbar's eject-only invariant is generalised. (Corrected 2026-08-07 — DEV-2.)**

*The original text of this decision was wrong on three counts and is retained here only as the
decision trail. It claimed the tail change forces `TASKBAR_APP_COUNT = (int)AppId::COUNT - 2` and
that "the assertion" needs rewriting. Checked against `taskbar.h:34-56`:*

| Assert / constant | With `LocalPlayer` appended | Original claim |
|---|---|---|
| `AppId::WebRadio == COUNT - 1` | **breaks** | correct |
| `AppId::Settings == AppId::WebRadio - 1` | **still holds** (tail is `Settings, WebRadio, LocalPlayer`) | wrongly implied broken |
| `TASKBAR_ICON_COUNT == TASKBAR_APP_COUNT` | **still holds** | wrongly implied broken |
| `TASKBAR_APP_COUNT = (int)AppId::WebRadio` | **still holds** — the ordinal *is* the taskbar app count | wrongly claimed to need recomputing |

*And the proposed replacement was actively worse: `COUNT - 2` hardcodes "there are exactly two
eject-only modes", so the third one silently breaks it — reintroducing the precise failure D7 exists
to prevent.*

**Corrected decision.** Exactly **one** assert changes, and the count stays derived rather than
literal — anchored to the *last taskbar slot* rather than to the eject-only tail, so it survives any
number of tail modes:

```c
static constexpr int TASKBAR_APP_COUNT = (int)AppId::Settings + 1;

static_assert((int)AppId::Settings + 1 == TASKBAR_APP_COUNT,
              "Settings must remain the last taskbar slot; every AppId after it is eject-only "
              "and must have no taskbar slot. See NEW-APP-CHECKLIST.md.");
```

The Settings-pinning assert (TASK-347) and the icon-count assert (TASK-242) are left untouched and
continue to do their jobs. The invariant being expressed is unchanged from the original intent —
*eject-only modes occupy the tail and never reach the taskbar* — only its encoding is fixed.

**D8 — Transport zones become capability-driven; shuffle/repeat/seek are un-gated, not rebuilt.**
The skin side already exists and is untouched: `chrome-001` bakes `SKIN_SHUFREP` (four sprites),
and `winampDisplay.h` already draws, hit-tests and optimistically caches shuffle and repeat. What
blocks reuse is that those zones are hardcoded Spotify — hit-tested inside `handleWinampInput()`
(whose own comment calls them "Spotify-only zones") and dispatched straight to
`spotifyTask::ACT_SHUFFLE`/`ACT_REPEAT`. WebRadio's existing workaround, the narrow
`handleVolumeGesturePublic()` entry point, does not generalise to a third mode. Each mode therefore
advertises a capability mask — `CAP_TRANSPORT | CAP_SEEK | CAP_SHUFFLE | CAP_REPEAT` — and
`handleWinampInput()` consults it instead of assuming the mode; a zone whose capability is absent is
neither drawn nor hit-tested. Spotify advertises all four, WebRadio only `CAP_TRANSPORT`
(behaviour identical to today, so this is a refactor for it), Player all four. The rendered state
is likewise sourced from the mode rather than from `spotifyTask::Snapshot`, the same seam shape as
D4's `PlaylistSource`. This also makes the posbar a **real** scrub control for local files —
`setFilePos()`, `setTimeOffset()`, `getAudioFileDuration()`, `getAudioCurrentTime()` all exist in
the vendored library — rather than WebRadio's estimated slew or Spotify's `seek()` round-trip.

**D9 — Local shuffle is a materialised bag; local repeat is binary.** Shuffle is a Fisher-Yates
permutation of `playOrder[]` computed on toggle-on and walked by `next`; re-rolling a random index
per advance is rejected as the standard broken implementation (repeats tracks, starves others).
Materialising it is also what makes Prev replay history rather than roll a new random, and what lets
tap-to-play move the bag cursor instead of reshuffling. Repeat is binary for v1, encoded in the
shipped tri-state domain (Player emits only `2` = off and `0` = repeat-all) so `drawRepeat()`'s
existing `s != 2 → ON` rule needs no change; repeat-one is deferred because the skin carries only
two repeat sprites and two indistinguishable ON states are tolerable for Spotify (the phone app is
the source of truth) but not for a device that is its own only display. All four shuffle×repeat
end-of-playlist cells are specified in the design §4.9 rather than left to implementation, including
the guard that a reshuffle-on-wrap must not re-open with the track that just finished. Auto-advance
hangs off the `audio_eof_mp3()` weak callback, which fires **on the audio pump task** and may only
set a flag — opening the next file from inside it would call `connecttoFS()` from within
`Audio::loop()` under the engine mutex, i.e. self-deadlock. Shuffle and repeat persist in
`g_settings` as Player-scoped state; Spotify's remain server-owned and are never written there.

**D10 — The three player modes are compile-time optional, behind presence flags, with exactly one
extra gated env.** `-DPLAYER_SPOTIFY`, `-DPLAYER_WEBRADIO`, `-DPLAYER_LOCAL` (presence only, never
`=0` — LL-006); absence removes the mode's `appRegistry.h` row, its object and its header. Four
consequences are handled explicitly rather than left to fall out: mode cycling iterates the
compiled-in set (a single-mode build must not cycle); a persisted `playerMode` naming an absent mode
falls back to the first compiled-in one (otherwise it resolves to a null app — a boot-crash class
bug); `TASKBAR_APP_COUNT` is computed from the compiled-in tail rather than a literal; and the
Settings player row lists only compiled-in modes. The existing negative `-DDISABLE_SPOTIFY` flag is
left alone — it is load-bearing for the harness's `get variant` fast path.

A full 2³ environment matrix is rejected: `check_build.sh` runs two full builds today and eight would
make the gate unusable. Exactly one development env is added — `cyd2usb_player` (Player only) — for
headroom during development and for isolating Player bugs, mirroring the existing `cyd2usb_webradio`
precedent. Production ships all three modes. Gate count goes 6 → 7, not 6 → 13.

**D11 — The debug-build DRAM reclaim is taken proactively, before the milestone starts.** Operator
decision, 2026-08-07. A map symbol dump attributes 11 956 B of the debug build's 12 792 B `.bss`
overage over production — 93 % — to two function statics inside one `#ifdef SERIAL_DEBUG` command:
`cmdScreenDump`'s `s_b64` (6 836 B) and `s_band` (5 120 B). Neither appears in the production map.
They are band buffers for an on-demand host-driven screenshot tool that runs for ~18 s when a human
asks for it, resident permanently in the one build that has 304 B of headroom. They move to
per-invocation `malloc`/`free` — preferable here to the lazy-malloc-once pattern used for
`WinampDisplay`, because it returns the memory to the heap rather than relocating it, and a dev tool
degrading on a fragmented heap is acceptable where a link failure is not. Expected debug headroom
after: ≈12.2 KB, measured before and after. Zero production impact — the code does not compile into
production. Scheduled first, ahead of every other task in the milestone; the alternative (reclaim
reactively when a phase fails to link) costs a debugging session and blocks that phase, while this
is one task and independently correct.

**D12 — Observability is product surface, not test scaffolding.** VE's review (VE-1, VE-2) found that
six reserved test ids assert on state the firmware does not expose, and that two more require ~3 hours
of real-time playback to reach the state under test. Both are symptoms of the same omission: the
design specified behaviour without specifying how it is observed. Rather than let VE retrofit probes,
the following ship **with the features that create the state**, consistent with the existing rule that
every app exposes a `dbgGet`/`dbgSet` surface (NEW-APP-CHECKLIST item 3):

| Surface | Task | Makes testable |
|---|---|---|
| `get pleditRepaints` — monotonic repaint counter | TASK-411 | the seqno redraw gate, and `T_PLE_14` (the X055 dirty-flag→seqno gap VE found) |
| `get plOrder` / `get plCursor` / `set plCursor` / `advance next\|prev` (steps the order engine **without decoding audio**) | TASK-418 | shuffle-bag coverage, prev-history, tap-to-play cursor, and all four end-of-list cells in seconds instead of hours |
| `configASSERT(xTaskGetCurrentTaskHandle() == g_loopTaskHandle)` on the open-next-track path, plus capturing the loopTask handle in `setup()` | TASK-410 | the pump-task/self-deadlock invariant — as a permanent assert that panics in *every* debug run, not a probe done once |

The third is a deliberate reclassification: a runtime assert is strictly stronger than a test, because
it holds on every execution rather than on the one where someone remembered to check. One reserved id
becomes an assert, and one (`T_AE_05`, "the diff is a move") is reclassified out of the test set
entirely — it is a review gate with no repeatable procedure, and counting it as a test inflates
coverage with something that cannot be re-run.

**D13 — Behaviour-neutrality is measured against a multi-run baseline, not a single run.** Four ids
turn on "identical pass set to the baseline" (`T_AE_01`, `T_PLE_08`, `T_PLR_17`, `T_PLR_18`). VE-3
established that a single-run comparison fails on this suite's *known* flake — `T_WR_TLS_01` (mirror
truncation, TASK-284), `T169` (network), `T_PR_05` (`[NETWORK]`-flaky) — rather than on regression,
and that the likely response under schedule pressure is to wave it through, costing the time and
buying nothing. The design cited LL-104 without operationalising it.

Protocol, binding on every "identical pass set" gate: baseline is **≥3 full runs before the refactor
lands**; the flaky set is pre-declared from those runs; the bar is *no test that passed in all three
baselines fails after, and no new failure outside the pre-declared flaky set*. This mirrors the
≥3-trial protocol VE established on TASK-402.

**Consequences**

*Easier.* A system-owned audio engine makes any future audio source (a fourth mode, a notification
chime, a test tone) a client rather than a fork. One PLEDIT renderer means gesture and skin fixes
land once instead of twice — and the existing divergence between the two copies gets resolved rather
than tripled. The index-based playlist model makes edit operations trivially cheap and gives the
project its first mutable, persisted user data structure beyond settings. Local playback needs no
TLS at all, so it is the cheapest of the three player modes: the ~40 KB mbedtls context that forces
the decoder and InBuff to stay runtime-JIT simply is not present.

*Harder / constrained.* The extraction touches the most fragile shipped code in the repo, and its
verification cost (full soak, LCD eyeball, pixel-identity) is a real part of the schedule rather
than a formality. Two tasks now touch the filesystem — loopTask and the audio pump — so all bulk SD
I/O on loopTask must be chunked and playlist save must pause playback; the engine mutex protects
`Audio` calls and must not be widened to cover the FS. Dropping `-DAUDIO_NO_SD_FS` adds a `File`
member and FATFS statics to `.dram0.bss` in a build whose debug env has twice sat at 0 B headroom,
so the budget must be re-derived from a fresh map, never remembered. Measured 2026-08-07 rather than
estimated: the debug build has **304 B** of `dram0_0_seg` headroom (production has 13 160 B), and
enabling SD/FS with the code actually referenced costs **88 B static DRAM and 3 984 B flash**,
leaving 216 B. SD/FS is cheap; the headroom it lands on is not. The consequence is architectural
rather than incidental — **no Player state may be static**; all of it is heap, acquired in
`resume()` and freed in `suspend()` (≈7.7 KB plus the FATFS work area), which is also why D10's

*From D8/D9 specifically.* The shuffle/repeat ask costs almost no new asset or render work — the
sprites, hit-tests, draw calls and optimistic-hold cache all shipped with `chrome-001` and are
reused verbatim. The cost lands instead on the capability refactor, which reaches into
`handleWinampInput()` — shared by Spotify and, indirectly, WebRadio. That refactor must be
behaviour-neutral for both existing modes, and "WebRadio still hit-tests nothing it didn't before"
is an explicit exit criterion rather than an assumption. In exchange the long-standing
`handleVolumeGesturePublic()` workaround stops being the pattern for how a non-Spotify mode borrows
a Winamp control. The play-order model adds 1 KB of permutations and one genuinely destructive
failure mode to guard against — shuffle leaking into what SAVE writes — which is why D3 was
restructured rather than patched.
