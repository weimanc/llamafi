### ADR-066 — [2026-09-04] — The run result artifact is the interface (IFC-008); `UNMET` exits 1

**Status**: accepted
**As-built**: not yet — IFC-008 exists as of this ADR's commit; TASK-624 and TASK-608 implement it.
**Ruled**: human, 2026-09-04, on the Architect's decision D
([M-HARNESS2-architect-review.md](../designs/M-HARNESS2-architect-review.md) §9). The exit-code
question was ruled *back* to the Architect as an architecture call inside an adopted decision; D4

**Requirements**: [R28, R29, R30, R31, R32, R33, R38](../../verification/M-HARNESS2-requirements.md)

**Context**

Today the machine interface to a test run is a `printf`. `app/tools/lib/results.py:271` prints
`  {tid}: {RESULTS[tid]}` and `run/player-gate:162` recovers verdicts from it with a `sed` regex.
That arrangement has already produced a false verdict: `results.py` writes `FLAKY-PASS`, the gate's
regex matched `FLAKE`, `FLAKE` ≠ `FLAKY`, the whole line was dropped, the cell scored `MISSING`, and
the gate printed **REGRESS** for a firmware regression that never happened — with the worst possible
polarity, since the *unresolved* flake parsed and the *resolved* one did not
([M-TESTARCH precedence](../designs/M-TESTARCH-precedence-hierarchy.md) §4.1; fixed as TASK-573).
Three separate consumers parse that human summary text.

The verdict vocabulary is also incomplete. A test whose precondition was never established is
recorded today as a SKIP, which reads as "not applicable to this configuration" — R28's framing is
correct: *a test that cannot run is not not-applicable, it is an unestablished premise*. And
`app/tools/lib/results.py:301` computes `rc = 0 if failed == 0 else 1`, which its own docstring flags as "the
single line where silently green would reappear".

**Decision**

**D1 — the schema-versioned JSON artifact is the sole machine interface to a run.** Every run emits
one. Every gate reads it. **No consumer parses the human summary text**, and the three that do today
are retired with R30's landing (TASK-608). The human summary remains, for humans, and is explicitly
not a contract.

**D2 — the verdict vocabulary is a closed enum, and `UNMET` joins it.** `PASS`, `FAIL`, `SKIP`,
`FLAKY-PASS`, `FLAKE`, `NOT-RUN`, `UNMET`. Closed means a gate matches an enum member, never a string
prefix — `app/tools/suite/serialdbg/_gate.py:129`'s `RESULTS.get(tid, "").startswith("FAIL")` is
exactly the shape this
replaces. A suite body may not write a verdict string; only the results layer may.

**`UNMET` and `NOT-RUN` are not synonyms and the distinction is load-bearing:**

| Verdict | Means | Attribution |
|---|---|---|
| `NOT-RUN` | never dispatched, because an earlier **class** failure blocked it | always carries `blocked_by=<class>/<id>` |
| `UNMET` | dispatched, but its **own premise** was not established, so it asserted nothing | carries the unmet premise, and may have no class failure to blame |

Without that split, `UNMET` becomes a second spelling of `NOT-RUN` within one milestone and the
vocabulary rots. IFC-008 states it as an invariant.

**D2a — `ORDER-DEPENDENT` is NOT an eighth verdict. The enum stays at seven.** *(TASK-644, ruled
2026-09-06.)* R28's verdict table listed `ORDER-DEPENDENT` as an eighth row; that table is wrong and
is corrected. Three different things were being spelled with one word, and they live at three
different scopes:

| Name | Scope | Who writes it | Where it lives |
|---|---|---|---|
| the seven verdicts | **one id, one run** | the results layer, during the run | `per-id.verdict` in the IFC-008 artifact |
| `ORDER-DEPENDENT` (R21) | **one id, across two runs** | the shuffle job, *after* both runs | the shuffle job's own comparison report |
| `ORDER-SENSITIVE` (`app/tools/suite/serialdbg/_order.py:185`) | **one candidate edge, no run at all** | a human, adjudicating statically | `EDGE_ADJUDICATION` |

*The decisive test is who can write it.* A verdict is what a producer can determine from the run it
is producing. **No single run can ever emit `ORDER-DEPENDENT`** — it is a statement about the
*difference* between two runs, and it is only knowable to something holding both artifacts. Putting
it in the per-id enum would define a member the sole producer (`app/tools/lib/results.py`, I2) is
structurally incapable of writing, and oblige every consumer to handle a value that can never arrive.
That is the same category error as folding `_order.py`'s static adjudication into a run verdict, one
scope further out.

R21 was **not** describing `_order.py`'s adjudication category, and it was not asking for an eighth
verdict either. It asked for a real, third thing: a cross-run comparison outcome, "naming both
orders" — which the verdict enum has no field for and by construction cannot carry.

**Consequence — this changes what TASK-636 must build.** R20/R21's implementer must emit
`ORDER-DEPENDENT` from the shuffle job as a **comparison outcome over two artifacts**, keyed by id
and naming both orders, and MUST NOT add a member to the verdict enum, extend `Verdict`, or teach
`classify()` an eighth token. Both artifacts are ordinary seven-verdict documents; the comparison is
a new consumer of IFC-008, not a change to it. Nothing landed under TASK-624 is invalidated: the
seven-member enum it shipped is correct as shipped.

**D3 — the artifact carries the run's premise, typed.** R30's fields — build identity (ELF hash and
env name), the board it ran against, the class order in force, per-class elapsed, the id set selected
and why — are part of the record, not a log line. Build identity in particular is what makes ADR-067's
verify-and-refuse checkable after the fact rather than only at the entry point.

**D4 — `UNMET`'s exit code is 1, and `UNMET` never owns an exit code of its own.**

This is the call ruled back to me. The allocation it must fit is
[M-TESTARCH precedence](../designs/M-TESTARCH-precedence-hierarchy.md) §4: **0** clean, **1** a test
failed, **2** `run/player-gate`'s composition refusal (`run/player-gate:221`, `:237`), **3** RIG — the host
could not address a board, **4** HEALTH — the board is not a valid subject / no result in this run is
trustworthy.

*The decisive precedent is `NOT-RUN`, which already does not own an exit code.* Its code is inherited
from its cause: a HEALTH failure carries it out at 4 (§4 rule 3), a CORE failure at 1 (§4 rule 4).
`UNMET` is the same kind of thing — a per-id verdict, not a run outcome — and it gets the same
treatment:

1. If the unmet premise is attributable to a class failure that already fired, **the existing
   precedence rules set the code** (3, 4 or 1) and `UNMET` changes nothing.
2. Otherwise — a premise that failed on its own, with no class failure to attribute it to — **the run
   exits 1**, and the artifact carries the reason.

**D4a — "attributable" is defined, and it is a property of the RUN, not of the row.** *(TASK-644,
ruled 2026-09-06. The word was used undefined in rule 1 above; this is the definition, and it is
where the next reader should stop rather than re-derive it.)*

> An `UNMET` is **attributable** when a gating-class (RIG / HEALTH / CORE) failure has already fired
> in the same run and therefore already owns the run's exit code under
> [M-TESTARCH precedence](../designs/M-TESTARCH-precedence-hierarchy.md) §4.

There is deliberately **nothing per-id to test**. An `UNMET` row never carries an attribution — I3
and `unmet()` *refuse* a `blocked-by=` premise, because an attributed `UNMET` is a `NOT-RUN` wearing
the wrong name. So "attributable" cannot mean "this row names its cause"; the only thing the exit-code
arithmetic can observe is whether a class failure fired at all. Rule 1 is therefore a
**worst-wins-by-precedence** rule and nothing more: `UNMET` contributes a **floor of 1**, and 3 or 4
supersede it if a class failure set them.

**TASK-624's implementer asked whether "attributable" meant "the `UNMET` is itself in a gating
class". That reading is CORRECT — but it answers a different question, and both answers are needed:**

| Question | Rule | Where it is built |
|---|---|---|
| does this `UNMET` **block the classes above it**? | yes iff the `UNMET` is itself in a gating class (R38) | `BLOCKING = {FAIL, UNMET}`, `app/tools/lib/results.py:183`, matched in `app/tools/suite/serialdbg/_gate.py:147` |
| does this `UNMET` **set the run's exit code**? | it floors it at 1, always, regardless of class; a class failure that already fired supersedes with 3 or 4 | `rc = 0 if (failed == 0 and not unmet_ids …)`, then `health_fail` last |

The two are independent, and conflating them is how a non-gating `UNMET` would silently become exit 0
(the "silently green" line this ADR exists to close) or a gating one would fail to block. **The
as-built code implements both correctly; nothing landed under TASK-624 is invalidated.** This entry
records the definition the code already obeys so the next reader is not re-deriving it from
arithmetic.

Why 1 and not the alternatives:

* **0 is forbidden.** R38 requires `UNMET` to block. `app/tools/lib/results.py:301` returning 0 for a run of 200
  `UNMET` ids is the exact "silently green" line the module's own docstring warns about.
* **4 is wrong, and dangerously so.** §4 rule 4 reserves it for "no test result in this run is
  trustworthy". A run with 200 PASS and one `UNMET` produced 200 trustworthy results; emitting 4 tells
  every consumer to discard all of them. Worse, the exit-4 arm being written for `run/player-gate:422`
  awards **no verdict at all** — so a single `UNMET` FEATURE id would void an entire gate leg. That is
  a bigger inversion than the one this ADR is fixing.
* **3 is wrong.** The host addressed the board fine; the premise failed inside the run.
* **A new code (5) is refused.** §4.1 is a standing warning that a new exit code silently breaks
  consumers — it is written from an incident where exactly that happened. A fifth code would cost the
  same consumer-teaching work as 4, and would tell the reader nothing that 1 plus the artifact does
  not.
* **1 is already the shipped precedent for this exact semantics.** `run/player-gate:190-193`'s
  `*:NOT-RUN` arm prints "the gate verified nothing for this cell" and returns **rc=1**, landed under
  TASK-573 and in the tree today. Exit 1 in this system does not mean "the firmware is broken"; it
  means "this run did not come back clean, read the body". Choosing anything else for `UNMET` would
  contradict a comparator that already ships.

**The exit code is a coarse signal and must stay one.** Typed gating (D5) reads the enum from the
artifact; the code exists so a shell `if` can tell clean from not-clean. Any consumer that needs to
distinguish `UNMET` from `FAIL` reads the artifact, and IFC-008 says so.

**D5 — gating is typed, and `UNMET` blocks.** A gate matches the enum member in the artifact. The
inversion selftest gains an arm for `UNMET` (`run/player-gate --selftest`, BP-068), so the "an
`UNMET` cell reads green" defect cannot be introduced silently — the same discipline that caught the
`FLAKY-PASS`/`FLAKE` inversion only after it had shipped.

**D6 — TASK-619 `A-7` is answered here, both halves.** The question was "specify the summary line as
an interface, or make it a JSON sidecar". The answer is **both, and in this order**: the artifact is
the interface (D1), the summary line stops being one, and the sidecar is the artifact's form. `A-7`
is not left open on the board; it folds into this ADR and IFC-008.

**Alternatives rejected**

| Alternative | Why not |
|---|---|
| Keep the human summary as the machine interface, tighten the regexes | Already tried by necessity; already produced a false REGRESS on a token that had shipped for years. A format with no schema and three parsers is not tightenable. |
| `UNMET` exits 4 | Voids trustworthy results and, at `run/player-gate:422`, voids whole gate legs on one FEATURE id. |
| `UNMET` exits with a new code 5 | §4.1's warning, paid twice, for information the artifact already carries precisely. |
| `UNMET` folded into `SKIP` (today's behaviour) | This *is* the defect. A SKIP is a statement about the configuration; an `UNMET` is a statement about the run. |
| `UNMET` folded into `NOT-RUN` | Loses attribution: `NOT-RUN` always names a blocking class failure, `UNMET` frequently has none. D2. |

**Consequences**

- *Easier*: gates stop parsing prose. A verdict token change becomes a schema version bump instead of
  a silent mis-parse. Per-class elapsed, build identity and the id-selection reason become queryable
  rather than archaeological.
- *Harder*: every consumer must be taught the artifact, and the three summary parsers must all retire
  in one change or the old path stays load-bearing. That is TASK-608's whole content and it is
  blocked on TASK-624 for good reason.
- *Constrained*: the artifact's schema is additive-only under its own version field, for the same
  reason IFC-007's key list is (ADR-065 D4).
- *Cost*: @Developer's estimate is ~1.5 d for the premise fields (build identity is already read by
  `run/player-gate`; `dut.py` has the env-verify machinery to hang the ELF hash on), ~1.5 d for the
  typed verdict, ~1 d for `UNMET` blocking plus the selftest arm
  ([Dev review](../designs/M-HARNESS2-DEV-review.md) rows 20, 21, 27).
