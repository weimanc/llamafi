### ADR-030 — 2026-05-25 — Velocity-joystick scroll model for PLEDIT

**Status**: accepted (2026-05-25)

**Context**:

The PLEDIT content-area scroll gesture (M-LIST-v3 / TASK-051d, TASK-078) is commit-on-release:
the list is frozen during drag and teleports by `abs(dy) / ROW_H` rows on Release. Live
feedback is absent, the coarse jump granularity (max 5 rows per swipe on a 65 px travel area)
makes navigating a 20-item queue laborious, and the tap/scroll discrimination heuristic
(`abs(dy) < 8 || (elapsed < 150 && abs(dy) < 16)`) produces accidental track plays.

The desired replacement: `dy = _dragCurrentY - _dragStartY` maps to **scroll speed** (rows/s),
not scroll distance. Holding the finger stationary at a nonzero offset scrolls continuously.
A dead zone (|dy| < DEAD_ZONE_PX) provides the tap region without elapsed-time logic.

Three options were evaluated in `designs/M-LIST-v4-velocity-scroll.md`:
- **A** drag-follows-position (iOS list): position-locked feel, requires sub-row rendering
- **B** velocity joystick (user request): speed from offset, integer scrollOffset, Phase-2-ready
- **C** hybrid position + momentum: full iOS model, most complexity

**Decision**:

**Option B — velocity joystick** — is adopted. `dy` maps to rows/second via a dead zone and
linear scale. A float accumulator `_scrollAccum` integrates velocity over time in a new
`tickScroll()` method called each app frame. `scrollOffset` advances in integer steps when the
accumulator crosses a row boundary. Tap is detected by Release within the dead zone alone.

Phase 2 (fling momentum on Release) and Phase 3 (rubber-band limits / Option C hybrid) are
explicitly deferred but architected for: `_scrollAccum` and the integrator are the same
primitive needed for momentum; adding fling requires only a `_flingVelocity` member and a
Release handoff, not a structural change.

Following VE review (`velocity-scroll-ve-review.md`), four changes were incorporated into
the design:

- `tickScroll` takes an explicit `float dt` parameter (not `millis()` internally), enabling
  the serial debug harness to inject synthetic time via `cmdTick n dtMs`
- `_scrollVelocity` is stored as a member after each tick and exposed via `dbgGet("scrollVelocity")`; `_scrollAccum` exposed via `dbgGet("scrollAccum")` — required for deterministic harness assertions
- `drawPlaylist()` seqno-change branch cancels an in-flight D_PLEDIT_SCROLL gesture to prevent tick re-scroll from the reset `scrollOffset`
- `_scrollSpeedK` is a mutable `float` member (not `static constexpr`) settable via `dbgSet("speedK", ...)` for in-session DUT calibration without reflash

`SCROLL_DEAD_ZONE_PX` remains `static constexpr int`.

**Consequences**:

Easier:
- Live visual feedback — list is no longer frozen during drag
- Tap discrimination reduced to a single dead-zone check — eliminates the `_dragStartMs` elapsed heuristic introduced in TASK-078 point 1
- Phase 2 fling momentum is a small additive change to `tickScroll()` — no structural rework

Harder / constrained:
- `SpotifyApp::tick()` must compute real dt and call `display->tickScroll(dt)` each frame — new call-site dependency with per-frame time bookkeeping
- `_scrollSpeedK` initial value (0.088 rows/s per px = 5 rows/s at max finger travel) requires DUT validation; `dbgSet("speedK", ...)` allows tuning without reflash
- `_dragStartMs` (added in TASK-078 point 1) becomes dead code — removal requires DUT evidence that the 8 px dead zone alone is sufficient (5 firm taps); see design §`_dragStartMs` removal
- Known limitation: Release while at a scroll limit with |dy| ≥ dead zone does not fire a tap — deferred to a future iteration (documented in design doc)

**Supersedes**: the commit-on-release scroll behavior of M-LIST-v3 / TASK-051d.
Supersedes: the two-axis tap discrimination of TASK-078 point 1 (elapsed + dy check).
