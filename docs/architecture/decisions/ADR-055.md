### ADR-055 — 2026-07-19 — Winamp chrome paints immediately after display init; boot progress AND whole-session WiFi status are surfaced through the title marquee, not a black screen / silence

**Status**: accepted (2026-07-20, human sign-off)

**Context**:

A timestamped fresh-boot capture (this session) showed the boot sequence
paints the Winamp skin chrome — a flash-resident composite blit that costs
no heap and negligible time — *last*, at `t≈4.1s`, after WiFi connect
(worst case ≈85 s across its three-stage fallback cascade,
`main.cpp:2199-2253`) and NTP sync (bounded 5 s). Between `displaySetup()`
(`main.cpp:2134`, `t≈0.8s`) and that first chrome paint
(`main.cpp:2415-2422`), the screen is a lit, solid-black rectangle — the
human explicitly reported hitting this on a dodgy network: *"the black
screen remains black for a prolonged time."*

Full investigation, including a line-by-line trace of every function the
early paint would call (confirming none of them depend on
`SettingsStorage::load()`, WiFi, NTP, or `spotifyTask::begin()` having run)
and the reasoning for placing the paint ~20 lines later than the
theoretical-earliest point (backlight-PWM sequencing; leaving the
SPIFFS-mount-failure hang path untouched), is in
`docs/architecture/designs/M-BOOT-UI.md`.

**2026-07-19 same-day scope extension**: the human resolved the design
doc's OQ2, which the original version of this decision had scoped out —
`wifiDiag::superviseTick()`'s background WiFi-reconnect supervisor
(`main.cpp:3886`, `wifiDiag.cpp:101-134`) runs silently for the entire
session, not just at boot, and produces nothing on screen regardless of
which app is foreground. The human decided the same marquee mechanism
should surface that too. Full investigation (why this isn't already
covered by existing per-app error indicators, how it coexists with
whatever the foreground app's own title machinery is doing, why Settings
needs the same suppression `superviseTick()` itself already uses) is in
the design doc's new §6. This ADR's Decision point 5, below, is new;
points 1-4 are unchanged from the original decision.

**Decision**:

1. **Paint the Winamp chrome (via `winampDisplay.showDefaultScreen()` +
   `renderTaskbar()`) immediately after `TouchCalStorage::load()` and the
   backlight-PWM handoff** (`main.cpp:~2176`), before `fetchConfigFile()`,
   `wifiDiag::begin()`, and the WiFi connect cascade begin. This is an
   *additional* direct call to the renderer, not a reordering of the
   existing `main.cpp:2415-2422` `g_apps[(int)AppId::Spotify]->init()` +
   `renderTaskbar()` block — that block is unchanged and its second pass is
   a cheap, idempotent repaint. `g_appLaunched` bookkeeping and
   `switchApp()`'s init-vs-resume branching are untouched by construction.
2. **Boot progress is surfaced through the existing title marquee**
   (`winampDisplay.setTitle()`), reusing its redraw-on-change behavior
   as-is. One `setTitle()` call is added at each existing WiFi/NTP
   phase-transition point in `setup()` — a single generic
   `"WI-FI: CONNECTING..."` string covers all WiFi fallback stages
   (hardcoded-SSID/NVS/SPIFFS-creds attempts, re-association settle; human
   decision, design doc OQ1 — simpler than per-stage text, nothing to keep
   in sync if the cascade is ever reordered), plus distinct strings for the
   connected/retry-in-background/no-credentials outcomes and the NTP
   sync/HTTPS-fallback phases — no new state machine, no second display
   mechanism. Transition to real content (track title, station title)
   requires no new code: `setTitle()`'s existing dedup means the first real
   call simply overwrites whatever boot-status string was showing, the same
   mechanism TASK-362 already relies on.
3. **Marquee-scroll liveness rides the wait loops' existing
   `esp_task_wdt_reset()`/`yield()` per-iteration hook.** Every WiFi wait
   loop already calls `esp_task_wdt_reset()` each iteration (TASK-288); the
   NTP loop calls `yield()`. Adding `winampDisplay.tickMarquee()` alongside
   those calls is a ~4-line addition, self-throttled internally, requiring
   no restructuring of the loops into async/cooperative shape. Priced as
   effectively free once the phase-text call sites are already being
   edited — shipped together with (2), not as a separate follow-up. Note
   (per decision 2's generic-string choice): every phase string, including
   the WiFi one, currently fits `TITLE_W` without scrolling, so this scroll
   hook is wired up but presently inert — it activates automatically if any
   future phase string is lengthened past the 25-char budget, at zero
   additional engineering cost then.
4. **Full touch responsiveness during the blocking WiFi/NTP waits is
   explicitly out of scope for this decision.** It is a materially larger
   change (reading touch state and running a gesture path inside loops that
   are currently pure `delay()`/wait), evaluated and consciously deferred —
   not defaulted away from without consideration. Same treatment for the
   WiFi fallback cascade's own worst-case duration (≈85 s): painting chrome
   early and showing status text makes that wait *look* better, it does
   not make it *shorter* — shortening/parallelizing the cascade itself is
   flagged as a separate, related opportunity, not entangled with this
   decision, and not solved here.
5. **(New, 2026-07-19 extension) The same marquee also surfaces
   `wifiDiag::superviseTick()`'s background reconnect, whole-session, via a
   centralized guard on `setTitle()` itself — not a per-app change.**
   `WinampDisplay` gains a small piece of state (an active flag + a
   stash buffer holding the most recently *attempted* real title) and
   `setTitle()` gains a guard: while the WiFi-down override is active,
   every caller's `setTitle()` call is stashed, not drawn — no foreground
   app's title machinery needs to know the override exists, and none of
   them can paint over it. Two new entry points
   (`showWifiDownOverride()`/`clearWifiDownOverride()`), driven by a new
   `loop()`-level edge-triggered detector (`WiFi.status() == WL_CONNECTED`,
   self-contained down-duration tracking, no new `wifiDiag` API), show
   `"WI-FI: RECONNECTING..."` once continuously down past a threshold
   (proposed 10 s, DUT-tunable — design doc OQ5) and restore the stashed
   title the instant `WiFi.status()` reports connected again. This active
   restore is required, not optional: Spotify's own `setTitle()` call is
   gated on the track actually *changing*
   (`handleCurrentlyPlaying()`/`!isSameTrack(...)`), so on an outage where
   the track doesn't change, Spotify would never naturally re-call
   `setTitle()` to clear the override — a passive "wait for the app's next
   real call" approach (which is what decision 2 relies on for boot, and
   which works there only because *some* real content is always eventually
   coming) would leave the marquee stuck on the outage message even after
   WiFi recovers. **The detector is suppressed by the identical
   `currentAppId != AppId::Settings` condition `superviseTick()` itself
   already uses** (`main.cpp:3886`) — load-bearing, not cosmetic:
   `switchApp()` wipes and every app (including Settings) repaints the
   *entire* app canvas on entry (the codebase's existing full-screen-canvas
   convention), so an ungated override would blit stray marquee text over
   the Settings UI, not just be redundant with it.

**Consequences**:

- *Easier*: on any boot — fast or slow, healthy AP or dodgy — the user sees
  the Winamp skin and taskbar within roughly a second of power-on, with
  status text on the title marquee, instead of an indeterminate span of
  solid black. As of the same-day extension, a WiFi outage *at any later
  point in the session*, with any app foreground, is now visible on the
  same marquee instead of being 100% silent (previously: a `[wifi-sup]`
  serial log line was the only signal, and — per the design doc's §6
  investigation — neither Spotify's own title (which goes silently stale
  indefinitely) nor the taskbar's active-slot indicator (which doesn't
  reflect this specific health state, a separate pre-existing `ADR-046`
  gap, see below) nor WebRadio's `ERROR_WIFI` state (dead code in
  production — never actually assigned) covered this. Directly answers the
  human's "embedded devices should have instant boot experience" complaint
  plus the broader ask to make the *whole* WiFi story visible, not just
  the boot slice of it.
- *Harder*: the boot-only portion remains a small, additive diff (new
  early-paint call site + ~10 `setTitle()` calls + ~4 `tickMarquee()`
  calls). The whole-session extension (decision 5) is a somewhat larger,
  but still small and centralized, addition: one guard clause in
  `setTitle()`, two thin wrapper methods, one new `loop()`-level detector
  block. The one real risk carried over from the original decision is
  text-budget drift: `TITLE_W` is 154px / 25 chars without scrolling — a
  future edit that lengthens a phase string past that budget silently
  starts scrolling instead of failing loudly (acceptable, designed
  overflow behavior, worth a VE eyeball at implementation). A second,
  narrower risk introduced by decision 5: the `loop()`-level detector's
  Settings-suppression condition must be kept in sync with
  `superviseTick()`'s own — enforced by convention/comment, not a shared
  constant, flagged in the design doc's registry entry (X042) as
  `risk: medium` specifically for that reason.
- *Constrained*: the new code must live inside the same `#ifdef
  WINAMP_DISPLAY` guard the existing `SpotifyApp`/`g_apps[]`/taskbar code
  already uses — scoped to `cyd2usb_winamp` and its `extends` family
  (`_debug`, `_screenlog`, `_webradio`, `_webradio_16k`,
  `_debug_noSpotify`). The non-Winamp `cyd`/`cyd2usb` and `trinity`
  (HUB75 matrix) envs are unaffected and out of scope. Decision 5's
  `loop()`-level detector must be gated identically to
  `wifiDiag::superviseTick()` — a shared-policy coupling, not a
  call-graph one (see design doc §6 and registry edge X042).
- *Explicitly not decided here* (flagged as related, separately-scoped
  opportunities in the design doc): shortening the WiFi fallback cascade's
  worst-case duration (§4); touch input during the blocking waits; a
  dot-cycle "connecting…" animation beyond marquee-scroll reuse (§3). New
  as of the same-day extension: fixing the taskbar active-slot indicator's
  own gap (not reflecting `spotifyTask::isHealthy()`, only
  `authError()`/`connecting()` — found while investigating §6, a real but
  separate defect in the already-accepted `ADR-046`, not touched by this
  decision — design doc OQ4).

**Verification gate** (handed to VE, per the design doc's Exit criteria —
qualitative per OQ3's resolution, not a precise timestamped capture):
DUT eyeball on a healthy AP confirms chrome+taskbar visible immediately on
boot with the phase-text sequence legible on the marquee; ≥1 boot forcing
the full WiFi fallback cascade (deliberately wrong credentials or
unreachable AP) confirms chrome+taskbar remain visible throughout with the
generic WiFi status text, no black screen at any point after
`displaySetup()` returns; a WebRadio-mode boot and a no-credentials boot
both confirm clean hand-off (no stale/glitched boot-status text) to
`switchApp(AppId::WebRadio)`/`switchApp(AppId::Settings)` respectively; one
screendump eyeball pass (BP-048) across every phase string confirms no
clipping. **New for decision 5**: WiFi dropped mid-session with a
non-Spotify, non-WebRadio app foreground shows the reconnect override
within one threshold-plus-one-`loop()`-tick window and clears within one
`loop()` tick of reconnect; the same with Spotify foreground and an
*unchanged* track across the outage confirms the active-restore mechanism
(not a passive wait) actually recovers the correct title; the same with
WiFi dropped while Settings is foreground confirms no marquee text ever
paints over the Settings UI and the indicator state is correct within one
`loop()` tick of returning to any non-Settings app. Full serialdbg suite
green on `cyd2usb_winamp`; `./run/check` 5-gate green.

**Supersedes**: none. Independent of `ADR-054`/`M-SPOTIFY-BOOT-GATE`
(confirmed no conflict — this decision's early chrome paint reads the same
`spotifyTask::` static accessors `ADR-054` already validated as safe
pre-`begin()`, and does not change when or whether `spotifyTask::begin()`
runs). Independent of `M-WEBRADIO-WINAMP-UI` (confirmed no shared surface —
that design touches the PLEDIT bar/time-digits/vis/volume slider, never the
title marquee; entry into WebRadio mode always goes through `switchApp()`'s
unconditional wipe-and-repaint, which cleanly supersedes this decision's
boot-status text the same way real track/station titles already do today).
Does not fix, and is independent of, the taskbar active-slot indicator gap
noted above (a candidate future amendment to `ADR-046`, not this ADR, if
the human wants it addressed).

**Companion design**: `docs/architecture/designs/M-BOOT-UI.md` (see §6 for
the 2026-07-19 extension).
