### ADR-012 — 2026-05-08 — Async Spotify HTTP on a dedicated FreeRTOS task

**Status**: accepted (2026-05-21 — TASK-031 DUT-verified; VE + Developer review complete)

**Context**:

TASK-029 perf-instrumentation captured on DUT (`cyd2usb_winamp`):

```
loop_max=4191ms slow=display.input:4189ms
loop_max=2014ms slow=spotify.poll:2013ms
```

The two worst loop paths are `display.input` and `spotify.poll`. Both block on the same thing: `SpotifyArduino` HTTP calls run synchronously on the Arduino loop task. While in flight, the loop task can't sample touch, can't redraw the display, can't service the heartbeat. Result: a 4-second freeze every time the user taps a button (touch handler fires the API call inline) and a 1.5–2 s freeze every poll cycle.

User-perceived "sluggish controls" maps directly to this. The optimistic-UI work in M5 (TASK-019 / ADR-011) only papered over the symptom — the underlying loop is still frozen. Original ADR-011 framing assumed only the polling cost; TASK-029 data widens that scope: touch-driven calls dominate.

**Decision**:

Move all HTTP that goes through `SpotifyArduino` onto a dedicated FreeRTOS task. The Arduino loop task **never blocks on HTTP**, only on local work (display, touch, log).

Concretely:

1. **One task: `spotifyTask`.** Pinned to APP_CPU (core 1, where Arduino's loop already runs). Stack 10 KB (mbedtls handshake needs ~6–8 KB; 2 KB headroom). Priority 1 (above tskIDLE_PRIORITY, below the WiFi/tcpip task at priority 18+). Owns: the global `WiFiClientSecure client`, the `SpotifyArduino spotify` instance, the consecutive-failure counter, the poll cadence timer.

2. **Request queue: `xQueueHandle reqQueue`, depth 8.** Loop posts a small struct `{ Action action; int32_t param; }`; the task `xQueueReceive` with a tick timeout that doubles as the poll-cadence sleep. Actions: `POLL`, `FORCE_POLL`, `NEXT`, `PREV`, `PLAY`, `PAUSE`, `SEEK(ms)`. Future-friendly for `SHUFFLE`, `REPEAT`, `VOLUME`. Loop posts with `0` timeout — drop-and-log on full queue rather than block.

3. **Snapshot slot: a single `volatile struct Snapshot` guarded by `portMUX_TYPE`.** Task writes after every successful poll; loop reads on every render. Fields: `isPlaying`, `progressMs`, `durationMs`, `capturedAtMs`, `trackUri[200]`, `trackName[128]`, `artistName[128]`, `albumName[128]`, plus a sequence counter so the loop can detect "new poll happened" cheaply. Critical sections kept tiny — `memcpy` under the spinlock, no logic.

4. **Display calls stay on the loop task.** The new task does NOT touch `tft`. `handleCurrentlyPlaying` becomes "write to snapshot"; the loop, on every iteration, compares snapshot's sequence counter to its last-rendered value and calls `printCurrentlyPlayingToScreen` / `displayTrackProgress` if anything changed. Avoids any concurrent SPI access to TFT_eSPI.

5. **`songStartMillis` / `songDuration` become atomic int32 globals.** On ESP32 (xtensa, 32-bit aligned), naturally atomic; no mutex needed for read-modify on `int32_t`. Task writes after a successful poll; loop reads in `updateProgressBar`. Touch handler still writes them (for the optimistic-UI freeze) — that write competes with the task's write, but the user-touch happens at a moment when the user *intends* the local value to win, so racing with a poll arriving in the same millisecond is exactly the right behaviour: whoever wrote last wins, and the next poll re-anchors anyway.

6. **Backoff stays inside the task.** Task owns `consecutiveSpotifyFailures`. Touch (REQ_NEXT etc.) calls reset it to 0 inside the task before processing. Loop never touches it.

7. **Touch handler new shape**:

   ```cpp
   case 0: spotifyTask::enqueue(spotifyTask::PREV); break;
   case 4: spotifyTask::enqueue(spotifyTask::NEXT); break;
   ...
   spotifyTask::enqueue(spotifyTask::FORCE_POLL);  // request a poll soon
   songStartMillis = 0;                              // optimistic freeze unchanged
   ```

   No more `spotify_display->previousTrack()` synchronous calls inline. Press → enqueue → return in microseconds.

**Expected impact**:

`loop_max` should drop from 4 191 ms to under 30 ms in the typical case (only display blits + log writes contribute to per-iteration cost). The 1.5–2 s `spotify.poll` blocks vanish entirely from the loop timeline. UI control responsiveness goes from "sluggish" to "instant".

**What this does not do**:

- Doesn't fix DMA-able blits (TASK-032; deprioritised).
- Doesn't fix the screenLog full-screen redraw tearing (the overlay is opt-in; not addressed here).
- Doesn't fix the `delay(80)` press-hold (TASK-034; ships separately, ~10 LOC).

**Memory impact**:

- New task stack: 10 KB.
- Queue: 8 × 8 bytes = 64 bytes.
- Snapshot struct: ~700 bytes.
- Spinlock: 8 bytes.

Total ~11 KB SRAM. Free heap on `cyd2usb_winamp` is ~200 KB. Comfortable.

**Risks + mitigations**:

| Risk | Mitigation |
|---|---|
| `WiFiClientSecure` accessed from two tasks | Task is the *only* user; loop never touches the client. |
| TFT_eSPI accessed from two tasks | Task never calls into `tft`; only the loop does. |
| Snapshot reader sees half-written struct | All reads under the same spinlock that writes use. Critical sections are bounded `memcpy`. |
| Queue full when user mashes buttons | `xQueueSend` with 0 timeout drops + emits a `LOG_W("spotifyTask", "queue full")`. Lost actions are diagnostically visible. |
| Token refresh races inside SpotifyArduino | Refresh runs inside the task, using the task-owned client. No second writer. |
| `consecutiveSpotifyFailures` and other counters racing | Owned by task; loop never reads/writes. |
| Backoff state divergence between user expectation and task | Touch-action reset is part of the queue protocol; task processes the action which includes the reset before issuing the call. Strict ordering. |
| Stack overflow on token refresh + JSON parse | 10 KB stack with 8 KB worst-case. 2 KB headroom. Add `uxTaskGetStackHighWaterMark` for the task to the heartbeat. |
| WiFi disconnect mid-call | Task receives `-1` from the call; existing backoff handles. No different from today. |

**Multi-role review** (inline, per LL-010):

| Role | Concern | Disposition |
|---|---|---|
| @VE | Testability: how do we verify that loop never blocks? | TASK-029 perf instrumentation already does — `loop_max=Nms` heartbeat field. Exit criterion: `loop_max < 100 ms` over a 5-min DUT window with active touch + poll. T060–T063 to be added. |
| @VE | Snapshot read consistency under load | T064: from a host script, hammer the device with rapid prev/next while polling concurrently; capture serial; assert no corrupt track-name strings render (no half-written UTF-8 sequences). DUT-runnable. |
| @VE | Queue-full behaviour visible | Already covered: `LOG_W("spotifyTask", "queue full")`. T065: rapid-fire touch and confirm the WARN appears in `/log` (or serial). |
| @Developer | `spotifyTask` task creation order vs WiFi up | Task starts after `spotifyRefreshToken()` returns and after `logsink::serverBegin()`. Order: WiFi, time, oauth, log server, **then** spotifyTask. Document in `.ino` with comments. |
| @Developer | What happens if the queue stays empty for >5 s? | Task's `xQueueReceive` timeout = `delayBetweenRequests` (5 s default). On timeout it self-issues a `POLL`. On a `FORCE_POLL` it polls immediately and resets the timer. Cadence preserved. |
| @Developer | The existing `spotifyLogic.h` has handleCurrentlyPlaying calling display methods directly | That gets refactored: `handleCurrentlyPlaying` writes the snapshot only; the loop does the display calls. Renamed accordingly. The existing `spotifyLogic.h` API stays for the loop side; internals change. |
| @QM | LL-013 — same numeric error code masking distinct bugs | Not applicable here; this is structural, not mbedtls-error territory. |
| @QM | LL-015 — optimistic-UI mutations must outlive the same loop iteration | Touch's `songStartMillis = 0` write happens before the post-touch poll completes. Snapshot write from the task happens later, on its own task. The current 1.5-second deferred-repoll guard becomes unnecessary in this design — touch's optimistic write isn't racing anything in the same loop iteration anymore. Remove the deferral as part of this work. |
| @PM | Sub-task split | (a) skeleton (header + task + queue + empty processing), (b) move POLL into the task, (c) move touch actions into the task, (d) remove the deferred-repoll guard now that the race is gone. ~half a day total. |

**Architect responses**:

All concerns above are accepted as-stated. Two amendments fold back into the design:
- VE T060–T065 to be authored at implementation time.
- The 1.5-second deferred-repoll guard from M5 becomes redundant and is removed in step (d) per @QM (LL-015).

**Sub-task split (PM)**:

| Step | Description | LOC est | Touches |
|---|---|---|---|
| TASK-031a | `spotifyTask.h` + storage TU; task creation wired into `.ino` after `spotifyRefreshToken`; queue + snapshot scaffolding; empty action handling (no API calls yet). | ~150 | 2 new files, .ino |
| TASK-031b | Move `getCurrentlyPlaying` into the task. Loop's `updateCurrentlyPlaying` becomes a snapshot-reader that calls display methods on snapshot-changed. | ~80 | spotifyLogic.h, .ino |
| TASK-031c | Move `nextTrack/previousTrack/play/pause/seek` into the task. Touch handler enqueues; loop never blocks on the API. | ~30 | winampDisplay.h, cheapYellowLCD.h |
| TASK-031d | Remove the 1.5 s deferred-repoll guard from M5 (LL-015 is no longer applicable since the race is gone). Restore `requestDueTime = 0` (or equivalent: enqueue FORCE_POLL). | ~10 | winampDisplay.h |

**Out of scope for this ADR**:

- Multiple Spotify accounts / multi-user. Not on roadmap.
- HTTP/2 or persistent connection reuse — out of scope; the lib's HTTP/1.0 + per-call connect pattern stays.
- Generic background-IO framework. Spotify is the only blocking IO source today.
