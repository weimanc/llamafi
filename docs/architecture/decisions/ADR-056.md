### ADR-056 — 2026-07-29 — Real per-block peak envelope for WebRadio's VU meter (amends ADR-009, WebRadio only)

**Status**: proposed — pending human eyeball sign-off (BP-048 gate; see
M-WEBRADIO-REAL-VIS.md's exit criteria)

**Context**:

ADR-009 chose a synthetic (decorative) VU envelope for the whole Winamp vis
system because the Spotify path never had access to real audio on-device —
the Web API endpoints that would have supplied it (`audio-features`/
`audio-analysis`) returned 403 for this app's client, and ADR-009 explicitly
flagged that constraint as Spotify-specific: "Adding a real audio source
later... means revisiting this ADR."

WebRadio invalidates that constraint for itself, but not for Spotify: it
decodes real PCM locally on the audioI2S pump task, so real audio levels are
actually available there. M-WEBRADIO-WINAMP-UI item 4 registered PROP-005 to
find out whether real levels were affordable under the board's decode-tail
budget (TASK-278) and DRAM constraints, without committing to shipping them.

That R&D (EXP-015 through EXP-018) found:

- **Cost is a non-issue.** Real per-block peak envelope measured identical
  `maxPumpMs` (42ms) to a no-op baseline, on real DUT hardware, across four
  independent measurements (rungs 1, 2, the peak-vs-RMS A/B, and rung 3's
  heavier per-band math). TASK-278's decode-tail kill gate never
  materialized.
- **Storage, not CPU, is this board's real constraint, and it's structural,
  not a one-off.** Any `SERIAL_DEBUG`-enabled build here links with zero
  bytes of static-BSS headroom (confirmed via the linker `.map` — `_bss_end`
  sits exactly at the segment boundary) — confirmed down to a single 4-byte
  pointer alone overflowing it. This generalizes past this one feature: any
  future change here that needs new persistent cross-task state must reuse
  existing storage or it will not link, independent of how small the
  addition is.
- **Quality is validated for the VU-mode envelope specifically** (531/9800
  changed px between two 1.5s-apart screendumps during real playback,
  needing no further tuning) — but only for `VIS_VU`. `tickAtlas()`/
  `tickWaveAtlas()` don't take a level argument at all and remain
  play/pause-gated only, exactly as before; a broader real-spectrum
  extension (rung 3, per-band Goertzel energy for `VIS_SPECTRUM`) was also
  found cost-free but is not part of what this ADR covers — it's
  unscheduled follow-on work with its own open UX question (does
  `VIS_SPECTRUM` return to the tap-cycle at all).

M-WEBRADIO-REAL-VIS.md (design doc, Architect) worked out the production
scope from this evidence and leaned narrow: ship the `VIS_VU` envelope only,
as `vu-002`.

**Decision**:

For WebRadio specifically, when real PCM is available on the pump task, use
a real per-block peak audio envelope instead of ADR-009's synthetic
swell/beat/noise recipe — **scoped to `VIS_VU` mode only**. Spotify's
synthetic path (ADR-009 option (e)) is otherwise completely unchanged: no
local audio there, no plan to change that, and its call site required zero
code changes.

Mechanism (landed as `vu-002`, commits `6444c4c`/`f3e0523`): `vu::tick()`
gains an optional `realAudio` parameter (default `false`). When true, it
trusts `vu::lLevelRef()`/`rLevelRef()` as already fresh rather than
synthesizing a target — those values are kept fresh by a permanent
`audio_process_extern` hook in `webRadioApp.h`, computing real per-block
peak L/R on the wrAudio pump task and writing directly into those same
statics. Single-writer discipline (`X043`): whichever mode is active
(Spotify synthetic vs. WebRadio real) is the sole writer for as long as
it's active, mechanically enforced (not just convention) by `switchApp()`'s
suspend-before-activate ordering plus `s_wrAudioMutex` serialization
between the pump task and any app switch.

This ADR also records, as a **sanctioned technique for this board**: any
future cross-task real-time state here (pump task ↔ UI thread) should be
implemented by promoting existing renderer statics to namespace-scope
accessors and swapping the writer by active mode — not by allocating new
storage, lazily or otherwise. The zero-DRAM-headroom finding above means
"just add a small buffer" is not a safe default assumption on this board,
the way it might be elsewhere.

**Consequences**:

- *Easier*: WebRadio's `VIS_VU` display is now genuinely audio-reactive,
  not decorative. The storage-reuse pattern this required is now documented
  and precedented (this ADR + `X043`), so the next feature that needs to
  move state across this same task boundary doesn't have to rediscover the
  DRAM wall from scratch by hitting a failed link.
- *Harder*: the visualizer's behavior is no longer uniform across data
  sources — `VIS_VU` is audio-reactive under WebRadio but still synthetic
  under Spotify, while `VIS_ATLAS_MODE`/`VIS_WAVE_ATLAS` remain pre-baked
  playback loops (play/pause-gated only) under *both* sources. This
  asymmetry should be kept explicit in any user-facing description of the
  visualizer, not implied to be uniformly "real" or uniformly "decorative."
- *Constrained*: any future extension of real-audio-driven vis on this
  board (e.g. rung 3's spectrum bands, still unscheduled) inherits the same
  zero-new-static-storage constraint as a hard link-time wall, not an
  optimization nice-to-have. Budget design time for finding a reuse point,
  same as this ADR's mechanism did, rather than assuming a small allocation
  will fit.

**Amends**: ADR-009 — narrowly, for the WebRadio case only. ADR-009's
original decision, reasoning, and the Spotify synthetic implementation it
describes are otherwise untouched and still in force.
