### ADR-027 — 2026-05-25 — TFT hardware state ownership contract in multi-app context

**Status**: accepted

**Context**:

`TFT_eSPI` is a singleton (`tft`) shared by all apps in the M-MULTIAPP shell. It maintains several process-global state fields that persist across any call boundary:

| Field | Setter | Default |
|-------|--------|---------|
| `textdatum` | `setTextDatum()` | `TL_DATUM` (0) |
| `textfont` | `setTextFont()` | 1 |
| `textsize` | `setTextSize()` | 1 |
| `textcolor` / `textbgcolor` | `setTextColor()` | white / black |
| `swapBytes` | `setSwapBytes()` | false |
| `cursor_x`, `cursor_y` | `setCursor()` | 0, 0 |

ADR-026 defined structural layering rules for the multi-app shell (dependency direction, hit-testing ownership, `renderTaskbar()` caller) but said nothing about TFT hardware state. The implicit assumption was that each app would manage its own TFT state, but no contract was recorded.

The bug that motivated this ADR: `ClockApp::drawTime/drawDate` called `tft.setTextDatum(MC_DATUM)` and returned without resetting to `TL_DATUM`. On the next Clock→Spotify switch, `WinampDisplay::drawPlaylist()` called `tft.drawString()` with `MC_DATUM` still active. Every PLEDIT row's text was left-shifted by `textWidth/2`, placing 2–3 characters over the left border and the remainder partially off-screen. (LL-035)

The scope of the problem is wider than the single incident: `textfont`, `textsize`, `textcolor`, and `swapBytes` are all similarly vulnerable. Any future app that sets these without resetting introduces a latent cross-app corruption.

---

**Decision**:

TFT hardware state is a shared resource with no per-app isolation. Every rendering path must follow a two-layer ownership rule:

**Layer 1 — Producer rule (reset at exit):**
A function that sets a TFT state field to a non-default value *must reset it to the default before returning*. This is the caller's responsibility; it is not acceptable to leave state for the next callee to clean up.

**Layer 2 — Consumer rule (assert at entry):**
A function that depends on a specific TFT state field *must assert that state at the top of the function*. Do not inherit TFT state from a prior call. This provides defense-in-depth: even if the producer rule fails (bug, future regression, external library call), the consumer is correct.

Both layers are required. Producer-only is insufficient because silent callers can forget; consumer-only is correct but becomes unmaintainable as the function count grows.

**Reference implementation already in the codebase:**

- `screenLog.h:58–88` correctly applies the producer rule for `swapBytes`: saves, sets `false`, restores on exit.
- `winampDisplay.h::drawPlaylist()` (post LL-035 fix) applies the consumer rule: calls `tft.setTextDatum(TL_DATUM)` before its `drawString` calls regardless of inherited state.
- `main.cpp::ClockApp::drawTime/drawDate` (post LL-035 fix) applies the producer rule: calls `tft.setTextDatum(TL_DATUM)` after its `drawString` calls.

**Scope of this ADR:**

This rule applies to all rendering functions in all `App` implementations and in shell-level code (`renderTaskbar`, `screenLog`, `WinampDisplay`). It does not apply to one-shot `setup()` or `displaySetup()` calls that set intentional persistent initial state (e.g. `tft.setSwapBytes(true)` in `WinampDisplay::displaySetup()`).

---

**Consequences**:

What becomes easier:
- New app authors have a named, documented contract to follow.
- Code review has a concrete checklist item: any `tft.set*()` with a non-default value must have a matching reset in the same scope, or the consuming function must assert its required state.
- The two-field classes of bug (datum leak, color leak) are structurally visible: grep for `setTextDatum` / `setTextColor` / `setTextFont` without a matching reset and the violation is apparent.

What becomes harder / constrained:
- Functions that set multiple TFT fields must reset all of them — the contract is per-field, not per-function. A function that sets both `textdatum` and `textfont` must reset both.
- `renderTaskbar()` currently leaks `setTextColor(TFT_WHITE, TASKBAR_BG_RGB565)`. This is benign today (every consumer sets its own color) but is a violation of the producer rule. It should be fixed when `renderTaskbar()` is next touched.

**Known compliant callers at time of ADR**:
- `screenLog.h` — swapBytes (compliant)
- `winampDisplay.h::drawPlaylist()` — textdatum (consumer rule, compliant post-fix)
- `main.cpp::ClockApp::drawTime/drawDate` — textdatum (producer rule, compliant post-fix)

**Known non-compliant callers at time of ADR** (benign today, should be fixed):
- `taskbar.h::renderTaskbar()` — textcolor not reset (LOW severity; all current consumers set their own color)

**Supersedes**: nothing. Extends ADR-026 (app lifecycle + layering rules) with a hardware-state addendum.

**Adopted from**: LL-035
