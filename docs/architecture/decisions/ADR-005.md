### ADR-005 — 2026-04-27 — Single `PlayerState` with locally interpolated position

**Status**: superseded by ADR-006 (2026-04-28)

**Superseded because**: the "single canonical `PlayerState` shared across `Poller` / `Interpolator` / `IntentHandler` / `VuSynth` / `Renderer`" framing depends on the layered component graph from ADR-001, which has been superseded. Under ADR-006, state lives where the Spotify-Diy-Thing baseline puts it — inside the `SpotifyArduino` instance and module-local globals in `spotifyLogic.h` — and there is no separate `Interpolator` task.

The *interpolation rule itself* survives and is still needed (the Winamp seek bar must advance smoothly between ~1 Hz polls). It is recorded in `architecture.md` Target section, not as a separate ADR. Summary of what survives:

- On each poll, stash `progress_ms` and a `millis()` timestamp.
- Each render frame, if playing, the displayed position is `progress_ms + (millis() - stamp)`.
- On the next poll, accept the API value as truth; if the gap exceeds ~500 ms, snap rather than glide.
- A user seek writes the local position and timestamp directly so subsequent frames continue from the new point.

The 500 ms snap threshold remains an Open Question (tuning, not architecture).

**Context**:
The renderer needs a current playback position at every frame (~30 FPS). The Spotify Web API only provides `progress_ms` snapshots at poll time (~1 Hz per the proposed tasking model). Without local interpolation, the seek bar would advance in 1-second jumps and the displayed elapsed-time field would update visibly only once per second, which breaks the Winamp aesthetic.

There is also a structural question: should playback metadata, position, VU buffer, and connection status live in one shared model, or be split across multiple component-owned stores?

Forces:
- The renderer is a pure function over current state; it benefits from a single read source.
- Multiple core components (`Poller`, `Interpolator`, `IntentHandler`, `VuSynth`) need to write to overlapping fields. Splitting risks divergence (e.g. two truths for `position_ms`).
- The system is single-process, single-MCU; locking concerns are bounded and manageable.
- Position-from-poll snaps would visibly stutter if used directly; interpolation is required regardless of where the field lives.

What needs a decision: data ownership shape, and the rule for advancing `position_ms` between polls.

**Decision**:
Adopt a single shared `PlayerState` instance as the canonical model for the renderer and for any component that needs to read playback truth. Its full shape is specified in the architecture's Component Architecture section.

Position interpolation rule:

- On every successful poll, `Poller` writes `progress_ms` from the API response into `PlayerState.position_ms`, and stamps `last_poll_clock_ms` from the `Clock` leaf.
- The `Interpolator` task ticks at ~50 ms (per ADR-001 tasking sketch). If `is_playing` is true, it advances `PlayerState.position_ms` by the elapsed wall-clock delta since the previous interpolator tick.
- If `is_playing` is false, the interpolator does not advance the position.
- On poll, if the difference between the API-reported `progress_ms` and the locally interpolated value exceeds **500 ms** in either direction, snap to the API value. Smaller differences are accepted to avoid visible jitter.
- The `IntentHandler`'s optimistic seek (per ADR-004) writes `position_ms` directly and updates `last_poll_clock_ms` to "now," so subsequent interpolation continues from the new position.

Concurrency:

- All writes to `PlayerState` happen on the main task / event loop. On an RTOS, a single mutex guards the struct; on a cooperative super-loop, no lock is required.
- The renderer reads under the same discipline; it never holds a reference to a sub-field across yields.

**Consequences**:
- *Easier*: One source of truth for the renderer; interpolation logic localised to one task; PC mirror behaves identically because it uses the same model and the same `Clock` interface.
- *Harder*: Any new playback-related field must be added thoughtfully — the struct is a hot data structure read every frame. Bloat costs cache-friendliness and code review attention.
- *Constrained*: Components that need playback truth must read from `PlayerState` rather than caching their own copies.
- *Open*: The 500 ms snap threshold is a starting value, subject to tuning once real network jitter is measured.
