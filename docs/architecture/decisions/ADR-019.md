### ADR-019 — 2026-05-16 — TLS root CA strategy: keep two hardcoded certs

**Status**: accepted (2026-05-16, Architect close of M7 open question)

**Context**:

The firmware reaches three Spotify domains over TLS:

| Domain | Purpose | Client |
|---|---|---|
| `api.spotify.com` | All player API calls (poll, next, prev, seek, volume, etc.) | `spotifyLogic.h:35` — `client.setCACert(spotify_server_cert)` |
| `accounts.spotify.com` | Access-token refresh (shared `WiFiClientSecure` client, reconnects per ADR-007) | same client, same cert |
| Album art CDN (`i.scdn.co`, `mosaic.scdn.co`) | JPEG image fetch | `cheapYellowLCD.h:272` — `client.setCACert(spotify_image_server_cert)` |

Both `spotify_server_cert` and `spotify_image_server_cert` are hardcoded PEM strings in the vendored `lib/SpotifyArduino/src/SpotifyArduinoCert.h`. Both resolve to **DigiCert Global Root CA G2**, which expires 2038-01-15.

Three alternative strategies were evaluated:

- **(A) Keep current** — two hardcoded DigiCert CA PEMs, applied via `setCACert()` before each connection. No firmware change needed.
- **(B) ESP-IDF cert bundle** — `esp_crt_bundle_attach()` against the full CA store bundled with ESP-IDF, eliminating dependency on a single root cert. Requires calling into mbedTLS config directly, which `WiFiClientSecure` in Arduino-ESP32 2.0.17 does not expose cleanly — the `WiFiClientSecure::setClientCertBundle()` API arrived in later versions. Adopting it would require bypassing `WiFiClientSecure` entirely or patching the Arduino-ESP32 layer.
- **(C) `setInsecure()`** — skip verification. Rejected categorically: no benefit over option A and eliminates the protections that CA pinning provides against endpoint impersonation.

**Decision**:

Keep option **(A)** — two hardcoded CA PEMs, unchanged. No new code required.

Rationale:

- The DigiCert Global Root CA G2 cert covers all three domains (`api.spotify.com`, `accounts.spotify.com`, and the Spotify CDN) and has been stable since the library shipped. The 2038 expiry is outside any credible project horizon.
- `accounts.spotify.com` shares the `api.spotify.com` client (stop/connect cycle per ADR-007) and the same root CA — one cert handles both.
- Option (B) is operationally appealing but requires a deeper Arduino-ESP32 patch that violates ADR-006's "leave the baseline architecture alone" constraint. The risk it mitigates (CA rotation) is extremely low on a fixed 25-year-lifetime root.
- The failure mode for a stale cert is obvious (TLS handshake failure, logged via M-LOG `esp_log`, device stops fetching) rather than silent. Remediation is a firmware reflash — acceptable for a hobbyist device.

**What changes if Spotify rotates to a new CA**:

Update `SpotifyArduinoCert.h` in the vendored `lib/SpotifyArduino/` with the new root CA PEM and reflash. No architectural change needed. The vendored fork is already carrying patches (ADR-007 stop/connect fix); a cert update is a further local patch in the same file.

**Consequences**:

- *No action required.* This ADR closes the open question by documenting the status quo as intentional.
- The cert expiry date (2038-01-15) is the only external event that would force a revisit without Spotify action. Note it here as the maintenance trigger.
- If the project ever migrates off Arduino-ESP32 2.0.17 to a version with clean `setClientCertBundle()` support, revisit option (B) — it becomes low-cost at that point.

**Closes**: "WiFi + TLS root CA strategy for `accounts.spotify.com` and `api.spotify.com`" from `architecture.md` Open Questions.
