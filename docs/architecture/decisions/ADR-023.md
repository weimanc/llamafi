### ADR-023 — 2026-05-17 — Operational state-drift staleness indicator (M-DRIFT)

**Status**: accepted (2026-05-17)

**Context**:

M-DRIFT (drift-001) surfaces when the DUT's chrome has gone stale at runtime — i.e.
`last_poll_age_ms` significantly exceeds the base poll cadence. This is distinct from
M-CONN's health indicator (which signals *connection failure* via `consecutiveFailures`)
and from M-SYNC (which validates *correctness at QA time* on a controlled rig). Drift
can occur during normal back-off recovery or when polling silently slows for unknown
reasons — it does not imply a connection fault.

Three open questions require a decision before TASK-060 (implementation) can start:

1. **Threshold** — at what `last_poll_age_ms` value does the indicator appear?
2. **Visual form** — what does the indicator look like?
3. **Collision** — does it collide with the conn-001 inactive-titlebar overlay, which
   also renders on `repaintChrome()`?

---

**Decision**

**1. Staleness threshold: 3 × base poll cadence = 15 000 ms (`N_STALE_MS`)**

Base poll is 5 000 ms. Three missed polls represents genuine staleness rather than
normal poll jitter. The back-off ladder's first step is 10 s (`consecutiveFailures = 1`);
at 15 s the DUT has missed at least two complete cycles regardless of jitter. This
threshold is conservative — it avoids false positives during normal single-failure
recovery — while still surfacing sustained staleness before the user notices stale
chrome.

`N_STALE_MS = 15000` defined as a compile-time constant in `winampDisplay.h`. Not
exposed via `set` command for now (unnecessary complexity; revisit if field tuning
proves necessary).

**2. Visual form: dimmed title bar tint (corner pip, not full overlay)**

The conn-001 inactive-titlebar overlay (`SKIN_TITLEBAR_INACTIVE`) is a full 275×14 px
blit. Reusing it for drift would create *ambiguity*: the user cannot distinguish
"connection dead" from "polling slow." Two distinct problems must have two distinct
signals.

The drift indicator is a **4×4 px amber pip** blit at the top-right corner of the
title bar area (`originX + 268, originY + 1`). Amber (RGB565 `0xFD00` ≈ orange-yellow)
is visually distinct from the inactive-titlebar grey and from the active-titlebar
chrome. The pip is small enough not to obscure the title text or conflict with the
inactive-titlebar sprite.

Pip baked as a 4×4 `uint16_t` array in `winampDisplay.h` (32 bytes). No atlas change.

**3. Collision resolution: layered rendering order**

`repaintChrome()` render order (revised):

1. `blitMainBackground()` (always)
2. Conn-001 inactive-titlebar blit (if `!isHealthy()`)
3. Drift amber pip blit (if `last_poll_age_ms > N_STALE_MS`)

Step 3 always runs *after* step 2. If the connection is also unhealthy, the pip appears
on top of the inactive-titlebar sprite in the top-right corner — both signals are
simultaneously visible and do not erase each other. The user sees:

- Grey title bar + pip = stale but connected (back-off or slow network)
- Grey title bar, no pip = connection faulted but recent poll (transitional)
- Active title bar + pip = (rare) polling slowed despite healthy connection
- Active title bar, no pip = nominal

**4. Threshold check placement**

Check performed inside `repaintChrome()` using `millis() - g_lastPollMs`. `g_lastPollMs`
is written by `spotifyTask` (already exists as the basis for heartbeat `last_poll_age_ms`
from TASK-058). No new shared variable; reads are non-atomic but the value is a
millisecond counter and a stale read is a one-pip-cycle error at worst.

**5. `last_render_age_ms` heartbeat field (TASK-059)**

Write `g_lastRenderMs = millis()` on every WinampDisplay path that consumes a new
snapshot and triggers a chrome repaint (the snapshot-seq watcher branch in `tick()`).
Does NOT fire on interpolation-only repaints (position bar, time digits) — those do
not reflect new Spotify state. Heartbeat exposes `last_render_age_ms = millis() -
g_lastRenderMs`. T111 validates this field tracks repaint cadence.

---

**Alternatives considered:**

**Reuse conn-001 inactive-titlebar overlay for drift**: Simpler — no new sprite.
Rejected: ambiguity between "connection dead" and "polling slow" undermines both
indicators' diagnostic value.

**Banner / full-width dim stripe**: More visible than a pip, but occludes track title
text and is disproportionate for a passive diagnostic. Rejected.

**Expose `N_STALE_MS` via `set stale_threshold <ms>`**: Useful for tuning in the field
but adds a writable debug var and a new `set` case. Deferred — start with compile-time
constant and revisit if threshold needs per-device adjustment.

**Self-comparator (periodic re-poll + diff against last rendered state)**: More powerful
(detects chrome mismatch, not just poll age) but much heavier. Deferred; option (d)
from the 2026-05-17 discussion. Prereq: drift-001 (a)+(b) proving insufficient in the
field.

---

**Consequences:**

What becomes easier:
- T112 (staleness indicator appears + clears) has a concrete threshold and visual to
  assert against.
- T113 (no false positive during back-off recovery) has a clear threshold to verify
  against (15 s > back-off step 1 = 10 s, so a single failure should not trip the pip).
- TASK-060 has unambiguous implementation spec: 4×4 amber pip, layered after conn-001.

What becomes harder:
- `repaintChrome()` grows a third conditional blit — small but real maintenance
  surface.
- If `N_STALE_MS` needs field adjustment, a reflash is required (no runtime tuning).
