### ADR-029 — 2026-05-25 — TLS root CA strategy for non-Spotify HTTPS endpoints

**Status**: accepted (2026-05-25)

**Context**:

M-MULTIAPP introduces two new network-fetching apps — Weather (`api.open-meteo.com`) and
Crypto (`api.coingecko.com`) — implemented via a planned `dataTask` FreeRTOS task. ADR-019
resolved TLS cert strategy for the Spotify domains only. It left non-Spotify endpoints
unaddressed.

The design docs for Weather (`designs/M-MULTIAPP/weather.md`) and Crypto
(`designs/M-MULTIAPP/crypto.md`) both show the source prototype's bare `HTTPClient` pattern:

```cpp
HTTPClient http;
http.begin("https://api.open-meteo.com/...");
```

On Arduino-ESP32 2.0.17, `HTTPClient::begin(String url)` for an HTTPS URL allocates an
internal `WiFiClientSecure` and calls `setInsecure()` on it. TLS handshake succeeds, but
certificate verification is silently disabled. The design docs carry a latent `setInsecure()`
invocation; this ADR corrects that.

**Current cert chain findings** (updated 2026-06-12; originally verified 2026-05-25):

| Host | Leaf issuer | Intermediate | Root CA | Root expiry |
|---|---|---|---|---|
| `api.open-meteo.com` | Let's Encrypt R13 | R13 ← ISRG Root X1 | ISRG Root X1 | 2030-09-30 |
| `api.coingecko.com` | Let's Encrypt YE1 | YE1 ← ISRG Root X1 | ISRG Root X1 | 2035-06-04 |

**Note (2026-06-12):** CoinGecko rotated from GTS Root R4 / WE1 to ISRG Root X1 / YE1 between 2026-05-25 and 2026-06-12. Both hosts now share the same root CA (ISRG Root X1). `COINGECKO_ROOT_CA` updated to ISRG Root X1 PEM (same as `OPEN_METEO_ROOT_CA`). Rotation diagnosed via HTTP -1 in T_CX_05 (LL-067, BP-030).

Both hosts use 90-day leaf certs (standard modern practice). Both now share ISRG Root X1 as root CA.

**Three options evaluated:**

- **(A) Hardcoded root CA PEMs** — new `dataTaskCerts.h` with two PEM string constants
  (`OPEN_METEO_ROOT_CA`, `COINGECKO_ROOT_CA`). Each `dataTask` fetch constructs a
  `WiFiClientSecure`, calls `setCACert()`, and passes it to `HTTPClient::begin(client, url)`.
  Explicit verification, auditable, consistent with ADR-019.

- **(B) `setInsecure()`** — disables verification entirely. Rejected categorically: provides
  no protection against endpoint impersonation; no operational advantage over option A.

- **(C) ESP-IDF cert bundle** (`esp_crt_bundle_attach()`) — covers all well-known CAs without
  per-endpoint PEMs. Rejected: same constraint as ADR-019 — `WiFiClientSecure` in
  Arduino-ESP32 2.0.17 does not cleanly expose the bundle API; adopting it requires bypassing
  the Arduino TLS layer or patching the platform. The risk it mitigates (CA rotation) is low
  given the expiry horizons above.

**Decision**:

Option **(A)** — two hardcoded root CA PEMs in a new `dataTaskCerts.h`, applied via
`setCACert()` on a `WiFiClientSecure` instance passed to `HTTPClient::begin()`.

**Required implementation pattern** (replaces bare `http.begin(url)` in design docs):

```cpp
#include "dataTaskCerts.h"

// Weather fetch
WiFiClientSecure tlsWeather;
tlsWeather.setCACert(OPEN_METEO_ROOT_CA);
HTTPClient http;
http.begin(tlsWeather, WEATHER_API_URL);
int code = http.GET();
// ...
http.end();

// Crypto fetch
WiFiClientSecure tlsCrypto;
tlsCrypto.setCACert(COINGECKO_ROOT_CA);
http.begin(tlsCrypto, CRYPTO_API_URL);
code = http.GET();
// ...
http.end();
```

`WiFiClientSecure` instances are stack-allocated per fetch, not reused across calls.
`dataTask` does not maintain a persistent TLS connection (unlike `spotifyTask`, which
holds a persistent `WiFiClientSecure` per ADR-007). Fetch cadence is 60 s; connection
setup overhead is negligible.

**`dataTaskCerts.h` contents**:

Two PEM string constants (both now ISRG Root X1 — CoinGecko rotated 2026-06-12):
- `OPEN_METEO_ROOT_CA` — ISRG Root X1 (Let's Encrypt root; expires 2035-06-04)
- `COINGECKO_ROOT_CA` — ISRG Root X1 (same root; CoinGecko rotated from GTS Root R4 to Let's Encrypt)

PEM text: standard public values, not secret. Pin the **root CA**, never the leaf or
intermediate — both hosts rotate leaf certs on a 90-day cycle.

**Rotation trigger**:

| Cert | Endpoint(s) | Maintenance trigger | Action |
|---|---|---|---|
| ISRG Root X1 | `api.open-meteo.com`, `*.api.radio-browser.info` | Expiry 2035-06-04 or Let's Encrypt CA change | Update `OPEN_METEO_ROOT_CA` PEM (`RADIO_BROWSER_ROOT_CA` is an alias) in `dataTaskCerts.h`, reflash |
| ISRG Root X1 + GTS Root R4 (bundle) | `api.coingecko.com` | Either root's expiry (2035-06-04 / 2036-06-22) or Cloudflare edge adding a third chain | Update `COINGECKO_ROOT_CA` bundle in `dataTaskCerts.h`, reflash (amendment 6 / TASK-298) |
| USERTrust RSA CA | `teletekst-data.nos.nl` | Expiry 2038-01-18 or Sectigo CA change | Update `TELETEXT_NOS_ROOT_CA` PEM in `dataTaskCerts.h`, reflash (added ADR-044) |
| DigiCert Global Root G2 + G2 TLS RSA SHA256 2020 CA1 (bundle) | `query1.finance.yahoo.com` | Root expiry 2038-01-15 / intermediate 2030-09-23 or DigiCert chain change | Update `YAHOO_FINANCE_ROOT_CA` bundle in `dataTaskCerts.h`, reflash (amendment 6) |
| GTS Root R4 | `opendata.adsb.fi` | Expiry 2036-06-22 or Cloudflare chain flip to ISRG (coingecko precedent — would need a bundle) | Update `PLANERADAR_ROOT_CA` PEM in `dataTaskCerts.h`, reflash (ADR-048; row added 2026-07-14, gap flagged by M-PR-LOCATIONS QM review) |
| ISRG Root X1 | `nominatim.openstreetmap.org` (**pending** — lands with M-PR-LOCATIONS) | OSM dropping the cross-signed `ISRG Root YR` from its served chain (chain reaches X1 only via that cross-sign) → bundle in `ISRG Root YR` | Planned alias `NOMINATIM_ROOT_CA` → `OPEN_METEO_ROOT_CA`; see M-PR-LOCATIONS design |

The failure mode for a stale cert is an observable TLS handshake failure (HTTP -1 from
`http.GET()`, logged by `dataTask`). Diagnose via `get cryptoHttpCode` serial command.
Remediation is a firmware reflash — acceptable for a hobbyist device (consistent with ADR-019).

**Quarterly check** (per BP-030, updated by the 2026-06-20 amendment / BP-039):
Run the host strict-verify preflight — it confirms each pinned root still *verifies*
the live chain (not merely that the issuer string is unchanged), which is the check
that on-device `setCACert()` actually performs:
```sh
./run/check-datatask-certs
```
Expected: every reachable endpoint reports `PASS`. A `FAIL` means the pinned root no
longer builds the chain (rotation or a genuinely incomplete server chain) → diagnose
before reflashing. An `ERROR` is network-unreachable from the check host, not a chain
fault — re-run from an unrestricted network.

> Superseded: the old issuer-grep form (`openssl … -showcerts | grep issuer`) is
> retired — it reads what the server *sends*, not what *verifies*, and that gap is
> exactly what let TASK-214's unconditional `setInsecure()` ship (LL-083 / BP-039).

**Consequences**:

What becomes easier:
- `dataTask` fetches are verified end-to-end. Endpoint impersonation or MITM is detectable.
- Cert management follows the same model as ADR-019 / `SpotifyArduinoCert.h` — one place per
  cert, one pattern across the codebase.

What becomes harder / constrained:
- Design docs for Weather and Crypto (`designs/M-MULTIAPP/weather.md`,
  `designs/M-MULTIAPP/crypto.md`) must update their `HTTPClient` snippets to use the
  two-arg `http.begin(client, url)` form. The bare `http.begin(url)` pattern is prohibited
  for HTTPS in this codebase.
- If CoinGecko migrates to a different CDN or CA (commercial service risk), the PEM must
  be updated and firmware reflashed. No in-field update path exists.
- Heap cost: each `WiFiClientSecure` stack allocation is ~200–300 bytes on the `dataTask`
  stack. Size the `dataTask` stack accordingly (≥8 KB recommended; `spotifyTask` uses 8 KB).

**Open question**:

If the project migrates to an Arduino-ESP32 release that cleanly exposes
`esp_crt_bundle_attach()` via `WiFiClientSecure`, option (C) becomes low-cost and should
be revisited — it would eliminate per-endpoint cert maintenance for all three endpoint
groups (Spotify, open-meteo, CoinGecko) in one change.

**Supersedes**: nothing. Extends ADR-019 scope to non-Spotify HTTPS endpoints.

**Closes**: "TLS cert strategy for `api.open-meteo.com` and `api.coingecko.com`"
(gap identified during M-MULTIAPP Weather/Crypto design review, 2026-05-25).

## Amendment — 2026-06-20 — radio-browser.info conditional fallback + host-verify discipline (Architect)

**Status of amendment**: interim-accepted, pending DUT evidence (T_WR_TLS_01). Not a final ADR change.

**Trigger**: TASK-214 introduced `tls.setInsecure()` for the radio-browser.info station-list fetch — option (B), which this ADR rejected categorically. QM raised it (LL-083) and the Architect was engaged on two questions: (3) whether a `setInsecure()` path may sit in `master` at all, and (4) what the standing pattern should be.

**Engaged by**: QM (LL-083 / BP-039), 2026-06-20. **Owner**: Architect. **Developer**: re-scoped the code before this review.

### (3) Governance of the conditional `setInsecure()` path

The original fix was an *unconditional* `setInsecure()` — a direct violation of this ADR's rejection of option (B). The re-scoped code (`fetchOneMirror()`) is materially different: it attempts `setCACert(RADIO_BROWSER_ROOT_CA)` first per mirror and only falls back to `setInsecure()` on a **connection/handshake/verify-level failure** (negative HTTPClient code), recording which path fired in `WebRadioStationsResult.tlsInsecure` (surfaced via `get wrLastHttp`).

Architect position: the conditional fallback is **interim-acceptable in `master`**, narrowly and with conditions, because:
- radio-browser.info is a community federation of independently-operated mirrors. Unlike open-meteo / CoinGecko (single commercial CDN each), per-mirror chain completeness is not something we control or can pin our way around if a given mirror genuinely ships an incomplete chain. This is a *materially different endpoint class* than the ones this ADR was written for.
- the station list carries no secret and no auth; the realistic MITM payload is a bad stream URL — annoying, not a credential/data-exfil risk (contrast Spotify/ADR-019).
- the fallback is observable (`tlsInsecure` flag), not silent — which is the specific property option (B) lacked when this ADR rejected it ("certificate verification *silently* disabled").

**This is not yet a blanket exception to the ADR.** It is gated on evidence:

**Decision gate (resolves at T_WR_TLS_01 on real hardware):**
- If `tlsInsecure:0` consistently across mirrors/runs → the strict path works; the `setInsecure()` fallback is dead code and **must be removed** (no ADR exception needed, this ADR stands unamended). Host re-check already shows `de1` verifying clean (BP-039), so this is the expected outcome.
- If `tlsInsecure:1` is required for some mirror that genuinely ships an incomplete chain → promote this amendment to a **formal ADR exception** scoped to `*.api.radio-browser.info` only, with the rationale above, and leave the conditional fallback. No other endpoint inherits it.

Until that gate resolves, the conditional path may remain but TASK-214 stays open and the milestone does not close on it.

### (4) Standing pattern + verification discipline

Adopted as the cert-strategy norm going forward, consistent with BP-039:
- **Host strict-verify is now mandatory before any cert/TLS root-cause is accepted.** `run/check-datatask-certs` performs the exact offline single-root `-verify_return_error` build that on-device `setCACert()` does, for every pinned endpoint, reading PEMs straight from `dataTaskCerts.h`. This **supersedes the issuer-grep step** in this ADR's "Quarterly check (per BP-030)" block above — replace that two-line `grep issuer` with `./run/check-datatask-certs`.
- **`-showcerts`/issuer inspection alone is insufficient** to accept or reject a chain (it shows what the server sends, not what verifies). This is the concrete failure that produced the unconditional fix.
- Option (C) (`esp_crt_bundle_attach()`) remains the preferred long-term elimination of all per-endpoint maintenance *and* this whole federation-chain problem — see Open question. If revisited, it subsumes the radio-browser fallback entirely.

**VE testability requirement**: the `tlsInsecure` flag must remain on the `get wrLastHttp` surface so the decision gate above is observable without a logic-analyser.

### (5) Amendment 2026-06-24 — media-stream transport is out of this ADR's scope (TASK-232)

The 2026-06-24 DUT run resolved the §(3) decision gate: **`tlsInsecure:0`** — `de1` (and the
others reached) verified clean via the pinned root; the `setInsecure()` fallback **never fired**.
Per the gate, this ADR stands unamended on the fetch path and the conditional `setInsecure()`
fallback is now **dead code slated for removal** (tracked under TASK-214; the `tlsInsecure`
surface stays for the quarterly check).

Separately, TASK-232 introduced playing radio **media streams** (`url_resolved`) over plain
`http://`. This is **explicitly outside this ADR's scope**, which governs *API endpoints*
(weather/crypto/stock/teletext/radio-browser-API) that this firmware fetches structured data
from. A media stream is a different class:

- It carries **no secret and no auth** — a public broadcast URL. The realistic MITM payload is a
  substituted audio stream: annoying, not a credential/data-exfil risk (same reasoning the §(3)
  fallback was judged on, and strictly weaker than even the station-list case).
- On this **no-PSRAM** board, HTTPS media playback is **not merely undesirable but impossible**:
  the audio-stream mbedTLS handshake hits `(-32512) SSL - Memory allocation failed` (ADR-045,
  Wall 1). There is no "verify properly instead" option to choose — the choice is cleartext HTTP
  or no WebRadio at all.

**Decision:** WebRadio plays `http://` streams only and filters `https://` out of the station
list (TASK-232). Accepted as a deliberate, documented exception for **media-stream transport
only**; it grants no precedent to any API-endpoint fetch, all of which remain bound by option (A)
above. If a future PSRAM-capable target makes HTTPS media playback feasible, prefer it there.

### (6) Amendment 2026-07-08 — rotation-prone pins become multi-root bundles; strict-verify preflight wired into run/test (TASK-298)

Two events falsified the "one root per endpoint" model:

1. **CoinGecko flip-flop.** api.coingecko.com (Cloudflare-fronted) rotated its served
   chain GTS→ISRG (caught 2026-06-12, note above) and back ISRG→GTS (caught 2026-07-08
   as a DUT `-9984` X509 verify failure that cost two contaminated full-suite runs to
   isolate). Cloudflare load-balances edge certs across CAs, so any single-root pin for
   a Cloudflare-fronted endpoint WILL break again. `COINGECKO_ROOT_CA` is now a
   **two-root concatenated PEM bundle** (ISRG Root X1 + GTS Root R4); mbedTLS
   `setCACert()`/`mbedtls_x509_crt_parse` accepts bundles natively.
2. **Yahoo intermediate pin retired.** TASK-109c had pinned the DigiCert **CA1
   intermediate** ("intentionally", but the recorded trail shows the choice followed the
   T_SF_07 probe's pin-what-the-server-sends shortcut rather than a reasoned exception
   to this ADR's pin-the-root rule). It worked under mbedTLS but failed the strict
   host-side preflight from day one and carried the same rotation fragility as (1).
   Human-approved 2026-07-08: `YAHOO_FINANCE_ROOT_CA` is now a bundle of **DigiCert
   Global Root G2** (self-signed, expires 2038) + the original CA1 intermediate.
   DUT-verified: T170/T176 PASS.

**Policy update:** the rule is now "pin **self-signed root(s)**; where the CDN/CA is
known to rotate across chains, pin a bundle of every observed root." Intermediates may
ride along in a bundle for belt-and-braces but never anchor alone.

**Detection:** `run/check-datatask-certs` (the §(4) strict-verify preflight) is now
**step 0 of `run/test`, warn-only** — a pinned-CA rotation names itself in one line
before the 30-minute suite instead of surfacing as a spray of fetch-test FAILs
(LL-103). With the yahoo repin, all reachable endpoints verify PASS; unreachable
federation mirrors report ERROR and never gate the run.
