### ADR-029 — 2026-05-25 — TLS root CA strategy for non-Spotify HTTPS endpoints

**Status**: proposed

**Context**:

M-MULTIAPP introduces two new network-fetching apps — Weather (`api.open-meteo.com`) and
Crypto (`api.coingecko.com`) — implemented via a planned `dataTask` FreeRTOS task. ADR-019
resolved TLS cert strategy for the Spotify domains only. It left non-Spotify endpoints
unaddressed.

The design docs for Weather (`designs/M-MULTIAPP/weather.md`) and Crypto
(`designs/M-MULTIAPP/crypto.md`) both show the source prototype's bare `HTTPClient` pattern:

```cpp
HTTPClient http;
http.begin("https://api.open-meteo.com/...");
```

On Arduino-ESP32 2.0.17, `HTTPClient::begin(String url)` for an HTTPS URL allocates an
internal `WiFiClientSecure` and calls `setInsecure()` on it. TLS handshake succeeds, but
certificate verification is silently disabled. The design docs carry a latent `setInsecure()`
invocation; this ADR corrects that.

**Current cert chain findings** (verified 2026-05-25):

| Host | Leaf issuer | Intermediate | Root CA | Root expiry |
|---|---|---|---|---|
| `api.open-meteo.com` | Let's Encrypt R13 | R13 ← ISRG Root X1 | ISRG Root X1 | 2030-09-30 |
| `api.coingecko.com` | Google Trust Services WE1 | WE1 ← GTS Root R4 | GTS Root R4 | ~2028 |

Both hosts use 90-day leaf certs (standard modern practice). Both have stable, multi-year
root CAs with no common ancestor — two root CA PEMs are required.

**Three options evaluated:**

- **(A) Hardcoded root CA PEMs** — new `dataTaskCerts.h` with two PEM string constants
  (`OPEN_METEO_ROOT_CA`, `COINGECKO_ROOT_CA`). Each `dataTask` fetch constructs a
  `WiFiClientSecure`, calls `setCACert()`, and passes it to `HTTPClient::begin(client, url)`.
  Explicit verification, auditable, consistent with ADR-019.

- **(B) `setInsecure()`** — disables verification entirely. Rejected categorically: provides
  no protection against endpoint impersonation; no operational advantage over option A.

- **(C) ESP-IDF cert bundle** (`esp_crt_bundle_attach()`) — covers all well-known CAs without
  per-endpoint PEMs. Rejected: same constraint as ADR-019 — `WiFiClientSecure` in
  Arduino-ESP32 2.0.17 does not cleanly expose the bundle API; adopting it requires bypassing
  the Arduino TLS layer or patching the platform. The risk it mitigates (CA rotation) is low
  given the expiry horizons above.

**Decision**:

Option **(A)** — two hardcoded root CA PEMs in a new `dataTaskCerts.h`, applied via
`setCACert()` on a `WiFiClientSecure` instance passed to `HTTPClient::begin()`.

**Required implementation pattern** (replaces bare `http.begin(url)` in design docs):

```cpp
#include "dataTaskCerts.h"

// Weather fetch
WiFiClientSecure tlsWeather;
tlsWeather.setCACert(OPEN_METEO_ROOT_CA);
HTTPClient http;
http.begin(tlsWeather, WEATHER_API_URL);
int code = http.GET();
// ...
http.end();

// Crypto fetch
WiFiClientSecure tlsCrypto;
tlsCrypto.setCACert(COINGECKO_ROOT_CA);
http.begin(tlsCrypto, CRYPTO_API_URL);
code = http.GET();
// ...
http.end();
```

`WiFiClientSecure` instances are stack-allocated per fetch, not reused across calls.
`dataTask` does not maintain a persistent TLS connection (unlike `spotifyTask`, which
holds a persistent `WiFiClientSecure` per ADR-007). Fetch cadence is 60 s; connection
setup overhead is negligible.

**`dataTaskCerts.h` contents**:

Two PEM string constants:
- `OPEN_METEO_ROOT_CA` — ISRG Root X1 (Let's Encrypt root; expires 2030-09-30)
- `COINGECKO_ROOT_CA` — GTS Root R4 (Google Trust Services root; ~2028 expiry)

PEM text: standard public values, not secret. Pin the **root CA**, never the leaf or
intermediate — both hosts rotate leaf certs on a 90-day cycle.

**Rotation trigger**:

| Cert | Maintenance trigger | Action |
|---|---|---|
| ISRG Root X1 | Expiry 2030-09-30 or Let's Encrypt CA change | Update `OPEN_METEO_ROOT_CA` PEM in `dataTaskCerts.h`, reflash |
| GTS Root R4 | Expiry ~2028 or CoinGecko CDN migration | Update `COINGECKO_ROOT_CA` PEM, reflash |

The failure mode for a stale cert is an observable TLS handshake failure (non-200 response
logged by `dataTask`), not a silent data gap. Remediation is a firmware reflash — acceptable
for a hobbyist device (consistent with ADR-019).

**Consequences**:

What becomes easier:
- `dataTask` fetches are verified end-to-end. Endpoint impersonation or MITM is detectable.
- Cert management follows the same model as ADR-019 / `SpotifyArduinoCert.h` — one place per
  cert, one pattern across the codebase.

What becomes harder / constrained:
- Design docs for Weather and Crypto (`designs/M-MULTIAPP/weather.md`,
  `designs/M-MULTIAPP/crypto.md`) must update their `HTTPClient` snippets to use the
  two-arg `http.begin(client, url)` form. The bare `http.begin(url)` pattern is prohibited
  for HTTPS in this codebase.
- If CoinGecko migrates to a different CDN or CA (commercial service risk), the PEM must
  be updated and firmware reflashed. No in-field update path exists.
- Heap cost: each `WiFiClientSecure` stack allocation is ~200–300 bytes on the `dataTask`
  stack. Size the `dataTask` stack accordingly (≥8 KB recommended; `spotifyTask` uses 8 KB).

**Open question**:

If the project migrates to an Arduino-ESP32 release that cleanly exposes
`esp_crt_bundle_attach()` via `WiFiClientSecure`, option (C) becomes low-cost and should
be revisited — it would eliminate per-endpoint cert maintenance for all three endpoint
groups (Spotify, open-meteo, CoinGecko) in one change.

**Supersedes**: nothing. Extends ADR-019 scope to non-Spotify HTTPS endpoints.

**Closes**: "TLS cert strategy for `api.open-meteo.com` and `api.coingecko.com`"
(gap identified during M-MULTIAPP Weather/Crypto design review, 2026-05-25).
