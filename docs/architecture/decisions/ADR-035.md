# ADR-035 — Touch UX Layer: Hitbox Primitive + Shell Busy Indicator

> Status: proposed
> Date: 2026-05-31
> Context: MULTIAPP — touch handling scattered across apps; no UX feedback when a tap triggers async work

---

## Problem

Two independent deficiencies in the current touch stack:

**1. No shared hitbox primitive.**
Every app that needs hit-testing reinvents the same coordinate arithmetic inline.
`StockApp` computes row index with `(y - START_Y) / ROW_H`; chart tabs with `(x - TABS_X) / TAB_W`; back button with `x < BACK_W * 2`. There is no shared rect or hit-test helper. Adding new apps or sub-views requires re-deriving the same patterns.

**2. No visual feedback that a tap registered.**
When a user taps a StockApp row or a Spotify transport button, async work begins (dataTask enqueue, spotifyTask enqueue). The display does not change immediately. The user cannot tell whether the tap was recognised or was missed. This leads to repeated taps which queue multiple actions.

The classic solution (sand-glass cursor) cannot be applied directly — there is no pointer. But the taskbar's active-app indicator bar (3 px green left edge) is always visible. It can encode processing state by changing colour.

---

## Decisions

### Decision 1 — Add `touch/hitbox.h`: shared Rect primitive

Add `app/src/touch/hitbox.h` with:

```cpp
struct Rect { int16_t x, y, w, h; };

inline bool hitTest(const Rect& r, int px, int py) {
    return px >= r.x && px < r.x + r.w
        && py >= r.y && py < r.y + r.h;
}

// Returns 0-based row index, or -1 if outside the rect.
inline int hitTestRow(const Rect& r, int rowH, int py) {
    if (py < r.y || py >= r.y + r.h) return -1;
    return (py - r.y) / rowH;
}

// Returns 0-based column index, or -1 if outside the rect.
inline int hitTestCol(const Rect& r, int colW, int px) {
    if (px < r.x || px >= r.x + r.w) return -1;
    return (px - r.x) / colW;
}
```

Apps adopt this incrementally. Existing apps are not required to migrate immediately — there is no interface change.

**Rationale:** The helper eliminates per-app arithmetic bugs and makes hitbox intent explicit in code review. The struct is 8 bytes; the inlines compile to the same instructions as the hand-rolled versions. No runtime overhead.

---

### Decision 2 — No new debounce layer; two existing mechanisms activated

No new debounce class or abstraction will be added. Two existing but incomplete mechanisms are corrected:

**2a — `touchScreenCoolDownTime` Phase 2 check (synchronous actions).**
`touchScreenCoolDownTime` is already set by VIS (300 ms), Shuffle (250 ms), and Repeat (250 ms) inside `handleWinampInput()`, but is only checked in the SERIAL_DEBUG `injectTouch()` path — never in production. In production these regions fall back to the shell's 200 ms cooldown, which is shorter than intended. Fix: add one check at the top of Phase 2 in `handleWinampInput()`:
```cpp
if (millis() <= touchScreenCoolDownTime) { _tickMarquee(); return false; }
```
No new mechanism — activates what was already written.

**2b — `g_shellBusy` gate on canvas Press (async actions).**
The shell's 200 ms `s_cooldownMs` expires long before a network fetch completes (1–3 s). During that window repeated taps are accepted. Fix: extend the existing gate in `appHandleInput()`:
```cpp
if (!s_inGesture && (millis() <= s_cooldownMs || g_shellBusy)) return;
```
While the amber indicator is shown, canvas Press events are blocked. Taskbar taps still pass (checked before this gate). No new mechanism — extends the existing gate by one condition.

The busy setter must appear after **all four** `handleInput()` call sites in `appHandleInput()` (Release-on-taskbar-interrupt, Press, Move, Release-on-finger-up) — not only after Press. `StockApp` dispatches on Release; a setter at only the Press site would never fire for Stock.

`cmdTap` currently calls `handleInput()` directly, bypassing `appHandleInput()`. `cmdTap` must be updated to check `g_shellBusy` for canvas taps so injected touches obey the same gate. Without this fix T-CDWN-02 cannot be tested.

**What does not change:** `VOLUME_DRAG_DEBOUNCE_MS` and similar per-app semantic rate-limiters stay in the app — they are not hardware debounce and do not belong in the shell.

---

### Decision 3 — No gesture recognizer

The current 3-phase `TouchPhase::Press / Move / Release` pipeline is sufficient for all implemented interactions (transport taps, volume drag, seek drag, PLEDIT scroll, taskbar scroll, stock row tap, tab tap, back tap). Adding a gesture recognizer (swipe direction, long-press, pinch) is deferred until a concrete interaction requirement that the 3-phase pipeline cannot express.

**Rationale:** A gesture recognizer adds latency (must wait for release + timer to disambiguate tap vs. long-press). On a 240 px display with one finger and a static app layout, the hit-zone is the gesture — no disambiguation is needed.

---

### Decision 4 — Shell-owned busy flag + amber taskbar indicator

**Flag:** `static bool g_shellBusy = false;` in `main.cpp`.

**API:** One function, callable from any app:
```cpp
void shell::setBusy(bool busy);
```
`setBusy()` sets `g_shellBusy`, then calls `renderActiveIndicator()` immediately.

**Indicator:** `renderActiveIndicator()` — a new free function in `taskbar.h` — repaints only the 3 px active bar for the currently-active slot, without repainting the full taskbar:
```cpp
void renderActiveIndicator(TFT_eSPI& tft, AppId activeApp, int scrollOffset, bool busy);
```
Colour: `TASKBAR_ACTIVE_COLOR` (`0x07E0`, green) when idle; `TASKBAR_BUSY_COLOR` (`0xFD20`, amber) when busy.

**Auto-clear:** Shell auto-clears busy after `SHELL_BUSY_TIMEOUT_MS = 3000` ms. Checked in `loop()` after `appTick()`. Prevents stuck amber if an app forgets to clear.

**Who calls `setBusy(true)`:** Apps that initiate async work on a user interaction:
- `StockApp` — on row tap (chart fetch) and tab tap (range change); calls `shell::setBusy()` directly (it lives in `main.cpp`)
- `SpotifyApp` — via `WinampDisplay` intermediary (see below)

**`App` ABC gains `hasPendingAsync()`:** The shell, not individual apps, calls `shell::setBusy()`. Default return value is `false` — apps with no async input need not override.

```cpp
// App ABC addition (appShell.h):
virtual bool hasPendingAsync() const { return false; }
```

`appHandleInput()` checks on transition only (guards against timer-reset on Move events):
```cpp
if (!g_shellBusy && g_apps[id]->hasPendingAsync()) shell::setBusy(true);
```

**WinampDisplay → SpotifyApp → shell chain (Option C, updated):** `WinampDisplay` exposes `_lastInputWasAsync` (always-on bool, reset per `handleWinampInput()` call, set at each async dispatch site in both Phase 2 and the Release handler) and `wasLastInputAsync()`. Async dispatch sites: PREV, PLAY, PAUSE, STOP, NEXT, Shuffle, Repeat, seek-drag Release, volume-drag Release, PLEDIT row tap Release, logo tap. VIS tap is synchronous — must NOT set the flag. `SpotifyApp::handleInput()` checks `wasLastInputAsync()` after both the Press and Release delegate calls and sets its own `mutable bool _actionDispatched`. `SpotifyApp::hasPendingAsync()` returns `_actionDispatched && spotifyTask::hasPendingActions()` — self-clears when the task queue drains. `WinampDisplay` has zero shell dependency. Note: `lastTouchResult` was not used — it is `#ifdef SERIAL_DEBUG` only.

**`StockApp::hasPendingAsync()`:** Tracks `bool _pendingAsync` internally. Set inside the stale-cache `if` block in `drillToChart()` only — not unconditionally. If the cache is fresh and no fetch is enqueued, `_pendingAsync` must not be set (no result will arrive to clear it; amber would stall until timeout). Same conditional applies to tab-range changes. Cleared when `pollStockChart()` resolves.

**`spotifyTask::hasPendingActions()` thread safety:** Implementation must use a `volatile bool _actionPending` flag. **Cleared only when the queue becomes empty** (when `xQueueReceive` returns `pdFALSE`) — not on every dequeue. Clearing on every dequeue causes `hasPendingAsync()` to return false between queued items, flashing the amber indicator for each action in a multi-action batch. Developer to confirm the existing queue uses `xQueueReceive` before implementing.

**Who calls `setBusy(false)`:** Shell only — via the primary loop poll (`hasPendingAsync()` returns false) or the fallback auto-clear after `SHELL_BUSY_TIMEOUT_MS`. No app calls `setBusy(false)` directly.

**Shell auto-clear:** After `SHELL_BUSY_TIMEOUT_MS = 3000` ms, shell calls `shell::setBusy(false)` regardless. Fallback only — the primary path clears promptly when `hasPendingAsync()` returns false.

**`renderTaskbar()` unchanged:** Gains `bool busy` param (default `false`). Full taskbar repaints use `g_shellBusy`; `switchApp()` always passes `false`.

---

## Rejected alternatives

**A — Per-app busy state (`App::isBusy()`):** Requires shell to poll every app on every taskbar repaint. Inverts responsibility — the shell should own the indicator; apps should push state, not expose it.

**B — Animate the indicator (pulse/blink):** Adds timer overhead and requires the indicator to be repainted on every loop iteration when busy. The static colour change is sufficient for "processing" feedback and costs one SPI write at transition only.

**C — Show a spinner in the app canvas:** Requires apps to reserve space and manage the spinner lifecycle. More intrusive than a taskbar indicator. The taskbar is always visible and always in the same location — ideal for global status.
