### ADR-016 — 2026-05-10 — M-CHROME tier 2.5 — volume knob (display + drag-to-set)

**Status**: accepted (2026-05-10 — TASK-044 + TASK-045 shipped end-to-end; VE gates T074 + T075 PASS; user-confirmed visual "works perfectly").

**Context**:

TASK-041 + TASK-043 closed the dynamic-VOLUME slider end-to-end (commits `b8f37d3..d67bdc4`). DUT user feedback during T070b verification:

1. *"the volume knob is not present"* — slider shows 5 colour-banded fill keyframes (KEYFRAME_0..4 + NONE) but no position cursor.
2. *"pressing on the volume slider area doesn't seem to do much"* — slider is read-only.

Both behaviours are correct against ADR-014 §A1.3 + OOS list (knob and touch control were explicitly deferred), but the user-visible result is incomplete. Phase the missing pieces in here.

User direction (2026-05-10):

- Pair the two slices into one ADR (this one) with two PRs: TASK-044 ships display-only knob; TASK-045 ships drag-to-set on top of the verified visual baseline.
- Touch model: **drag-to-track** (continuous finger tracking with debounced setVolume calls). Tap-to-set rejected as too coarse.
- Knob source: **shared BALANCE.BMP knob sprite** — canonical Winamp 2 reuses one 14×11 knob across BALANCE and VOLUME. The bake tool already crops `(15, 422, 14, 11)` from BALANCE.BMP for the static balance composite; same crop drives the volume knob.

This ADR records the design decisions for both slices in one place. Implementation order is forced (TASK-044 before TASK-045): touch needs the knob to be visible, and verifying the visual position math against known volumes is far easier in isolation than tangled with drag dispatch.

**Asset inspection** (per LL-016, done before locking the design):

VOLUME.BMP rows 420-432 — originally referenced in ADR-014 §A1.3 as a candidate "knob sprite" — were inspected via `_decode_bmp_rle8` + per-row pixel scan. The 13-tall band is **NOT** a separate knob; it's a fill-level frame (non-cyan content x=0..27 = ~40% fill, x=31..67 = groove). Using rows 420-432 would just paint another keyframe on top of the active keyframe. Decision-locked: knob comes from BALANCE.BMP.

**Decision**:

1. **Knob source.** `BALANCE.BMP` crop `(15, 422, 14, 11)`. Identical to the crop the static-composite path already uses (winampDisplay.h doesn't see it; lives in `bake_skin.py::composite_static_decoration`). Single source of truth across BALANCE + VOLUME.

2. **Knob in atlas.** Emit as a separate `SKIN_VOLUME_KNOB[14*11]` uint16_t array — 308 bytes flash. Rejected: padding the existing 68-wide SKIN_VOLUME atlas with cyan to fit an 11-row knob row (would waste 1188 bytes of cyan padding). Separate array preserves the "one purpose per atlas" pattern.

3. **Knob position math.** `knob_screen_x = originX + VOLUME_X + (percent * (VOLUME_W - VOLUME_KNOB_W)) / 100`, where `VOLUME_W=68`, `VOLUME_KNOB_W=14`, so the knob's left edge travels through `0..54` as percent goes `0..100`. `knob_screen_y = originY + VOLUME_Y + 1` (centered vertically in the 13-tall slot, knob is 11 tall).

4. **Sentinel rendering.** When `volumePercent < 0` (KEYFRAME_NONE), **skip the knob blit**. The greyed-empty track is a sufficient "no active device" signal; a knob with no fill behind it would mislead the user into thinking the slider is at a real position.

5. **Touch model: drag-to-track.** State machine in `WinampDisplay`:
   - `D_IDLE` — no drag in progress.
   - `D_VOLUME_DRAG` — finger held down inside the volume slot.
   - Transition `D_IDLE → D_VOLUME_DRAG` when `ts.touched()` fires AND `hitTestVolume` returns a valid percent.
   - Transition `D_VOLUME_DRAG → D_IDLE` when `!ts.touched()` AND state was `D_VOLUME_DRAG`.

6. **Hit test.** New private method `long WinampDisplay::hitTestVolume(int sx, int sy)`. Returns `0..100` if `(sx, sy)` falls inside `(originX + VOLUME_X, originY + VOLUME_Y, 68, 13)`, else `-1`. Mirrors `hitTestPosbar` (winampDisplay.h:304) — same `originX/originY` offset trick, same return-percent-or-`-1` shape.

7. **Drag dispatch.** Per loop iteration during `D_VOLUME_DRAG`:
   - Call `drawVolume(percent)` immediately (optimistic visual). Updates `lastVolumeRendered`.
   - If `(millis() - lastVolumeEnqueuedMs) > 300` AND `percent != lastVolumeEnqueuedPct`: enqueue `ACT_VOLUME(percent)`. Update `lastVolumeEnqueuedMs / Pct`.
   - Set `optimisticVolumeUntilMs = millis() + 2000` (extends the optimistic window every drag sample).

8. **Drag-end.** On the iteration where `ts.touched()` returns false but state is still `D_VOLUME_DRAG`:
   - If `lastVolumeRendered != lastVolumeEnqueuedPct`: enqueue `ACT_VOLUME(lastVolumeRendered)` (final commit).
   - Reset `dragState = D_IDLE`.
   - Optimistic window keeps running for ~2 s (set during the last touch sample).

9. **`ACT_VOLUME` queue action.** New enum member in `spotifyTask::Action`. `Request.param` (int32_t) carries the percent (0..100). Dispatch in `spotifyTaskStorage.cpp::run` switch:
   ```cpp
   case ACT_VOLUME:
       LOG_D("spotify.action", "ACT_VOLUME pct=%d", req.param);
       s_spotify->setVolume((int)req.param);
       break;
   ```
   **No `doPoll()` after.** Drag fires many ACT_VOLUMEs; calling doPoll on each would burst polls + race the dedup gate. Next regular poll re-syncs naturally within 5-10 s.

10. **Optimistic-UI freeze (LL-015).** New public method on the display interface:
    ```cpp
    virtual unsigned long getOptimisticVolumeUntil() const { return 0; }  // base no-op
    ```
    `WinampDisplay` overrides to return `optimisticVolumeUntilMs`. In `spotifyLogic.h::updateCurrentlyPlaying`, gate the existing volume dedup check on `millis() >= sp_Display->getOptimisticVolumeUntil()`. Prevents the next regular poll's stale `volumePercent` from re-anchoring the slider over the user's chosen position before Spotify commits.

11. **Queue safety.** ACT_VOLUME goes through the existing bounded queue with `xQueueSend(timeout=0)` — drop-and-warn on full. 300 ms debounce keeps queue depth bounded at ~1 in practice. ACT_VOLUME ordering with concurrent ACT_PREV / ACT_NEXT etc. is not a concern: queue is FIFO, and per-action results are independent.

12. **Sub-task split.** Two PRs, one ADR:
    - **TASK-044** — display-only knob. Bake + layout macro + drawVolume blit. Single commit.
    - **TASK-045** — drag dispatch on top of the visual baseline. Single commit. Depends on TASK-044.

**Why this shape:**

- *Two-task split* — display-only is a minimal-blast-radius improvement that ships before the touch design is finalised on hardware. If the drag UX needs tuning after Sitting 2's DUT verify, TASK-044's visual is unaffected.
- *Drag over tap-to-set* — user explicitly chose drag (more responsive feel, matches the user mental model of "grab and slide"). The 300 ms debounce + 2 s optimistic window resolve the rate-limit + flicker concerns the simpler model would have avoided.
- *Shared BALANCE knob* — canonical Winamp design intent + zero-design-overhead. Skin author already provides a 14×11 knob in BALANCE.BMP that's visually consistent with the existing balance composite.
- *No `doPoll()` post-action for ACT_VOLUME* — drag-burst protection. Other ACT_* dispatch handlers do call doPoll; volume is the only burst-prone action class today.

**Architect responses**: all accepted as-stated.

**Verification gates**:

- **TASK-044 close**:
  - DUT visual: knob visible on slider when track playing; knob at left when volume=10, right when volume=90, missing when volume=-1.
  - Bake determinism: `gen/golden.sha256` regenerated and re-bake byte-identical.
  - Build: `cyd2usb_winamp` clean; flash budget delta ≤ +400 bytes.
- **TASK-045 close**:
  - DUT manual: tap-and-drag inside slider slot moves the knob in real time; finger lift commits to Spotify (verified by host-side `curl /v1/me/player`); no slider snap-back during the optimistic window.
  - **T074** — drag inside slot dispatches setVolume; Spotify host-side `volume_percent` matches released percent within ≤ 30 s.
  - **T075** — optimistic-UI freeze: no slider flicker during/after drag for ~2 s. No visible "snap-back-then-snap-forward" between drag-end and the next poll.
  - Regression: T070a + T070b still pass.
  - Heartbeat poll-success rate ≥ 90 % over a 5-min idle window post-flash.

**Out of scope (deferred)**:

- Volume control via voice / NFC — separate input modality.
- Drag bounds extension into the BALANCE area to "cross-drag" balance + volume — visual confusion risk, no canonical precedent.
- Snap-to-keyframe-bucket (round to nearest 0/20/40/60/80) — feels less responsive; user should be able to set fine values even if the visual snaps to 5 colours.
- Pressed-state knob sprite (highlighted variant) — BALANCE.BMP doesn't ship a separate pressed knob; would need synthetic. Polish; defer.
- Push the LOCAL_PATCHES set upstream to `witnessmenow/spotify-api-arduino` — separate strategic decision, see LOCAL_PATCHES.md "Strategy decision (open)".

**Consequences**:

- *Easier*: dynamic VOLUME slider is now fully interactive — read AND write. Closes the user-perceived gap in M-CHROME tier 2.
- *Harder*: state machine in `checkForInput` grows. Future touch features (drag-on-other-elements, multi-touch gestures) can extend the same state machine pattern.
- *Constrained*: the 300 ms debounce + 2 s optimistic window are tuning knobs that may need DUT-side adjustment if user feel is off. Hardcoded for now; no runtime configuration.
- *Process*: this ADR is the third instance of the LL-010 pattern (multi-role review pre-implementation, inline). Consistent precedent.
