### ADR-028 — 2026-05-25 — Canvas abstraction layer (display portability)

**Status**: rejected — not adopted (2026-07-18 sweep — `app/src/canvas.h` was never created; renderers still bind `TFT_eSPI` directly (12 `extern TFT_eSPI tft` refs). The simulation/portability motivation was met differently: host-side preview via M-PREVIEW-FRAMEWORK tools, and the PC-mirror target is out of scope per ADR-006. No remaining driver for a runtime canvas indirection on a 240×320 single-display product.)

**Context**:

Every renderer in the project calls `TFT_eSPI tft` directly. The driver is a global singleton
defined in `cheapYellowLCD.h` and referenced via `extern TFT_eSPI tft` in four other files:

```
cheapYellowLCD.h   — defines TFT_eSPI tft; 12 direct calls (setup + JPEG decode)
winampDisplay.h    — 45 direct tft. calls (skin atlas blits, fills, text)
vuMeter.h          — extern tft; drawFastHLine / drawFastVLine
taskbar/taskbar.h  — extern tft; fillRect, drawFastHLine, drawChar
screenLog.h        — extern tft; fillScreen, drawString; saves/restores setSwapBytes
main.cpp           — fillRect, drawRoundRect, drawString, color565 (ClockApp)
```

`SpotifyDisplay` (the existing virtual interface) abstracts the Spotify domain —
"show track name", "draw progress bar" — not the drawing layer. It provides no
portability for the renderer itself.

Two problems share the same root:

1. **Portability**: swapping the display driver requires touching every renderer.
   Porting to a different MCU, a different TFT library (LVGL, SDL2, MCUFRIEND),
   or a host-side simulator requires changes in six files.

2. **Shared TFT state** (see LL-035, ADR-027): `TFT_eSPI` maintains process-global
   mutable registers (`textdatum`, `textfont`, `textsize`, `textcolor`, `swapBytes`).
   Any caller can mutate them; no caller is guaranteed to find them in a known state.
   ADR-027's two-rule fix (producer reset + consumer assert) is discipline-based.
   A stateless Canvas API eliminates the problem structurally.

**Complete primitive inventory** (actual call sites, not hypothetical):

| Primitive | Where used |

---

**Decision**:

Introduce a `Canvas` pure-virtual interface in `app/src/canvas.h`. All renderers receive
`Canvas&` as a dependency instead of using `extern TFT_eSPI tft`. `TFTCanvas` is the
concrete ESP32/TFT_eSPI implementation. Alternative implementations (SDL2, LVGL, mock)
implement the same interface for simulation and test.

### Design principles

**1. Text is stateless.**
`setTextFont`, `setTextSize`, `setTextDatum`, `setTextColor` do not appear in `Canvas`.
All text-rendering state is explicit in the `drawString`/`drawChar` call parameters.
`TFTCanvas` manages TFT_eSPI's mutable registers internally and resets them before
returning. The state-leak class of bugs (LL-035, ADR-027) is eliminated structurally —
there is no shared text state to leak.

**2. Pixel format is explicit per call.**
`pushImage` takes an explicit `PixelFormat` parameter (`RGB565_LE` or `RGB565_BE`).
`setSwapBytes` never appears outside `TFTCanvas`. Call sites document what format their
pixel data is in, not what driver state they need.

**3. Font and alignment are named enums, not driver constants.**
`CanvasFont` and `TextAlign` replace TFT_eSPI's integer font indices (1/2/4/6) and
datum constants (`TL_DATUM`, `MC_DATUM`, etc.). `TFTCanvas` translates. Future
implementations provide their own mapping.

**4. Batching is an optional hint, not a contract.**
`beginWrite`/`endWrite` have default no-op implementations in the base class.
`TFTCanvas` overrides them to `startWrite`/`endWrite`. Callers that bracket expensive
blits get the SPI optimization on TFT_eSPI; other implementations ignore the hint.

**5. Canvas is rendering-only.**
Hardware setup (`init`, `setRotation`) and touch input are outside the interface.
`init`/`setRotation` stay in `CheapYellowDisplay::displaySetup()` operating on
`TFT_eSPI` directly. Touch has a separate abstraction path (not in scope here).

**6. `color565` has a default implementation.**
RGB565 packing is pure math: `(r&0xF8)<<8 | (g&0xFC)<<3 | (b>>3)`. The default
implementation is correct for all platforms. Override only if the target uses a
different color space or bit layout.

### Interface definition

```cpp
// app/src/canvas.h
#pragma once
#include <stdint.h>

// Pixel memory layout for pushImage data.
enum class PixelFormat { RGB565_LE, RGB565_BE };

// Logical font sizes. Concrete implementations map to platform font resources.
// TFTCanvas maps: Small→1, Medium→2, Large→4, ExtraLarge→6 (TFT_eSPI font indices).
enum class CanvasFont { Small, Medium, Large, ExtraLarge };

// Text horizontal alignment. Replaces TFT_eSPI datum constants.
// Y coordinate always refers to the top of the glyph (equivalent to TL/TC/TR_DATUM).
enum class TextAlign  { Left, Centre, Right };

class Canvas {
public:
    virtual ~Canvas() = default;

    // ── Geometry ─────────────────────────────────────────────────────────────

    virtual int width()  const = 0;
    virtual int height() const = 0;

    // ── Color ────────────────────────────────────────────────────────────────

    // Default: standard RGB565 pack. Override for non-standard color spaces.
    virtual uint16_t color565(uint8_t r, uint8_t g, uint8_t b) const {
        return ((uint16_t)(r & 0xF8) << 8)
             | ((uint16_t)(g & 0xFC) << 3)
             |  (uint16_t)(b >> 3);
    }

    // ── Fill primitives ──────────────────────────────────────────────────────

    virtual void fillScreen  (uint16_t color) = 0;
    virtual void fillRect    (int x, int y, int w, int h, uint16_t color) = 0;
    virtual void fillCircle  (int cx, int cy, int r, uint16_t color) = 0;
    virtual void fillTriangle(int x0, int y0, int x1, int y1,
                               int x2, int y2, uint16_t color) = 0;

    // ── Outline primitives ───────────────────────────────────────────────────

    virtual void drawRect      (int x, int y, int w, int h, uint16_t color) = 0;
    virtual void drawRoundRect (int x, int y, int w, int h,
                                int radius, uint16_t color) = 0;
    virtual void drawCircle    (int cx, int cy, int r, uint16_t color) = 0;
    virtual void drawFastHLine (int x, int y, int w, uint16_t color) = 0;
    virtual void drawFastVLine (int x, int y, int h, uint16_t color) = 0;

    // ── Pixel blit ───────────────────────────────────────────────────────────

    // Push a row-major RGB565 pixel buffer. fmt declares the byte order of data.
    // The implementation handles any byte-swap required by the physical driver.
    // Callers document their data format at the call site; no external setSwapBytes.
    virtual void pushImage(int x, int y, int w, int h,
                           const uint16_t* data,
                           PixelFormat fmt = PixelFormat::RGB565_LE) = 0;

    // ── Text (fully stateless) ───────────────────────────────────────────────

    // Draw string. All rendering state explicit — no setTextFont/Datum/Color.
    // x is the alignment anchor: left edge (Left), centre (Centre), right edge (Right).
    // y is always the top of the glyph row.
    virtual void drawString(const char* str, int x, int y,
                            CanvasFont font, TextAlign align,
                            uint16_t fg, uint16_t bg) = 0;

    // Draw a single character glyph. font specifies size; fg/bg are explicit.
    virtual void drawChar(char ch, int x, int y,
                          CanvasFont font,
                          uint16_t fg, uint16_t bg) = 0;

    // ── SPI batching hint ────────────────────────────────────────────────────

    // Bracket a sequence of draw calls into a single driver transaction.
    // Default: no-op. TFTCanvas overrides to startWrite/endWrite.
    // Callers may call these freely; non-batching implementations ignore them.
    virtual void beginWrite() {}
    virtual void endWrite()   {}
};
```

### TFTCanvas — concrete implementation sketch

```cpp
// app/src/tft_canvas.h
#pragma once
#include <TFT_eSPI.h>
#include "canvas.h"

class TFTCanvas : public Canvas {
    TFT_eSPI& _tft;

    static uint8_t font(CanvasFont f) {
        switch (f) {
            case CanvasFont::Small:      return 1;
            case CanvasFont::Medium:     return 2;
            case CanvasFont::Large:      return 4;
            case CanvasFont::ExtraLarge: return 6;
        }
        return 1;
    }
    static uint8_t datum(TextAlign a) {
        switch (a) {
            case TextAlign::Left:   return TL_DATUM;
            case TextAlign::Centre: return TC_DATUM;
            case TextAlign::Right:  return TR_DATUM;
        }
        return TL_DATUM;
    }

public:
    explicit TFTCanvas(TFT_eSPI& tft) : _tft(tft) {}

    int width()  const override { return _tft.width(); }
    int height() const override { return _tft.height(); }

    void fillScreen  (uint16_t c) override { _tft.fillScreen(c); }
    void fillRect    (int x, int y, int w, int h, uint16_t c) override
                     { _tft.fillRect(x, y, w, h, c); }
    void fillCircle  (int cx, int cy, int r, uint16_t c) override
                     { _tft.fillCircle(cx, cy, r, c); }
    void fillTriangle(int x0, int y0, int x1, int y1, int x2, int y2, uint16_t c) override
                     { _tft.fillTriangle(x0,y0, x1,y1, x2,y2, c); }
    void drawRect    (int x, int y, int w, int h, uint16_t c) override
                     { _tft.drawRect(x, y, w, h, c); }
    void drawRoundRect(int x, int y, int w, int h, int r, uint16_t c) override
                     { _tft.drawRoundRect(x, y, w, h, r, c); }
    void drawCircle  (int cx, int cy, int r, uint16_t c) override
                     { _tft.drawCircle(cx, cy, r, c); }
    void drawFastHLine(int x, int y, int w, uint16_t c) override
                     { _tft.drawFastHLine(x, y, w, c); }
    void drawFastVLine(int x, int y, int h, uint16_t c) override
                     { _tft.drawFastVLine(x, y, h, c); }

    // Byte-swap set per-call; TFTCanvas owns the swap register — no external setSwapBytes.
    void pushImage(int x, int y, int w, int h,
                   const uint16_t* data, PixelFormat fmt) override {
        _tft.setSwapBytes(fmt == PixelFormat::RGB565_LE);
        _tft.pushImage(x, y, w, h, data);
    }

    // Stateless text: set all registers, draw, reset datum before returning.
    // Producer rule (ADR-027) enforced at the single point where TFT_eSPI is called.
    void drawString(const char* str, int x, int y,
                    CanvasFont f, TextAlign a,
                    uint16_t fg, uint16_t bg) override {
        _tft.setTextFont(font(f));
        _tft.setTextSize(1);
        _tft.setTextDatum(datum(a));
        _tft.setTextColor(fg, bg);
        _tft.drawString(str, x, y);
        _tft.setTextDatum(TL_DATUM);   // reset: producer rule (ADR-027)
    }

    // drawChar with inline font arg does not mutate textfont global in TFT_eSPI.
    void drawChar(char ch, int x, int y, CanvasFont f,
                  uint16_t fg, uint16_t bg) override {
        _tft.setTextColor(fg, bg);
        _tft.drawChar(ch, x, y, font(f));
    }

    void beginWrite() override { _tft.startWrite(); }
    void endWrite()   override { _tft.endWrite(); }
};
```

**Note on `setSwapBytes` ownership in `TFTCanvas`:** `pushImage` sets the swap register
per call based on `PixelFormat`. After `TFTCanvas` is adopted, no code outside
`TFTCanvas` should call `tft.setSwapBytes()` — the register is owned by the Canvas
implementation. `screenLog.h`'s current save/restore pattern becomes unnecessary once
it receives a `Canvas&` instead of `extern TFT_eSPI tft`.

### Migration path

**Phase 1 — introduce the interface (no renderer changes yet)**
1. Write `canvas.h` and `tft_canvas.h`.
2. Instantiate `TFTCanvas g_canvas(tft)` in `cheapYellowLCD.h` alongside the existing `tft` global.
3. No call sites changed. Build must still pass `check_build.sh`.

**Phase 2 — thread `Canvas&` into renderers one file at a time**
For each of the four `extern TFT_eSPI tft` files, in any order:
- `taskbar/taskbar.h` — simplest; 4 calls, no text state
- `screenLog.h` — remove save/restore swapBytes; receive `Canvas&`
- `vuMeter.h` — only HLine/VLine calls
- `winampDisplay.h` — largest; 45 calls; this is the main value

For each file:
- Replace `tft.X(...)` with `canvas.X(...)` using the Canvas API.
- Remove `#include <TFT_eSPI.h>` and `extern TFT_eSPI tft`.
- Receive `Canvas&` as a constructor parameter or function argument.
- Defensive `setTextDatum(TL_DATUM)` in `drawPlaylist()` becomes unnecessary
  (stateless API), but can remain harmlessly until the migration is complete.

**Phase 3 — run check_build.sh gate after each file**
`check_build.sh` verifies both `cyd2usb_winamp` and `cyd2usb_winamp_debug` compile
clean. This is the minimum safety gate per BP-008.

**Phase 4 — remove `extern TFT_eSPI tft` from non-owner files**
Once all four files are migrated, only `cheapYellowLCD.h` and `tft_canvas.h` include
`<TFT_eSPI.h>`. All other compilation units are driver-agnostic.

**Phase 5 — alternative implementation (on porting need)**
Write `SimCanvas : Canvas` (SDL2 or LVGL). No renderer changes. Swap the concrete
instance at construction in the platform's `main()` / `setup()`.

### What this does NOT cover

- **Touch input**: separate abstraction, separate ADR. Not in scope.
- **Font rasterization**: `TFTCanvas` maps `CanvasFont` to TFT_eSPI bitmap fonts.
  The skin glyph atlas (`blitSprite` path) is already driver-agnostic — it's a
  `pushImage` call over a pixel array. The `drawString` path (PLEDIT, ClockApp,
  screenLog) is the only one that depends on `CanvasFont` mapping.
- **Hardware setup** (`init`, `setRotation`, `tft.height()` in JPEG callback):
  these remain in `CheapYellowDisplay::displaySetup()` touching `TFT_eSPI` directly.
  They are one-time setup, not rendering operations.
- **JPEG decode callback** (`pDraw->pPixels` → `tft.pushImage`): the JPEG decoder
  callback currently bypasses all abstraction. It can be migrated to `canvas.pushImage`
  in Phase 2 as part of `cheapYellowLCD.h`, but it requires the `Canvas&` to be
  accessible from the static callback. Pattern: store `Canvas*` in a module-level
  pointer set before decode, cleared after.

---

### Open questions

1. **`CanvasFont` mapping completeness**: TFT_eSPI ships with smooth fonts and GFX
   fonts in addition to the four bitmap fonts mapped above. None are currently used in
   this project. If a future app needs smooth fonts, the enum and `TFTCanvas` mapping
   will need extending. No change to the interface is required — only the enum and
   mapping switch.

2. **`drawCentreString`**: `CheapYellowDisplay` uses `tft.drawCentreString()` which
   is `drawString` with `TC_DATUM`. Under Canvas it becomes
   `drawString(str, cx, y, font, TextAlign::Centre, fg, bg)`. The call site changes are
   mechanical; no interface change required.

3. **JPEG decode callback and `Canvas&` accessibility**: see "What this does NOT cover"
   above. Resolve when `cheapYellowLCD.h` is migrated in Phase 2.

4. **`color565` in ClockApp**: currently called as a TFT method to produce a gradient
   colour per pixel. Since the default `Canvas::color565` is pure math, the call
   `canvas.color565(r, g, b)` is semantically and numerically identical. No behaviour
   change.

---

**Consequences**:

What becomes easier:
- Porting to a different display driver: implement `Canvas`, swap the instance.
  Zero renderer changes.
- Host-side simulation (SDL2/LVGL): `SimCanvas` produces a pixel buffer; renderers run
  unchanged on a dev machine. Test harness can assert pixel content without hardware.
- TFT shared-state bugs (ADR-027): structurally impossible once renderers use the
  stateless Canvas API. The two-rule discipline in ADR-027 collapses to one enforcement
  point in `TFTCanvas::drawString`.
- Code review: `#include <TFT_eSPI.h>` outside `cheapYellowLCD.h` / `tft_canvas.h`
  is an immediate review flag.

What becomes harder / constrained:
- Virtual dispatch per draw call. On ESP32 at 240 MHz the bottleneck is SPI bandwidth
  (~50 Mbit/s for this panel), not function call overhead. Profiling has not identified
  the draw loop as a CPU hotspot. Accept.
- `TFT_eSPI`-specific extensions (e.g. DMA blits, sprite buffers, smooth fonts) are
  not in the interface. If needed, they must be accessed by downcasting to `TFTCanvas`
  in platform-specific code — an explicit seam, not a silent leak.
- Migration is incremental work (4 files, ~70 call sites). Estimated effort: 1–2
  Developer sessions. Not free, but bounded and reversible.

**Supersedes**: nothing. Complements ADR-026 (app lifecycle) and ADR-027 (TFT state
ownership). ADR-027's producer/consumer rules become implementation details of
`TFTCanvas` once this migration is complete, but should remain documented as the
rationale for `TFTCanvas`'s internal reset behaviour.

**Blocks**: nothing currently. Activate when a porting need arises or when host-side
simulation becomes a test-harness priority.
