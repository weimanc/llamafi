### ADR-015 — 2026-05-10 — Switch primary poll endpoint to `/me/player`

**Status**: accepted (2026-05-21 — TASK-043 DUT-verified; T073 + T070a + T070b PASS)

**Context**:

TASK-041 (M-CHROME tier 2 dynamic VOLUME) shipped end-to-end at commits `b8f37d3..8075176`, faithful to ADR-014 Amendment 1. T070a/T070b verification on the DUT (2026-05-10) found that `Snapshot.volumePercent` stays at the `-1` sentinel on every successful 200 OK poll, regardless of which Spotify Connect device is active or what its volume is.

The lib parser (`SpotifyArduino.cpp:636-640`) is correct as written — it falls through to `-1` when `device` or `device.volume_percent` is null. The bug is upstream: **the response from `/v1/me/player/currently-playing` does not contain a `device` field at all**. The Spotify OpenAPI spec (`resource/web-api/official-open-api.yaml:4701, 4967-4985`) declares `CurrentlyPlayingContextObject` as the response shape and includes `device` as a top-level property. The actual server returns a *subset* — same shape minus `device`, `repeat_state`, `shuffle_state`, `smart_shuffle`. Wire-captured 2026-05-10:

```
/me/player/currently-playing  HTTP 200
  top-level keys: ['actions', 'context', 'currently_playing_type',
                   'is_playing', 'item', 'progress_ms', 'timestamp']
  has device key: False
```

`/me/player` returns the complete `CurrentlyPlayingContextObject` shape — including `device`. Side-by-side capture, same access token, ~150 ms apart:

| Field | `/me/player/currently-playing` | `/me/player` | match |
|---|---|---|---|
| `is_playing` | true | true | ✓ |
| `progress_ms` | 136102 | 136266 | ✓ (drift = inter-request elapsed) |
| `currently_playing_type` | `'track'` | `'track'` | ✓ |
| `context.uri` | `spotify:album:...lo` | `spotify:album:...lo` | ✓ |
| `item.uri` | `spotify:track:...87` | `spotify:track:...87` | ✓ |
| `actions.disallows` | `['resuming']` | `['resuming']` | ✓ |
| `device` | absent | full DeviceObject | superset |
| `repeat_state` | absent | `'off'` | superset |
| `shuffle_state` | absent | `false` | superset |
| `smart_shuffle` | absent | `false` | superset |

`/me/player` is a strict superset of `/me/player/currently-playing` for the fields the firmware actually consumes. There is no field the firmware reads from `/currently-playing` that is missing from `/me/player`.

This is the second documented instance of the spec-vs-server divergence pattern (LL-013 family — first instance was the M1-spike "spec says 204, server returns 200" payment-controls bug). Same shape, different surface: trust the wire, not the document.

**Decision**:

1. **Change the primary poll endpoint to `/v1/me/player?additional_types=episode`.**
   - Update `SPOTIFY_CURRENTLY_PLAYING_ENDPOINT` in `lib/SpotifyArduino/src/SpotifyArduino.h` from `/v1/me/player/currently-playing?additional_types=episode` to `/v1/me/player?additional_types=episode`.
   - The function name `getCurrentlyPlaying` is misleading after this change (it now polls the player-state endpoint, not the named "currently playing" endpoint), but renaming is a downstream cleanup decision. Keep the name today; document the surface in `LOCAL_PATCHES.md`.

2. **Keep the existing parser logic in `getCurrentlyPlaying`.** The fields the parser reads (`is_playing`, `progress_ms`, `currently_playing_type`, `context.uri`, `item.*`, `device.volume_percent`) are all present in `/me/player`'s response with identical shape. No parser change required beyond what TASK-039 already added.

3. **204 No Content semantics**: both endpoints return 204 when there is no active session. The poll-loop's existing 204 handling (`spotifyTaskStorage.cpp:124-127`) continues to work unchanged. Verify on DUT.

4. **Existing `getPlayerDetails` (the explicitly-named `/me/player` caller) is not touched by this ADR.** It serves a different need (full player state, including `repeat_state`, `shuffle_state`) and remains available. No code currently calls it.

5. **TASK-039's parser patch stays.** It now correctly reads from a response that actually contains `device.volume_percent`. The patch was right; the *endpoint it was patched into* was wrong. This ADR moves the endpoint into alignment with the patch.

**Why a single endpoint change rather than a second poll for device info**:

- Zero increase in HTTP-round-trip cost. Response payload grows by `device` (~150 bytes on the wire) plus three small primitives — negligible against the existing 2.6 KB body.
- Zero increase in parser complexity. Same filter, same struct, same callback — the parser was already designed to ignore fields it doesn't include in the filter.
- One source of truth for poll state. A second poll for device info would create the question "which one wins on disagreement, and at what cadence?" — needless complexity for a data point that travels alongside the rest of the player state.
- Keeps the `currently-playing` endpoint available as a fallback if a future Spotify policy change ever restricts `/me/player`.

**Impact on TASK-041**:

- T070a (volume snapshot reaches DUT chrome within one poll) becomes runnable without further code change once this ADR is implemented.
- T070b (sentinel keyframe shows when no active device) — sentinel behaviour is preserved: `/me/player` returns 204 No Content when no device is active, the snapshot writer's 204 path leaves `volumePercent` at the existing snapshot's value (or `-1` on first poll). On the active-device transition, `volumePercent` jumps to the real value, dedup gate fires, KEYFRAME_NONE → real keyframe.
- TASK-041 does not need to be re-opened structurally. Its implementation against ADR-014 Amendment 1 is correct; it just needs this upstream fix to receive non-sentinel data.

**Architect responses**: all accepted as-stated. Single TASK proposed.

**Verification gates**:

- **T073 — host-side wire-comparison** (new, below).
- **T070a + T070b** — re-run on DUT post-commit. Both must pass before TASK-043 closes.
- **Determinism** — bake artefacts unchanged; `golden.sha256` continues to pass.
- **Build** — `cyd2usb_winamp` env builds clean.
- **Regression watch** — heartbeat poll-success rate over a 5-minute idle period must be ≥ 90% (matches current behaviour on a healthy network). Catches any unexpected 4xx/5xx that would point to a missed scope or filter mismatch.

**Out of scope (deferred)**:

- Renaming `getCurrentlyPlaying` to reflect the actual endpoint it now polls. Cosmetic; defer.
- Surfacing `repeat_state` / `shuffle_state` in the snapshot. Useful for future chrome (the existing SHUFREP composite is currently static at "EQ off / PL on" per ADR-014); revisit if M-CHROME tier 3 lands.
- Switching to `getPlayerDetails` instead. Different code path, different struct, different callback — disruptive for what should be a one-line URL change.

**Consequences**:

- *Easier*: TASK-041 unblocks with one URL change. Volume slider becomes functional end-to-end.
- *Harder*: function name `getCurrentlyPlaying` no longer matches the URL it queries. Developers reading the lib must consult `LOCAL_PATCHES.md` to understand. Not great; deferred rename addresses if it hurts.
- *Constrained*: future Spotify endpoint deprecations. If `/me/player` is ever deprecated in favour of a new shape (e.g., a v2 endpoint), a second migration is needed. Same migration cost as today.
- *Process*: this is the second instance of LL-013. Strong promotion case for "spec says X, server says Y" as a best-practice rule that mandates wire capture before any filter-patch ADR.
