### ADR-048 — 2026-07-10 — M-PLANERADAR ADS-B parse strategy: chunked per-object filtered stream parse

**Status**: accepted (2026-07-11)

**Context**:

M-PLANERADAR's fetch/parse strategy (design doc D1) was the project's one real
technical risk: the reference project (`ESP32-Plane-Radar`) holds **two** full
copies of the adsb.fi response on heap (an Arduino `String`, then a complete
`JsonDocument`). On our board that peak sits next to the ~50 KB Spotify TLS
session — the same contention class that produced the tlsYield saga
(5 fixed layers, see `docs/architecture/designs/M-PLANERADAR-plane-radar-app.md`
D1 and the tlsYield project memory). A busy-airspace fetch (Schiphol TMA,
25 km preset) returns dozens of aircraft with full v3 field sets — tens of KB.

The design doc's original lean (D1-b, before phase 0) was "one filtered
`JsonDocument` for the whole response, keeping only the 15 fields used." Phase
0 (`docs/architecture/designs/M-PLANERADAR/phase0-parse-heap.md`) built a
host-compiled ArduinoJson trial against real captured fixtures (`busy_33km.json`,
71 aircraft, 34 921 B; `home_13km.json`, the typical case) plus a Python oracle
for cross-validation, specifically to replace that estimate with a measured
number before firmware started.

**That original lean was falsified.** One filtered document for the whole
response scales ~410 B/aircraft and hit **29.4 KB** on the 71-aircraft
worst-case capture — not the small fixed budget the design assumed.

**Decision**:

Adopt **D1(b′): chunked per-object filtered parse.** Scan the JSON stream to
the `ac` array, then `deserializeJson()` **one aircraft object at a time**
through a 15-field filter into a small reused `DynamicJsonDocument` (~4 KB),
filling a fixed-size result record per aircraft as it goes. Measured peak
parse heap: **~4 KB fixed, independent of traffic** (71-aircraft and
23-aircraft captures both peak at the same ~4 KB — only the *result* array
grows, and that's capped separately).

Fixed-size result record (firmware transcription target):

```cpp
struct PrAircraft {           // packed target ~40 B
    float   lat, lon;         // 8
    float   distNm;           // 4  server 'dst' — truncation sort key
    int16_t noseDeg, trackDeg;// 4  (0.1° not needed; whole degrees)
    int16_t gsKnots;          // 2
    int32_t altFt;            // 4  (INT32_MIN = "GND", INT32_MAX = unknown)
    char    callsign[9];      // 9
    char    type[5];          // 5
    // + pad → 40 B
};
static constexpr uint8_t PR_MAX_AIRCRAFT = 24;   // 24 × 40 B ≈ 1 KB result payload
```

Truncation policy: when the feed exceeds `PR_MAX_AIRCRAFT`, keep the
nearest-first set by the server-computed `dst` (NM) field — validated 100%
present in the field census, so it's a free, reliable sort key requiring no
client-side range math (only a guard). Verified to match a Python oracle
exactly (24/24 KEPT set on the busy fixture and on the field-poor synthetic
`nofields` fixture). Truncated/malformed input (`truncated.json`) fails
cleanly with `IncompleteInput` at both parse legs tested, with no partial-record
garbage — and leg C (the adopted one) additionally reports the object index
where the stream died, useful for error-code granularity.

Heading precision: firmware stores `noseDeg`/`trackDeg` as whole-degree
`int16_t` (0.1° resolution isn't needed). Confirmed visually imperceptible at
the render radius used (240 px disc, ≤118 px from center) —
`phase0-preview-ui.md` Q6, after fixing a preview-tool bug that had initially
tested full float precision instead of the rounded value that ships.

**Consequences**:

- Peak parse-heap contribution from ADS-B fetch is now a measured constant
  (~4 KB fixed + ~1 KB result payload), not traffic-dependent — this
  isolates the *parse* term of R1 (payload heap spike vs. Spotify TLS
  coexistence) so the DUT-side 30-min foreground soak (parent doc exit
  criterion 4) tests one variable (live TLS coexistence), not two.
- `PrAircraft`'s field set and truncation policy are now transcription-ready
  for the firmware fetcher — implementation should not re-derive fallback
  chains or truncation rules, only port the measured lean.
- Single-pool-grab assumption holds (`allocs=1` for the chunked-parse variant
  measured; the whole-document variant showed `allocs=2` from capacity-doubling)
  — relevant if future capacity tuning is needed.
- Does **not** settle the coexistence term of R1 (parse heap running
  alongside a live Spotify TLS session) — that stays DUT-side by design, per
  the parent doc's phase-0 section.

**Supersedes**: the original D1(b) lean in
`docs/architecture/designs/M-PLANERADAR-plane-radar-app.md` (single
whole-document filtered parse) — that doc's D1 section is updated in place
with a "Phase-0 revision" note rather than silently replaced, per this
project's design-doc convention.

**Full measurement detail**: `docs/architecture/designs/M-PLANERADAR/phase0-parse-heap.md` Results.
