### ADR-011 — 2026-05-07 — Loop responsiveness during blocking Spotify calls (tier 1)

**Status**: accepted

**Context**:

M3 DUT verification (2026-05-07) and the on-screen log overlay (TASK-018) both confirmed the same structural issue: every Spotify poll blocks the super-loop synchronously. While `SpotifyArduino::getCurrentlyPlaying()` is in flight (TLS handshake + HTTP request + response read + JSON parse), nothing else runs — time digits don't advance, the progress thumb freezes, touch is dead, the heartbeat skips, the on-screen log doesn't update.

The blast radius is heavily network-dependent. On a clean network the call is ~600–2000 ms per poll. On the Marriott guest WiFi we've been testing on, two failure modes have been observed (TASK-018 follow-up):

- **Case (a)**: TLS handshake torn down by the AP — `errno=128` + `MBEDTLS_ERR_SSL_CONN_EOF` (-29312) — fails fast, ~hundreds of ms.
- **Case (b)**: handshake succeeded, but the server (or AP) never replied — `readBytesUntil` blocks for `SPOTIFY_TIMEOUT` (2 s) before giving up.

`SPOTIFY_TIMEOUT` is already aggressive (2 s). The dominant cost in the failure window isn't a single slow call — it's that we **retry every 5 s into the same black hole**, so a flaky network produces a steady ~40 % loop blockage with no exit.

**Decision**:

Tier 1: keep the synchronous architecture; add a **per-poll-failure exponential backoff** with reset-on-success; add a **longest-block-millis heartbeat metric** so we can see whether tier 1 is enough or tier 2 is needed.

Tier 1 details:

1. **Backoff on consecutive failures.** Track `consecutiveFailures` in `spotifyLogic`. After every non-success poll (status != 200 && status != 204), the interval to the next poll doubles, starting at the existing `delayBetweenRequests` (5 s) and capped at 60 s. Reset to 5 s on the next success. Standard binary exponential.
2. **Reset on user-initiated action.** Touch input (prev/next) currently sets `requestDueTime = 0` to force an immediate poll. Keep that behaviour; also reset the backoff counter — touch implies "user wants fresh state, don't punish them".
3. **Heartbeat: expose `block_max_ms`.** Wrap each `getCurrentlyPlaying` in a `millis()` measurement; track the max since the last heartbeat and reset after each emit. Adds one field to the existing `hb` line: `block_max=<ms>`.

What this does **not** do (deferred, considered tier 2 — separate ADR if pursued):

- Async IO / FreeRTOS worker task — categorical fix, but a substantial restructure.
- Speculative shortened-timeout-on-failure — saves a fraction of a second per failure, swamped by the backoff savings.
- Touch debouncing tied to backoff state — UX nicety, not on critical path.

**Why not tier 2 right now**:

Tier 1 changes ~30 LOC and zero architecture. With backoff capping at 60 s, a network outage flips the loop from "blocked 40 % of the time" to "blocked < 4 %" without rewriting how IO works. The on-screen log overlay will show whether tier 1 is sufficient — if `block_max=2000+` shows up routinely and the UI still feels frozen, tier 2 becomes justified. We have no use case yet for the precision tier 2 buys (no real-time interaction beyond touch, which already invalidates the cache and re-polls).

**Verification gate**:

- DUT-observed: with backoff active on Marriott WiFi, the screen overlay should keep updating at near-normal cadence even during a failure burst — only every ~60 s do we see a poll line.
- `block_max_ms` in heartbeat: under 2500 ms in normal play; should jump to 2000-ish during a (b) burst (one poll's `SPOTIFY_TIMEOUT`), stay there until backoff caps, then resume.
- Touch on screen → instant repoll (verifies backoff reset).
- Network restored: next successful poll resets `consecutiveFailures` and the `block_max` floor.

**Consequences**:

- *Easier*: failure bursts no longer monopolise the loop. The on-screen log keeps updating during outages. Heartbeat exposes block-max for quick health check.
- *Harder*: a recovering network won't show fresh state for up to 60 s after recovery (until the next backed-off poll fires). Touch is the manual override.
- *Constrained*: still synchronous IO. If a single call exceeds `SPOTIFY_TIMEOUT` for legitimate reasons (slow response with valid data), the renderer still freezes for that call's duration. Tier 2 is the exit if we ever observe that.
