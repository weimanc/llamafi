> Owner: Architect
> Status: draft — designer-review PASS 2026-07-10; executed (see Results)
> Date: 2026-07-10

## Context / pain points

The reference embeds a global major-airport runway DB generated by
`scripts/build_large_airports.py` from OurAirports CSVs (`large_airport` rows
+ their non-helipad runways), coordinates as int32 ×1e7 fixed-point, emitted
as a ~140 KB C source file (`large_airports_data.cpp`). Compiled flash cost is
what matters, not source size — fixed-point int32 records compress to roughly
20 B per runway endpoint pair plus per-airport ICAO+coords. Our flash sits at
~62 %; the DB fits, but a stationary device renders at most a handful of
airports, ever. Parent-doc D3 lean is a trimmed bake behind a build flag; this
trial produces the actual numbers to accept or revise that lean.

## Goals

1. Measured **compiled** size (bytes in `.rodata`, not source KB) for each
   bake variant.
2. In-range content check: airports + runway strips within the 36.8 km
   worst-case fetch radius of the home location (25 km preset × 4/3 × 118/107,
   per the corrected formula in phase0-api-probe), per variant (does trimming
   ever cost us a visible runway?).
3. Adoption plan for the script into our bake conventions
   (`run/bake-airports`, `app/gen/`, golden.sha256 determinism gate, ADR-008
   pattern).

## Design

### Design space — variants to bake (options + tradeoffs)

| Variant | Filter | Expectation |
|---|---|---|
| V-global | none (reference as-is) | upper bound; reference ships this on a 4 MB C3 |
| V-europe | bbox lat 35..62, lon −11..30 | the "generous continental" lean from the parent doc — **lean going in; the size table decides** |
| V-nl500 | 500 km radius around home default (52.3676, 4.9041) | aggressive trim; still covers any plausible relocation within the region |

Bbox filtering is a ~10-line patch to the script (filter `airports.csv` rows
before the runway join), applied as a parameter, not a fork — the adopted
script takes `--bbox` / `--center-radius-km` arguments with V-europe as the
committed default.

### Measurement method (host-only, no firmware build)

Compile the generated `.cpp` standalone:

```sh
g++ -c -Os large_airports_data.cpp && size large_airports_data.o
```

`.rodata` bytes = flash cost of the data to first order (same bytes end up in
the ESP32 image's flash-mapped `drom`). A firmware-build delta check happens
once, later, when the app lands — not needed to decide OQ2.

### In-range content check

Small analysis script over the generated arrays: for each variant, list
airports + strip counts within 36.8 km and 100 km of the home default. The
100 km ring is the "user changes lat/lon in settings without re-baking"
tolerance band — the variant chosen must keep the overlay correct for any
location the SPIFFS-config workflow can plausibly set without a rebake, and
the answer to "what happens outside the baked region" must be *graceful
absence* (empty overlay), never garbage.

### Adoption into project conventions

- Script lands as `app/tools/bake_airports.py` (our naming), wrapped by
  `run/bake-airports`; output to `app/gen/airport_db.c` + `airport_db.h`.
- Output determinism: sort all emitted arrays (ICAO order), no timestamps in
  the generated header comment except a `-- source CSV commit/date --` line
  fed from a pinned input; extend `app/gen/golden.sha256` (T025 pattern).
- **Input pinning**: OurAirports CSVs change upstream daily. The bake fetches
  from a pinned commit of `davidmegginson/ourairports-data` (raw URL with
  commit hash, recorded in the script), not `main` — otherwise the
  determinism gate breaks on every upstream edit. Refreshing the pin is a
  deliberate, reviewed bump.
- Helipad-exclusion and `large_airport`-only filters kept as-is from the
  reference (they encode OurAirports data quirks we'd otherwise rediscover).

## Open questions

- Is `large_airport` the right class filter for this region? Within the
  36.8 km worst-case ring of the home default only Schiphol qualifies, so the
  question doesn't bite at home — but inside the 100 km relocation band the
  class filter decides what a relocated user sees (Rotterdam ~55 km,
  Lelystad ~43 km from the home default). Answer with data: count
  `medium_airport` rows + runways inside the chosen bbox variant and evaluate
  their inclusion cost before deciding. **Answered in Results** — and the
  premise partly aged: current OurAirports data classifies Rotterdam EHRD as
  `large_airport`, so large-only already covers it; medium-only adds military
  fields + Lelystad for +25.5 KB → excluded.

## Exit criteria

1. Size table: V-global / V-europe / V-nl500 → `.rodata` bytes + airport/strip
   counts.
2. In-range check: chosen variant covers 100 km band around home default with
   zero loss vs V-global; out-of-region behaviour confirmed graceful-empty.
3. OQ2 closed: variant decision + rationale written into Results and mirrored
   to the parent doc (revising D3 if the numbers surprise).
4. `medium_airport` question answered for the home region (include or
   document exclusion).
5. Adoption plan confirmed feasible: trial run of the parameterised script
   produces byte-identical output on two consecutive runs (determinism
   precondition for the golden.sha256 gate).

## Results

> Executed 2026-07-10 via `app/tools/host/pr_airport_bake_trial.py`
> (replicates the reference selection logic; sizes use the reference struct
> layout — Airport 16 B, Runway 24 B padded, from `large_airports.h`).
> **Caveat:** fetched from OurAirports `main` (85 716 airports / 48 096
> runways on the day); the adoption bake must pin a commit per the plan above.

### Size table

| Variant | `large_airport` only | large + medium |
|---|---|---|
| V-global | 1 114 ap / 1 707 rw / **57.4 KB** | 4 428 ap / 6 344 rw / 217.9 KB |
| V-europe | 240 ap / 355 rw / **12.1 KB** | 776 ap / 1 050 rw / 36.7 KB |
| V-nl500 | 39 ap / 70 rw / **2.2 KB** | 159 ap / 237 rw / 8.0 KB |

### In-range check (home default)

- Within 36.8 km: **EHAM only** — identical across all variants (zero loss vs
  V-global; exit criterion 2 ✅).
- Within 100 km, large-only: **EHAM + EHRD**. Data-quality surprise: current
  OurAirports classifies Rotterdam **EHRD as `large_airport`** — the open
  question's "RTM is medium" premise was stale. Medium inclusion would add
  EHDL/EHGR/EHKD/EHVK (military) + EHLE (Lelystad).

### OQ2 decision

**V-europe, `large_airport` only, 12.1 KB** — R3 (flash) is a non-issue at
this size; the bbox still covers any plausible relocation (100 km band check
passes today with EHAM+EHRD). `medium_airport` inclusion (criterion 4):
**excluded** — +25.5 KB buys mostly military fields; revisit only on a user
complaint, and the parameterised `--classes` bake makes that a one-line
change. V-global at 57.4 KB remains affordable as a fallback if bbox
maintenance ever annoys.

### Determinism (criterion 5)

Selection logic is a pure function of the CSVs; output ordering will be
ICAO-sorted in the adoption bake. Two-run byte-identity check deferred to the
actual `run/bake-airports` implementation (this trial emits no C file) —
noted as the one criterion that transfers to the firmware milestone rather
than closing here.
