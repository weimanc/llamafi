### EXP-018 — 2026-07-29 — WebRadio real-vis: real per-band spectrum energy (PROP-005 rung 3)
**Hypothesis**: PROP-005's rung 3 — fixed-point 4-8 band energy via Goertzel or IIR band-pass, NOT a full FFT — can real per-band energy drive `VIS_SPECTRUM`'s 19 bars within the decode-tail budget, at the same bar count the firmware's actual spectrum-style vis already uses?

**Band count**: 19, matching `VIS_ATLAS_BARS` (`gen/vis_atlas.h`) — the real-Winamp-footage atlas mode's bar count, i.e. what this firmware's spectrum-style visual actually shows today (per the user's requirement that the band count match). This is also `vuMeter.h`'s existing `SPEC_BARS` constant, already used by the (currently unreachable — see below) synthetic `tickSpectrum`.

**Note on VIS_SPECTRUM's reachability**: `vu::nextMode()`'s tap-cycle is Atlas → WaveAtlas → VU → Blank → Atlas — `VIS_SPECTRUM` was removed from the cycle at some point ("superseded by atlases" per the in-code comment) and is currently dead code from the user's perspective. This experiment force-sets `vu::s_modeRef() = VIS_SPECTRUM` every WebRadio tick under `WR_VIS_BANDS` (test-only, not gated behind a one-shot latch — deliberately no new static needed) purely to make the rung observable. Reviving `VIS_SPECTRUM` in the tap-cycle is a production/UX decision for the graduation step, not part of this spike.

**Approach**: One Goertzel resonator per band (19 total), recomputed fresh every decoded block — no coefficient caching, since honest per-block cost is what PROP-005's kill gate is for ("decode-tail regresses vs TASK-278 baseline → stop, report"), not an already-optimized number. Center frequencies log-spaced 80 Hz–14 kHz (19 points, flash-resident `constexpr` table — confirmed via `nm` it lands in `.rodata`, zero DRAM cost). Mono mix `(L+R)/2`, same simplification `tickSpectrum`'s synthetic mode already made via its single `envelope` value.

**The real storage fight (worth documenting — this rung nearly stalled here)**: a 19-`float` energy array (76 B) obviously doesn't fit the zero-headroom budget (EXP-015/016/017). Tried the project's own established fallback — lazy-`calloc` once, cache the pointer in one static — reasoning a single 4-byte pointer must surely fit somewhere. It didn't: **even one new static pointer, alone, overflowed `cyd2usb_winamp_bands` by 8 bytes.** Confirmed via `nm -S` the pointer itself really is 4 bytes; the other 4 is linker section-alignment padding — meaning the real floor on this build isn't "N bytes," it's "any new static at all," full stop, regardless of size. (An earlier same-session sanity check with a deliberately *unreferenced* static pointer built clean — that was `--gc-sections` dead-stripping it, a false negative; a real, referenced 4-byte pointer is what actually overflowed. Don't repeat that check as if it proved zero-cost storage is available — it proved the opposite once used for real.)

**Resolution**: `tickSpectrum`'s own five per-bar arrays (`specPeak`, `specH`, `specVel`, `lastBinH`, `lastPeakRow`) already exist unconditionally (production code, not gated) — promoted `specPeak`/`specH`/`specVel` from tickSpectrum-local statics to namespace-scope accessors (`vu::specHRef()` etc., same "inline function wrapping a function-local static" pattern as `lLevelRef()`/`rLevelRef()`), and extracted the spring-damper + peak-fall math into a shared `vu::updateSpectrumBar(i, lvl)`. Real mode's writer (webRadioApp's `audio_process_extern`, pump task) calls `updateSpectrumBar()` directly per band per block — the *exact* smoothing tickSpectrum used to run on the UI thread, just invoked at the pump's cadence instead. `tickSpectrum` in real mode does zero recomputation: it only reads `specH()`/`specPeak()` (already fresh) and draws. Net new static bytes: **zero** (moved existing storage, not duplicated — `lastBinH`/`lastPeakRow` stayed as `tickSpectrum`-local since they're pure UI-thread dedup cache, no pump-task writer needed). Confirmed via clean link of `cyd2usb_winamp_bands` and byte-identical flags-off `cyd2usb_winamp_debug`.

**DUT measurement**: `get wrPump` after 45s of station-0 playback: `maxPumpMs=42ms` (cycles ~6000/45s) — **identical to every prior rung** (tap-only, peak, RMS). 19 Goertzel resonators, each doing a full per-sample IIR pass over the block (19× the per-sample work of rungs 1/2), still doesn't move the needle at this measurement's resolution. Visual: two screendumps of the title+vis region 1.5s apart during live playback showed 100/9800 changed pixels with visibly different bar patterns — less dramatic than rung 2's 531/9800 (expected: each band captures only its narrow frequency slice, vs. rung 2's full-broadband peak/RMS driving every bar from the same one number) — confirms real per-band content, not a flatline, but reads more subdued than the (already-validated) rung 2 envelope.

**Conclusion**: Validated, with a caveat. Cost is a non-issue (identical 42ms across all four experiments run this session). The zero-headroom static-BSS wall is real and *does* generalize past "reuse a same-sized existing 2-float pair" (EXP-016) to "any new mutable state at all" — the fix pattern that scales is "find an existing writer-swap point on an already-linked structure," not "allocate smaller." Visual quality is unresolved: per-band levels look under-driven relative to rung 2's broadband envelope, likely needing per-band gain compensation (a pink-noise-style makeup curve, similar in spirit to the *fake* shape it's replacing) before it reads as good as the synthetic version did.

**Recommendation**: Don't block PROP-005's graduation proposal on this — rung 2 alone was already sufficient (VU + atlas gating, the explicitly-called-out best value/cost point) and rung 3's cost result supports including bands too, but rung 3's *visual tuning* (gain per band, and the separate decision of whether to revive `VIS_SPECTRUM` in the tap-cycle at all) is real follow-up work, not a quick fix. Propose rung 2 for immediate production intake; hand rung 3 off as a documented, cost-cleared, but visually-unfinished follow-on rather than folding it into the same proposal.
