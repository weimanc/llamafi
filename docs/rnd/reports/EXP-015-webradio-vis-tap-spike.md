### EXP-015 — 2026-07-29 — WebRadio real-vis: tap-point cost spike (PROP-005 rung 1)
**Hypothesis**: `ESP32-audioI2S`'s weak-linked `audio_process_extern(int16_t* buff, uint16_t len, bool *continueI2S)` hook (Audio.cpp:4215-4221) fires once per decoded PCM block, pre-gain/filter/volume, on the wrAudio pump task — before rung 2's real envelope math is written, is *touching* every sample in that hook (pass-through, no math) measurably cheaper than the TASK-278 decode-tail budget can absorb?

**Approach**: Confirmed two weak hooks exist in the vendored fork: `audio_process_extern` (per-block, pre-filter, in `sendBytes()`) and `audio_process_i2s` (per-sample, post-gain/filter, in `playSample()` — much higher call frequency, not the target here). Wired `audio_process_extern` in `webRadioApp.h` to sum every interleaved L/R sample into an accumulator, forced live via an `asm volatile` guard (no persistent storage — see DRAM note below), always `*continueI2S = true`. Gated behind a new build flag `WR_VIS_TAP_SPIKE`, wired into a new scratch PlatformIO env `cyd2usb_winamp_debug_vistap` (extends `cyd2usb_winamp_debug`) so the flag-off debug build stays byte-identical to today. A-vs-B: flashed each variant, entered WebRadio (`switchApp 11`), waited for the station-list fetch (`get wrCount` pending=0), played station 0 for 45s, read `get wrPump` (existing TASK-278/VE-2-2 pump observability: `maxPumpMs` = worst single `Audio::loop()` call on the dedicated wrAudio pump task).

**Outcome**: `maxPumpMs` identical at **42ms** in both trials (tap enabled: 5881 pump cycles / 45s; tap disabled: 5953 cycles / 45s). `maxMutexWaitMs` (75 vs 63ms) and `stackHwm` (4684 vs 4812B) differences are within normal run-to-run noise, not attributable to the hook. First attempt hit a DRAM budget wall: a naive implementation using two file-static globals (`bool` + `int32_t`, ~8 bytes) overflowed `cyd2usb_winamp_debug`'s `dram0_0_seg` by exactly 8 bytes — that env's static-BSS headroom is effectively zero (see `feedback_dram_bss_static_buffers.md`). Fixed by using no persistent storage at all (stack-local accumulator + `asm volatile` dead-code guard) instead of the lazy-malloc pattern that class of bug normally calls for; confirmed via `run/check` that flag-off debug still links clean.

**Conclusion**: Validated — the tap point is free. Touching the full decoded PCM block per-call adds no observable decode-tail regression at the resolution `get wrPump` can measure (ms granularity, TASK-278's tail-spike budget was fought down to ~50ms/0-spikes, so 42ms with zero variance across trials is comfortably inside that envelope).

**Recommendation**: Continue to rung 2 (envelope: per-block peak/RMS into the `vu::tick()` seam via a lock-free single-writer/single-reader snapshot, same pattern as the ICY title queue). Rung 1's zero-footprint constraint (no static globals fit) carries forward — rung 2's L/R level snapshot will need the same lazy-malloc-once pattern already established for other static-buffer-vs-DRAM-budget conflicts in this codebase, not a plain file-static.
