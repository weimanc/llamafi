## The record

**Read the "not established" line before quoting any of this.** Four measurement windows; monitor state stated per window because it is a confound.

**(1) Idle, 20 min** (22:46:44–23:06:44), tmux monitor **up** (port held open), no harness activity: zero USB events, `ch341` line count flat at 52. Weak control — against a historical base rate of roughly one event per hour, zero in 20 min is what the null predicts; it also cannot separate no-reset from no-app-boot. What it does kill is the "spontaneous flapping independent of our activity" framing.

**(2) Across one `run/test-targeted T_PMT_04`** (23:07:41→23:09:05, monitor **down** for steps 1-5 by the script's own design): three remove+add cycles at 23:08:28 / 23:08:36 / 23:09:01. **The first write-up of this said "three resets, three re-enumerations" and was wrong**: PlatformIO passes `--before default_reset --after hard_reset` (`platforms/espressif32/builder/main.py`), with no override in `app/platformio.ini`, so each flash is **two** resets — five-plus in the run, three events. The two silent ones are exactly the two that stop in the **ROM bootloader**; all three that fired had booted the **application**. Timestamp attributions for 23:08:36 (`BOOT_WAIT`=8, degenerate against a ~8 s app-boot current peak) and 23:09:01 (3 s early for its supposed reset) are **inferred and weak** — do not cite them as evidence.

**(3) Block A/B**, identical `default_reset` in both arms, differing only in whether the app boots afterwards: **arm A (`--after no_reset`, ROM bootloader) 0/20; arm B (`--after hard_reset`, app boots) 10/20** (Fisher two-tailed p=0.0004). Arm A ran *first* in both blocks and still scored zero, which argues against a naive time confound.

**(4) Interleaved A/B, 12 pairs**, run specifically to remove the ordering confound: **0/12 and 0/12 — a null.** The phenomenon stopped: the disconnect counter has been frozen at 28 across 24 further trials including 12 app boots, and arm B's own block showed it dying mid-run (7 hits, then 8 straight misses).

**NOT ESTABLISHED, therefore**: that the app boot causes the re-enumeration. The association is strong but the confound-free test had no discriminating power because the effect was absent during it.

**Established**: DTR is *exonerated* as a sufficient cause — 20 full DTR/RTS reset sequences that stopped in the ROM bootloader produced zero disconnects — so the two theories floated earlier in the session (port-open-resets-it; failing cable acting independently) are both dead as stated.

**The phenomenon is non-stationary**, which is why every previous attempt to reason about it from one window has failed.

**Next**: the cable/powered-hub null test (needs a human, still the decisive one); re-run the interleaved A/B *when the rig is flapping again*, since it only has power then; and log the harness's open timestamp directly (one `print` before `self.ser.open()`) to kill the 8 s degeneracy. **Do not** change the serial-open path on this evidence — `_wait_for_ready` gates every readiness check on `boot_seen`, so suppressing the reset would silently disable the WiFi and poll gates. The tolerable-retry direction (wait for the node, re-open **once**, honour the reset gap, re-resolve rather than reuse, and make it **loud and counted** so rig degradation stays visible) is @Architect-supported but should land *after* the cable test, not before, or it masks the thing being measured.

**When it stopped, precisely** (30-min `udevadm` window, 23:07:20–23:37:20): clusters at 23:08:28/23:08:36/23:09:01 (the aborted run), 23:16:50–23:17:49 (block n=5), 23:21:07–23:22:22 (block n=15) — then **nothing from 23:22:22 to 23:37:20**. The stop lands exactly where arm B's n=15 block flipped from 7 straight hits to 8 straight misses, and the `ch341` disconnect counter has read 28 ever since: through the 24 interleaved trials **and** through the `T_PMT_04` run that subsequently PASSED. So the run that aborted saw 3 re-enumerations and the run that passed saw 0 — which closes the loop on "the disconnects are what break runs" without saying anything about what causes them. No cable was touched and nothing was reconfigured between 23:22:22 and the stop; whatever changed, changed on its own.

**(5) The human re-plugged the DUT (2026-08-31 23:56), and it explains nothing — the recovery had already happened 33 minutes earlier.** The first write-up of this window claimed "re-seating the connector stopped it". **That was wrong, and it is the third time in one session that this investigation attributed causation to the most recent salient event without checking the timeline.** The actual sequence: last USB event **23:22:22**; then the interleaved A/B (24 trials, 12 application boots) at 23:22–23:37 with the disconnect counter frozen at 28; then a `T_PMT_04` run that **PASSED with zero disconnects**; *then* the re-plug at 23:56 (counter 28→29, i.e. the re-plug itself). The post-re-plug suite was clean — but so was everything for the 33 minutes before it. **The re-plug is uninformative about the cause**: it neither fixed nor broke anything, because there was nothing left to fix when it happened. What it does buy is a known-good baseline going forward, and it removes "a connector that was bad *at that moment*" from the live candidate list.

**Standing advice, corrected**: a re-seat is still the right *first* action when the rig flaps, because it is thirty seconds against hours of instrumentation — but on this evidence it must not be recorded as the fix, and anyone who re-seats during a flap should note that spontaneous recovery is common enough here to mimic a successful intervention.

**(6) FIRST HARD CAUSE FOUND, 2026-09-01 — and it is ours.** An orphaned `pio device monitor` (two of them, holding no tty, outliving their session) drove **~420 re-enumerations at ~1.45 s** — the exact cadence flagged in this task's own window-3 data as "the classic signature of a device browning out shortly after enumerating". Killing the host processes stopped it instantly: **0 disconnects in 135 s idle**. So at least some of this investigation's phenomenon is **host-generated**, not hardware, and the brownout reading of the 1.49 s cadence was probably wrong. Filed as TASK-558 (raised to P2). **NOT claimed**: that this explains all of TASK-557. The 2026-08-31 block A/B measured **20 clean DTR resets producing zero disconnects**, which does not sit neatly with "reopen ⇒ reset ⇒ re-enumerate"; an orphan may do something more aggressive than a clean open, or the device may enter a state where a reset does re-enumerate. Unresolved, and deliberately not guessed — this investigation has already produced four retracted causal claims.

**What to do first when it next flaps**: `pgrep -f '[p]io device monitor'` and kill orphans BEFORE forming any theory; then `[bootreason]` (TASK-572) says whether a reset was BROWNOUT/PANIC/WDT. **Owner:** @RnD · **Deps:** none; currently gating TASK-553's measurement, hence P2. Original filing follows.

**2026-09-02 measurement, 2/2 identical, controlled single opens with numeric-windowed `dmesg`:** a host port-open asserts DTR/EN → the board resets (`rst:0x1 POWERON_RESET`, `[bootreason] 1 POWERON` at t=0.82 s) → boot reaches `[bootphase] 3 wifi` at t=1.41 s → **the CH340 drops off USB at t=1.47 s**, exactly one disconnect per open, reattaching 0.43 s later (often on the *same* `ttyUSBn`). So `device-vanished` is **self-inflicted and deterministic**, timed to WiFi-init inrush — not a random rig flap. The board itself is fine: leave it alone after the drop and it completes the next boot and runs for hours (9 h 26 m observed, `disc=0`). This is why 8 consecutive harness opens failed in TASK-565 while the board was healthy the whole time. Supply remains the physical hypothesis (2 × `[bootreason] 9 BROWNOUT` recorded), but the harness-side consequence is now fully characterised and fixable without touching hardware — see TASK-576.

**2026-09-02 bulk-transfer evidence (the physical-infra test that had never actually been run — an earlier session substituted a firmware-size calculation for it).** Flash *writes* are clean and always have been: 1.9 MB @921600 with `Hash of data verified` on every chunk, 911-912 kbit/s, no retries — but writes are host→device under an end-to-end hash, so they **structurally cannot** reveal a marginal return path. A device→host bulk read does: `esptool read_flash 0x0 0x200000` failed once with `Corrupt data, expected 0x1000 bytes but received 0xff9 bytes` — **7 bytes lost mid-stream at 77%**. First hard evidence of *corruption* on this link as distinct from the enumeration drops. Rate not established: 1 event in ~15 MB (2 MB@921600 3 trials → 1 fail; 512 KB@921600 3/3 OK; 2 MB@921600 2/2 OK on retest; 2 MB@230400 2/2 OK), so not baud-dependent at this sample size, and a host-side USB scheduling hiccup is not excluded. Reproduce with `esptool read_flash` loops — cheap, no flash wear, and the only test so far that stresses device→host.

**2026-09-02, later: the fault is no longer self-inflicted, and it progressed within one session.** Idle measurement, nothing holding the port: **~1 spontaneous USB disconnect per minute** (60 s windows: 1, 1; an earlier 60 s window caught 4 events). The *same* measurement that morning was **0 in 45 s**, and the tmux monitor had held a session for ~40 min with dozens of console commands. By evening the monitor cannot survive a single open — its log freezes at `[wifi-ev] t=683` every time, which is the fd dying at the measured t≈1.5 s drop. So the progression across one day is: stable → drops only on a host-triggered boot → drops unprompted. That rules out the harness as the cause of the current state and makes this a **physical fault requiring intervention** (cable, connector, hub, or supply; thermal is a live candidate given the progression over hours of use). **Consequence: the DUT is unusable for test sessions until it is addressed** — TASK-566, TASK-565's owed hardware run, and TASK-577 are all blocked behind it.

**2026-09-02 — SOLVED, it is power delivery, not the data link.** Controlled A/B, same cable/host/port, minutes apart, sole variable = what the ESP32 is running: **bootloader (no WiFi, no backlight, no SD) → 0 USB disconnects in 120 s; application running → 77 in 120 s.** Corroborating: 12 MB of `read_flash` bulk transfer completed clean while the chip sat in the bootloader (6/6 × 2 MB), with **0 packets dropped by the kernel** across an 812 426-packet `usbmon` capture, **0 ch341 URB/protocol errors ever, 0 xHCI errors ever**, and USB autosuspend ruled out (`power/control=on`, `runtime_suspended_time=0`). Signal-integrity faults produce `-EPROTO`/`-71`/CRC errors — there are none; clean disconnects with no error logging is what the CH340 losing VBUS looks like. So the link is sound and **the board's supply collapses whenever it draws application-level current**. **Correction — no rail was measured.** There is no voltage telemetry: the firmware has none (the only ADC use is the LDR on GPIO34) and the ESP32 classic has no internal VDD path, so none is obtainable in software on this board. The sole supply instrument is the ESP32 brownout detector via `[bootreason] 9 BROWNOUT` (3 events recorded), and it watches **VDD3P3**, not 5 V — at `BROWNOUT_DET_LVL_SEL_0`, the lowest threshold (~2.43 V), so it fires only on a deep sag. A **3.3 V** explanation is therefore at least as likely as a 5 V one and is more parsimonious: if the CH340 shares the 3.3 V rail (CH340C runs at 3.3 V), one regulator droop explains the ESP32 brownout and the USB disconnect together with 5 V healthy. **Consequence for the fix:** an external supply / powered hub / second USB socket helps only if the sag is *upstream* of the regulator; if the regulator itself is the limit it may change nothing. Distinguishing them needs a meter on the rails, or the load A/B below. Not a cable *data* problem either way. Host-side instrumentation is exhausted: `TIOCGICOUNT` is unimplemented by ch341 (`ENOTTY`), and debugfs `usbmon` is blocked by kernel lockdown `[integrity]` under Secure Boot (the `/dev/usbmon1` char device works and was used instead).

**2026-09-02 — MEASURED, with the one instrument this chip has (TASK-578).** The ESP32's brownout comparator, re-armed at its highest threshold with the reset off and the latched raw status polled (`app/src/debug/bodWatch.*`, `-DBOD_WATCH`, debug env only): **`[bod] TRIP tag=time t=1533-1535ms thres=7 det=0`, 4/4 boots, exactly one trip each.** So **VDD3P3 falls below the level-7 threshold (~2.80 V) during WiFi init** — a >15% transient sag on the 3.3 V rail, recovered by the time it is polled — and it coincides with the USB drop measured at t≈1.47-1.53 s, so those are one event. This replaces the retracted "5 V rail sags" guess with a measurement, and it points at **3.3 V**, not 5 V. **Second finding, and it is the actionable one:** `intEnaBefore=1` — ESP-IDF enables the brownout *interrupt* (`rstEna` reads 0 out of the box, so the hardware reset was never the path), and its ISR panics and restarts. That handler is what converts a survivable transient into a reboot loop. With the interrupt cleared the chip rides straight through: **0 USB disconnects in 120 s against 77 for the production build in the identical test**, and 2 h 18 m of continuous uptime. **This is a workaround, not a fix — it masks real hardware marginality**, and a deeper sag would then produce undefined behaviour instead of a clean reset, with flash/SD writes in flight at risk. Promoting it beyond the debug env is an @Architect call, not a default. The physical question (why the rail sags) is unchanged and still wants a meter or the GPIO35 divider — GPIO35/ADC1_CH7 is the only free ADC pin on this board.

**2026-09-02, serial-integrity trial (`serialburst` + `app/tools/burst_check.py`): the link is CLEAN and loss does not correlate with the BOD — because there is no loss.** 4 x 2000 checksummed numbered lines (~150 KB each) emitted from the *application*, so `[bod]` lines ride the same stream (esptool's bulk read cannot do this: it runs in the ROM bootloader where bodWatch is not loaded, so it can measure loss or the supply, never both). Result: **0 bytes lost, 0 corrupt lines, 0 `[bod]` trips during any burst.** The 7-9 apparent "missing" lines per run were an artefact of the probe, not the link — Arduino `Serial` is not line-atomic across FreeRTOS tasks, and each gap resolves to a burst line another task's `printf` cut into (`#781 AAAA...[E][ssl_client.cpp...`), with sequence numbers matching the gaps exactly. **Correction to the earlier reading:** the disconnect is NOT the sag hitting the CH340 directly. With the brownout ISR cleared the sag still occurs (4/4 boots, t~1535 ms) yet the USB link no longer drops at all — 3/3 opens ran the full window with no hangup, against 5/5 hangups before. So the drop was mediated by ESP-IDF's panic-restart, not by VBUS collapse, and "clean disconnects = CH340 losing VBUS" was over-read. It also makes the single unexplained 7-byte `read_flash` corruption less likely to be signal-related.

**2026-09-02, threshold sweep — the sag is BRACKETED, and two methodological faults were corrected first (both raised by the human, both real).** (1) *The burst measurement was unfounded as first reported.* `cmdSerialBurst` blocks `loop()` for its whole duration, so `bodWatchTick()` could not run and nothing polled the comparator during the burst; the checker also stopped reading at `phase:end`, so a trip would have been latched, reported afterwards, and missed. Fixed: `bodWatchClear()` before the burst and `bodWatchPollQuiet()` inside the emit loop (silent, because printing there is the very interleaving artefact that made an earlier run look like 0.4% loss). Re-measured, the firmware itself now reports `bodTrips:0 firstTripSeq:-1` — **0 trips during a burst, properly established this time.** (2) *The threshold is an orthogonal variable and was left pinned at 7*, which only ever supported "below level 7". Added `bod <0..7>`, persisted in `RTC_NOINIT` so it survives the reboot (the sag lands ~1.5 s in, long before the console exists, so a runtime setter alone cannot sweep it). **Verified sweep, setter acked and `armed` confirmed on every row, 2 reps each: levels 3 and 2 TRIP; levels 1 and 0 do NOT.** So VDD3P3 dips below level 2's threshold and stays above level 1's — and the monotonic trip/no-trip boundary confirms the level→voltage ordering empirically rather than assuming it. On the widely-published ESP32 table (0:2.43 … 7:2.80 V — **not verifiable from the precompiled framework tree here, so treat the absolute numbers as indicative**) that puts the floor near **2.5 V, a ~25% sag from 3.3 V**. An earlier unverified pass also produced a 6-trip row at level 6; the setter was not ack-checked then, so trip *counts* from that pass are not trustworthy — only the verified trip/no-trip boundary above is. **The sag is NOT boot-only.** Trip tags across the session: 16 `tag=time` (boot window) but also **5 `tag=run`** — steady-state trips from `loop()`, all at level 6, clustered inside 10 s and interleaved with WiFi/TLS failures (`Host is unreachable`, `STA_DISCONNECTED`). So the rail dips whenever the radio works hard, not only at init. Trips by level over the whole log: **0 at levels 0-1**, then 4/3/1/1/6/6 at levels 2/3/4/5/6/7 — consistent with the verified sweep. But note the depth is **not stationary across the day**: production recorded `[bootreason] 9 BROWNOUT` (IDF's default level 0) this morning, and by evening the sag stops above level 1, so the margin against the default trip point moves. That variability is the reliability issue, and it is exactly what made this look intermittent for weeks. **One loose thread, flagged not buried:** a `bod` query reported `tripsSinceArm=1` on a boot with no matching `[bod] TRIP` line in the log — most likely a line mangled by the printf interleaving proven above, but unexplained, and no conclusion here rests on it.

**2026-09-02, boot-inrush MITIGATION EXPERIMENT — NEGATIVE, cleanly. Neither lever, nor both together, moves the sag.** Two candidate firmware mitigations active across the phase-3 (WiFi-init) window only, selected at runtime from `RTC_NOINIT` (`bodmit <0..3>`, bit0=backlight duty forced to 0, bit1=WiFi TX power to 2 dBm) so a variant x threshold sweep costs a reboot rather than a reflash. **4 variants x thresholds 2 and 3 x 3 reps = 24 boots: `[bod] TRIP` on 24/24.** Setter ack and post-reboot `armed`/`mask` verified on every row (0 discards, 0 setup failures across 72 boots in three passes). Trip now tagged `wifi-end`, polled immediately *before* the restore, so it is unambiguously inside the mitigated window. **Two instrumentation faults were found and fixed before the result was believed, and both had already produced a wrong answer:** (1) `WiFi.setTxPower()` returns false without touching the driver unless `STA_STARTED_BIT` is set, and this env builds at `CORE_DEBUG_LEVEL=0` so its `log_w()` is invisible — called right after `WiFi.mode(WIFI_STA)` it silently did nothing, and pass 1's "TX reduced" rows were **not actually reduced** (in-window readback 19.5 dBm). Moved after `WiFi.begin()` with a read-back retry; pass 3 confirms 2 dBm in-window. (2) A host-side regex `tag=(\w+)` could not match the hyphen in `wifi-end`, turning pass 2 into an all-cells **false no-trip** — including the control, which is what gave it away. Every reported row now carries its own applied-state proof: `duty=0` for the backlight leg, `txdbm=2` for the TX leg. **Side effects:** none material. Time-to-`STA_GOT_IP` medians 1421 / 1439 / 1447 / 1448 ms for control / BL / TX / both — within run-to-run spread; the TX legs additionally show three ~935 ms outliers (faster, not slower). No `tag=run` trips in any 20 s post-boot window. One incidental anomaly, reported not buried: a single control boot at level 7 showed no trip at all, out of 31 control boots that otherwise all tripped; an immediate 3x re-check at level 7 tripped 3/3. **Conclusion: the sag is not driven by the backlight or by radio TX power. It is the WiFi PHY/PA bring-up current itself, or the regulator, and firmware cannot reach it — this needs a meter or a hardware change.** Code kept behind `bodmit` (default 0 = unmitigated, `-DBOD_WATCH`/debug env only) so the experiment is one revert; it is **not** a product change and should not be promoted. Board deliberately left on the `-DBOD_WATCH` debug build (production's IDF brownout ISR still boot-loops this hardware).

## The original filing (superseded row, kept for the audit trail)

Instrument the CH340 re-enumeration properly. [ADR-062](../architecture/decisions/ADR-062.md) put root-causing it out of scope on the grounds of "no dmesg access on this host for this user" — **that constraint no longer holds**, `dmesg`/`dmesg -T` read fine today, which makes this the highest-value cheap follow-up in the area. Capture a passive `udevadm monitor --udev --subsystem-match=usb` log across ≥3 normal `run/test-targeted` runs and correlate against harness open/close timestamps: if port-open caused disconnects the correlation is 1:1, and on the evidence so far it is measurably not (intervals observed: 1.49/1.49/1.50/3.87/7.90/24.3/181 s, plus a port open with no disconnect at all). Pair with a cable/powered-hub null test — a ~1.49 s enumerate-then-vanish cadence is the classic signature of a device browning out just after enumerating. Opens no serial port, so it costs no DUT time. **Owner:** @RnD · **Deps:** none.
