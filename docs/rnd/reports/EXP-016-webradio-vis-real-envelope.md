### EXP-016 — 2026-07-29 — WebRadio real-vis: real peak envelope (PROP-005 rung 2)
**Hypothesis**: Following EXP-015 (tap point is free), can a real per-block peak envelope drive VU/atlas gating in place of the ADR-009 synthetic one, within the same zero-static-BSS-headroom constraint, at visibly better quality than the synthetic decoration?

**Approach**: `audio_process_extern` (WR_VIS_ENVELOPE flag) computes per-block peak (max abs sample) for L/R from the interleaved `int16_t` buffer, then applies the existing `vu::ATTACK`/`vu::RELEASE` one-pole smoothing constants directly into `vu::lLevelRef()`/`vu::rLevelRef()` — the same statics `vu::tick()` already uses for the synthetic envelope, rather than any new storage (EXP-015 established there is no headroom to spend). Added an optional `realAudio` parameter (default `false`, so Spotify's call site is untouched) to `vu::tick()`: when true, it skips the synthetic swell/beat/noise block entirely and trusts `lLevelRef()`/`rLevelRef()` as already fresh, only forcing them to 0 on `!playing`. WebRadio's call site (`webRadioApp.h::tick()`) passes `realAudio=true` under `WR_VIS_ENVELOPE`. Single-writer discipline: the pump task owns those statics while WebRadio real-mode is active, `vu::tick()` itself owns them in Spotify's synthetic mode — never both at once, matching the codebase's established "single-producer volatile, no torn 32-bit reads on Xtensa" pattern (same class as the existing wrPump observability counters).

Build/measure path mirrored EXP-015: two scratch envs on a production+`-DSERIAL_DEBUG`-only base (`cyd2usb_winamp_vistap2` for rung 1, `cyd2usb_winamp_envelope` for rung 2) rather than `cyd2usb_winamp_debug`, since EXP-015 found debug's `dram0_0_seg` pegged at exactly 0 bytes slack (`_bss_end == segment end`, verified via the firmware `.map`) — and confirmed the same is true of ANY `SERIAL_DEBUG`-enabled build, not just the debug env specifically (production+`-DSERIAL_DEBUG`-only landed at the identical `_bss_end` address as full debug). This is the real constraint EXP-015 undersold: it isn't "the debug env is tight," it's "SERIAL_DEBUG's own static footprint consumes ~all of this chip's static-BSS headroom, in any build that includes it." `cyd2usb_winamp_envelope` built clean with **zero bytes of DRAM growth** vs the rung-1 scratch env, confirming the reuse-not-add approach actually holds at zero footprint.

DUT verification: entered WebRadio (`switchApp 11`), waited for station fetch (`get wrCount` pending=0, 30 stations), played station 0. `get wrPump` after 45s: `maxPumpMs=42ms` (cycles 5887) — identical to both the EXP-015 baseline and the tap-only build, i.e. real peak-detection math adds no measurable decode-tail cost either. Visual check: two screendumps of the title+vis region (x=0,y=20,w=140,h=70) 1.5s apart during live playback showed 531/9800 changed pixels, with visibly taller/differently-shaped bars between frames (saved, not committed: `env_vis1.png`/`env_vis2.png`) — confirms the vis is actually tracking the real audio stream, not flatlined.

**Conclusion**: Validated. Real per-block peak envelope is free (same 42ms pump ceiling as synthetic and as the rung-1 no-op), needs zero new persistent storage by reusing `vu::lLevelRef()`/`rLevelRef()`, and visibly animates in step with real playback.

**Recommendation**: Propose for graduation. The `vu::tick(..., realAudio=false)` seam and the `audio_process_extern` peak-envelope hook are both small, isolated, zero-footprint changes — a production PR from Developer should be low-risk. Rung 3 (fixed-point bands for spectrum-style modes) is optional follow-on, not a blocker: rung 2 alone already replaces the ADR-009 mock for VU + atlas gating, which was rung 2's explicit target ("likely the best value/cost point" per PROP-005). Left rung 3 unexplored this session — RMS (vs peak) is also worth a quick A/B before graduating, since peak-only can look "jumpy" compared to a blended peak+RMS approach; that's a cheap follow-up, not a new rung.

**Branch**: rnd/webradio-vis

**Notes**:
- Kill gate check: no heap allocation, no new static storage (0 bytes DRAM growth measured); decode-tail unaffected (42ms, matches TASK-278 budget in both A and B).
